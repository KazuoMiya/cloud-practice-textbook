:::goal
- セキュリティの6つの基本原則を、具体的な設定と結びつけて説明できる
- よくある事故の原因と対策を挙げられる
- 費用が膨らむ典型パターンと、予算アラートの限界を説明できる
:::

設定ミスや、不要な権限・リソースの放置は、情報漏えいや不正利用、想定外の請求の原因になります。セキュリティでは権限と公開範囲、コストでは止め忘れとデータ転送を押さえれば、大きな失敗の多くは防げます。

## セキュリティの基本原則

1. 最小権限：人にもプログラムにも、業務に必要な最低限の権限だけを与える。「とりあえず管理者権限」は厳禁
2. 管理者アカウント（AWSのルートユーザー）は日常で使わない：多要素認証（MFA）を必ず設定し、普段は個別のユーザーで作業する
3. アクセスキーをコードに書かない：GitHubに公開されたキーは数分で悪用されることがある。IAMロールやシークレット管理サービスを使う
4. 公開範囲を絞る：データベースやストレージをインターネットに公開しない。セキュリティグループで送信元とポートを限定する
5. 暗号化：保存データと通信の両方を暗号化する。多くのサービスは設定ひとつで有効にできる
6. 記録を残す：誰がいつ何を操作したかを記録する（AWSではCloudTrail）。管理操作の直近90日分は既定で確認できるが、長期保存には、証跡（トレイル）などによる保存設定が必要。S3のファイル操作などのデータイベントは、別途記録対象に設定する

## よくある事故と対策

| よくある事故 | 何が起きるか | 対策 |
|---|---|---|
| ストレージの公開設定ミス | 顧客情報などが誰でも閲覧可能になる | 公開ブロック設定を既定で有効にし、例外は承認制にする |
| アクセスキーの流出 | 第三者に大量のサーバーを起動され、高額請求や情報漏えいにつながる | キーを発行しない設計にする、リポジトリのシークレット検知を有効にする |
| 退職者・異動者のアカウント放置 | 権限が残ったまま不正利用される | 社内のID管理と連携し、定期的に棚卸しする |
| 管理用ポートを全世界に公開（例：SSHの22番を送信元0.0.0.0/0に許可） | 管理用ポートに世界中から攻撃が届く | 接続元IPを限定する、踏み台やセッション管理サービスを使う |

:::note 事故に気づいたら
事故の対応で最も大切なのは、被害を広げないことと、一人で抱え込まないことです。たとえばアクセスキーの流出に気づいたら、まずそのキーを無効にし、すぐに上長や案件の責任者に報告します。原因の調査や証拠の確認は、その後に行います。具体的な手順は{{ch:ts}}のシナリオ12で練習します。
:::

## コストが膨らむ典型パターン

- 検証用に作ったサーバーやデータベースの止め忘れ
- 本当の負荷より大きすぎるスペックの選択
- 外部へのデータ転送量（動画配信、大量ダウンロード、リージョン間の複製）
- 古いバックアップやログを削除せず保存し続ける
- NATゲートウェイやロードバランサーなど、起動しているだけで時間課金されるネットワーク部品

## コスト管理の基本動作

- 予算アラートを最初に設定する：一定額を超えたらメールやチャットに通知する。ただし通知であって利用額の上限ではなく、請求データの反映にも時間差があるため、超過を確実に止めるものではない
- タグを付ける：プロジェクト名・環境（本番／検証）・担当者をタグで付け、誰の費用かを追えるようにする
- 夜間・休日は検証環境を自動停止する
- 長期で使い続けるものは割引プラン（AWSの Savings Plans、リザーブドインスタンスなど）を検討する
- 料金計算ツール（AWS Pricing Calculator など）で事前に見積もる

こうしたコストを可視化し、開発・財務・経営が一緒に最適化していく取り組みを「FinOps」と呼びます。

:::sum
- セキュリティは、権限を最小にし、公開範囲を絞り、暗号化し、記録を残すことが基本
- 設定の誤りと、不要な権限や資源の放置は、事故の原因になる。高度な対策より先に、ここを固める
- 費用は、止め忘れ、大きすぎるスペック、外向きのデータ転送、消されない保存データ、時間課金のネットワーク部品で膨らむ
- 予算アラートは通知であり、上限ではない。タグと片付けの習慣とセットで使う
:::

## 章末問題

:::q 指摘 | 権限の付けすぎ
あるバッチ処理は、S3の特定のバケットからファイルを読み取るだけです。構築を急いでいたため、このバッチが動くサーバーのIAMロールには、すべての操作ができる管理者権限（AdministratorAccess）が付けられています。何が問題で、どう直すべきですか。
:::a
問題は、バッチやサーバーが乗っ取られたとき、またはバッチにバグがあったときの被害の範囲です。管理者権限があれば、すべてのデータの読み出し、資源の削除、新しいユーザーの作成、大量のサーバーの起動まで、何でもできてしまいます。

直し方は、必要な操作と対象だけを許可することです。この例なら「そのバケットの中のオブジェクトを読み取る操作（s3:GetObject）」と、必要なら「一覧を取得する操作（s3:ListBucket）」だけを許可します。

何が必要かわからないときは、まず広めの権限で動かして実際に使われた操作を記録から確認し、絞り込む方法があります（{{ch:sec}}）。大切なのは「後で絞る」を実際に行うことで、急いで付けた広い権限は、そのまま本番に残りがちです。
:::

:::q 分析 | 請求を見て削減する
ある検証用アカウントの先月の請求の内訳は次のとおりでした（金額は演習用の例）。削減できそうな項目を3つ選び、対策を答えてください。

| 項目 | 金額 | 状況 |
|---|---|---|
| EC2 | 320ドル | 開発用の4台が24時間動いている。使うのは平日の日中だけ |
| NATゲートウェイ | 135ドル | 3つのAZに1台ずつある |
| EBSスナップショット | 90ドル | 2年前からの日次スナップショットがすべて残っている |
| RDS | 150ドル | 検証用の1台。マルチAZ構成 |
| データ転送 | 15ドル | ― |
:::a
解答例：

1. EC2：夜間と休日に止める。平日の12時間だけ動かせば、稼働時間は約3分の1になる。あわせて、使用率を見てスペックを下げられないか確認する
2. NATゲートウェイ：検証環境なら1台にまとめる。可用性は下がるが、検証環境では許容できることが多い。S3などへの通信だけなら、ゲートウェイ型のVPCエンドポイントに置き換えられないかも検討する
3. EBSスナップショット：保存期間を決め（例：日次は14日分）、古いものを自動で削除する設定にする
4. RDS：検証用なら単一AZにする。費用はおよそ半分になる。使わない時間帯は停止する（7日後に自動で起動する点に注意）

金額の大きい順に手を付けること、そして「検証環境に本番と同じ可用性は必要か」を問うことが要点です。逆に、本番環境で同じ削減をする場合は、可用性の要件と照らして判断します。
:::

:::q 説明 | 予算アラートの限界
新人が「予算アラートを月5ドルに設定したので、5ドルを超えて請求されることはありません」と言っています。正しい理解を説明してください。
:::a
予算アラートは、費用が設定額を超えた（または超えそうな）ときに通知する仕組みで、利用を止める機能ではありません。通知を受けた後、人が原因を調べて資源を止めなければ、費用は増え続けます。

さらに、通知の元になる費用のデータは1日に数回しか更新されないため、通知が届くのは実際の利用から数時間遅れます。高価な資源を誤って大量に作った場合、通知が届く前に設定額を大きく超えることがあります。

そのため、予算アラートだけに頼らず、作ったものはその日のうちに片付ける、翌日に請求画面を確認する、という習慣と組み合わせます。
:::

:::q 設計 | タグの決まりを作る
複数の案件と環境が1つのAWSアカウントに混在しています。費用を案件ごとに把握できるようにするため、すべての資源に必ず付けるタグを3つ決めてください。それぞれ、何のために必要かも答えてください。
:::a
解答例：

| タグ | 値の例 | 目的 |
|---|---|---|
| Project | order-system | どの案件の費用かを集計する |
| Environment | prod、stg、dev | 本番とそれ以外を分ける。停止してよいか、権限をどう分けるかの判断にも使う |
| Owner | チーム名や担当者 | 不明な資源を見つけたときに、誰に確認すればよいかがわかる |

タグは、付け忘れや表記の揺れ（prod と production の混在など）があると集計に使えません。値の候補をあらかじめ決め、IaCで自動的に付ける、タグのない資源を定期的に検出する、といった仕組みで守ります。なお、費用の集計にタグを使うには、請求の設定で「コスト配分タグ」として有効にする必要があります。アカウントそのものを案件や環境ごとに分ける方法は{{ch:org}}で扱います。
:::

:::q 対応 | アクセスキーを公開してしまった
作業中に、AWSのアクセスキーを書いた設定ファイルを、誤って公開のGitHubリポジトリにpushしてしまったことに気づきました。最初の30分で行うことを、順に答えてください。
:::a
解答例：

1. そのアクセスキーをすぐに無効にする（削除でもよいが、まず無効化が早い）。リポジトリからファイルを消すだけでは不十分。公開された時点で、すでに第三者に取得されたものとして扱う
2. 上長や案件の責任者に、事実をそのまま報告する。「いつ、どのキーを、どこに公開したか」「今どこまで対応したか」を伝える
3. そのキーでどのような操作が行われたかを、操作の記録（CloudTrail）で確認する。見覚えのないサーバーの起動、ユーザーやキーの作成がないかを、すべてのリージョンで確認する
4. 見つかった不正な資源やユーザーを、責任者と相談のうえで止める。請求の画面も確認する
5. リポジトリの履歴からも該当の情報を取り除く。ただし1のとおり、これは被害を防ぐ手段にはならない

報告をためらって時間がたつほど、被害は大きくなります。再発を防ぐには、そもそも長期のアクセスキーを発行しない（IAMロールや一時的な認証情報を使う）、リポジトリの秘密情報の検知を有効にする、という設計と仕組みが有効です。
:::
