{{ch:s8}}では、ECSとFargateで、コンテナを1つのサービスとして動かしました。サービスの数が数十、数百になり、複数のチームが同じ基盤を使うようになると、基盤そのものの設計と運用が、独立した仕事になります。この章では、その中心にあるKubernetesと、AWSでの選択肢を扱います。

## コンテナの基盤が解決すること

多数のコンテナを、多数のサーバーの上で動かすとき、人の手では追いつかない仕事があります。

| 仕事 | 内容 |
|---|---|
| 配置 | どのコンテナを、どのサーバーで動かすか。空いている場所を見つけて置く |
| 回復 | 止まったコンテナを、起動し直す。サーバーが壊れたら、別のサーバーで動かす |
| 増減 | 負荷に応じて、コンテナの数と、サーバーの台数を変える |
| 入れ替え | 新しい版へ、止めずに少しずつ入れ替える。失敗したら戻す |
| 発見と振り分け | コンテナの場所は絶えず変わる。名前で相手を見つけ、正常なものへ振り分ける |
| 設定と秘密情報 | 環境ごとの設定や、パスワードを、コンテナに安全に渡す |

これらを自動で行う仕組みを、コンテナオーケストレーションと呼びます。AWSでは、ECSとEKSが、その役割を担います。

## ECSか、EKSか

| 観点 | Amazon ECS | Amazon EKS |
|---|---|---|
| 成り立ち | AWSが独自に作った仕組み | オープンソースのKubernetesを、AWSが管理して提供する |
| 覚えること | 少ない。AWSのほかのサービスと同じ感覚で扱える | 多い。Kubernetes自体の概念と、周辺の道具の知識が要る |
| 周辺の道具 | AWSのサービスと組み合わせる | 世界中で作られた道具や、既製の構成を使える |
| 持ち運び | AWSに固有 | ほかのクラウドやオンプレミスのKubernetesと、同じ書き方で扱える |
| 版の更新 | 意識することは少ない | Kubernetesの版が定期的に上がり、追従する作業が要る |

選ぶ基準は、技術の優劣ではなく、組織の事情です。

- Kubernetesの経験者がいる。ほかのクラウドやオンプレミスでもKubernetesを使っている。Kubernetes向けに作られた製品を使いたい。こうした理由があれば、EKS
- そうした理由がなく、AWSの上でコンテナを確実に動かしたいだけなら、ECS。覚えることと、運用の手間が少ない

「Kubernetesが必要な理由」を具体的に言えないなら、ECSから始めるのが無難です。Kubernetesは、できることが多いぶん、決めることと、保守することも多くなります。

## Kubernetesの基本

Kubernetesでは、「何を、いくつ、どう動かしたいか」を、文書（マニフェスト）として宣言します。Kubernetesは、実際の状態を絶えず見張り、宣言された状態との差を埋め続けます。{{ch:s7}}のIaCと同じ、「手順ではなく、あるべき状態を書く」考え方です。

| 用語 | 役割 |
|---|---|
| Pod | 動かす最小の単位。1つ以上のコンテナの集まり。作られては消える、使い捨てのもの |
| Deployment | 「このPodを、3つ動かし続ける」という宣言。数を保ち、新しい版への入れ替えも行う |
| Service | Podの集まりに、変わらない名前と宛先を与える。Podが入れ替わっても、同じ名前で届く |
| Ingress | クラスターの外からの通信を、どのServiceへ届けるかの決まり。AWSでは、ALBと結び付けて使う |
| Namespace | クラスターの中を、チームや環境ごとに区切る入れ物 |
| ConfigMap、Secret | 設定と、秘密情報。Podに渡す |
| ノード | Podを実際に動かすサーバー |
| コントロールプレーン | 宣言を受け取り、状態を見張り、配置を決める、クラスターの頭脳 |

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3                      # 3つ動かし続ける
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: 111122223333.dkr.ecr.ap-northeast-1.amazonaws.com/web:3f2a1c
          resources:
            requests: { cpu: 250m, memory: 256Mi }   # 配置の判断に使う、必要な量
            limits: { memory: 512Mi }                # これを超えると止められる
          readinessProbe:                            # 通信を受けられる状態かを確かめる
            httpGet: { path: /healthz, port: 8080 }
```

## 手元のクラスターで確かめる

Kubernetesの考え方は、手元のPCで、費用をかけずに確かめられます。kind（Kubernetes in Docker）は、Dockerのコンテナをノードに見立てて、PCの中にクラスターを作る道具です。EKSは、動かしている間、コントロールプレーンに時間料金がかかります。そのため、この本の実習は、kind で行います。ここで身に付ける宣言の書き方、調べ方、壊れ方は、EKSでも同じです。

実習に使うファイルは、この本のリポジトリの [labs/k8s](https://github.com/KazuoMiya/cloud-practice-textbook/tree/main/labs/k8s) にあります。この節の手順は、変更のたびに、実際のクラスターで最初から最後まで動かして確かめています。

### 準備

| 用意するもの | 確かめ方 |
|---|---|
| Docker（Docker Desktop など） | `docker version` |
| kind | `kind version` |
| kubectl | `kubectl version --client` |

入れ方は、[kind の公式の手順](https://kind.sigs.k8s.io/docs/user/quick-start/)と、[kubectl の公式の手順](https://kubernetes.io/docs/tasks/tools/)に従います。会社のPCで使う場合は、Docker Desktop の利用条件（会社の規模によっては、有料の契約が要ります）と、社内の決まりを、先に確かめてください。

### クラスターを作る

```yaml
# labs/k8s/kind.yaml
# 手元のPCの中に作る、実習用のクラスター。Dockerのコンテナ1つが、ノード1台になる
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: cloudbook
nodes:
  - role: control-plane
  - role: worker
  - role: worker
```

```bash
kind create cluster --config kind.yaml
kubectl wait --for=condition=Ready nodes --all --timeout=120s
kubectl get nodes
```

クラスターを作った直後は、ワーカーが `NotReady` と表示されることがあります。2行目は、すべてのノードの準備が整うのを待つ命令です。コントロールプレーンが1台、ワーカーが2台の、3台のノードが `Ready` と表示されます。第2部で、2つのAZにサーバーを分けたのと同じように、2台のワーカーにPodを分けて置きます。

### 宣言して、動かす

```yaml
# labs/k8s/web.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: cloudbook
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: cloudbook
spec:
  replicas: 2                      # 2つ動かし続ける
  selector:
    matchLabels:
      app: web
  template:                        # Podのひな形
    metadata:
      labels:
        app: web
    spec:
      topologySpreadConstraints:   # できるだけ、別々のノードに分ける
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: web
      containers:
        - name: web
          image: nginx:1.27-alpine
          # 第14章のサーバーと同じく、自分の名前を返すページを作ってから、Webサーバーを起動する
          command: ["sh", "-c", "echo \"<h1>$(hostname)</h1>\" > /usr/share/nginx/html/index.html && exec nginx -g 'daemon off;'"]
          ports:
            - containerPort: 80
          resources:
            requests:              # 配置の判断に使う、必要な量
              cpu: 50m
              memory: 32Mi
            limits:                # これを超えると、止められる
              memory: 128Mi
          readinessProbe:          # 通信を受けられる状態かを確かめる
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: cloudbook
spec:
  selector:
    app: web                       # このラベルが付いたPodへ届ける
  ports:
    - port: 80
      targetPort: 80
```

第2部で作ったものと、次のように対応します。

| 第2部で作ったもの | Kubernetesでの対応 |
|---|---|
| 起動テンプレート（サーバーの作り方） | Deployment の中の、Podのひな形（template） |
| Auto Scalingグループ（台数を保つ） | Deployment（replicas） |
| ターゲットグループとALB（変わらない宛先） | Service |
| ALBのヘルスチェック | readinessProbe |
| ユーザーデータ（起動時の準備） | コンテナイメージと、起動時のコマンド |
| 2つのAZへの分散 | 複数のノードへの分散 |

```bash
kubectl apply -f web.yaml
kubectl -n cloudbook rollout status deployment/web --timeout=180s
kubectl -n cloudbook get pods -o wide
```

2つのPodが `Running` になり、`NODE` の列に、別々のワーカーが表示されます。

### Service 経由で届く

クラスターの中に、確認用のPodを一時的に作り、Service の名前（`web`）で10回取りに行きます。

```bash
kubectl -n cloudbook run client --rm -it --restart=Never --image=busybox:1.36 -- \
  sh -c 'for i in $(seq 10); do wget -qO- http://web; echo; done'
```

Podの名前が、2種類表示されます。{{ch:s3}}で、ALBのURLを開くたびにホスト名が切り替わったのと同じです。Podが入れ替わってアドレスが変わっても、`web` という名前で届き続けます。

### 回復、増減、入れ替え、ノードの退避

次の4つを、順に試します。1つ試すたびに、`kubectl -n cloudbook get pods -o wide` で、何が変わったかを確かめてください。

1. Podを1つ消す。`kubectl -n cloudbook get pods` で名前を調べ、`kubectl -n cloudbook delete pod Podの名前` で消す。すぐに、別の名前のPodが作られ、2つに戻る
2. 数を変える。`web.yaml` の `replicas: 2` を `4` に書き換えて、適用する。確かめたら、`2` に戻して、もう一度適用する
3. 止めずに入れ替える。`web.yaml` のイメージを `nginx:1.28-alpine` に書き換えて、適用する。新しいPodが通信を受けられる状態になってから、古いPodが消える。履歴を表示し、前の版に戻す
4. ノードを空ける。ワーカーの1台から、Podを退避させる。Podは、残りのノードで作り直される。確かめたら、ノードを元に戻す

```bash
# 2、3：ファイルを書き換えてから
kubectl apply -f web.yaml
kubectl -n cloudbook rollout status deployment/web --timeout=180s

# 3：履歴を表示し、前の版に戻す
kubectl -n cloudbook rollout history deployment/web
kubectl -n cloudbook rollout undo deployment/web

# 4：ノードを空けて、元に戻す
kubectl drain cloudbook-worker2 --ignore-daemonsets --delete-emptydir-data --timeout=120s
kubectl uncordon cloudbook-worker2
```

数は、`kubectl scale` という命令でも変えられます。しかし、命令で変えると、ファイルに書いた内容と、実際の状態がずれます。{{ch:s7}}で学んだとおり、変更は、ファイルを書き換えて適用します。3で前の版に戻した後も、`web.yaml` を元の内容に戻しておきます。

### わざと壊してみる

Podが期待どおりに動かないとき、調べる順番は決まっています。Podの一覧で状態を見て、詳細（`describe`）の最後に出るイベントを読み、ログを読みます。詳細は、Podを1つ指定して表示します。複数のPodをまとめて指定すると、イベントが表示されないことがあります。3つの壊し方で、この順番を練習します。1つ試すたびに、最後の `rollout undo` で元に戻します。

```bash
# 1. 存在しないイメージを指定する
kubectl -n cloudbook set image deployment/web web=nginx:0.0.0-none
# 2. 通らないヘルスチェックにする
kubectl -n cloudbook patch deployment web --type=json -p '[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/healthz"}]'
# 3. すぐに終了するコマンドにする
kubectl -n cloudbook patch deployment web --type=json -p '[{"op":"replace","path":"/spec/template/spec/containers/0/command","value":["sh","-c","echo starting; exit 1"]}]'

# 調べる
kubectl -n cloudbook get pods
kubectl -n cloudbook describe pod Podの名前
kubectl -n cloudbook logs Podの名前 --previous
kubectl -n cloudbook get events --sort-by=.lastTimestamp

# 元に戻す
kubectl -n cloudbook rollout undo deployment/web
```

| 壊し方 | 新しいPodの状態 | 手がかり |
|---|---|---|
| 1. 存在しないイメージ | `ErrImagePull` から `ImagePullBackOff` になる | 詳細のイベントに、イメージを取得できなかった理由が出る |
| 2. 通らないヘルスチェック | `Running` だが、`READY` が `0/1` のまま | 詳細のイベントに、`Readiness probe failed` と、返ってきたステータスコードが出る |
| 3. すぐに終了するコマンド | `CrashLoopBackOff` になり、`RESTARTS` が増えていく | `--previous` を付けたログに、終了する前の出力が残っている |

3つとも、古い2つのPodは動き続け、Service 経由の応答は止まりません。Deployment は、新しいPodが通信を受けられる状態になるまで、古いPodを消さないためです。2では、新しいPodは `Running` と表示されますが、通信の宛先には加わりません。`Running` は「コンテナが動いている」ことを、`READY` は「通信を受けられる」ことを表します。この2つを区別して読むことが、Kubernetesの調査の基本です。

{{ch:ts}}のシナリオと比べてみてください。ヘルスチェックの宛先を誤る、という同じ誤りでも、仕組みによって、起きることが違います。

### 実技の合格基準

次のすべてを、コマンドの出力で示せたら合格です。

| 番号 | 確かめること | 合格の状態 |
|---|---|---|
| 1 | クラスターができている | 3台のノードが `Ready` |
| 2 | 宣言どおりに動いている | 2つのPodが `Running` で、`READY` が `1/1`。別々のノードにある |
| 3 | Service 経由で届く | Podの名前が、2種類表示される |
| 4 | 自動で回復する | Podを1つ消すと、別の名前のPodが作られ、2つに戻る |
| 5 | 止めずに入れ替えて、戻せる | 入れ替えの履歴に、2つ以上の版が表示される。前の版に戻せる |
| 6 | 壊れたときに、原因を調べられる | 3つの壊し方について、Podの状態、イベントやログの手がかり、利用者への影響を説明できる |
| 7 | 片付けが済んでいる | クラスターの一覧に、何も表示されない |

提出するもの：1〜5、7の出力と、6の説明。

### 片付け

```bash
kind delete cluster --name cloudbook
kind get clusters
```

クラスターを消せば、PCの中に作ったものは、すべて消えます。費用は、最初から最後までかかりません。

### EKSで動かすときに変わること

同じ `web.yaml` は、EKSにもそのまま適用できます。変わるのは、クラスターの外側です。EKSのクラスターは、動かしている間、費用がかかります。試す場合は任意とし、その日のうちに消してください。

| 項目 | kind | EKS |
|---|---|---|
| クラスターを作る | `kind create cluster` で、数分 | コントロールプレーンとノードを作る。権限、ネットワーク、版の設計が要る |
| ノード | PCの中のコンテナ | EC2など。前の節の表のとおり、方式によって担当が変わる |
| 外からの入口 | PCの中だけで確かめる | Ingress や Service から、ALBなどのロードバランサーを作る |
| イメージの置き場所 | 公開のレジストリから取得する | Amazon ECR に置き、取得の権限を設計する（{{ch:s8}}） |
| Podの権限 | 考えなくてよい | PodごとにIAMロールを割り当てる |
| 費用 | かからない | コントロールプレーン、ノード、ロードバランサーに、時間料金がかかる |

## EKSでは、誰が何を管理するか

EKSでは、コントロールプレーンをAWSが管理します。ノードの管理は、選ぶ方式によって変わります。

| ノードの方式 | 利用者が担当すること |
|---|---|
| 自分で用意したEC2 | ノードのOSの更新と修正プログラムの適用、台数の増減、Kubernetesの版への追従まで、すべて |
| マネージドノードグループ | ノードの作成と入れ替えの操作を、AWSが補助する。いつ更新するかの判断と実行は、利用者 |
| Fargate | ノードを意識しない。Podごとに実行環境が用意される。使えない機能がある |
| EKS Auto Mode | ノードの用意と入れ替え、台数の自動調整、ロードバランサーや保存領域との連携まで、AWSが管理する。ノードは、最長21日で自動的に入れ替えられる |

どの方式でも、コンテナイメージの中身、アプリの設定、Kubernetesの上の権限と通信の決まりは、利用者の担当です。{{ch:model}}の責任共有モデルが、ここでも形を変えて現れます。

## 運用で問題になりやすい点

### 版の更新に追従する

Kubernetesは、年に数回、新しい版が出ます。EKSでは、それぞれの版に支援の期間があり、期間を過ぎると、追加の料金がかかる延長の支援に入り、さらに過ぎると、自動的に版を上げられます。計画的に、年に1〜2回は版を上げる作業を、運用の予定に組み込みます。版を上げると、廃止された書き方が使えなくなることがあるため、検証環境で先に確かめます。

### 必要な量と、上限を宣言する

Podには、必要なCPUとメモリの量（requests）と、使ってよい上限（limits）を書きます。

- 必要な量を書かないと、Kubernetesは、ノードの空きを正しく判断できず、1つのノードにPodを詰め込みすぎる
- メモリの上限を超えたコンテナは、強制的に止められる。止められた記録（OOMKilled）が繰り返し出ていれば、上限が小さいか、アプリがメモリを使いすぎている
- 必要な量を大きく書きすぎると、実際には空いているのに、ノードが足りないと判断され、台数と費用が増える

### 2段階で増減する

- Podの数：負荷に応じて、Podを増減する（Horizontal Pod Autoscaler）
- ノードの数：置き場所が足りなくなったら、ノードを増やす。空いたら減らす（Karpenter など）

Podが増えても、置くノードがなければ、Podは待たされます。ノードの起動には、数十秒から数分かかるため、急増には、あらかじめ余裕を持たせておく必要があります（{{ch:perf}}）。

### アドレスが足りなくなる

EKSの標準のネットワークの方式では、Podの1つひとつに、VPCのIPアドレスが割り当てられます。Podは、サーバーよりもはるかに数が多いため、サブネットのアドレスを使い切ることがあります。使い切ると、新しいPodが起動できません。EKSを使うVPCでは、Pod用に大きなサブネット（/20 以上など）を、最初から確保します（{{ch:s2}}の章末問題）。

### 権限を、Podごとに分ける

ノードのIAMロールに、すべてのアプリの権限をまとめて付けると、そのノードの上のすべてのPodが、すべての権限を使えてしまいます。Podごとに、別々のIAMロールを割り当てる仕組み（EKS Pod Identity など）を使い、アプリごとに最小の権限にします。

### 止めずに入れ替わるようにする

ノードの更新や、台数の調整のたびに、Podは別のノードへ移されます。つまり、Podは日常的に止められ、起動し直されます。それでもサービスが止まらないためには、アプリの側の作りが必要です。

- 複数のPodを、別々のノードとAZに分けて動かす
- 通信を受けられる状態かどうかを、正しく答える（readinessProbe）。準備ができる前に、通信を受けない
- 止める合図を受けたら、処理中の依頼を終えてから終了する
- 同時に止めてよいPodの数に、上限を設ける（PodDisruptionBudget）
- 状態は、Podの外（データベースなど）に持つ

## サービスを分けすぎない

コンテナの基盤があると、システムを小さなサービスに分けること（マイクロサービス）が、技術的には簡単になります。しかし、分けることには代償があります。

| 得られること | 代償 |
|---|---|
| チームごとに、独立して変更し、公開できる | サービスの間の通信が、失敗や遅延の原因になる |
| 負荷の高い部分だけを、増やせる | 複数のサービスにまたがるデータの整合性を、保つのが難しい |
| 障害の影響を、一部にとどめられる | 1つの依頼が多数のサービスを通るため、調査に、横断的な追跡（トレース）の仕組みが要る |

分ける理由として大きいのは、技術よりも、組織の事情です。複数のチームが、互いを待たずに変更できるようにする、ということです。チームが1つなら、無理に分けず、1つのまとまったアプリとして作り、必要になったところから切り出すほうが、うまくいきます。

:::sum
- コンテナの基盤は、配置、回復、増減、入れ替え、発見を自動で行う
- ECSとEKSは、組織の事情で選ぶ。Kubernetesが必要な理由を言えないなら、ECSから
- EKSでは、ノードの方式によって、利用者の担当範囲が変わる。版への追従は、定期的な仕事になる
- Podの調査は、一覧の状態、詳細のイベント、ログの順に読む。`Running` と `READY` は別のもの
- Podは日常的に入れ替わる。必要な量の宣言、アドレスの確保、Podごとの権限、止めずに入れ替わる作りが要る
:::

## 章末問題

:::q 選択 | ECSか、EKSか
次の3つの状況で、ECSとEKSのどちらを勧めますか。理由も答えてください。

1. 開発者5人の会社。Webアプリを1つと、バッチを数個、コンテナで動かしたい。インフラの専任はいない
2. オンプレミスですでにKubernetesを運用しており、同じ定義と道具を使って、AWSにも展開したい
3. 20のチームが、100以上のサービスを動かす。Kubernetes向けに作られた、サービス間の通信の管理や、デプロイの道具を使いたい。基盤の専任のチームがある
:::a
1. ECS（Fargate）。覚えることと、運用の手間が少ない。専任がいない体制で、Kubernetesの版への追従や、周辺の道具の保守を続けるのは、負担が大きい
2. EKS。すでにある知識、定義、道具を活かせる。オンプレミスとAWSで、同じ運用ができる
3. EKS。Kubernetesの周辺の道具を使う理由があり、基盤を運用する体制もある。ノードの運用の負担を減らすため、EKS Auto Mode などの、管理の範囲が広い方式を検討する

共通するのは、「運用する人と体制に合っているか」で選んでいることです。
:::

:::q 調査 | Podが起動しない
新しい版をデプロイしたところ、新しいPodが「Pending」（待ち）の状態のまま、起動しません。考えられる原因を3つ以上挙げ、最初に実行するコマンドを答えてください。
:::a
最初に実行するのは、`kubectl describe pod <Podの名前>` です。末尾の「Events」に、待たされている理由が書かれています。

考えられる原因：

- ノードの空きが足りない：Podが必要とするCPUやメモリを、置けるノードがない。ノードを増やす仕組みが働いているか、台数の上限に達していないかを確かめる
- 必要な量の指定が大きすぎる：どのノードにも収まらない量を、指定している
- アドレスが足りない：サブネットのIPアドレスを使い切っている
- 置ける場所の条件に合うノードがない：特定の種類のノードやAZを指定している。ノードの側に、特定のPod以外を受け付けない設定がある
- 保存領域を用意できない：Podが必要とする保存領域が、別のAZにある、または作成に失敗している

「Pending」は、「どのノードで動かすかが、まだ決まっていない」状態です。イメージの取得の失敗や、アプリの起動の失敗は、別の状態（ImagePullBackOff、CrashLoopBackOff）として表示されます。状態の名前が、どの段階で止まっているかの手がかりになります。
:::

:::q 計算 | アドレスは足りるか
EKSのクラスターを、2つのサブネット（どちらも /24）に作りました。Podには、1つにつき1つのIPアドレスが割り当てられます。ノードは20台で、ノード自身も、それぞれIPアドレスを使います。

1. 2つのサブネットで使えるIPアドレスは、合計でいくつですか
2. このクラスターで、最大でいくつのPodを動かせますか。ノードの分を引いて、概算してください
3. 繁忙期に、Podを800まで増やす計画があります。どうしますか
:::a
1. /24 で使えるのは251個。2つで502個
2. ノードの20個を引いて、約480個。実際には、ノードがあらかじめ予備のアドレスを確保する動きや、ロードバランサーなどが使う分があるため、これより少なくなる
3. 足りない。次のような対応を取る
    - Pod用に、大きなサブネット（/20 など）を追加する。VPCの範囲に空きがなければ、VPCに追加の範囲を関連付ける
    - 新しく設計するなら、最初から、Pod用のサブネットを大きく取る
    - アドレスの使い方を変える設定（まとまった範囲をノードに割り当てる方式や、IPv6の利用）を検討する

アドレスの不足は、繁忙期に、Podを増やそうとして初めて表面化します。平常時の数ではなく、最大の数で計算しておくことが大切です。
:::

:::q 設計 | ノードが入れ替わっても止まらない
EKS Auto Mode では、ノードが最長21日で自動的に入れ替えられます。入れ替えのとき、そのノードの上のPodは、止められて、別のノードで起動し直されます。それでもサービスが止まらないために、アプリと設定の側で必要なことを、4つ以上挙げてください。
:::a
解答例：

1. Podを複数動かし、別々のノードとAZに分ける。1つしかなければ、入れ替えのたびに止まる
2. 同時に止めてよい数に、上限を設ける（PodDisruptionBudget）。たとえば「常に2つ以上は動いている」と宣言する
3. 通信を受けられる状態かを、正しく答える。起動して準備ができるまで、通信を受けない
4. 止める合図を受けたら、新しい依頼の受け付けをやめ、処理中の依頼を終えてから終了する。終了までの猶予の時間を、処理の長さに合わせて設定する
5. 状態を、Podの中に持たない。ログイン中の情報や、処理の途中経過は、外のデータストアに置く
6. 起動を速くする。イメージを小さくし、起動時の重い処理を減らす
7. 長時間かかるバッチ処理は、途中で止められても、やり直せるか、再開できるように作る

これらは、Auto Mode に限らず、コンテナの基盤で動かすアプリすべてに共通する作法です。「Podは、いつでも止められるもの」として作ることが、基盤の自動化の恩恵を受ける前提になります。
:::
