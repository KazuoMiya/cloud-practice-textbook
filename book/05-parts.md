:::goal
- 構成図に出てくる部品を、6つの分野に分類できる
- オブジェクト・ブロック・ファイルの3種類のストレージを、用途で使い分けられる
- IaC、CI/CD、監視、バックアップが何のための仕組みかを説明できる
:::

クラウド上のシステムは、ほぼ例外なく「コンピュート」「ストレージ」「データベース」「ネットワーク」「ID・権限」「監視・運用」の6分野の組み合わせでできています。構成図を見たら、まず各部品がどの分野に属するかを分類すると理解が速くなります。

## 6つの分野

| 分野 | 役割 | 代表サービス（AWS） | 最初に押さえるポイント |
|---|---|---|---|
| コンピュート | プログラムを動かす | EC2、Lambda、ECS、EKS | VM・コンテナ・関数のどれで動かしているか |
| ストレージ | ファイルやデータを保存する | S3、EBS、EFS | 用途に応じた3種類の使い分け（次の節） |
| データベース | 構造化されたデータを管理する | RDS、Aurora、DynamoDB | リレーショナルかNoSQLか、バックアップの方法 |
| ネットワーク | 部品同士と外部をつなぐ | VPC、ELB、Route 53、CloudFront | どこがインターネットに公開されているか |
| ID・権限 | 誰が何をできるかを決める | IAM、IAM Identity Center | 最小権限の原則、人とプログラムの権限を分ける |
| 監視・運用 | 状態を見張り、記録する | CloudWatch、CloudTrail | 何を監視し、異常時に誰へ通知するか |

ネットワーク（VPC、サブネット、セキュリティグループなど）は、初めての人が最もつまずきやすい分野です。そのため{{ch:net}}で、通信の基本から順に説明します。

## ストレージの3種類

| 種類 | イメージ | 代表サービス（AWS） | 主な用途 |
|---|---|---|---|
| オブジェクトストレージ | URLでアクセスする巨大な倉庫。容量は事実上無制限 | S3 | 画像・動画、バックアップ、ログ、静的Webサイト、データ分析の元データ |
| ブロックストレージ | サーバーに接続するハードディスク | EBS | OSやデータベースのデータ領域 |
| ファイルストレージ | 複数のサーバーで共有するフォルダ | EFS、FSx | 共有ファイル、既存アプリの移行 |

迷ったときは、次の順に考えます。まず「サーバーのディスクとして使うか」を考え、そうならブロックストレージです。次に「複数のサーバーから同じフォルダとして読み書きするか」を考え、そうならファイルストレージです。どちらでもなく、ファイルを1つずつ保存して取り出せればよいなら、オブジェクトストレージを選びます。オブジェクトストレージは容量あたりの費用が安く、耐久性も高いため、「サーバーのディスクに置かなくてよいものは外に出す」のが基本です。

## 運用を支える仕組み

- IaC（Infrastructure as Code）：サーバーやネットワークの構成をコードで書き、同じ環境を何度でも再現できるようにする。Terraform、CloudFormationが代表
- CI/CD：コードの変更を自動でビルド・テストし、本番に反映できる状態まで自動化する仕組み。本番反映まで自動で行う「継続的デプロイ」と、本番反映の前に人の承認を挟む「継続的デリバリー」がある。GitHub Actions、AWS CodePipelineなど
- 監視：CPU使用率などの「メトリクス」、アプリが出力する「ログ」、処理の流れを追う「トレース」の3つを集める
- バックアップと復旧：データの定期取得と、復旧までの許容時間（RTO）、どの時点までデータを戻せればよいか（RPO）の目標設定（{{ch:ha}}で詳しく扱う）

手作業でクリックして作った環境は再現も確認も難しいため、現場ではIaCで管理するのが標準になりつつあります。

## 構成図を6分野に分類してみる

次の部品の一覧は、{{ch:pattern}}で扱うWeb 3層構成に出てくるものです。初めて見る構成図でも、このように分野に振り分けるだけで、全体の骨組みが見えてきます。

| 部品 | 分野 | この構成での役割 |
|---|---|---|
| Route 53 | ネットワーク | ドメイン名から接続先を調べる |
| CloudFront | ネットワーク | 利用者の近くからコンテンツを配信する |
| ALB | ネットワーク | 通信を複数のサーバーに振り分ける |
| EC2（Auto Scaling） | コンピュート | アプリを動かす。台数を自動で増減する |
| RDS | データベース | 業務データを保存する |
| S3 | ストレージ | 画像やバックアップを保存する |
| IAMロール | ID・権限 | サーバーに、必要な操作だけを許可する |
| CloudWatch | 監視・運用 | 状態を見張り、異常を通知する |

分類できない部品があれば、それが次に調べるべきものです。

:::sum
- クラウドのシステムは、コンピュート・ストレージ・データベース・ネットワーク・ID・権限・監視・運用の6分野の組み合わせ
- ストレージは、ディスクとして使うならブロック、共有フォルダならファイル、それ以外はオブジェクト
- IaCは環境の再現、CI/CDは変更を届ける流れ、監視は異常に気づくこと、バックアップは元に戻すことを支える
:::

## 章末問題

:::q 選択 | ストレージを選ぶ
次の5つのデータについて、オブジェクト・ブロック・ファイルのどれに保存するのが適切かを答えてください。

1. データベースサーバーのデータ領域
2. 利用者がアップロードした写真
3. 複数のアプリサーバーから同時に読み書きする帳票のテンプレート
4. 7年間の保存が義務づけられている監査ログ
5. 既存の業務パッケージが前提としている、Windowsの共有フォルダ
:::a
1. ブロックストレージ（EBS）。OSからディスクとして見え、細かい単位で高速に読み書きできる
2. オブジェクトストレージ（S3）。容量を気にせず保存でき、URLで配信もできる
3. ファイルストレージ（EFS）。複数のサーバーから同じフォルダとして使える。読み取りが中心なら、S3に置いて各サーバーが取得する方法もある
4. オブジェクトストレージ（S3）。長期保存向けの安い保存クラスへ自動で移す設定ができる（{{ch:data}}）
5. ファイルストレージ（FSx for Windows File Server）。既存アプリの前提を変えずに移せる
:::

:::q 読み取り | 復旧の目標と実力
あるシステムは、毎日午前2時にバックアップを取得しています。バックアップからの復元には3時間かかることが、練習でわかっています。ある日の午後2時に、データが壊れる障害が起きました。

1. 失われるデータは何時間分ですか
2. 最悪の場合、何時間分のデータを失う可能性がありますか
3. 復旧が終わるのは、最短でいつごろですか
:::a
1. 午前2時から午後2時までの12時間分
2. 約24時間分。バックアップ取得の直前に障害が起きた場合
3. 午後5時以降。復元の3時間に、障害に気づくまでの時間、判断の時間、復元後の動作確認の時間が加わる

このシステムの実力は「データは最大24時間分を失う（RPO）、復旧には3時間以上かかる（RTO）」です。要件がこれより厳しいなら、バックアップの頻度を上げる、変更の記録から任意の時点へ戻せる機能を使う、といった見直しが必要です（{{ch:ha}}）。
:::

:::q 説明 | 手作業とIaCの違い
管理画面で手作業で作った環境と比べて、IaCで作った環境の利点を3つ挙げてください。
:::a
解答例：

1. 再現できる：同じコードから、検証用と本番用など同じ構成の環境を何度でも作れる
2. 変更を確認できる：適用の前に差分を確認でき、誰がいつ何を変えたかがコードの履歴として残る
3. レビューできる：構成がコードになっているので、適用の前に他の人が内容を確認できる

このほか、不要になった環境をまとめて削除できる、手順書と実際の設定がずれない、といった利点もあります。一方で、管理画面での手動変更を混ぜると、コードと実際の構成がずれる（ドリフト）ため、変更の入口をコードに一本化する運用が必要です（{{ch:s7}}）。
:::

:::q 判断 | 継続的デリバリーか、継続的デプロイか
ある金融系のシステムでは、本番環境への変更の前に、責任者の承認を記録として残すことが社内規程で定められています。CI/CDを導入する場合、どちらの方式が合いますか。
:::a
継続的デリバリーです。ビルドとテスト、検証環境への反映までを自動で行い、本番への反映の前に人の承認を挟みます。承認の操作そのものをCI/CDの仕組みの中で行えば、誰がいつ承認したかが自動で記録されます。

「承認が必要だから自動化できない」のではなく、「承認以外をすべて自動化する」と考えるのが要点です。
:::

:::q 選択 | 何を見て調べるか
次の3つの調査では、メトリクス・ログ・トレースのうち、まずどれを見ますか。

1. 昨夜、応答が遅くなった時間帯を特定したい
2. ある利用者の操作でエラーになった原因を知りたい
3. 1つのリクエストが複数のサービスを通る中で、どこに時間がかかっているかを知りたい
:::a
1. メトリクス。応答時間やCPU使用率の推移から、いつ起きたかがわかる
2. ログ。その時刻のエラーメッセージや処理の記録から、何が起きたかがわかる
3. トレース。サービスをまたいだ処理の流れと、それぞれの所要時間がわかる

実際の調査では、メトリクスで時間帯を絞り、ログで内容を確かめる、という順に組み合わせます（{{ch:s5}}）。
:::
