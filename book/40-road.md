クラウドは、読むだけでは身につきません。また、一度身につければ終わり、でもありません。この章では、この本を使った学び方と、到達の確かめ方、その先の進み方をまとめます。

## 5つのレベル

| レベル | 状態 | この本の範囲 | 確かめ方 |
|---|---|---|---|
| 1. 理解 | 用語と仕組みを、説明できる | 第1部 | 第1部の章末問題に、自分の言葉で答えられる。構成図の部品を、6分野に分類できる |
| 2. 構築 | 手順を見ながら、構築できる | 第2部のステップ1〜4 | 公式のハンズオンなどを参考に、Web 3層構成を作り、片付けられる |
| 3. 自走 | 手順なしで構築し、問題を切り分けられる | 第2部の全体、{{ch:ts}} | ステップ1〜6を、自力で作れる。わざと壊した状態から、原因を特定して直せる。{{ch:ts}}のシナリオの半分以上で、解答と同じ方向の仮説を立てられる |
| 4. 設計 | 要件から構成を考え、理由を説明できる | 第3部、{{ch:uc}}、{{ch:rev}} | {{ch:uc}}のケースで、構成の案と、判断の記録を作り、レビューで説明できる。他人の設計に、根拠のある指摘ができる |
| 5. 主導 | 複数のシステムや、組織にまたがる設計と運用を、主導できる | 第4部、{{ch:cap}} | {{ch:cap}}の成果物を、ひととおり作れる。条件の変更に、影響の範囲を見きわめて答えられる |

案件で、構築の担当を任されるにはレベル3、設計に加わるにはレベル4が、ひとつの目安です。レベル5は、この本だけで到達するものではなく、実際の案件での経験と、失敗を通じて、身につけていくものです。

## 学習の進め方

業務と並行して、週に5〜7時間ほど学ぶ場合の目安です。

| 段階 | 期間の目安 | 行うこと | 到達の確認 |
|---|---|---|---|
| 全体像の理解 | 1〜2週間 | 第1部を読む。ネットワークが初めての人は、{{ch:net}}に時間をかける。各社の入門向けの無料のトレーニング（AWS Skill Builder、Microsoft Learn、Google Cloud Skills Boost）を、1コース受ける | 第1部の章末問題 |
| 手を動かす | 5〜6週間 | {{ch:env}}の準備をしたうえで、ステップ1〜4を行う。毎回、片付けて、請求の画面を確かめる | 各ステップの確認ポイントを、人に説明する |
| 運用と自動化 | 4〜5週間 | ステップ5〜8を行う。{{ch:ts}}のシナリオに取り組む | 環境を、すべて削除した状態から、コードで作り直す |
| 設計 | 4〜6週間 | 第3部を読み、{{ch:uc}}のケース1〜8に取り組む。{{ch:rev}}と{{ch:calc}}を解く | ケースを1つ選び、チームの前で、構成と判断を説明する |
| 上級と総合 | 継続 | 担当する案件に近い、第4部の章を読む。{{ch:uc}}のケース9〜12と、{{ch:cap}}に取り組む | {{ch:cap}}の評価の基準で、すべての観点が「合格」に届く |

各段階で、作ったものを、必ずその日のうちに削除し、翌日に請求の画面を確かめる習慣を、続けてください。予算アラートは、利用の上限ではありません。

指導役がいる場合の進め方と、費用をかけずに進められる範囲は、{{ch:mentor}}にまとめています。

## 分野別のチェック

次の項目を、自分の言葉で説明でき、実際にできることを確かめます。

### 基礎と構築（レベル1〜3）

- [ ] オンプレミスとクラウドの違いを、費用・調達の期間・規模の変更の3点で説明できる
- [ ] IaaS・PaaS・SaaSの違いと、それぞれで利用者が責任を持つ範囲を説明できる
- [ ] IAM：ユーザー・グループ・ロール・ポリシーの違いを説明し、最小権限のポリシーを書ける
- [ ] ネットワーク：VPCのアドレスの設計と、ルートテーブルを、自分で決められる。パブリックとプライベートを、ルートテーブルから判定できる
- [ ] コンピュート：EC2とAuto Scaling、Lambda、ECSの使い分けを説明できる
- [ ] ストレージとデータベース：S3・EBS・RDS・DynamoDBを使い分け、バックアップから復元できる
- [ ] 運用：監視する項目とアラームを決め、障害の報告書を書ける
- [ ] IaC：環境をすべて削除し、コードから作り直せる。適用の前に、差分を読める
- [ ] CI/CD：自動のテストとデプロイの流れを作り、前の版に戻せる
- [ ] 切り分け：通信が通る順に、原因を絞り込める。エラーの出方の違いから、疑う場所を言える

### 設計（レベル4）

- [ ] 要件：あいまいな要望を、質問を通じて、数字の要件にできる
- [ ] 可用性：障害の単位ごとに備えを選び、RTOとRPOを満たす構成を説明できる
- [ ] セキュリティ：守るものと入口を整理し、層ごとの対策を選べる。重なったポリシーの判定ができる
- [ ] 性能：ピーク時の数字から、台数を概算できる。キャッシュとキューの使いどころと、注意点を説明できる
- [ ] データ：データの性質から、置き場所を選べる。整合性の違いが、画面の動きにどう表れるかを説明できる
- [ ] 費用：構成の月額を見積もり、費用が増える要因と、下げる方法を説明できる
- [ ] 判断の記録：検討した案、選んだ理由、受け入れたデメリット、見直す条件を書ける
- [ ] レビュー：他人の設計に、事実・リスク・提案の形で、重要度を付けて指摘できる

### 上級（レベル5）

- [ ] 複数のアカウントの構成と、SCPによる柵を設計できる
- [ ] 複数のVPCと、社内のネットワークの接続を、分離と冗長性を考えて設計できる
- [ ] 既存のシステムを、移行の戦略に仕分け、切り替えと切り戻しを計画できる
- [ ] 信頼性の目標を数字で決め、変更を、段階的に、戻せる形で届ける仕組みを設計できる
- [ ] 障害の対応を指揮し、非難のない振り返りを行える
- [ ] 複数のリージョンや、複数のクラウドを使う理由と代償を、説明できる

## 資格の活かし方

資格は、ゴールではなく、知識の抜けを見つける道具として使います。手を動かす学習と並行して学ぶと、試験の問題の状況が、具体的に想像できるようになり、理解が早まります。逆に、手を動かさずに問題集だけで合格しても、案件では役に立ちません。

AWSの認定は、基礎、アソシエイト、プロフェッショナル、専門知識の4つの段階に分かれています（[AWS認定](https://aws.amazon.com/certification/)）。

| タイミング | 資格の例 | ねらい |
|---|---|---|
| 第1部を終えたころ | AWS Certified Cloud Practitioner | 全体の用語、料金、責任共有モデルの確認 |
| 第2部を終えてから、3〜6か月以内 | AWS Certified Solutions Architect – Associate | 設計の定番のパターンと、判断の基準の確認 |
| 担当が決まったら | 開発、運用、データ、機械学習など、担当に合ったアソシエイトの資格 | 担当の分野を深める |
| 第3部と第4部に取り組みながら | AWS Certified Solutions Architect – Professional、セキュリティなどの専門知識の資格 | 複雑な要件のもとでの、設計の判断の確認 |

ほかの事業者にも、同じような段階の資格があります。

| レベル | Microsoft Azure | Google Cloud |
|---|---|---|
| 入門 | Azure Fundamentals（AZ-900） | Cloud Digital Leader |
| 基礎（設計・構築） | Azure Administrator Associate（AZ-104） | Associate Cloud Engineer |
| 上級 | Azure Solutions Architect Expert ほか | Professional Cloud Architect ほか |

最初の1社は、参画する予定の案件で使うクラウドを選ぶのが、最も効率的です。特に決まっていなければ、国内の案件の数と、情報の量が多いAWSから始めるのが無難です。資格の名称、出題の範囲、提供の終了は、たびたび改定されます。受験の前に、必ず、公式のサイトで最新の情報を確かめてください。

## 学び続ける

クラウドは、毎週のように、新しい機能が加わり、仕様が変わります。この本の内容も、やがて古くなります。変わらないのは、考え方と、確かめる習慣です。

- 一次情報に当たる：迷ったら、公式のドキュメントを読む。この本の{{ch:refs}}に挙げた資料は、その入口
- 変化を、定期的に眺める：週に15分、新しい機能のお知らせに目を通す。すべてを理解する必要はない。「そういうものが出た」と知っているだけで、必要になったときに思い出せる
- 自分の環境を持つ：小さくてよいので、自分で設計し、動かし続けるものを持つ。費用を払い、障害を経験し、版を上げる。読んだだけの知識が、経験に変わる
- 人に説明する：社内の勉強会で発表する。後輩に教える。説明に詰まったところが、次に学ぶこと
- 人の設計を読む：先輩の構成図や、設計書を読み、自分なら別の案を出せるかを考える。公開されている事例や、障害の振り返りの文書も、よい教材になる
- 記録を残す：詰まったこと、原因、解決の方法を、書き留める。半年後の自分と、同じことで詰まる誰かを、助ける

## おわりに

この本で扱ったのは、個々のサービスの使い方よりも、考え方です。何を守り、何を許容するかを、要件から決める。数字で確かめる。複数の案を比べる。判断を記録する。壊して、確かめる。人ではなく、仕組みを直す。サービスの名前や画面は変わっても、これらは変わりません。

最初は、誰でも、構成図の箱の名前がわからないところから始めます。作って、壊して、説明することを繰り返せば、必ず、設計を語れるようになります。この本が、その道のりの、手元の地図になれば幸いです。
