:::goal
- 設計を、決まった観点に沿って漏れなく確かめられる
- 指摘を、事実・リスク・提案の形で、重要度を付けて伝えられる
- レビューを受ける側として、判断の記録と未決の事項を用意できる
:::

設計は、自分ひとりでは完成しません。自分の設計の穴は、自分には見えにくいからです。レビューは、設計の品質を上げるための最も費用対効果の高い方法であり、レビューする力は、設計する力と表裏一体です。他人の設計の弱点を見つけられる人は、自分の設計でも同じ弱点を避けられます。

## レビューの進め方

1. 前提から確かめる：構成を見る前に、要件と制約を確かめる。要件がわからなければ、構成が適切かどうかは判断できない。「マルチAZになっていない」は、要件によっては正しい設計
2. 通信とデータの流れを追う：利用者から、入口、アプリ、データまでを、{{ch:pattern}}の5つの観点で読む
3. 観点ごとに確かめる：次の節の観点に沿って、順に確かめる
4. 壊してみる：「このサーバーが止まったら」「このAZが止まったら」「この認証情報が漏れたら」「アクセスが10倍になったら」と、頭の中で壊す
5. 指摘をまとめる：重要度を付け、事実と理由を添える



## Well-Architected Framework で確かめる

AWSが公開している設計の指針で、6つの柱（観点）から構成を確かめます。ハンズオンで作った構成を、次の問いで自己チェックしてみてください。AWSの管理画面には、質問に答える形でレビューできる Well-Architected Tool もあります。

| 柱 | 問いの例 |
|---|---|
| 運用上の優秀性 | 変更や障害対応の手順は決まっているか。手作業に頼っていないか |
| セキュリティ | 最小権限になっているか。データは暗号化されているか。操作の記録は残るか |
| 信頼性 | 1つのAZが止まっても動くか。バックアップから実際に戻せるか |
| パフォーマンス効率 | 負荷に合った種類と大きさを選んでいるか。負荷の増減に追いつけるか |
| コスト最適化 | 使っていない資源はないか。誰が費用を把握しているか |
| 持続可能性 | 必要以上の資源を使っていないか。使用率を上げ、無駄を減らしているか |

柱ごとの問いを、もう少し具体的な確認項目にしたのが次の一覧です。すべてを満たす必要はありません。満たしていない項目について、「わかったうえで選んでいるか」を確かめます。

### 運用上の優秀性

- [ ] 構成はコードで管理され、同じ環境を作り直せる
- [ ] 変更は、差分の確認と承認を経て、自動で適用される
- [ ] 問題のある変更を、前の状態に戻す手順がある
- [ ] 利用者への影響に気づく監視があり、通知を受けた後の動きが決まっている

### セキュリティ

- [ ] 人とプログラムの権限が分かれ、それぞれ必要な範囲に絞られている
- [ ] 長く使える認証情報（アクセスキー、埋め込まれたパスワード）がない
- [ ] インターネットから直接届く部品が、必要最小限になっている
- [ ] 保存データと通信が暗号化され、操作の記録が保存されている

### 信頼性

- [ ] 単一障害点が洗い出され、残すものは理由が記録されている
- [ ] RTOとRPOが決まっており、構成がそれを満たす
- [ ] バックアップからの復元を、実際に試している
- [ ] 上限値（クォータ）が、必要な最大の量を上回っている

### パフォーマンス効率

- [ ] 応答時間と処理量の目標が、数字で決まっている
- [ ] 負荷の増減に、台数や処理能力が追いつく
- [ ] データベースが、最初の詰まりどころにならないよう考えられている

### コスト最適化

- [ ] 月額の見積もりが、前提とともに示されている
- [ ] 本番以外の環境が、必要以上に大きくない。使わない時間は止まる
- [ ] 誰の費用かがわかり、増えたときに気づく仕組みがある

### 持続可能性

- [ ] 使用率の低い資源が、放置されていない
- [ ] 不要になったデータが、自動で削除または安い保存先へ移る

## よくある指摘

設計のレビューで繰り返し見つかる問題は、ある程度決まっています。自分の設計を出す前に、次の一覧で確かめておくと、レビューの時間を本質的な議論に使えます。

| よくある問題 | 例 |
|---|---|
| 見落とされた単一障害点 | NATゲートウェイが1台。バッチ用のサーバーが1台。DNSや認証の基盤 |
| 広すぎる権限 | Action や Resource が「*」。複数のアプリで1つのロールを使い回している |
| 戻せない | バックアップはあるが、復元を試していない。デプロイを前の版に戻す手順がない |
| 気づけない | 監視が資源の指標だけで、利用者から見たエラーや遅さを測っていない |
| 前提のない数字 | 見積もりや台数に、根拠となる利用量の前提が書かれていない |
| 上限の未確認 | 同時に動かせる数、接続の数、APIの呼び出しの頻度などの上限を確かめていない |
| 手作業への依存 | 構築や切り替えの手順が、特定の人の記憶と手作業に頼っている |
| 片方向の設計 | 切り替える手順はあるが、戻す手順がない。作る手順はあるが、消す手順がない |

## 指摘の伝え方

指摘は、相手が次に何をすればよいかがわかる形で伝えます。「事実」「リスク」「提案」の3つをそろえ、重要度を付けます。

| 重要度 | 意味 |
|---|---|
| 必須 | このままでは、要件を満たさない、または事故につながる。対応するまで先に進めない |
| 推奨 | 対応したほうがよいが、判断は設計者に任せる。対応しない場合は、理由を記録する |
| 質問 | 意図を確かめたい。答え次第で、指摘になるかもしれない |

悪い例と良い例を比べます。

- 悪い例：「可用性が低いと思います」
- 良い例：「【必須】データベースが単一AZの構成になっています（事実）。要件の『復旧は30分以内』に対し、AZの障害時にはバックアップからの復元が必要で、練習では50分かかっています（リスク）。マルチAZ構成にするか、要件の見直しを利用部門と合意することを提案します（提案）」

レビューで評価するのは、設計であって、人ではありません。「なぜこうしなかったのか」ではなく、「この場合、どうなりますか」と聞くと、意図を確かめながら、一緒に穴を探す形になります。

## レビューを受ける準備

レビューを受ける側の準備で、レビューの質は大きく変わります。

- 要件と制約を1枚にまとめる：何を満たすための設計かを、最初に共有する
- 構成図と、通信の流れを用意する
- 判断の記録を添える：検討した案と、選んだ理由（{{ch:req}}）。レビューする人が、同じ検討を繰り返さずに済む
- 決まっていないこと、不安なことを、自分から挙げる：「ここは迷っている」と示せば、そこに議論を集中できる
- 指摘は、その場で反論せず、まず記録する：対応するかどうかは、後で理由とともに決める

:::sum
- レビューは、要件と制約の確認から始める。要件がわからなければ、構成の良し悪しは判断できない
- 6つの柱の観点で確かめ、満たしていない項目は「わかったうえで選んでいるか」を見る
- 指摘は、事実・リスク・提案をそろえ、重要度を付けて伝える
- 受ける側は、判断の記録と、迷っている点を自分から示す
:::

## 章末問題

:::q 書き直し | 伝わる指摘にする
レビューで、次の3つのコメントが出ました。それぞれ、事実・リスク・提案をそろえた指摘に書き直してください。前提は自分で補ってかまいません。

1. 「セキュリティが甘い」
2. 「これだと高くつきませんか」
3. 「監視が足りない」
:::a
解答例：

1. 「【必須】アプリサーバーのIAMロールに、S3のすべての操作がすべてのバケットに対して許可されています（事実）。アプリの脆弱性を突かれた場合、ほかのシステムのバケットのデータまで読み出しや削除ができてしまいます（リスク）。このアプリが使う2つのバケットに対する、読み取りと書き込みだけに絞ることを提案します（提案）」
2. 「【推奨】検証環境が、本番と同じ大きさのサーバー4台とマルチAZのデータベースで、常時稼働する構成になっています（事実）。見積もりでは、検証環境だけで月額の約4割を占めます（リスク）。サーバーを2台に減らし、データベースを単一AZにし、夜間と休日は停止することを提案します。AZ障害の試験を検証環境で行う予定があれば、その期間だけ構成を戻す方法もあります（提案）」
3. 「【必須】アラームが、サーバーのCPU使用率だけに設定されています（事実）。アプリがエラーを返している場合や、データベースの空き容量がなくなった場合に、利用者からの連絡まで気づけません（リスク）。ロードバランサーの5xxエラーの割合、正常なターゲットの数、データベースの空き容量と接続数にアラームを追加し、通知先と最初の確認手順を決めることを提案します（提案）」

どれも、元のコメントでは、相手は何を直せばよいのかわかりません。事実を具体的に書くためには、設計を実際に読み込む必要があります。指摘の質は、読み込みの深さで決まります。
:::

:::q 指摘 | 短い説明から問題を見つける
次の設計の説明を読み、指摘を3つ以上、重要度を付けて挙げてください。要件は「社外の会員が24時間使う予約サイト。復旧は1時間以内。個人情報を扱う」です。

「ALBの後ろにEC2を2台（どちらもAZ-a）置く。データベースはRDSの単一AZで、毎日スナップショットを取る。EC2にはSSHで入れるよう、22番ポートを運用会社の拠点のIPアドレスに限定して開ける。データベースのパスワードは、アプリの設定ファイルに書く。デプロイは、担当者がサーバーに入ってファイルを置き換える」
:::a
解答例：

- 【必須】EC2が2台とも同じAZにある。AZの障害で両方が止まる。別のAZに分ける
- 【必須】データベースが単一AZで、復旧はスナップショットからの復元になる。復元にかかる時間が1時間以内に収まるかを確かめていない。また、毎日のスナップショットでは、最大24時間分の予約を失う。マルチAZ構成と、任意の時点に戻せるバックアップを検討する。RPOが要件に書かれていないため、まず確認する
- 【必須】データベースのパスワードを設定ファイルに書いている。サーバーに入れる人や、設定ファイルを含むリポジトリを読める人に漏れる。Secrets Manager に置き、実行時に取り出す
- 【推奨】SSHのポートを開けている。接続元を限定しているが、鍵の管理と、誰が入ったかの記録が課題になる。Session Manager に切り替え、ポートを閉じる
- 【推奨】デプロイが手作業。手順の誤りが起きやすく、2台の中身がずれる。前の版に戻す手順も不明。イメージやコンテナによる入れ替えと、自動化を検討する
- 【質問】個人情報を扱うが、保存データの暗号化、操作の記録の保存、WAFの有無が書かれていない。どうなっているか
- 【質問】監視と、夜間の障害時の連絡体制はどうなっているか

要件に「24時間」「1時間以内」「個人情報」と書かれているので、それぞれに対応する観点（可用性、復旧、セキュリティ）から順に確かめると、漏れなく見つけられます。より本格的な演習は{{ch:rev}}で行います。
:::
