:::goal
- データの性質と使われ方から、保存先の種類を選べる
- リレーショナルデータベースとキーバリュー型のデータベースの設計の違いを説明できる
- S3の保存クラスとライフサイクルを使い、保存期間に応じて費用を下げられる
- 整合性の違いが、アプリの動きにどう表れるかを説明できる
:::

データの置き場所は、システムの中で最も変えにくい判断です。サーバーは作り直せますが、データベースの種類を後から変えるには、データの移行とアプリの書き直しが必要になります。だからこそ、流行や慣れではなく、データの性質と使われ方から選びます。

## データについて、先に聞くこと

| 問い | なぜ聞くか |
|---|---|
| どのような形のデータか | 表の形で、項目同士に関係があるか。項目が決まっていない文書か。ファイルそのものか |
| どう読むか | キーを指定して1件ずつ読むのか。条件を組み合わせて検索するのか。大量に集計するのか |
| どう書くか | 書き込みの頻度は。複数のデータを、まとめて矛盾なく更新する必要があるか |
| どのくらいの量で、どう増えるか | 今の件数と、1年後、3年後の見込み。1つのサーバーに収まる規模か |
| 読んだ内容は、最新でなければならないか | 残高のように、必ず最新を読む必要があるか。数秒の遅れを許せるか |
| いつまで保存し、いつ消すか | 法令や規程で決まった期間。古いデータを読む頻度 |

特に「どう読むか」が決め手になります。同じ注文のデータでも、「注文番号で1件読む」「顧客ごとに一覧を出す」「月ごとに売上を集計する」では、適した置き場所が違います。1つのシステムの中で、目的ごとに複数の置き場所を使い分けるのは、ごく普通のことです。

## 置き場所の地図

| 種類 | AWSの例 | 向いている使い方 | 注意する点 |
|---|---|---|---|
| リレーショナルデータベース | RDS、Aurora | 項目同士に関係があり、条件を組み合わせて検索する。複数の更新をまとめて矛盾なく行う | 書き込みは基本的に1台が受け持つ。大きくなるほど、拡張に工夫が要る |
| キーバリュー型・ドキュメント型 | DynamoDB | キーを指定した読み書きが大量にある。規模が大きく変動する | 読み方を先に決めて設計する。後から別の読み方を足すのは難しい |
| インメモリ | ElastiCache | キャッシュ、ログイン中の情報、順位表 | メモリ上にあるため、消えても困らない使い方を基本にする |
| オブジェクトストレージ | S3 | 画像や文書、バックアップ、ログ、分析の元データ | ファイルの一部だけを書き換えることはできない |
| 全文検索 | OpenSearch Service | 文章の中の言葉での検索、ログの検索と可視化 | 元のデータは別に持ち、検索用の写しとして使う |
| データウェアハウス | Redshift、Athena | 大量のデータの集計と分析 | 1件ずつの細かい更新には向かない |

迷ったときの出発点は、リレーショナルデータベースです。扱える人が多く、読み方が後から変わっても対応しやすいためです。そのうえで、規模や読み書きの性質が合わない部分を、ほかの種類に切り出します。

## リレーショナルデータベース：RDSとAurora

どちらも、PostgreSQLやMySQLと互換のあるデータベースを、事業者の管理のもとで動かすサービスです。Auroraは、保存の仕組みをクラウド向けに作り直したもので、データを3つのAZにまたがる6つの複製として持ちます。障害時の切り替えの速さ、読み取り用の複製の追加のしやすさ、保存領域の自動の拡張に特徴があります（切り替えの目安は{{ch:ha}}）。

設計で決めることは、どちらを選んでも共通しています。

- 大きさ：CPUとメモリ。最初は小さめに始め、指標を見て調整する
- 可用性：単一AZか、マルチAZか
- 読み取りの分散：読み取り用の複製を使うか。使う場合、複製の遅れをアプリがどう扱うか
- 接続の数：アプリのサーバーや関数が増えたとき、接続の上限を超えないか
- 保守：修正プログラムの適用の時間帯、バージョンを上げる計画
- 守り：暗号化、バックアップの保持期間、削除保護

## キーバリュー型データベース：DynamoDBの考え方

DynamoDBは、リレーショナルデータベースとは設計の順序が逆になります。リレーショナルデータベースでは、まずデータの形を整理し、読み方は後から問い合わせで決められます。DynamoDBでは、まず「どう読むか」をすべて書き出し、それに合わせてキーを決めます。

| 用語 | 役割 |
|---|---|
| パーティションキー | データをどの保存場所に置くかを決めるキー。読むときは、必ずこのキーを指定する |
| ソートキー | 同じパーティションキーの中での並び順を決めるキー。範囲を指定して読める |
| グローバルセカンダリインデックス（GSI） | 別のキーでも読めるようにするための、もう1つの索引 |

たとえば注文のデータを「顧客ごとに、新しい順に一覧を出す」なら、パーティションキーを顧客のID、ソートキーを注文の日時にします。これで、ある顧客の最近の注文を、1回の問い合わせで効率よく読めます。「注文番号で1件読む」という別の読み方も必要なら、注文番号をキーにしたGSIを追加します。

パーティションキーには、値がよく散らばる項目を選びます。少数の値に読み書きが集中すると、その保存場所だけが混雑し、全体に余裕があっても処理が制限されます。日付や、種類の少ない区分をそのままパーティションキーにするのは、典型的な失敗です。

料金の方式は、使った分だけ払うオンデマンドと、処理能力をあらかじめ決めておく方式から選べます。負荷が読めないうちはオンデマンドで始め、安定してから見直すのが無難です。

## オブジェクトストレージ：S3の保存クラスとライフサイクル

S3には、読み出す頻度に応じた保存クラスがあります。保存の単価が安いクラスほど、読み出しに料金や時間がかかります。

| 保存クラス | 向いているデータ | 読み出し | 最低の保存期間 |
|---|---|---|---|
| 標準（Standard） | 頻繁に読むデータ | すぐ。読み出しの料金なし | なし |
| 標準－低頻度アクセス（Standard-IA） | 月に1回も読まないが、必要なときはすぐ読みたい | すぐ。読み出した量に料金 | 30日 |
| Intelligent-Tiering | 読む頻度が予測できない | すぐ。読まれ方を見て、自動で安い層へ移す | なし |
| Glacier Instant Retrieval | 四半期に1回程度しか読まないが、すぐ読みたい | すぐ。読み出しの料金は高め | 90日 |
| Glacier Flexible Retrieval | めったに読まない保管用 | 数分から数時間 | 90日 |
| Glacier Deep Archive | 法令上の長期保管など、ほぼ読まない | 半日程度 | 180日 |

最低の保存期間より早く消したり移したりすると、残りの期間の分も料金がかかります。短い期間で消えるデータを、安いクラスに入れると、かえって高くつきます。

ライフサイクルルールを設定すると、「作成から30日後に低頻度アクセスへ、1年後にアーカイブへ、7年後に削除」のような移動と削除を自動で行えます。あわせて、次の2つを検討します。

- バージョニング：上書きや削除をしても、前の版を残す。誤操作から戻せる。古い版にも料金がかかるため、古い版を消すルールと組み合わせる
- オブジェクトロック：決めた期間、誰にも削除や上書きをさせない。改ざんされてはならない記録に使う

## 整合性：読んだ内容は最新か

データを複数の場所に複製する仕組みでは、「書いた直後に読んで、必ず最新が返るか」が、製品や読み方によって違います。

| 置き場所 | 書いた直後の読み取り |
|---|---|
| RDS・Auroraのプライマリ | 最新が返る |
| RDS・Auroraの読み取り用の複製 | 複製の遅れの分だけ、古い内容が返ることがある |
| DynamoDB | 既定の読み方では、ごく短い間、古い内容が返ることがある。指定すれば、必ず最新を読める（料金は高くなる） |
| S3 | 最新が返る |
| キャッシュ、CDN | 保存の期限が切れるまで、古い内容が返る |

これは、画面の動きとして表れます。「登録した直後に一覧を開くと、今登録したものが出ていない」という不具合は、書き込みはプライマリへ、一覧の読み取りは複製へ、と分けたときによく起きます。対策は、登録の直後の読み取りだけはプライマリから行う、登録した内容を画面側で一覧に足して見せる、などです。どこで古さを許し、どこで許さないかを、機能ごとに決めておきます。

## データの一生を設計する

- 分類する：個人情報、機密、社内限り、公開、のように区分を決め、区分ごとに置き場所と権限、暗号化の要否を決める
- 保存期間を決める：何年残すか、その根拠は何か。期限が来たら、誰が、どう消すか
- 本番のデータを、ほかの環境に持ち出さない：検証や開発には、作ったデータか、個人を特定できないように加工したデータを使う
- 持ち出しの経路を把握する：データが、ほかのシステムや分析の基盤へどう流れているか。写しがどこにあるか

:::sum
- 置き場所は、データの形と、読み方、書き方、量、整合性、保存期間から選ぶ。1つのシステムで複数を使い分けてよい
- リレーショナルデータベースは形から、DynamoDBは読み方から設計する
- S3は、読む頻度に合った保存クラスとライフサイクルで費用を下げる。最低の保存期間に注意する
- 複製やキャッシュがあるところでは、古い内容が返ることがある。許す場所と許さない場所を決める
:::

## 章末問題

:::q 選択 | 置き場所を選ぶ
次の6つのデータについて、最初に検討する置き場所を答えてください。

1. 受注、顧客、商品のデータ。受注の登録では、在庫の引き当てと同時に矛盾なく更新する
2. ログイン中の利用者の情報。数百ミリ秒ごとに読まれ、30分で不要になる
3. 利用者がアップロードした契約書のPDF
4. IoT機器から毎秒数千件届く計測値。機器のIDと時刻で読む
5. 商品の説明文を対象にした、言葉での検索
6. 3年分の売上データを使った、月次や商品別の集計
:::a
1. リレーショナルデータベース（RDS、Aurora）。複数の表をまとめて矛盾なく更新する必要がある
2. インメモリのデータストア（ElastiCache）。速く読め、期限が来たら自動で消せる。DynamoDBに、期限で自動的に消える設定を使って置く方法もある
3. オブジェクトストレージ（S3）。データベースには、ファイルの場所と、検索に使う項目だけを持つ
4. キーバリュー型（DynamoDB）、または時系列のデータ向けのデータベース。大量の書き込みを受けられ、機器のIDと時刻をキーにして読める
5. 全文検索（OpenSearch Service）。元のデータはリレーショナルデータベースに持ち、検索用の写しを作る
6. データウェアハウス（Redshift）、またはS3に置いたデータへの問い合わせ（Athena）。業務用のデータベースで重い集計を行うと、業務の処理が遅くなる

5と6は、元のデータの「写し」を別の置き場所に作る形です。写しをどう最新に保つか（どのくらいの遅れを許すか）が、次の設計の問いになります。
:::

:::q 設計 | DynamoDBのキーを決める
会員制のサービスで、利用者の「お気に入り」を保存します。読み方は次の2つです。パーティションキーとソートキーを決めてください。

- ある利用者のお気に入りを、登録の新しい順に20件ずつ表示する
- ある利用者が、特定の商品をお気に入りに入れているかを確かめる

また、後から「ある商品を、お気に入りに入れている人の数を知りたい」という要望が出た場合、どう対応しますか。
:::a
解答例：パーティションキーを利用者のID、ソートキーを「登録の日時」にすると、1つ目の読み方には合いますが、2つ目の読み方（特定の商品があるか）は、その利用者のすべてのお気に入りを読まないとわかりません。

2つの読み方の両方に合わせるには、たとえば次のようにします。

- パーティションキー：利用者のID、ソートキー：商品のID。これで2つ目は、キーを指定して1件読むだけで済む
- 1つ目のために、「パーティションキー：利用者のID、ソートキー：登録の日時」の索引を追加する。同じパーティションキーで別の並び順が欲しいときは、ローカルセカンダリインデックス（テーブルの作成時にだけ定義できる）か、GSIを使う

後からの要望（商品ごとの人数）には、次のどちらかで対応します。

- 商品のIDをパーティションキーにしたGSIを追加し、件数を数える。人気の商品では件数が多くなり、毎回数えるのは高くつく
- お気に入りの登録と解除のたびに、商品ごとの人数を別の項目として加算・減算しておく。読むのは速いが、更新の処理が増える

読み方が後から増えると、このように索引の追加や、集計値の持ち方の工夫が必要になります。設計の前に、読み方をできるだけ洗い出しておく理由です。
:::

:::q 計算 | 保存クラスを移すと、いくら変わるか
監査用のログを、毎月100GBずつ、S3にためていきます。演習用の仮単価を、1GBあたり月額で、標準 0.025ドル、低頻度アクセス 0.0125ドル、アーカイブ 0.002ドルとします。読み出しはないものとします。

1. すべて標準に置いたまま、3年たった時点での、その月の保存の料金はいくらですか
2. 「作成から3か月は標準、その後9か月は低頻度アクセス、1年を過ぎたらアーカイブ」とした場合、3年たった時点での、その月の料金はいくらですか
:::a
1. 3年で 100GB × 36か月 = 3,600GB。3,600 × 0.025 = 90ドル
2. 3年たった時点で、
    - 標準にあるのは、直近3か月分の300GB：300 × 0.025 = 7.5ドル
    - 低頻度アクセスにあるのは、その前の9か月分の900GB：900 × 0.0125 = 11.25ドル
    - アーカイブにあるのは、残りの24か月分の2,400GB：2,400 × 0.002 = 4.8ドル
    - 合計 23.55ドル

月額は約4分の1になります。データは増え続けるため、差は年々広がります。実際には、クラスを移すときの料金、読み出すときの料金、最低の保存期間があるため、「本当に読まないか」「読むとしたら、どのくらい待てるか」を確かめてから決めます。
:::

:::q 原因 | 登録したのに一覧に出ない
データベースの負荷を下げるため、一覧の表示は読み取り用の複製から、登録はプライマリへ、と分けました。その後、「登録の直後に一覧を開くと、今登録したものが出ていない。少したって開き直すと出る」という報告が増えました。原因と対策を答えてください。
:::a
原因：プライマリから読み取り用の複製への複製には、わずかな遅れがあります。登録の直後に複製から読むと、まだ複製されていない、古い状態が返ります。負荷が高いときほど、遅れは大きくなります。

対策の例：

- 登録の直後の読み取りだけは、プライマリから行う。たとえば、登録した利用者自身の、その後数秒間の読み取り
- 登録の応答で返した内容を、画面の側で一覧に加えて表示する。読み直さない
- 複製の遅れを監視し、遅れが大きい複製からは読まないようにする
- 遅れを許せない画面と、許せる画面を分ける。集計や検索は複製から、本人の最新の情報はプライマリから読む

読み取りの分散は、「どの読み取りなら、少し古くてもよいか」を機能ごとに決めて、初めて安全に使えます。
:::

:::q 改善 | 特定のキーに集中する
アクセスログをDynamoDBに保存しています。パーティションキーは日付（例：2026-11-10）、ソートキーは時刻です。アクセスが増えるにつれ、テーブル全体の処理能力には余裕があるのに、書き込みが制限されるようになりました。原因と、キーの見直しの案を答えてください。
:::a
原因：その日の書き込みが、すべて「今日の日付」という1つのパーティションキーに集中しています。DynamoDBは、パーティションキーの値ごとにデータを分けて置くため、1つの値に集中すると、その場所の処理能力の上限に当たります。テーブル全体の余裕は、ほかの（過去の日付の）場所にあるだけで、使えません。

見直しの案：

- 値がよく散らばる項目をパーティションキーにする。たとえば、利用者のIDやセッションのID。「利用者ごとのログを時刻順に読む」という読み方に合う
- 日付で読みたい場合は、日付に番号を付け足して分散させる（例：2026-11-10#3 のように、0から9の番号を振り分ける）。読むときは、10個のキーを読んでまとめる
- そもそもの置き場所を見直す。ログのように、大量に書いて、後から集計するデータは、S3にためてAthenaで読むほうが、安くて扱いやすいことが多い

3つ目のように、「このデータは、この置き場所でよいのか」に立ち返るのが、最も効果的なこともあります。
:::
