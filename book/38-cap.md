:::goal
- 1つの題材について、要件の整理から、構成、判断の記録、見積もり、移行の計画までを、ひととおり作り上げる
- 作ったものを人に説明し、質問と指摘に、根拠を持って答える
- 条件が変わったとき、どこを変えればよいかを、すばやく判断する
:::

この本の仕上げとして、1つのシステムを、最初から最後まで設計します。これまでの章の演習は、観点ごとに分かれていました。実際の案件では、それらが、同時に、互いに影響し合いながら出てきます。可用性を上げれば費用が増え、費用を抑えれば運用の手間が増えます。その釣り合いを、自分で決めて、説明する練習です。

正解は、1つではありません。評価の対象は、構成の見た目ではなく、判断の根拠です。

## 題材：高速バスの予約システムの刷新

ある高速バスの会社が、予約システムを、クラウドへ移して作り直すことになりました。あなたは、設計の担当です。最初の打ち合わせで、次のことがわかりました。

| 項目 | わかっていること |
|---|---|
| 現状 | オンプレミスで稼働。サーバーの保守が、1年後に切れる。Webサーバー4台、アプリサーバー4台、データベース（商用の製品）2台 |
| 利用者 | 会員は30万人。Webとスマートフォンのアプリから予約する |
| 負荷 | 平常時は、毎秒20件ほど。大型連休の便の発売の開始時（年に数回、日時は事前に決まる）は、開始から15分ほど、その20倍になる |
| 予約 | 同じ座席を、2人に売ってはならない。決済は、外部の決済サービスを使う |
| 社内の利用 | コールセンター（50席）が、同じシステムで、電話での予約を受ける。全国20か所の営業所が、運行の管理の画面を使う |
| 夜間の処理 | 毎晩、売上の集計と、提携するバス会社への連携ファイルの作成を行う。朝5時までに終える |
| 止まったとき | 「30分以内に再開したい。受けた予約は、失えない」と言われている |
| 情報 | 氏名、連絡先を預かる。カードの番号は、持たない |
| 体制 | 情報システムの担当は3人。構築と、平日日中の運用は、外部に委託する。夜間は、当番の1人が、電話で呼び出される |
| 予算 | 月額100万円以内（演習では、1ドル = 150円として計算する） |

打ち合わせで、聞けていないことも、多くあります。

## 作るもの

次の10点を、作ります。分量は、全体で、A4に10〜15ページ程度が目安です。

| 番号 | 成果物 | 内容 | 主に使う章 |
|---|---|---|---|
| 1 | 質問の一覧 | 設計の前に、顧客に確かめること。それぞれ、答えによって、設計の何が変わるかを添える | {{ch:req}} |
| 2 | 要件の整理 | 非機能要件を、6つの大項目で、数字にする。確かめられていないものは、仮定として明記する | {{ch:req}} |
| 3 | 構成図 | 2つ以上の案。通信の流れと、AZをまたぐ配置がわかるもの | {{ch:pattern}}、{{ch:perf}} |
| 4 | 判断の記録 | 主な判断を、3件以上。検討した案、選んだ理由、受け入れたデメリット、見直す条件 | {{ch:req}} |
| 5 | ネットワークと権限 | アドレスの割り当て、サブネット、セキュリティグループ、社内との接続。アカウントの分け方と、人とプログラムの権限 | {{ch:s2}}、{{ch:sec}}、{{ch:org}} |
| 6 | 可用性とデータの保護 | 障害の単位ごとの備え。バックアップと復元。リージョンの障害への方針 | {{ch:ha}} |
| 7 | 監視と目標 | 利用者から見た指標と、目標の数字。通知するものと、通知を受けた後の動き | {{ch:s5}}、{{ch:sre}} |
| 8 | 届け方と移行 | デプロイの方式。現行のシステムからの、データの移行と、切り替えの計画。切り戻しの条件 | {{ch:s8}}、{{ch:mig}} |
| 9 | 見積もり | 月額の概算と、前提。本番と、それ以外の環境。発売の開始の日の、追加の費用 | {{ch:cost}} |
| 10 | リスクと未決の事項 | わかっている弱点、決められなかったこと、次に確かめること | {{ch:review}} |

## 進め方

個人で取り組む場合は、4週間が目安です。

| 週 | 行うこと |
|---|---|
| 1週目 | 題材を読み、質問の一覧を作る。答えが得られない前提で、仮定を置く。要件を整理する（成果物の1、2） |
| 2週目 | 構成の案を、2つ以上描く。比べて、1つを選ぶ。判断を記録する（3、4） |
| 3週目 | 選んだ案を、詳しくする。ネットワーク、権限、可用性、監視（5、6、7） |
| 4週目 | 届け方と移行、見積もり、リスクをまとめる。全体を見直し、発表の準備をする（8、9、10） |

チームで行う場合は、2日間の研修としても実施できます。1日目に、成果物の1から4までを作って中間の発表を行い、2日目に、残りを作って最終の発表を行います。講師や先輩が、顧客の役として、質問に答えると、より実務に近くなります。

:::tip 最初に、数字を出す
構成を描き始める前に、計算をしてください。発売の開始時の、毎秒の件数。そのとき、同時に処理している数。必要な台数。データベースの接続の数。1年分の予約のデータの量。数字があれば、構成の案を、根拠を持って比べられます。数字がなければ、好みの議論になります。
:::

## 評価の基準

自分の成果物を、次の表で確かめます。勉強会や面談では、評価する側も、この表を使います。

| 観点 | まだ足りない | 合格 | 優れている |
|---|---|---|---|
| 要件の把握 | 題材に書かれたことを、そのまま写している | あいまいな点を、質問と仮定にしている。数字になっている | 質問ごとに、答えによる設計への影響が示されている。要件同士の衝突に、気づいている |
| 構成 | 1つの案だけ。定番の構成を、そのまま当てはめている | 2つ以上の案があり、要件に照らして比べている | 発売の開始時の急増、座席の二重販売の防止など、この題材に固有の難しさに、構成で答えている |
| 判断の根拠 | 「一般的だから」「推奨されているから」 | 要件と数字に結び付いた理由がある。デメリットを書いている | 見直す条件が、具体的。選ばなかった案が、どの条件なら有利になるかを説明できる |
| 可用性とデータ | 「マルチAZにする」とだけ書かれている | 障害の単位ごとに、何が起き、何分で戻るかが書かれている。復元の方法がある | 目標の30分を、時刻を追って検証している。試験と訓練の計画がある |
| セキュリティ | 「暗号化する」「WAFを入れる」の列挙 | 守るものと、入口が整理され、層ごとに対策がある。権限が、役割ごとに分かれている | 委託先の権限、本番のデータへのアクセス、記録の保全まで、考えられている |
| 性能 | 台数の根拠がない | ピーク時の数字から、台数と、データベースの負荷を見積もっている | 急増に、台数の自動調整が間に合わないことを踏まえた備えがある。試験の計画がある |
| 費用 | 合計の金額だけ | 項目ごとの内訳と、前提がある。予算に収まっている | 最も費用のかかる項目と、下げる方法が示されている。発売の日の増分を、分けて見積もっている |
| 運用と移行 | 触れていない | 監視、通知、デプロイ、切り替えの手順がある | 3人の体制で回ることを、考えている。切り戻しの条件と期限がある |
| 説明 | 資料を読み上げる | 結論から話し、質問に、根拠を示して答える | わからないことを、わからないと言い、どう確かめるかを答える |

すべての観点で「優れている」を目指す必要はありません。まず、すべてが「合格」に届いていることを確かめ、そのうえで、得意な観点を伸ばします。

## 発表と、レビュー

発表は15分、質疑は15分を目安にします。レビューする側は、次のような問いを使います。

- この構成で、最初に壊れるのは、どこですか。そのとき、利用者には、何が見えますか
- 発売の開始の1分前に、何台が動いていますか。それは、誰が、いつ増やしますか
- 2人が、同時に、同じ座席を選んだら、何が起きますか。決済の途中で、利用者が画面を閉じたら
- データベースが切り替わる間、コールセンターの担当者は、何をしますか
- 夜中の3時に、バッチが失敗しました。誰が、どうやって気づき、朝5時までに、何をしますか
- 委託先の作業者は、本番の会員の情報を、見られますか。見たことは、記録されますか
- 月額の中で、最も大きい項目は、何ですか。予算が2割減ったら、何を変えますか
- 切り替えの当日、何を確かめて、合格としますか。戻すと決めるのは、何時までですか
- この設計で、いちばん自信がないのは、どこですか

最後の問いには、正直に答えてください。弱点を把握していることは、設計者としての信頼につながります。

## 方向性の一例

:::q 総合 | 構成の方向性
自分の成果物を作り終えてから、開いてください。これは、唯一の正解ではなく、比べるための一例です。
:::a
質問の例：発売の開始時の件数は、実績の数字か。伸びの見込みは。「30分以内」は、深夜も同じか。コールセンターと営業所は、どのネットワークから使うか。商用のデータベースを、別の製品に変えてよいか。提携先との連携は、何本あり、どの方式か。委託先は、どこから、どう作業するか。

数字の整理の例：発売の開始時は、毎秒約400件。1件の処理を0.2秒とすると、同時に処理している数は約80。座席の確保は、特定の便に集中する。

構成の方向性：

- 入口：CloudFrontとAWS WAF。空席の照会など、数秒の古さを許せる応答は、短くキャッシュする
- 発売の開始時：開始の前に、予定に合わせて台数を増やす。受けきれない分は、順番に待ってもらう画面に並べ、後ろへ流す量を一定に保つ。座席の確保は、後ろの処理が受けられる速さで行う
- アプリ：コンテナ（ECSのFargate）を、3つのAZで。状態は、外のデータストアに持つ
- 座席の二重販売の防止：座席の確保は、データベースの中で、「まだ空いていること」を条件にした更新として、1回の操作で行う。確保した座席には期限を付け、決済が完了しなければ、自動で戻す。決済は、予約ごとの一意の番号で、二重の実行を防ぐ
- データベース：AuroraのマルチAZ構成。読み取りは、複製へ。商用の製品からの移行は、変換と試験の工数を見積もったうえで、判断を記録する。期限が厳しければ、まず同じ製品のまま移し、後で置き換える案もある
- 社内の利用：コールセンターと営業所は、社内のネットワークから、専用の接続（VPN、または専用線）で使う。管理の画面は、インターネットに公開しない
- 夜間の処理：時刻で起動するコンテナの処理にし、やり直せる作りにする。終わっていないことを、朝4時の時点で検知する
- 可用性：AZの障害は、自動で切り替わる。リージョンの障害には、別のリージョンへ、データを継続的に複製しておく。30分という目標を、リージョンの障害にも適用するかは、費用を示して、顧客と決める
- 体制：3人で回すため、サーバーの保守が要らない部品を選ぶ。通知は、利用者に影響があるものに絞り、手順を用意する
- 移行：データは、事前に写して、変更を反映し続ける。発売の開始日と、大型連休を避けて、切り替える。新旧を並べて動かす期間と、切り戻しの期限を決める

判断の記録に書くべき、主な分かれ目：データベースを置き換えるか、そのまま移すか。発売の開始時の急増を、台数で受けるか、待ってもらう仕組みで受けるか。リージョンの障害に、どこまで備えるか。

見積もりでは、平常時の月額と、発売の開始の日の増分を、分けて示します。予算の100万円（約6,700ドル）に対して、どの項目が、どれだけを占めるかを、確かめてください。
:::

## 条件を変えて、もう一度

設計の力は、条件が変わったときに試されます。成果物ができたら、次の条件のうち、1つを選び、「どこを、どう変えるか」を、30分で答えてみてください。構成を一から描き直すのではなく、影響を受ける部分と、受けない部分を、見分けることが目的です。

| 変わる条件 | 考えること |
|---|---|
| 予算が、月額50万円になった | 何を削るか。削った結果、どの要件を、どこまで下げることになるか。それを、顧客に、どう説明するか |
| 提携が広がり、利用が10倍になる | 最初に詰まる部品は、どこか。今の構成の延長で届くか、作りを変える必要があるか |
| リージョンの障害でも、5分以内に再開する | DRの戦略を、どれに変えるか。データの複製の遅れを、どう扱うか。費用は、どれだけ増えるか |
| 保守の期限が、半年後に早まった | 何を後回しにするか。作り直しをやめて、そのまま移す部分は、どこか |
| 海外からの旅行者にも、販売する | 言語、通貨、時刻の扱い。応答の速さ。個人情報の決まり。どこまでが技術で、どこからが、ほかの専門家に確かめることか |
| 運用を、すべて自社の3人で行う | 夜間の呼び出しを減らすために、何を自動にするか。3人が扱える技術に、絞れているか |

ここまで取り組めば、この本の内容を、ひととおり使ったことになります。作った成果物は、手元に残しておいてください。半年後に見直すと、自分の成長と、次に学ぶべきことが、よくわかります。
