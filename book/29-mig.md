:::goal
- 既存のシステムを、7つの移行戦略に当てはめて仕分けできる
- 棚卸しから切り替えまでの流れを計画し、切り戻しの条件を決められる
- データの転送にかかる時間を概算し、移し方を選べる
:::

新しく作るシステムより、すでにあるシステムをクラウドへ移す案件のほうが、数は多くあります。移行は、技術の問題である前に、段取りの問題です。動いている業務を止めずに、何を、どの順で、どう移し、問題があればどう戻すか。この章では、その考え方を扱います。

## 7つの移行戦略

移すと決めたシステムを、すべて同じ方法で移す必要はありません。AWSは、移行の進め方を7つの戦略（7つのR）に整理しています。

| 戦略 | 内容 | 向いている場合 |
|---|---|---|
| リタイア（Retire） | 使われていないものを、廃止する | 利用の実績がない。ほかのシステムと機能が重複している |
| リテイン（Retain） | 当面、今の場所に残す | 移行の効果が小さい。近く廃止する。規則や技術の制約で移せない |
| リホスト（Rehost） | 大きく変更せずに、そのまま移す。リフト＆シフトとも呼ぶ | 期限が迫っている。数が多い。まず移してから改善したい |
| リロケート（Relocate） | 仮想化の基盤ごと、クラウド上の同じ基盤へ移す | 既存の仮想化基盤の運用を、変えずに移したい |
| リパーチェス（Repurchase） | 別の製品、多くはSaaSに置き換える | メール、会計、顧客管理など、既製のサービスで足りる業務 |
| リプラットフォーム（Replatform） | 中核は変えずに、一部をマネージドサービスなどに置き換える | 自分で運用しているデータベースをRDSへ、のように、少ない変更で運用の手間を減らせる |
| リファクタリング（Refactor） | クラウドに適した構成へ、作り直す | 事業の中心で、頻繁な改修や大きな伸縮が必要。作り直す投資に見合う効果がある |

国内では、「まず移し（クラウドリフト）、その後に最適化する（クラウドシフト）」という段階的な進め方の意味で「リフト＆シフト」と言うことがあります。AWSの用語でのリフト＆シフト（リホスト）とは指す範囲が違うため、会話では、どちらの意味かを確かめてください。

最初に検討するのは、リタイアです。棚卸しをすると、使われていないシステムが見つかることは、珍しくありません。移さないことが、最も安く、最も早い移行です。

## 全体の流れ

AWSは、移行を3つの段階で説明しています。

| 段階 | 行うこと | 成果物 |
|---|---|---|
| 評価 | 現状の棚卸し。移行の目的と効果の整理。大まかな費用の比較 | 移行する理由と、経営の合意 |
| 準備 | 土台（{{ch:org}}のランディングゾーン、{{ch:xnet}}のネットワーク）の用意。体制と技能の準備。数システムでの試行 | 詳細な計画と、移行の型 |
| 移行と最新化 | システムを、まとまりごとに順に移す。移した後に最適化する | 移行の完了と、旧環境の廃止 |

{{fig:migflow|移行の流れ。リハーサルの結果を、計画に返す}}

### 棚卸しで調べること

- 何があるか：サーバー、OSとその版、ミドルウェア、データベース、データの量
- どう使われているか：CPUやメモリの実際の使用率、利用者の数、使われる時間帯。今の機器の大きさをそのまま写すと、多くの場合、大きすぎる
- 何とつながっているか：システム同士の通信の関係。ほかのシステムから呼ばれているか、どこを呼んでいるか。一緒に移さないと動かないものを見つける
- 制約は何か：ライセンスの条件、保守の期限、止められる時間帯、データを置ける場所

特に、つながりの把握が計画の質を決めます。文書に書かれていない連携（深夜のファイル転送、古いバッチ）は、実際の通信を記録して調べないと見つかりません。

### 移す順番

つながりの強いシステムを、同じまとまり（移行の波）にします。順番は、次の考え方で決めます。

1. 最初は、小さく、止まっても影響の少ないものから始める。手順と道具を確かめ、型を作る
2. 型ができたら、数の多い、似た構成のものをまとめて移す
3. 複雑で重要なものは、経験を積んでから移す。ただし、保守の期限など、動かせない日付があるものは、逆算して早めに着手する

## データを移す

移行で最も時間がかかり、最も慎重さが必要なのが、データです。

| 対象 | 方法 | 要点 |
|---|---|---|
| データベース | 一度すべてを写し、その後の変更を継続して反映し続ける（AWS Database Migration Service など） | 切り替えの直前まで、新旧のデータを近い状態に保てる。止める時間を短くできる |
| データベース（種類を変える場合） | 定義や、データベースの中に書かれた処理を、新しい種類に合わせて変換する | 自動で変換できない部分が残る。アプリの修正と試験の工数を見込む |
| ファイル | 専用の転送サービス（AWS DataSync など）で、差分を繰り返し写す | 件数が非常に多い場合は、量よりも件数が時間を決める |
| 回線では間に合わない大量のデータ | 記憶装置に入れて、運ぶ | 転送にかかる日数を計算して判断する |

転送にかかる時間は、あらかじめ計算します。データの量（ビット）を、使える回線の速さ（ビット毎秒）で割ります。たとえば、10TBを、実際に使える速さが100Mbpsの回線で送る場合、

- 10TB = 10 × 8 × 10の12乗ビット = 8 × 10の13乗ビット
- 8 × 10の13乗 ÷（100 × 10の6乗）= 80万秒 ≒ 9.3日

となります。回線は業務でも使っているため、移行に使えるのは、契約した速さの一部です。夜間だけ送るなら、日数はさらに延びます。

## 切り替える

切り替えは、移行の中で最も緊張する場面です。成否は、当日ではなく、事前の準備で決まります。

| 決めること | 内容 |
|---|---|
| 切り替えの形 | 一度にすべて切り替えるか。利用者や機能を分けて、段階的に切り替えるか。新旧を並行して動かし、結果を比べる期間を設けるか |
| 止める時間 | 業務を止められる時間帯と長さ。その中に、最後のデータの同期、確認、切り戻しの時間が収まるか |
| 判断の基準 | 何を確かめて、合格とするか。件数の一致、主要な操作の成功、応答時間など。あらかじめ一覧にする |
| 切り戻しの条件と期限 | 何が起きたら戻すか。何時までに判断するか。その時刻を過ぎると、戻せなくなるのはなぜか |
| 戻した場合のデータ | 新しい環境で受け付けた更新を、旧環境にどう反映するか。できないなら、切り替え後のどの時点までを「戻せる期間」とするか |
| 通信の向け先 | DNSで切り替えるなら、応答が保存される時間（TTL）を、数日前から短くしておく。切り替えの当日に短くしても、古い長い設定がすでに保存されている |

本番と同じ手順を、検証環境で、時間を測りながら通しで練習します。少なくとも1回、できれば複数回行います。練習で起きた問題と、かかった時間が、当日の計画の根拠になります。

:::warn 旧環境を消すまでが移行
切り替えが終わると、関心は次のシステムに移りがちです。しかし、旧環境の機器、回線、ライセンス、保守の契約を止めない限り、費用は二重にかかり続けます。「戻せる期間」が過ぎたら、旧環境のデータの保管と消去、契約の終了までを、計画に含めて実行します。
:::

## 移した後に、良くしていく

リホストで移した直後のシステムは、クラウドの上にあるだけで、クラウドの利点はまだ得られていません。むしろ、オンプレミスの機器の大きさを写したままだと、費用は高くなりがちです。次の順で改善します。

1. 大きさを合わせる：実際の使用率を見て、小さくする。使わない時間は止める（{{ch:cost}}）
2. 運用を載せ替える：監視、バックアップ、修正プログラムの適用を、クラウドの仕組みに置き換える
3. 部品を置き換える：自分で運用しているデータベースや、ファイルの共有、ジョブの管理を、マネージドサービスにする
4. 作りを変える：効果の大きい部分から、少しずつ作り直す。古いシステムの手前に入口を置き、機能を1つずつ新しい作りに切り替えていく進め方が、一度にすべてを作り直すより安全

「後で最適化する」は、計画と予算に入れておかないと、実行されません。移行の計画を立てるときに、移行後の改善の期間と体制まで含めておきます。

:::sum
- 移行は、システムごとに7つの戦略から選ぶ。最初に検討するのは、廃止
- 棚卸しでは、実際の使用率と、システム同士のつながりを調べる。つながりでまとまりを作り、小さなものから移す
- データの転送時間は計算で見積もる。切り替えは、判断の基準と切り戻しの期限を決め、通しで練習する
- 旧環境の廃止と、移行後の改善までを、計画と予算に含める
:::

## 章末問題

:::q 仕分け | 移行戦略を選ぶ
ある会社の棚卸しで、次の6つのシステムが見つかりました。それぞれに合う戦略を選び、理由を答えてください。

1. 3年前に利用をやめたはずの、旧版の営業支援システム。サーバーは動いている
2. 自社で構築して運用しているメールサーバー
3. 2年後に、新システムへの統合で廃止が決まっている在庫照会システム。機器の保守は3年残っている
4. 機器の保守が半年後に切れる、社内向けの業務システム30個。構成は似ている
5. 自社で運用しているPostgreSQLを使う、会員管理システム。データベースの運用の負担が大きい
6. 事業の中心である予約サイト。繁忙期にアクセスが集中し、毎週のように機能を追加している
:::a
1. リタイア。通信の記録で、本当に使われていないことを確かめたうえで、データを保管して廃止する
2. リパーチェス。メールは、SaaSで足りる代表的な業務。自分で運用を続ける理由は少ない
3. リテイン。2年後に廃止が決まっており、保守も残っている。移行の費用を回収できない
4. リホスト。期限が迫っており、数が多い。まず変更を最小限にして移し、期限に間に合わせる。移した後に、大きさの見直しなどを行う
5. リプラットフォーム。アプリはほぼそのままに、データベースをRDSやAuroraに置き換える。少ない変更で、運用の負担を減らせる
6. リファクタリングの候補。伸縮と、頻繁な変更が求められ、作り直す効果が大きい。ただし、一度にすべてを作り直すのではなく、まずリプラットフォームで移し、負荷の集中する部分や、変更の多い部分から、段階的に作り直す進め方が現実的

6のように、1つのシステムに対して、複数の戦略を時期をずらして組み合わせることもあります。
:::

:::q 計算 | 転送にかかる日数
24TBのファイルを、会社からAWSへ送ります。回線の契約は500Mbpsですが、業務への影響を避けるため、移行に使えるのは、その20%までです。

1. すべてを送るのに、何日かかりますか
2. 送るのを、夜間の8時間だけに限る場合は、何日かかりますか
3. この結果を見て、計画の上で検討することを挙げてください
:::a
1. 使える速さは 500Mbps × 20% = 100Mbps。24TB = 24 × 8 × 10の12乗 = 1.92 × 10の14乗ビット。1.92 × 10の14乗 ÷ 10の8乗 = 192万秒 ≒ 22.2日
2. 1日に送れるのは3分の1になるため、約67日
3. 検討すること：
    - 最初の転送を早く始める。全体の日程の中で、転送が最も長い作業になり得る
    - 最初にすべてを送った後は、差分だけを繰り返し送る。切り替えの当日に送る量を、小さくする
    - 送る必要のないデータ（古いもの、重複したもの）を、先に除く
    - 一時的に回線を増やす、または記憶装置に入れて運ぶ方法と比べる
    - 計算は理論上の値。ファイルの件数が多いと、さらに時間がかかる。少量で試して、実際の速さを測る

数字にしてみると、「切り替えの前の週に転送を始める」といった計画が成り立たないことが、早い段階でわかります。
:::

:::q 計画 | 4時間で切り替える
データベースを含む業務システムを、オンプレミスからAWSへ移します。業務を止められるのは、日曜の午前2時から6時までの4時間です。データベースは300GBあり、すべてを写すのに6時間かかることが、練習でわかっています。切り替えの手順と、切り戻しの判断の時刻を計画してください。
:::a
解答例：すべてを写すのに6時間かかるため、止めてから写し始めたのでは間に合いません。事前に写し、変更を継続して反映する方式にします。

事前（数日前から）：

- データベースをすべて写し、その後の変更を継続して反映する状態にする。反映の遅れを監視する
- DNSの応答が保存される時間を、短く変更しておく
- 新しい環境で、アプリの動作を確かめておく

当日：

| 時刻 | 作業 |
|---|---|
| 2:00 | 旧システムへの入口を閉じ、更新を止める。旧データベースのバックアップを取る |
| 2:15 | 残りの変更が、新しいデータベースにすべて反映されたことを確かめる。反映を止める |
| 2:30 | 件数や合計値を、新旧で比べる |
| 3:00 | 新しい環境のアプリを、新しいデータベースにつなぎ、あらかじめ決めた項目を確かめる |
| 4:00 | 切り戻しの判断。合格の基準を満たさなければ、ここで戻すと決める |
| 4:00〜 | 合格なら、DNSを新しい環境へ向ける。外からのアクセスで、動作を確かめる |
| 5:30 | 完了の報告。予備の時間 |

切り戻しの判断を4時に置くのは、戻す作業（入口を旧環境に向け直し、旧システムを再開して確かめる）に必要な時間を、6時までの中に残すためです。4時を過ぎて新しい環境で業務の更新を受け付け始めると、戻した場合に、その更新を旧環境に反映する手段が必要になります。その方法がなければ、「業務を再開した後は戻さない。問題は、新しい環境の上で直す」と、あらかじめ決めておきます。

この時刻は、練習で測った時間にもとづいて決めます。練習なしに、当日の時刻表は作れません。
:::

:::q 評価 | 「まず全部そのまま移す」という方針
ある会社が、「200台のサーバーを、まず全部そのままクラウドへ移す。最適化は、その後で考える」という方針を立てました。この方針の利点と、起きやすい問題を挙げ、問題を避けるための工夫を提案してください。
:::a
利点：

- 早い。アプリの変更が少なく、手順を型にして、多数を短期間で移せる
- 期限に間に合わせやすい。データセンターの契約や、機器の保守の終了に合わせられる
- 移した後は、実際の使用率が見えるようになり、改善の判断がしやすくなる

起きやすい問題：

- 費用が上がる。オンプレミスの機器の大きさをそのまま写すと大きすぎ、24時間動かし続ければ、従量課金の利点も出ない
- 「その後」が来ない。移行が終わると、予算と体制が解散し、最適化が行われないまま、高い費用が定着する
- 不要なものまで移す。使われていないシステムを、費用をかけて移してしまう
- 運用が二重になる。古い運用の方法（手作業の構築、サーバーに入っての変更）が、そのままクラウドに持ち込まれる

工夫：

- 移す前に、廃止できるものと、残すものを仕分ける
- 移すときに、少なくとも大きさだけは、実際の使用率に合わせる
- 最適化の期間、体制、予算を、最初の計画に含める。「移行の完了」を、切り替えではなく、費用の目標の達成で定義する
- 効果の大きい少数のシステム（データベースの運用が重いものなど）は、最初からリプラットフォームにする

そのまま移すこと自体は、正しい選択であることが多くあります。問題は、移した後の姿を決めないまま、移すことです。
:::
