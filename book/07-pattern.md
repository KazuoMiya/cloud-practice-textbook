:::goal
- Web 3層構成の図を見て、通信の流れ、公開範囲、冗長化の仕組みを説明できる
- 静的サイト配信、サーバーレス、コンテナ、イベント駆動などの定番パターンと、向いている用途を挙げられる

案件で出会う構成の多くは、数種類の定番パターンの組み合わせです。最も基本になるのが「Web 3層構成」で、これを理解すれば他のパターンも読み解けます。

## Web 3層構成

{{fig:web3|Web 3層構成の例（AWS）。①は名前解決、②はWeb通信。マルチAZで冗長化している}}

利用者はまずDNS（Route 53）でドメイン名から接続先を調べ（①）、その後のWeb通信はCDN（CloudFront）を経由してロードバランサーに届きます（②）。DNSは接続先を教えるだけで、Web通信そのものはDNSを通りません。ロードバランサーは通信を2つのAZのアプリサーバーに振り分けます。データベースはプライベートサブネットに置き、別AZのスタンバイへ同期複製しておくことで、片方のAZが止まってもスタンバイへ自動で切り替わります。ただしRDSのマルチAZ構成でも切り替えには通常60〜120秒程度かかるため、アプリ側で再接続できるようにしておく必要があります。「プレゼンテーション層・アプリケーション層・データ層」の3つに分かれるので、3層構成と呼ばれます。図中のVPC・サブネットなどネットワーク部品の役割は、{{ch:net}}で説明しています。

## その他の定番パターン

| パターン | 構成の流れ（AWSの例） | 向いている用途 | 特徴 |
|---|---|---|---|
| 静的サイト配信 | CloudFront → S3 | 企業サイト、LP、SPAの画面 | サーバーが不要で安価かつ高速 |
| サーバーレス | API Gateway → Lambda → DynamoDB | API、業務の自動化、アクセスに波があるサービス | サーバー管理が不要。通常のLambdaのオンデマンド実行では、使われていない時間の計算料金がかからない（待機容量を確保するProvisioned Concurrencyは待機時間にも課金される） |
| コンテナ | ALB → ECS（Fargate）またはEKS → RDS | マイクロサービス、継続的に改修するWebアプリ | 開発環境と本番環境の差が小さく、デプロイが速い |
| イベント駆動 | S3へのアップロード → イベント通知 → Lambda → 結果を保存 | 画像の変換、ファイル取込、通知処理 | 「何かが起きたら動く」仕組みを少ないコードで作れる |
| データ分析基盤 | 各種データ → S3（データレイク）→ Glue（加工）→ Redshift・Athena → BIツール | 売上分析、アクセスログ分析 | 大量データを安価に貯め、必要なときだけ集計できる |
| 生成AI（RAG） | 社内文書 → ベクトル検索 → 生成AI（Bedrock）→ チャット画面 | 社内問い合わせ対応、文書検索 | 社内データを根拠に回答させられる |

:::tip パターンを選ぶときの4つの問い
1. すぐに結果を返す必要があるか：その場で返すなら同期の構成、後でよいならキューを挟んだ非同期の構成
2. 負荷に波があるか：波が大きく、使われない時間があるならサーバーレス。常に一定ならサーバーやコンテナの常時稼働
3. 1回の処理はどのくらいの長さか：数秒から数分なら関数。長時間ならコンテナやサーバー
4. 状態をどこに持つか：サーバーの外（データベースやストレージ）に出せるなら、台数を自由に増減できる
:::

## 構成図を読むときの5つの観点

1. 外から中へ：利用者 → 入口 → アプリ → データの順に通信を追う
2. 公開範囲：インターネットから直接届く部品はどれか
3. 冗長化：1台、または1つのAZが止まったらどうなるか
4. データの所在：どこに保存され、どうバックアップされているか
5. 管理範囲：自分たちがOSから保守する部品（IaaS）と、事業者に任せている部品（マネージドサービス）の区別

## 例題：構成を言葉から読み解く

構成は、図ではなく文章で伝えられることもあります。次の説明を、5つの観点で読んでみます。

「利用者はCloudFront経由でアクセスする。画面のファイルはS3から、APIはALBの後ろのEC2（2つのAZに各1台、Auto Scalingで最大6台）から返す。データはRDSのマルチAZ構成に保存し、画像はS3に置く。EC2とRDSはプライベートサブネットにあり、外部への通信はNATゲートウェイ1台を通る」

| 観点 | 読み取れること |
|---|---|
| 外から中へ | 利用者 → CloudFront →（画面）S3、（API）ALB → EC2 → RDS |
| 公開範囲 | インターネットから直接届くのはCloudFrontとALB。EC2とRDSには直接届かない |
| 冗長化 | EC2は2つのAZ、RDSもマルチAZ。NATゲートウェイは1台で、置いてあるAZが止まるとEC2から外部への通信が止まる |
| データの所在 | 業務データはRDS、画像と画面のファイルはS3。バックアップの取り方は書かれていないので確認が必要 |
| 管理範囲 | OSから保守するのはEC2だけ。CloudFront、ALB、RDS、S3は事業者に任せている |

このように読むと、「NATゲートウェイが1台であること」と「バックアップの記載がないこと」が、次に質問すべき点として浮かび上がります。

:::sum
- 多くの構成は、Web 3層構成と数種類の定番パターンの組み合わせ
- DNSは接続先を教えるだけで、Web通信そのものは通らない
- マルチAZでも切り替えには時間がかかる。アプリ側の再接続とセットで設計する
- 構成図は、外から中へ、公開範囲、冗長化、データの所在、管理範囲の5つの観点で読む
:::

## 章末問題

:::q 選択 | パターンを選ぶ
次の5つの要望について、最初に検討するパターンを答えてください。

1. 会社案内のサイト。更新は月に数回で、内容は文章と画像だけ
2. モバイルアプリ向けのAPI。昼休みと夕方に利用が集中し、深夜はほとんど使われない
3. 社内規程やマニュアルをもとに、質問に答えるチャット
4. 取引先からファイルが届くたびに、内容を検査してデータベースに取り込む処理
5. 複数のチームが毎日のように改修する、常時稼働の業務Webアプリ
:::a
1. 静的サイト配信（CloudFront → S3）。サーバーが不要で、安価で速い
2. サーバーレス（API Gateway → Lambda → DynamoDB）。波が大きく、使われない時間の計算料金がかからない
3. 生成AI（RAG）。社内文書を検索し、その内容を根拠に回答させる（{{ch:dataai}}）
4. イベント駆動（S3へのアップロード → 通知 → 処理）。失敗したものを後からやり直せるよう、キューを挟む
5. コンテナ（ALB → ECS → RDS）。環境の差が小さく、デプロイが速い。チームごとに分けて改修しやすい

実際の案件では、1つのシステムの中で複数のパターンを組み合わせます。たとえば5のシステムでも、画面のファイルは1の形で配信し、帳票の作成は4の形で行う、といった具合です。
:::

:::q 発見 | 単一障害点を探す
次の構成で、そこが止まるとシステム全体が使えなくなる箇所（単一障害点）をすべて挙げ、それぞれの対策を答えてください。

「ALB（2つのAZ）→ EC2が1台（AZ-a）→ RDS（単一AZ、AZ-a）。EC2から外部への通信は、AZ-aのNATゲートウェイ1台を通る」
:::a
| 箇所 | 止まったときの影響 | 対策 |
|---|---|---|
| EC2が1台 | アプリが止まる | Auto Scalingで2つのAZに2台以上置く。ALBのヘルスチェックで異常な1台を外す |
| RDSが単一AZ | データの読み書きができなくなる。復旧はバックアップからの復元 | マルチAZ構成にする。切り替え中の再接続をアプリ側で扱う |
| NATゲートウェイが1台 | 外部のAPIを呼ぶ処理や、更新プログラムの取得が止まる | AZごとにNATゲートウェイを置く。外部への通信が業務に必須かどうかで判断する |

ALBは2つのAZにまたがっているため、単一障害点ではありません。なお、すべてをAZ-aに置いているため、AZ-aの障害で3つが同時に止まります。対策の要否は、どれだけ止まってよいかという要件と費用で決めます（{{ch:ha}}）。「単一障害点がある = 悪い設計」ではなく、「知らずに残っている」ことが問題です。
:::

:::q 説明 | DNSが止まると何が起きるか
同僚が「Web通信はすべてRoute 53を通っているので、Route 53の負荷が心配だ」と言っています。この理解のどこが違うかを説明してください。
:::a
DNSは、ドメイン名から接続先のIPアドレスを調べるための仕組みで、Web通信そのものはDNSを通りません。利用者の端末は、最初にDNSで接続先を調べ（名前解決）、その後は調べた接続先（CloudFrontやALB）と直接やり取りします。

また、調べた結果は一定の時間（TTL）、端末や途中のDNSサーバーに保存されるため、アクセスのたびにRoute 53へ問い合わせが届くわけでもありません。この保存の仕組みは、接続先を切り替えたときに「古い接続先がしばらく使われ続ける」原因にもなります（{{ch:ts}}のシナリオ9）。
:::

:::q 設計 | 切り替えの60〜120秒にアプリがすべきこと
RDSのマルチAZ構成では、障害時の切り替えに通常60〜120秒程度かかります。この間とその後に、アプリが正しく動き続けるために必要な作りを3つ挙げてください。
:::a
解答例：

1. データベースへは、IPアドレスではなくエンドポイント（DNS名）で接続する。切り替えで接続先のIPアドレスが変わるため
2. 接続が切れたら、少し待ってから接続し直す。待つ時間を少しずつ延ばしながら数回試す（リトライ）。接続をためておく仕組み（コネクションプール）を使っている場合は、切れた接続を捨てて作り直す設定にする
3. 接続や問い合わせに、適切な長さのタイムアウトを設定する。応答しない接続を待ち続けると、アプリ全体が止まったように見える

あわせて、切り替え中の利用者には「しばらくしてからもう一度お試しください」のような案内を返すなど、エラーの見せ方も決めておきます。切り替えを実際に起こして試す方法は、{{ch:s4}}で扱います。
:::
