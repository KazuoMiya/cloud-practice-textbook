:::goal
- ステップ2〜4の構成をコードで定義し、削除した状態からコマンド1つで作り直せる
- 適用の前に、何が作られ、何が変更・削除されるかを差分で確認できる
- 手動の変更とコードのずれ（ドリフト）を検出し、解消する手順を説明できる
:::

ステップ2〜4の構成をコードで定義し、何度でも同じ環境を作り直せるようにします。ここまでのステップで、同じ構成を何度か手で作り直してきたはずです。その手間と、「前回と同じに作れたか自信がない」という不安を、コードで解消します。



端末から操作する前に、{{ch:s1}}の「手元の端末は一時的な認証情報で操作する」を実施します。`aws sts get-caller-identity --profile cloudbook-lab` で対象を確認し、IaCにも同じ学習用プロファイルを指定してください。アクセスキーをIaCファイルやステートへ書き込みません。

## ツールを選ぶ

| ツール | 特徴 | 向いている場面 |
|---|---|---|
| AWS CloudFormation | AWS公式。YAMLかJSONで書き、追加のツールが要らない | AWSだけを使う案件、IaCの仕組みの理解 |
| AWS CDK | TypeScriptやPythonで書き、CloudFormationに変換して実行する | プログラミングに慣れた開発チーム |
| Terraform | AWS以外のクラウドやサービスも同じ書き方で扱える | 複数のクラウドを使う案件、すでに採用している案件 |

案件で使われているツールを優先して学ぶのが効率的です。決まっていなければ、まずCloudFormationで仕組みを理解し、その後に案件に合わせてCDKかTerraformへ進むことを勧めます。

どのツールでも、考え方は共通しています。

| 考え方 | CloudFormation | Terraform |
|---|---|---|
| あるべき構成を書いたファイル | テンプレート | 設定ファイル（.tf） |
| 1回の適用でまとめて管理される単位 | スタック | ステート（state）で管理される範囲 |
| 適用前の差分の確認 | 変更セット | terraform plan |
| 適用 | スタックの作成・更新 | terraform apply |
| 実際の構成とのずれの検出 | ドリフト検出 | terraform plan で差分として表示される |

「手順」ではなく「あるべき状態」を書く、という点が要です。ツールは、今の状態とあるべき状態を比べ、差を埋めるために必要な操作を自分で決めます。CloudFormationの最小の例を示します。

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Parameters:
  Env:
    Type: String
    Default: dev
Resources:
  Vpc:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: 10.0.0.0/16
      EnableDnsHostnames: true
      Tags:
        - Key: Name
          Value: !Sub '${Env}-vpc'
  PublicSubnetA:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref Vpc
      CidrBlock: 10.0.0.0/24
      AvailabilityZone: !Select [0, !GetAZs '']
Outputs:
  VpcId:
    Value: !Ref Vpc
```

`!Ref Vpc` のように、ほかの資源を名前で参照している点に注目してください。ツールはこの参照から、作る順番（VPCが先、サブネットが後）を自動で決めます。環境ごとに変わる値は Parameters で受け取り、同じテンプレートから開発用と本番用を作れるようにします。

## 進め方

1. ステップ2のVPCをコードで書き、「作成 → 削除 → 作成」を繰り返す
2. ステップ3・4の部品を、少しずつコードに追加する
3. 適用する前に、何が変わるかの差分を確認する習慣をつける（CloudFormationの変更セット、cdk diff、terraform plan）
4. コードをGitで管理し、変更のたびにコミットする
5. 管理画面で手動の変更を加え、コードとの差（ドリフト）を検出してみる

## つまずきやすい点

| 症状 | よくある原因 | 対処 |
|---|---|---|
| 初回の作成に失敗し、スタックが ROLLBACK_COMPLETE のまま更新できない | 最初の作成に失敗したスタックは、更新できない | イベントの一覧で、最初に失敗した資源とその理由を読む。スタックを削除し、テンプレートを直して作り直す |
| スタックの削除に失敗する | 中身が残っているS3バケットなど、ツールが消せない資源がある | 失敗した資源を確認し、中身を空にしてから、もう一度削除する |
| 小さな変更のつもりが、資源が作り直された | 変更した項目が、作り直し（置き換え）を伴う種類だった | 適用の前に、差分に「置き換え」と表示されていないかを必ず確認する |
| 管理画面で直した設定が、次の適用で元に戻った | コードに書かれた状態が「正」として適用された | 手で直した内容は、コードにも反映する |
| （Terraform）ほかの人と同時に適用して、状態が壊れた | 状態を記録するファイル（ステート）を、各自の手元に置いていた | ステートは共有の保存場所に置き、同時に適用できないようにロックする |

## 設計の問い

コードで書けるようになると、次は「どう分けるか」が問いになります。

- 何を1つの単位にまとめるか：ネットワーク、データベース、アプリのように、変更の頻度と影響の範囲が違うものは分ける。毎日変わるアプリの設定と、めったに変えないVPCを同じ単位にすると、アプリの変更のたびにネットワークまで差分の確認が必要になる
- 環境の違いをどう表すか：開発・検証・本番で同じコードを使い、違いはパラメータで渡す。環境ごとにコードを複製すると、やがて内容がずれていく
- 消えては困るものをどう守るか：データベースやバケットには、スタックを削除しても残す設定（CloudFormationの DeletionPolicy）や、削除保護を付ける
- 秘密情報をどう扱うか：パスワードはコードにもパラメータにも書かず、Secrets Manager に生成・管理させて参照する

## 確認ポイント

- すべて削除した状態から、コマンド1つで同じ環境を作り直せる
- 適用前に、何が作られ、何が変更・削除されるかを確認できる
- パスワードなどの秘密情報をコードに書いていない

## わざと壊してみる

:::lab
テンプレートで作ったセキュリティグループに、管理画面から受信ルールを1つ手で追加します。ドリフト検出（Terraformなら plan）を実行し、どのように表示されるかを確認してください。次に、コードを変えずにもう一度適用したとき、手で追加したルールがどうなるかを確かめます。ツールや資源の種類によって、元に戻る場合と残る場合があります。その違いを記録しておくと、案件で「手動の変更がいつの間にか消えた（消えなかった）」ときの理解に役立ちます。
:::

## 片付け

IaCで作ったものは、必ずIaCのコマンドで削除します（スタックの削除、terraform destroy）。管理画面から個別に消すと、ツールの記録と実際の構成がずれ、次の操作が失敗します。削除の後、残す設定にした資源や、削除に失敗した資源が残っていないかを確認してください。

## 本番ではどう変わるか

| 項目 | 学習での進め方 | 本番で加わること |
|---|---|---|
| 適用する人 | 自分の端末から自分で適用する | CI/CDから適用する。人の端末には、本番を変更できる権限を持たせない |
| レビュー | なし | コードの変更と、適用前の差分の両方を、ほかの人が確認してから適用する |
| 手動の変更 | 自由 | 原則として禁止。障害対応でやむを得ず行った場合は、後で必ずコードに反映する |
| ずれの検出 | 気づいたときに | 定期的に検出を実行し、ずれが見つかったら通知する |
| 既存の資源 | すべて新しく作る | 手で作られた既存の資源を、コードの管理下に取り込む作業（インポート）が発生する |

:::sum
- IaCは「手順」ではなく「あるべき状態」を書く。ツールが差分から必要な操作を決める
- 適用の前に必ず差分を確認する。特に「置き換え」と「削除」を見落とさない
- 変更の入口をコードに一本化する。手動の変更は、ずれと事故のもとになる
- 変更の頻度と影響の範囲で単位を分け、環境の違いはパラメータで表す
:::

## 章末問題

:::q 読み取り | 差分に「置き換え」が出た
本番のデータベース（RDS）の設定を1か所変更するため、テンプレートを直して変更セットを作りました。差分を見ると、RDSの資源に「置き換え：True」と表示されています。このまま適用すると何が起きますか。どうすべきですか。
:::a
「置き換え」は、今の資源を変更するのではなく、新しい資源を作り、古い資源を削除することを意味します。データベースの場合、新しい空のデータベースが作られ、データの入った古いデータベースが削除されます。削除時に残す設定をしていなければ、データを失います。

すべきこと：

1. 適用しない
2. どの項目の変更が置き換えを引き起こしているかを、公式ドキュメントの各項目の説明（更新時の動作）で確認する。データベースの識別子、暗号化の有無、サブネットグループなどが該当しやすい
3. その変更が本当に必要かを見直す。必要なら、スナップショットからの復元や、データの移行を含む手順を別に計画する

変更セットや plan は、この種の事故を防ぐための仕組みです。差分は「何行変わったか」ではなく、「追加・変更・置き換え・削除のどれか」を資源ごとに読みます。あわせて、データベースには削除保護と、削除時にスナップショットを残す設定を付けておきます。
:::

:::q 対応 | 障害対応で手動変更をした後
深夜の障害対応で、通信を通すために、管理画面からセキュリティグループのルールを1つ追加して復旧させました。この環境はIaCで管理されています。翌朝、何をすべきですか。
:::a
1. 手動で行った変更を記録する：いつ、誰が、何を、なぜ変えたか。障害報告書にも書く
2. その変更が恒久的に必要かを判断する：一時的な回避策だったのか、もともとコードに欠けていた設定だったのか
3. 必要な変更であれば、コードに反映する：コードを直し、レビューを受け、差分を確認する。このとき、差分が「変更なし」になれば、コードと実際の構成が一致したことになる
4. 不要な変更であれば、元に戻す：これもコードの適用を通じて行うのが望ましい

放置すると、次に誰かがコードを適用したときに、手動で追加したルールが消えて同じ障害が再発する、あるいは残り続けて「誰も理由を知らないルール」になります。緊急時の手動変更そのものは、やむを得ない場合があります。問題は、変更したことではなく、コードに戻さないことです。
:::

:::q 設計 | 1つの巨大なテンプレート
ある案件では、VPC、データベース、アプリのサーバー、監視の設定まで、すべてが1つのテンプレートに書かれています。アプリの設定を毎日変更するたびに、全体の差分を確認して適用しています。どのような問題が起きやすいですか。どう分けますか。
:::a
起きやすい問題：

- 影響の範囲が広い：アプリの小さな変更の適用で、誤ってネットワークやデータベースまで変更する危険がある
- 差分が読みにくい：毎回、関係のない資源まで確認の対象になり、重要な差分を見落としやすい
- 権限を分けられない：アプリの担当者にも、ネットワークやデータベースを変更できる権限が必要になる
- 適用に時間がかかり、失敗したときの巻き戻しも大きくなる

分け方の例：

| 単位 | 中身 | 変更の頻度 |
|---|---|---|
| ネットワーク | VPC、サブネット、ルートテーブル、ゲートウェイ | まれ |
| データ | データベース、バケット | まれ。削除からの保護を付ける |
| アプリ | サーバーやコンテナ、ロードバランサー、アプリ用の権限 | 頻繁 |
| 監視 | アラーム、ダッシュボード | ときどき |

単位の間では、VPCのIDのような値を出力として公開し、ほかの単位から参照します。分ける基準は「一緒に変更されるものは一緒に、別々に変更されるものは別々に」です。
:::

:::q 防止 | スタックを消したらデータベースも消えた
検証環境の整理のつもりでスタックを削除したところ、それは本番のスタックで、データベースも一緒に削除されてしまいました。同じ事故を防ぐ設定や仕組みを、3つ以上挙げてください。
:::a
解答例：

1. 削除時の動作を指定する：データベースの資源に、スタックの削除時にスナップショットを残す、または資源そのものを残す設定（DeletionPolicy）を付ける
2. データベースの削除保護を有効にする：有効な間は、データベースを削除する操作そのものが失敗する
3. スタックの削除保護（終了保護）を有効にする：本番のスタックは、保護を外さない限り削除できない
4. 権限で防ぐ：本番のスタックを削除できる権限を、日常の作業用の権限から外す
5. 環境を取り違えにくくする：本番と検証でAWSアカウントを分ける（{{ch:org}}）。スタックの名前に環境名を入れる
6. バックアップを別に持つ：自動バックアップは、データベースの削除と一緒に消える設定になっていることがある。AWS Backup などで、別に管理されたバックアップを持つ

1つの対策に頼らず、何重にも防ぐのが基本です。特に5の「アカウントを分ける」は、取り違えそのものを起こりにくくする、最も効果の大きい対策です。
:::
