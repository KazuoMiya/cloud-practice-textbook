:::goal
- データベースを外部への経路のないサブネットに置き、アプリサーバーからだけ接続できるようにする
- パスワードをコードに書かずに、アプリからデータベースへ接続する仕組みを説明できる
- バックアップから復元し、かかった時間を自分の数字として持つ
:::

データベースをプライベートな場所に置き、アプリサーバーからだけ接続できるようにします。データベースは、システムの中で最も「作り直しがきかない」部品です。サーバーは捨てて作り直せますが、データは失うと戻りません。このステップでは、置き場所と守り方に加えて、戻し方までを自分の手で確かめます。



{{fig:dbsecret|接続情報の流れ。パスワードは、Secrets Manager の中にだけある}}

## 進め方

1. DB用サブネット2つで、DBサブネットグループを作る
2. RDS for PostgreSQL（またはMySQL）を、小さいインスタンスで作る。「パブリックアクセス」はなしにする
3. 管理者パスワードは、作成画面でSecrets Managerに管理させる設定を選ぶ
4. DBのセキュリティグループで、アプリサーバーのセキュリティグループからの5432番（MySQLなら3306番）だけを許可する
5. Session Managerでアプリサーバーに入り、DBクライアントで接続してテーブルを作る。続けて、Webページからデータを登録・一覧表示できる簡単な画面（例：メモの登録と一覧）を作り、「ブラウザ → ALB → EC2 → RDS」の経路がつながることを確かめる。アプリは接続情報をSecrets Managerから取得する（EC2のIAMロールに読み取りの権限を付ける）
6. スナップショットを取り、そこから別のDBとして復元してみる（確認が終わったら、復元したDBは削除する）

学習では単一AZで十分です。マルチAZ構成は、料金がほぼ倍になるため、切り替えの仕組みを確かめるときに短時間だけ試してください。

接続の確認には、次のようなコマンドを使います。エンドポイントは、RDSの管理画面に表示されるDNS名です。

```bash
# Secrets Manager から接続情報を取り出す（アプリも同じAPIを呼ぶ）
aws secretsmanager get-secret-value --secret-id <シークレットのARN> \
  --query SecretString --output text

# アプリサーバーの中から接続する
psql -h <RDSのエンドポイント> -U postgres -d postgres
```

## つまずきやすい点

接続に失敗したときは、エラーの種類で、どこまで届いているかがわかります。

| エラーの出方 | 意味 | 疑うところ |
|---|---|---|
| しばらく待たされた後、タイムアウトする | 通信が相手に届いていないか、返事が戻ってきていない | セキュリティグループ、ネットワークACL、ルートテーブル、接続先の指定 |
| すぐに「接続を拒否された（Connection refused）」と出る | 相手には届いたが、そのポートで待ち受けているものがない | ポート番号の誤り、データベースが起動していない |
| 「パスワード認証に失敗した」と出る | データベースまで届いている。ネットワークは正常 | ユーザー名、パスワード、データベース名 |
| 「名前を解決できない」と出る | エンドポイントのDNS名からIPアドレスを調べられない | エンドポイントの書き間違い、VPCのDNSの設定 |

このほか、DBサブネットグループを作るときに「2つ以上のAZのサブネットが必要」というエラーが出ることがあります。単一AZで動かす場合でも、サブネットグループには複数のAZのサブネットを入れておく決まりです。

## 確認ポイント

- DBへの接続に、IPアドレスではなくエンドポイント（DNS名）を使う理由（切り替え時にIPアドレスが変わる）を説明できる
- パスワードをコードや設定ファイルに書かずに済む仕組みを説明できる
- バックアップ（自動バックアップとスナップショット）からの復元にどのくらい時間がかかったかを記録している

## 実技の合格基準

次のすべてを、コマンドの出力や画面で示せたら合格です。

| 番号 | 確かめること | 合格の状態 |
|---|---|---|
| 1 | データベースが公開されておらず、暗号化されている | PubliclyAccessible が False、StorageEncrypted が True |
| 2 | パスワードを、Secrets Manager が管理している | SecretStatus が active。コード、設定ファイル、コマンドの履歴に、パスワードが残っていない |
| 3 | データベースが受け付けるのは、アプリサーバーからの通信だけである | 受信ルールが5432番（MySQLなら3306番）だけで、送信元がアプリサーバーのセキュリティグループのID。IPアドレスの範囲での許可がない |
| 4 | アプリサーバーから接続し、データを読み書きできる | Session Manager で入ったサーバーから接続し、作ったテーブルに1行を登録して読める |
| 5 | ブラウザからデータベースまでがつながっている | ALBのURLの画面でメモを登録でき、一覧に表示される。別のサーバーに振り分けられても、同じ一覧が表示される |
| 6 | バックアップから戻せる | スナップショットから別のデータベースとして復元し、4で登録した行を読める。復元にかかった時間（分）を記録している |
| 7 | 片付けが済んでいる | データベース（復元したものを含む）と、手動のスナップショットが残っていない |

```bash
DB_ID='自分のDBインスタンスの識別子'
DB_SG='データベースのセキュリティグループのID'

# 1、2
aws rds describe-db-instances --db-instance-identifier "$DB_ID" \
  --query 'DBInstances[].[PubliclyAccessible,StorageEncrypted,MasterUserSecret.SecretStatus]' --output table
# 3
aws ec2 describe-security-groups --group-ids "$DB_SG" \
  --query 'SecurityGroups[].IpPermissions[].[FromPort,ToPort,UserIdGroupPairs[].GroupId,IpRanges[].CidrIp]'
# 6
aws rds describe-db-snapshots --db-instance-identifier "$DB_ID" \
  --query 'DBSnapshots[].[DBSnapshotIdentifier,Status,SnapshotCreateTime]' --output table
# 7（片付けの後）
aws rds describe-db-instances --query 'DBInstances[].[DBInstanceIdentifier,DBInstanceStatus]' --output table
aws rds describe-db-snapshots --snapshot-type manual --query 'DBSnapshots[].DBSnapshotIdentifier'
```

提出するもの：1〜3、6、7の出力、4と5の画面、復元にかかった時間。

## わざと壊してみる

:::lab
DBクライアントの接続をいったん切断し、DBのセキュリティグループからアプリの許可を外してから、新しく接続を試します。接続がタイムアウトする様子とエラーメッセージを記録してください。接続したままでは、既存の接続が切れずに使い続けられることがあります（セキュリティグループの接続追跡）。「つながらないときの確認順」（{{ch:net}}）に沿って原因を特定する練習になります。
:::

余裕があれば、マルチAZ構成に変更し、切り替えを自分で起こしてみてください。RDSの再起動で「フェイルオーバーを伴う再起動」を選ぶと、スタンバイへの切り替えが起きます。アプリから1秒ごとに問い合わせを続けながら実行し、何秒間エラーになったか、エンドポイントのDNS名が指すIPアドレスがどう変わったかを記録します。{{ch:pattern}}で学んだ「切り替えには時間がかかり、アプリの再接続が必要」を、自分の数字で確かめられます。確認が終わったら、単一AZに戻すか削除します。

## 片付け

削除時に最終スナップショットを残すかどうかを選べます。RDSは停止しても7日後に自動で起動するため、使わないなら削除してください。復元の練習で作ったDBと、不要になったスナップショットも削除します。

## 本番ではどう変わるか

| 項目 | 学習での構成 | 本番で決めること |
|---|---|---|
| 可用性 | 単一AZ | マルチAZ構成。切り替えにかかる時間と、アプリの再接続を合わせて設計する |
| バックアップ | 既定のまま | 自動バックアップを何日分残すか。任意の時点に戻せる機能（ポイントインタイムリカバリ）で、どこまでさかのぼれるか |
| 暗号化 | 意識しない | 保存データの暗号化を、作成時に有効にする。作成後に暗号化へ切り替えるには、スナップショットを暗号化してコピーし、そこから作り直す必要がある |
| 誤操作への備え | なし | 削除保護を有効にする。削除時には最終スナップショットを必ず残す |
| 保守 | 意識しない | 修正プログラムを適用する時間帯（メンテナンスウィンドウ）と、バージョンを上げる方針を決める |
| 接続の数 | 1台から数本 | アプリの台数が増えると接続の数も増える。上限を超えないよう、接続をまとめる仕組み（コネクションプール、RDS Proxy）を使う（{{ch:ts}}のシナリオ5） |
| 監視 | なし | CPU使用率、接続数、空き容量、空きメモリを見張る（{{ch:s5}}） |

:::sum
- データベースは、外部への経路のないサブネットに置き、アプリサーバーのセキュリティグループからの通信だけを許可する
- 接続にはエンドポイント（DNS名）を使う。切り替えのときにIPアドレスが変わるため
- パスワードは Secrets Manager に置き、アプリは実行時に取り出す
- バックアップは、取るだけでなく、戻してみて初めて備えになる。復元は新しいDBとして作られる
:::

## 章末問題

:::q 切り分け | エラーの出方から原因を絞る
アプリサーバーからデータベースへの接続で、次の3つのエラーが、それぞれ別の日に出ました。それぞれ、最初に確認するものを答えてください。

1. 30秒ほど待たされた後に、タイムアウトする
2. すぐに「Connection refused」と表示される
3. すぐに「password authentication failed」と表示される
:::a
1. ネットワークの許可と経路。データベースのセキュリティグループに、アプリサーバーのセキュリティグループからの該当ポートの許可があるか。接続先のエンドポイントが正しいか。待たされた後に失敗するのは、通信が黙って捨てられているときの出方
2. ポート番号と、データベースの状態。接続先のポートが正しいか（PostgreSQLなら5432）。データベースが起動中、変更中、停止中でないか。すぐに拒否されるのは、相手には届いているが、そのポートで待ち受けるものがないときの出方
3. 認証情報。ユーザー名とパスワード、接続先のデータベース名。Secrets Manager の値が、最近変更（ローテーション）されていないか。ここまで来ていれば、ネットワークは正常

エラーメッセージを「つながらない」とひとまとめにせず、出方の違いを記録する習慣が、切り分けを速くします。
:::

:::q 設計 | 復元にかかる時間を見積もる
スナップショットからの復元を練習したところ、復元の操作を始めてから新しいDBが使えるようになるまで25分かかりました。「障害から1時間以内に復旧する」という目標を立てる場合、25分のほかに、どのような時間を見込む必要がありますか。
:::a
解答例：

- 気づくまでの時間：障害が起きてから、監視の通知が届き、担当者が状況を確認するまで
- 判断の時間：復元すると決めるまで。どの時点に戻すかの判断と、関係者への確認を含む
- 接続先を切り替える時間：復元すると、新しいDBが別のエンドポイントで作られる。アプリの接続先を新しいものに変える（または、新しいDBの名前を付け替える）作業が必要
- 確認の時間：データが正しく戻っているか、アプリが動くかを確かめる
- 失われた分の扱い：戻した時点から後に行われた操作を、どう補うか

25分は、あくまで「復元の操作そのもの」の時間です。データの量が増えれば、この時間も延びます。目標を立てるなら、気づいてから業務を再開するまでの一連の流れを、手順書に沿って通しで練習し、その時間を測ります。
:::

:::q 選択 | 3日前の状態に戻したい
自動バックアップを7日分残す設定にしています。今日の午前10時に、3日前の午後3時に行われたデータの誤った更新に気づきました。3日前の午後2時55分の状態を取り出すには、どの機能を使いますか。また、取り出したデータで、今の本番のDBはどうなりますか。
:::a
ポイントインタイムリカバリ（任意の時点への復元）を使います。自動バックアップと変更の記録をもとに、保持している期間の中の任意の時点の状態を復元できます。

復元されたデータは、今の本番のDBを上書きするのではなく、別の新しいDBとして作られます。今の本番のDBは、そのまま動き続けます。そのため、次のどちらにするかを決める必要があります。

- 誤った更新の影響が一部のデータに限られる場合：復元したDBから必要なデータだけを取り出し、今の本番のDBを修正する。3日間に行われた正しい更新は残せる
- 影響が広く、切り分けられない場合：復元したDBに切り替える。その後の3日間の更新は失われるため、別の手段で補う

多くの場合、前者が選ばれます。「戻す」とは、DBを丸ごと過去に戻すことだけではありません。
:::

:::q 原因 | パスワードを更新したらアプリが止まった
Secrets Manager で、データベースのパスワードの自動更新（ローテーション）を有効にしました。更新が行われた直後から、アプリがデータベースに接続できなくなりました。考えられる原因と、対策を答えてください。
:::a
よくある原因は、アプリが起動時に一度だけパスワードを取得し、その値を使い続けていることです。パスワードが更新されると、新しく接続を作ろうとしたときに、古いパスワードで認証に失敗します。すでに確立している接続は使い続けられるため、更新の直後ではなく、接続を作り直したタイミングで突然失敗し始めることもあります。

対策：

- 認証に失敗したら、Secrets Manager から最新の値を取り直して、もう一度接続する作りにする
- 取得した値を長時間保持しない。一定の時間で取り直す
- 更新の方式として、2つのユーザーを交互に切り替える方式を選び、切り替えの間も古い側が使えるようにする

秘密情報を「コードに書かない」だけでなく、「途中で変わっても動き続ける」ところまでが、設計の範囲です。検証環境で実際に更新を起こし、アプリが動き続けるかを確かめてから、本番で有効にします。
:::
