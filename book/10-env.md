:::goal
- 「作る・壊す・説明する」を1セットにした学び方を、自分の週の予定に組み込める
- 学習用のAWSアカウントを、登録方式とプランの違いを理解したうえで安全に用意できる
- 最初の30分で行う安全対策と、毎回の片付けを、理由とともに説明できる
:::

第1部で全体像と用語を押さえたら、第2部ではAWSを題材に、自分の手で作り、壊し、説明します。この章では、その進め方と、安心して失敗できる環境の用意を扱います。第2部を終えると、小規模なWebシステムを要件から考えて構築し、コードで再現し、監視と後片付けまで一通り行える状態になります。

第2部は、画面のクリック手順を1つずつ書いた手順書ではありません。各ステップで「何を作り、何を確認し、何を説明できればよいか」を示します。具体的な操作は、AWSが無償で公開している動画ハンズオン「AWS Hands-on for Beginners」や公式チュートリアルを併用してください。管理画面は頻繁に変わるため、手順は公式の最新版に従うのが確実です。

基礎力は、読んだ量ではなく「作って、壊して、説明した回数」で身につきます。各ステップは、次の5つの原則に沿って進めてください。

:::tip 第2部の前に
第2部では、Linuxのコマンド操作と、Gitでのコードの管理を前提にします。慣れていない場合は、先に{{ch:basics}}を通してください。AWSのアカウントがなくても、無料で練習できます。
:::

## 5つの原則

1. 作る前に構成図を描く：何を作り、通信がどう流れるかを、紙やdraw.ioで先に描く。描けないところが、まだ理解できていないところ
2. 一次情報で確かめる：AWS公式ドキュメント（各サービスのユーザーガイド）を正とし、ブログや記事は補助にする。公開日の古い記事は、画面や仕様が今と違うことがある
3. わざと壊す：セキュリティグループを閉じる、サーバーを止めるなど、意図的に失敗させ、エラーの出方と直し方を確かめる
4. 毎回片付ける：作ったものはその日のうちに削除し、請求画面で費用を確認する
5. 人に説明する：週に1回、作ったものを構成図と一緒に5分で説明する。説明に詰まった部分が、次の学習テーマ

## 1週間の進め方の例

| タイミング | やること | 時間の目安 |
|---|---|---|
| 週の初め | 公式ドキュメントやハンズオン動画で、そのステップの仕組みを読む | 1時間 |
| 週の中盤（3日） | 手を動かして構築し、わざと壊して直す | 各1時間 |
| 週の終わり | 片付け、学習ログの整理、構成図の清書 | 1時間 |
| 翌週の初め | チーム内で5分の説明と質疑 | 30分 |

## 学習ログの付け方

ステップごとに、次の項目を記録してください。特にエラーと解決方法の記録は、案件に入ってから最も役に立つ資産になります。

- 日付と取り組んだステップ
- 作ったもの（構成図のリンクか画像）
- うまくいかなかったこと、その原因と解決方法
- 参照した公式ドキュメントのURL
- 次に確かめたいこと
- かかった費用（反映に時間がかかるため、翌日以降に請求画面で確認した金額）

記録の例を示します。体裁は自由ですが、エラーメッセージは要約せず、そのまま貼り付けておくと後で検索できます。

```text
2026-11-12  ステップ3（ALBとAuto Scaling）2日目
作ったもの  ALB、ターゲットグループ、Auto Scalingグループ（最小2台）
詰まった点  ターゲットが unhealthy のまま。理由は Health checks failed
原因        アプリ用セキュリティグループの送信元を、ALBのIPアドレスの範囲で指定していた。
            ALBのIPアドレスは変わるため、ALBのセキュリティグループを指定するのが正しい
解決        受信ルールの送信元をALB用のセキュリティグループに変更。約30秒で healthy に
参照        ターゲットグループのヘルスチェック（Elastic Load Balancing ユーザーガイド）
次に試す    ヘルスチェックのパスを存在しないものに変えると、どう表示されるか
費用        翌日確認。0.41ドル（ALBとNATゲートウェイで大半）
```

:::warn ハンズオンを始める前に
学習で最も避けたいのは、想定外の請求とアカウントの乗っ取りです。この章の残りの設定を、最初のステップに進む前に必ず済ませてください。
:::

## どのアカウントで学ぶか

第一候補は、会社が用意する検証用（サンドボックス）アカウントです。権限や予算の上限が組織として管理されているため、最も安全です。用意されている場合はそちらを使い、社内のルールに従ってください。

個人で新しくAWSアカウントを作る場合は、「登録方式」と「プラン」の2つを選びます。

### 登録方式：この本は従来方式（advanced）が前提

2026年秋から、AWSの登録方式は2つになりました（[登録方式の比較](https://docs.aws.amazon.com/accounts/latest/reference/sign-up-for-aws.html)）。

| 項目 | 新方式（Sign up for AWS） | 従来方式（Sign up for AWS (advanced)） |
|---|---|---|
| ログイン | AWS Builder IDでログインする。ルートユーザーは作られず、IAMユーザーは管理画面へのログインに使えない | ルートユーザー（登録したメールアドレス）と、自分で作るIAMユーザーやロール |
| 管理の単位 | プロジェクト（AWSが初期設定を済ませたアカウント） | AWSアカウント |
| リージョン | 連絡先の住所で自動的に決まる。日本の住所ならシドニー（ap-southeast-2）で、変更できない（[プロジェクトのリージョン](https://docs.aws.amazon.com/accounts/latest/reference/project-regions.html)） | 自由に選べる（東京も選べる） |
| 使えるサービス | 一部に限られる | すべて |
| 支出上限 | 有料プランで設定できる | 設定できない（予算アラートなどで管理する） |

第2部は、東京リージョンでVPCなどを一から作るため、従来方式で作ったアカウントを前提にしています。新方式で作ったアカウントでは、ルートユーザーやリージョンの設定を含め、本文どおりには進められません。

新方式のアカウントでも「高度な機能」を有効にすればリージョンを選べるようになりますが、有料プランへの移行が必要です。また、設定していた支出上限は解除され、元の状態には戻せません（[高度な機能の有効化](https://docs.aws.amazon.com/accounts/latest/reference/activate-advanced-features.html)）。「支出上限を設定したから、その後も安心」とはならない点に注意してください。

### プラン：無料プランと有料プラン

登録方式とは別に、2025年7月15日以降に作るアカウントは、作成時に「無料プラン」か「有料プラン」を選ぶ仕組みです（[AWS Free Tier FAQ](https://aws.amazon.com/free/free-tier-faqs/)）。

| 項目 | 無料プラン | 有料プラン |
|---|---|---|
| もらえるクレジット | 作成時に100ドル、所定の操作で最大100ドル追加 | 同じ |
| 使えるサービス | 一部（クレジットを一度に使い切るようなサービスなどは対象外） | すべて |
| クレジットを使い切ったとき | 課金されず、アカウントが停止される | 通常の従量課金に切り替わる |
| 期間 | 最長6か月。終了後90日以内に有料プランへ移行しないと、アカウントとデータが削除される | 期限なし |
| プランの変更 | いつでも有料プランへ移行できる | 無料プランには戻れない |

第2部の学習期間（目安12週間）は、無料プランの6か月に収まります。個人のアカウントで学ぶ場合は、無料プランで始めるのが安全です。次の点に注意してください。

- AWS Organizations への参加や AWS Control Tower の設定を行うと、有料プランに切り替わり、元に戻せません（[AWS Builder Center](https://builder.aws.com/content/3Kkt4kNiDSUnO3n6db2weSNubzE/the-dollar0-aws-account-in-2026-free-plan-credits-guardrails)）。学習用アカウントでは使わないでください
- クレジットの有効期限は、公式FAQの中でも6か月と12か月の記載が混在しています。請求画面で自分のアカウントの期限を確認してください
- 月額の支出上限（20ドルから）は、新方式の有料プランでだけ使える機能で、従来方式のアカウントでは使えません。従来方式では、次の節の予算アラートとコスト異常検出、そして毎回の片付けで費用を管理します

## 最初の30分で必ずやること（従来方式のアカウント）

1. ルートユーザー（登録したメールアドレスでログインする、すべての権限を持つユーザー）に多要素認証（MFA）を設定し、以後は日常の作業に使わない
2. 日常作業用のユーザー（この本では、作業用ユーザーと呼ぶ）を作り、MFAを設定する。アクセスキーは発行しない。手元の端末から操作する方法は{{ch:s1}}で扱う。会社の環境では、IAM Identity Center によるシングルサインオンで入るのが一般的
3. AWS Budgets で予算アラートを2つ作る。1つは月額の予算（例：5ドル）、もう1つは少額でも課金が出たら通知する予算。既定ではクレジットがマイナスの費用として計算され、クレジットの消費に気づけないため、クレジットを含めない設定にする
4. 請求や無料枠に関する通知の宛先を、普段見るメールアドレスにする
5. コスト異常検出（Cost Anomaly Detection）を有効にする。利用料金はかからない
6. 使うリージョンを東京（ap-northeast-1）に決め、作業のたびに画面右上のリージョン表示を確認する

予算アラートの元になる費用データの更新は1日に数回のため、通知は数時間遅れることがあります。通知だけに頼らず、片付けの習慣とセットで使ってください。

## 費用がかかりやすいもの

| もの | 注意点 | 対策 |
|---|---|---|
| NATゲートウェイ | 起動しているだけで時間料金がかかる。東京で1台1時間あたり約0.062ドル（30日で約45ドル）に、通過したデータ量の料金が加わる | 使う日だけ作り、終わったら削除する |
| パブリックIPv4アドレス | 使用中か未使用かにかかわらず、1時間あたり0.005ドル | 使っていないElastic IPを解放する |
| ロードバランサー | 起動している時間に料金がかかる | 使う日だけ作る |
| EC2 | 停止中もディスク（EBS）の料金はかかる | 使い終わったら「停止」ではなく「終了」する |
| RDS | 停止しても7日後に自動で起動する | 使い終わったら削除する |
| CloudWatch Logs | ログの保存期間が既定で無期限 | ロググループに保存期間を設定する |

NATゲートウェイの料金は[ISSOHの解説](https://issoh.co.jp/?p=3105)（2026年8月の料金表）による目安です。最新の料金はAWSの料金ページで確認してください。

## 毎回の片付けチェックリスト

- [ ] EC2インスタンスを「終了」した
- [ ] ロードバランサーとNATゲートウェイを削除した
- [ ] 使っていないElastic IPを解放した
- [ ] RDSと、復元の練習で作った別のDBを削除した（残したいデータはスナップショットを取った）
- [ ] 不要なS3バケット、CloudWatchのロググループ、スナップショット、AWS Backupの復旧ポイントを削除した（バックアップ計画を削除しても、取得済みのバックアップは残る）
- [ ] 東京以外のリージョンに、誤って作ったものが残っていないか確認した
- [ ] IaCで作ったものはIaCのコマンドで削除し、保持設定で残ったものや、削除に失敗したもの（中身が残ったS3バケットなど）がないか確認した
- [ ] 翌日以降に、請求画面やCost Explorerで費用を再確認した（費用の反映には時間がかかり、24時間以上かかることもある）

## やってはいけないこと

- アクセスキーをコードに書いたり、GitHubに載せたりする。公開されたキーは短時間で悪用されることがある
- SSH（22番）やRDP（3389番）を、0.0.0.0/0（どこからでも）に開ける
- ルートユーザーで日常の作業をする
- 会社や顧客の本物のデータを、学習用アカウントに入れる

:::sum
- 基礎力は「作って、壊して、説明した回数」で身につく。構成図、一次情報、わざと壊す、片付け、説明の5つを毎回行う
- 学習には会社の検証用アカウントが第一候補。個人で作るなら、この本は従来方式のアカウントを前提にする
- ルートユーザーのMFA、作業用ユーザー、予算アラート、コスト異常検出、リージョンの固定を最初に済ませる
- 予算アラートは通知であって上限ではない。毎回の片付けと、翌日の請求確認までを習慣にする
:::

## 章末問題

:::q 計算 | 消し忘れの費用
ハンズオンの後、NATゲートウェイ1台と、使っていないElastic IP（パブリックIPv4アドレス）2個を消し忘れ、30日間そのままにしてしまいました。本文の料金の目安（NATゲートウェイは1時間あたり約0.062ドル、パブリックIPv4アドレスは1時間あたり0.005ドル）を使って、かかった費用を概算してください。データの通過はなかったものとします。
:::a
- NATゲートウェイ：0.062ドル × 24時間 × 30日 = 44.64ドル
- パブリックIPv4アドレス：0.005ドル × 24時間 × 30日 × 2個 = 7.2ドル
- 合計：約52ドル

何も通信していなくても、置いてあるだけでこの費用がかかります。1時間あたりの単価は小さく見えても、消し忘れると月単位で効いてきます。なお、NATゲートウェイを削除しても、割り当てていたElastic IPは自動では解放されません。片付けのチェックリストで別の項目になっているのは、このためです。
:::

:::q 判断 | どの登録方式で作るか
個人で新しくAWSアカウントを作って第2部に取り組みます。新方式（Sign up for AWS）と従来方式（Sign up for AWS (advanced)）のどちらで作るべきですか。理由を2つ挙げてください。また、新方式にしかない利点を1つ挙げてください。
:::a
従来方式で作ります。理由は次のとおりです。

1. 第2部は東京リージョンでVPCなどを一から作るが、新方式では日本の住所で登録するとリージョンがシドニーに固定され、変更できない
2. 新方式ではルートユーザーが作られず、使えるサービスも一部に限られるため、本文のとおりに進められない

新方式にしかない利点は、有料プランで月額の支出上限を設定できることです。ただし「高度な機能」を有効にすると上限は解除され、元に戻せません。従来方式では上限を設定できないため、予算アラート、コスト異常検出、毎回の片付けで費用を管理します。
:::

:::q 指摘 | 通知が来なかった理由
ある人が、月額5ドルの予算アラートを1つ設定して学習を始めました。無料プランのクレジットが残っているうちは通知が一度も来ず、気づいたときにはクレジットの大半を使っていました。なぜ通知が来なかったのでしょうか。どう設定すべきでしたか。
:::a
既定の設定では、クレジットがマイナスの費用として計算されます。利用料がクレジットで相殺されている間は、予算から見た費用が0ドル付近のままになり、5ドルのしきい値に達しません。

予算を作るときに、クレジットを費用の計算に含めない設定にします。こうすると、クレジットで支払われた分も利用額として数えられ、消費の進み具合に気づけます。あわせて、少額でも課金が発生したら通知する予算をもう1つ作っておくと、想定外の利用に早く気づけます。
:::

:::q 発見 | 片付け漏れを探す
ハンズオンの翌日、Cost Explorerを見ると、次のサービスに前日の日付で費用が出ていました。すべて「片付けたはず」のものです。それぞれ、何が残っている可能性がありますか。

1. EC2 その他（EC2-Other）
2. Relational Database Service
3. CloudWatch
:::a
1. EC2 その他：NATゲートウェイ、EBSのボリュームやスナップショット、データ転送などがここに計上される。インスタンスを「停止」しただけでディスクが残っている、NATゲートウェイが残っている、といった原因が考えられる。なお、パブリックIPv4アドレス（Elastic IPを含む）の料金は、ここではなく「VPC」の分類に計上される。NATゲートウェイを消した後のElastic IPが残っていると、「VPC」に費用が出続ける
2. RDS：停止しただけのDB（保存領域の料金は続く。7日後には自動で起動する）、復元の練習で作った別のDB、手動で取ったスナップショット
3. CloudWatch：ロググループに保存されたログ、アラーム、ダッシュボード

まず確認するのは、費用の日付です。費用のデータは反映に時間がかかるため、前日の日付の費用は、片付ける前の利用分かもしれません。片付け後の日付で費用が出続けているかを、さらに翌日に確認します。それでも続いていれば、Cost Explorerで使用タイプ別に内訳を表示し、何の料金かを特定します。東京以外のリージョンに誤って作っていないかも確認してください。
:::
