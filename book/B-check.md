## 学習環境：最初の30分

詳しくは{{ch:env}}を参照してください。

- [ ] ルートユーザーに、多要素認証を設定した。以後、日常の作業には使わない
- [ ] 日常の作業用の利用者を作り、多要素認証を設定した
- [ ] 予算の通知を2つ作った（月額の予算と、少額でも課金が出たら通知する予算）。クレジットを含めない設定にした
- [ ] 請求に関する通知の宛先を、普段見るメールアドレスにした
- [ ] コスト異常検出を、有効にした
- [ ] 使うリージョンを決め、画面右上の表示を、作業のたびに確かめることにした



## 学習環境：毎回の片付け

- [ ] EC2インスタンスを「終了」した
- [ ] ロードバランサーとNATゲートウェイを削除した
- [ ] 使っていないElastic IPを解放した
- [ ] RDSと、復元の練習で作った別のDBを削除した（残したいデータはスナップショットを取った）
- [ ] 不要なS3バケット、CloudWatchのロググループ、スナップショット、AWS Backupの復旧ポイントを削除した（バックアップ計画を削除しても、取得済みのバックアップは残る）
- [ ] 東京以外のリージョンに、誤って作ったものが残っていないか確認した
- [ ] IaCで作ったものはIaCのコマンドで削除し、保持設定で残ったものや、削除に失敗したもの（中身が残ったS3バケットなど）がないか確認した
- [ ] 翌日以降に、請求画面やCost Explorerで費用を再確認した（費用の反映には時間がかかり、24時間以上かかることもある）

## 案件：参画した最初の週に確認すること

- [ ] システム構成図と各部品の役割（どれが最新版か）
- [ ] AWSアカウントの分け方（本番・検証・開発が別のアカウントか）と、自分に付与された権限
- [ ] 自分が作業してよい環境と、触ってはいけない環境
- [ ] 名前の付け方とタグのルール
- [ ] 変更の手順（申請、承認、作業してよい時間帯、手順書の書式）
- [ ] IaCのリポジトリの場所と、管理画面での手動変更が許されているか
- [ ] 監視の仕組みと、障害時の連絡体制（誰に、どの手段で）
- [ ] 費用を管理している人と、予算
- [ ] 質問してよい相手と、質問の窓口

## 案件：本番で作業する前

詳しくは{{ch:field}}を参照してください。

- [ ] 手順書があり、レビューを受けた。実行するコマンドの値は、すべて埋めてある
- [ ] 確認の方法と、期待する結果が、手順ごとに書かれている
- [ ] 切り戻しの手順と、中止の基準が書かれている
- [ ] 作業の日時と、影響の範囲を、関係者に知らせた
- [ ] 作業の前の状態を記録した。必要なバックアップを取った
- [ ] 実施する人と、確認する人の、2人がそろっている
- [ ] 画面右上の、アカウントとリージョンを確かめた

## 設計：レビューに出す前

詳しくは{{ch:review}}を参照してください。

- [ ] 要件と制約を、1枚にまとめた。非機能要件が、数字になっている
- [ ] 構成の案を、2つ以上比べた。判断の記録がある
- [ ] 単一障害点を洗い出した。残すものには、理由が書かれている
- [ ] RTOとRPOに対して、何分で、どこまで戻せるかを、説明できる。復元を試した、または試す計画がある
- [ ] 人とプログラムの権限が分かれ、必要な範囲に絞られている。長く使える認証情報がない
- [ ] インターネットから直接届く部品が、必要最小限になっている
- [ ] ピーク時の数字から、台数と、後ろの部品の上限を確かめた
- [ ] 上限値（クォータ）が、必要な最大の量を上回っている
- [ ] 月額の見積もりが、前提とともにある。データ転送、NATゲートウェイ、ログ、バックアップ、本番以外の環境を含めた
- [ ] 監視する指標と、通知を受けた後の動きが決まっている
- [ ] 変更を届ける方法と、戻す方法が決まっている
- [ ] 決まっていないことと、不安な点を、自分から挙げた

## 公開：本番に出す前

- [ ] 本番と同じ構成の環境で、主な操作を確かめた
- [ ] 負荷試験を行い、最初に詰まる部品と、限界を確かめた
- [ ] 1台の停止、1つのAZの停止、データベースの切り替えを、実際に試した
- [ ] バックアップからの復元を、実際に行い、時間を測った
- [ ] アラームが、実際に通知されることを確かめた。通知の宛先は、個人ではなく、チームになっている
- [ ] 通知ごとの、最初の確認の手順がある
- [ ] 問題のある版を、前の版に戻す手順を、実際に試した
- [ ] 証明書、ドメイン、契約、版の支援など、期限のあるものを一覧にし、通知を設定した
- [ ] 操作の記録が、長期保存されている。記録の保存先は、消されない場所にある
- [ ] 検証用に開けたポート、一時的に付けた強い権限、試験用のデータが、残っていない
- [ ] 費用の通知と、異常の検知が、本番のアカウントで有効になっている
- [ ] 障害のときの、連絡の体制と、役割が決まっている

## 障害：最初の15分

詳しくは{{ch:sre}}を参照してください。

- [ ] 影響を確かめた。誰が、何を、どのくらい使えないか。広がっているか
- [ ] 役割を決めた。指揮、作業、連絡、記録
- [ ] 直前の変更を確かめた。あれば、戻すことを、最初に検討した
- [ ] 原因がわからなくても打てる手（戻す、切り離す、増やす、切り替える）を検討した
- [ ] 第一報を出した。影響の範囲、今の状況、次に報告する時刻
- [ ] 戻す前の状態の記録（ログ、設定、画面）を残した

## 移行：切り替えの前

詳しくは{{ch:mig}}を参照してください。

- [ ] 切り替えの手順を、通しで練習し、時間を測った
- [ ] 合格の基準（件数の一致、主な操作、応答時間）が、一覧になっている
- [ ] 切り戻しの条件と、判断の時刻が決まっている。戻した場合の、データの扱いが決まっている
- [ ] DNSのTTLを、数日前に短くした
- [ ] 連携先のシステムの担当者に、日時を知らせた。相手の側の設定（許可するIPアドレスなど）の変更を、依頼した
- [ ] 当日の体制と、連絡の手段、判断する人が決まっている
- [ ] 月末、期末、繁忙期を避けた日程になっている
- [ ] 切り替えの後、旧環境を、いつまで残し、いつ止めるかが決まっている
