:::goal
- 2つのAZにサーバーを置き、ロードバランサーで振り分ける構成を作れる
- 1台が壊れたとき、何がそれを検知し、何が入れ替えるのかを順に説明できる
- SSHのポートを開けずに、サーバーへ入って調査できる
:::

2つのAZにサーバーを置き、1台が壊れても自動で元に戻る仕組みを作ります。このステップで作る「起動テンプレート → Auto Scalingグループ → ターゲットグループ → ロードバランサー」のつながりは、AWSでサーバーを動かす構成の基本形です。

サーバーは「大切に直しながら長く使うもの」ではなく、「いつでも捨てて、同じものを作り直せるもの」として扱います。そのために、サーバーの中身は起動時のスクリプト（ユーザーデータ）で自動的に作られるようにしておきます。次は、Amazon Linux 2023 でWebサーバーを入れ、ホスト名を表示するページを作る例です。

```bash
#!/bin/bash
dnf install -y nginx
echo "<h1>$(hostname)</h1>" > /usr/share/nginx/html/index.html
systemctl enable --now nginx
```



## 進め方

1. EC2用のIAMロールを作り、Session Manager（SSHを使わずにサーバーへ入る仕組み）用の権限を付ける
2. 起動テンプレートを作る。ユーザーデータ（起動時に実行するスクリプト）でWebサーバーを入れ、そのサーバーのホスト名を表示するページを作る
3. アプリ用サブネット2つにまたがるAuto Scalingグループを作る（最小2台）
4. パブリックサブネット2つを指定してALBとターゲットグループを作り、Auto Scalingグループにターゲットグループを関連付ける（EC2インスタンスは自動で登録される）。あわせて、Auto Scaling側でElastic Load Balancingのヘルスチェックを有効にし、アプリの起動にかかる時間に合わせて猶予期間を設定する
5. セキュリティグループを、{{ch:net}}の「セキュリティグループの設定例」のとおりに設定する。アプリサーバーは、ALBのセキュリティグループからの通信だけを受け付ける
6. SSHの22番は開けず、Session Managerでサーバーに入る

独自ドメインと証明書がない場合、学習ではHTTP（80番）で動作を確認してかまいません。本番ではHTTPSが前提です。HTTPで試す場合は、ALBのリスナーとALBのセキュリティグループの受信ルールを80番にそろえ、ターゲットグループの転送先ポートとWebサーバーの待ち受けポートも一致させてください。また、プライベートサブネットからSession Managerを使うには、NATゲートウェイかVPCエンドポイントを通じて、Systems Managerへの通信経路が必要です。

## つまずきやすい点

| 症状 | よくある原因 | 確かめ方 |
|---|---|---|
| ターゲットが unhealthy のまま | アプリ用のセキュリティグループで、ALBからの通信を許可していない。ヘルスチェックのポートやパスが、Webサーバーと合っていない | ターゲットグループに表示される理由を読む。サーバーに入り、`curl localhost` で自分自身に応答するかを試す |
| ALBが503を返す | ターゲットグループに、ターゲットが1台も登録されていない。または、登録されたターゲットがすべて unused（使われていない）の状態 | ターゲットグループの登録状況を確認する。Auto Scalingグループにターゲットグループを関連付けたか。ターゲットのあるAZが、ALBで有効になっているか |
| 全台が unhealthy なのに、503ではなく、502や504、タイムアウトになる | 正常なターゲットが1台もないとき、ALBは振り分けを止めず、全台に送り続ける（フェイルオープン）。そのため、症状はサーバー側の状態で決まる | ターゲットグループの画面で、登録が0台なのか、全台が unhealthy なのかを見分ける。後者なら、1行目と同じ手順で、ヘルスチェックに失敗する理由を調べる |
| Session Manager の一覧にサーバーが出ない | IAMロールに必要な権限（AmazonSSMManagedInstanceCore）がない。サーバーから Systems Manager へ届く経路がない | ロールの内容を確認する。プライベートサブネットのルートテーブルに、NATゲートウェイへの経路（またはVPCエンドポイント）があるか |
| Webサーバーが入っていない | 起動時に外部へ出られず、ソフトウェアの取得に失敗した | サーバーに入れるなら `/var/log/cloud-init-output.log` を読む。入れないなら、まず外部への経路を疑う |
| サーバーが起動と終了を繰り返す | アプリの起動より先にヘルスチェックが始まり、異常と判定されて入れ替えられている | ヘルスチェックの猶予期間を、起動にかかる時間より長くする（{{ch:ts}}のシナリオ10） |

:::tip 症状からではなく、通信の順に確かめる
うまくいかないときは、思いついた設定を順に変えてみたくなりますが、変えた設定を戻し忘れて状況を悪くしがちです。「利用者 → ALB → サーバー」の順に、どこまで届いているかを1つずつ確かめてください。ALBのURLで503や504が返るなら、ALBまでは届いています。サーバーの中で `curl localhost` が応答するなら、Webサーバーは動いています。残るのは、その間です。
:::

## 確認ポイント

- ALBのURLを何度か開くと、表示されるホスト名が切り替わる理由を説明できる
- 22番を開けずにサーバーへ入れる仕組みと、それが安全な理由を説明できる
- ALBのヘルスチェックとAuto Scalingのヘルスチェックの違いを説明できる。Auto Scalingは既定ではEC2自体の状態しか見ないため、Webサーバーのプロセスが止まっただけでは入れ替えない。Elastic Load Balancingのヘルスチェックを有効にして初めて、ALBが異常と判断したサーバーを入れ替える

## わざと壊してみる

:::lab
1台を手動で終了し、Auto Scalingが新しいサーバーを起動してALBに組み込むまでの流れを観察します。次に、アプリのセキュリティグループからALBの許可を外し、ALBがエラーを返す様子を確認してから元に戻します。
:::

## 片付け

Auto Scalingグループ、ALB、ターゲットグループ、起動テンプレートの順に削除します。Auto Scalingグループを残したままサーバーだけ終了すると、すぐに新しいサーバーが起動します。

## 本番ではどう変わるか

| 項目 | 学習での構成 | 本番で加わること |
|---|---|---|
| 通信の暗号化 | HTTPで確認してもよい | HTTPSが前提。ALBに証明書を設定し、HTTPで来た通信はHTTPSへ転送する |
| 台数の決め方 | 最小2台で固定 | 負荷に応じて増減する。CPU使用率などの目標値を決め、それを保つように台数を調整させる（ターゲット追跡）。増える時期がわかっていれば、予定に合わせて先に増やす |
| サーバーの中身 | 起動のたびにスクリプトで作る | 必要なソフトウェアを入れた状態のイメージ（AMI）をあらかじめ作っておき、起動を速くする。外部からの取得に失敗して起動できない、という事態も防げる |
| サーバーの更新 | 作り直す | 新しいイメージに切り替え、稼働中のサーバーを少しずつ入れ替える（インスタンスの更新）。直接ログインして変更することはしない |
| ログ | サーバーの中にある | サーバーの外（CloudWatch Logs など）に送る。サーバーが入れ替わるとログも消えるため |
| AZの障害 | 2つのAZに1台ずつ | 1つのAZが止まっても、残りの台数で負荷に耐えられるように最小台数を決める（{{ch:ha}}） |

:::sum
- サーバーは、起動テンプレートから何度でも同じものを作れるようにしておく
- ロードバランサーは異常なサーバーへの振り分けを止め、Auto Scalingは台数を保つ。入れ替えまでさせるには、Auto Scaling側でロードバランサーのヘルスチェックを有効にする
- アプリサーバーは、ロードバランサーのセキュリティグループからの通信だけを受け付ける
- サーバーへは Session Manager で入る。受信ポートを開けず、誰が入ったかの記録も残る
:::

## 章末問題

:::q 説明 | 1台が壊れてから回復するまで
Auto Scalingグループ（最小2台、希望2台、最大4台）が、2つのAZに1台ずつサーバーを置いています。ロードバランサーのヘルスチェックも有効です。1台のサーバーでWebサーバーのプロセスが止まりました。回復までに起きることを、順に説明してください。
:::a
1. ロードバランサーのヘルスチェックが、決められた回数だけ連続して失敗する
2. ロードバランサーが、そのサーバーを異常と判定し、振り分けを止める。この時点から、利用者の通信は残りの1台だけに届く
3. Auto Scalingが、ロードバランサーの判定を受けて、そのサーバーを異常とみなす
4. Auto Scalingが、異常なサーバーを終了し、台数を希望の2台に戻すために新しいサーバーを起動する
5. 新しいサーバーが起動し、ユーザーデータでWebサーバーが入り、ヘルスチェックに合格する
6. ロードバランサーが、新しいサーバーへの振り分けを始める

2から6の間は、1台で全体の負荷を受けています。この時間は、サーバーの起動とアプリの準備にかかる時間で決まります。「1台でも耐えられるか」「この時間をどこまで短くできるか」が、設計で考える点です。
:::

:::q 比較 | 2種類のヘルスチェック
Auto Scalingグループのヘルスチェックを、既定の設定（EC2の状態だけを見る）のままにしていました。この状態で、サーバーのOSは動いているが、Webサーバーのプロセスだけが止まった場合、何が起きますか。ロードバランサーのヘルスチェックを有効にした場合と比べてください。
:::a
既定の設定の場合：ロードバランサーは、そのサーバーを異常と判定して振り分けを止めます。しかしAuto Scalingは、EC2そのものは正常に動いているため、異常とはみなしません。サーバーは入れ替えられず、振り分けから外れたまま残り続けます。台数の上では2台ですが、実際に処理しているのは1台、という状態が、誰かが気づくまで続きます。

ロードバランサーのヘルスチェックを有効にした場合：Auto Scalingが、ロードバランサーの判定も使ってサーバーを異常とみなし、入れ替えます。

「振り分けを止める」のと「入れ替える」のは、別の仕組みが担当しています。自動で回復する構成にするには、この2つをつなぐ設定が必要です。
:::

:::q 設計 | 急増に間に合わない
あるアプリは、サーバーの起動からリクエストを受けられるようになるまでに5分かかります。CPU使用率が50%を保つように台数を調整する設定にしていますが、テレビで紹介された直後の急増では、台数が増える前に応答が遅くなり、エラーが出ました。対策を3つ挙げてください。
:::a
解答例：

1. 起動を速くする：必要なソフトウェアを入れたイメージをあらかじめ作り、起動時の準備を減らす。5分が1〜2分になれば、増えるまでの時間が短くなる
2. 先に増やしておく：放送の時刻がわかっているなら、その前に台数を増やす予定を入れる
3. 余裕を持たせる：目標のCPU使用率を下げる（例：40%）、最小台数を増やす。平常時の費用は増えるが、急増を受け止める余力ができる
4. サーバーに届く前に減らす：画像や変化の少ないページをCDNから返し、サーバーが処理する通信そのものを減らす

台数を自動で増やす仕組みは、ゆるやかな増加には有効ですが、数分で数倍になる急増には追いつきません。急増が予想されるなら、「増やす」より「先に用意する」「届く量を減らす」を組み合わせます（{{ch:perf}}）。
:::

:::q 説明 | SSHのポートを開けない利点
サーバーへのログインを、SSH（22番ポート）ではなく Session Manager で行う利点を、3つ挙げてください。
:::a
解答例：

1. 受信ポートを開けなくてよい：22番を開ける必要がなく、外部からの攻撃が届く入口がなくなる。プライベートサブネットのサーバーに入るための踏み台サーバーも要らない
2. 鍵の管理が要らない：SSHの秘密鍵を配ったり、退職者の鍵を消したりする作業がなくなる。誰が入れるかは、IAMの権限で管理する
3. 記録が残る：誰がいつどのサーバーに入ったかが CloudTrail に残る。設定すれば、操作の内容も記録できる

本番環境では、そもそも人がサーバーに入らなくて済む運用（ログは外に送る、変更はイメージの入れ替えで行う）を目指します。入る必要があるときも、申請と記録を伴う手順にするのが一般的です。
:::
