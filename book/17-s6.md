:::goal
- API Gateway、Lambda、DynamoDB で、サーバーを管理しないAPIを作れる
- サーバーを使う構成と比べて、管理するものと料金のかかり方の違いを説明できる
- 関数の上限（実行時間、同時に動く数）を踏まえて、向く処理と向かない処理を判断できる
:::

サーバーを管理しない設計を体験し、ステップ3との違いを理解します。このステップで作るものはVPCの外にあり、ここまでの構成とは独立しています。OSも台数も意識せずに動く一方で、設計で考えることがなくなるわけではありません。考える対象が、サーバーから「権限」「上限」「失敗したときの動き」に移ります。

関数の中身は、次のような短いコードです。HTTP APIから届いたリクエストの種類を見て、DynamoDBへの登録か取得かを行います。

```python
import json, os, uuid
import boto3

table = boto3.resource('dynamodb').Table(os.environ['TABLE_NAME'])

def response(status, body):
    return {'statusCode': status,
            'headers': {'content-type': 'application/json; charset=utf-8'},
            'body': json.dumps(body, ensure_ascii=False)}

def handler(event, context):
    method = event.get('requestContext', {}).get('http', {}).get('method')
    if method == 'POST':
        raw = event.get('body')
        if (event.get('isBase64Encoded') or not isinstance(raw, str)
                or len(raw.encode('utf-8')) > 1024):
            return response(400, {'error': 'invalid body'})
        try:
            data = json.loads(raw)
        except (ValueError, TypeError):
            return response(400, {'error': 'invalid JSON'})
        text = data.get('text') if isinstance(data, dict) else None
        if not isinstance(text, str) or not text.strip() or len(text) > 200:
            return response(400, {'error': 'text must be 1-200 characters'})
        item = {'id': str(uuid.uuid4()), 'text': text.strip()}
        table.put_item(Item=item)
        return response(201, item)
    if method == 'GET':
        return response(200, table.scan(Limit=20).get('Items', []))
    return response(405, {'error': 'method not allowed'})
```

テーブルの名前は環境変数で渡し、コードには書きません。なお、テーブル全体を読む scan は、学習用の簡易な書き方です。件数が増えると遅く高価になるため、本番ではキーを指定して取得する設計にします（{{ch:data}}）。



## 公開する前の安全条件

学習用でも、認証なしの書き込みAPIは公開しません。URLを秘密にすることやCORSの設定は、認証の代わりになりません。この章ではIAM認証を使い、学習用ロールから署名したリクエストだけを受け付けます。個人情報・業務データは保存せず、架空の短いメモだけで試します。

| 設定 | 学習時の値・条件 |
|---|---|
| ルート | `GET /notes` と `POST /notes` の2つだけ。両方に `AWS_IAM` を設定し、認証なしの `$default` ルートは作らない |
| 呼び出す人 | 学習用ロールに、対象API・ステージ・GET/POSTの `/notes` に限った `execute-api:Invoke` を許可する |
| 関数の権限 | 対象テーブルへの `dynamodb:PutItem` と `dynamodb:Scan`、必要なログ出力だけを許可する |
| APIの流量 | ステージの既定値を毎秒1リクエスト、バースト2にする。これは学習用に小さくした設定値で、AWSの既定値ではない |
| 関数・テーブル | 関数の予約済み同時実行を1、タイムアウトを5秒にする。テーブルは学習用に小さなプロビジョンド容量（例：読み取り・書き込み各5）を使う |
| ログ | 保持期間を1日にし、メモ本文、Authorizationヘッダー、セッショントークンを記録しない |
| 終了条件 | 動作確認が終わったら、その場でAPIから順に削除し、翌日に持ち越さない |

:::warn 制限値は費用の上限ではない
API Gatewayのスロットリングはベストエフォートであり、設定値を絶対に超えない保証ではありません。Lambdaの同時実行数を制限しても、APIへのアクセスや保存済みデータなどの費用すべては止まりません。予算通知、短時間での実施、削除確認を併用します。新しいアカウントでは利用可能な同時実行枠が少なく、予約済み同時実行を1に設定できない場合があります。設定できない場合は、公開APIによる演習には進まず、Lambdaの管理画面からのテストまでにとどめて学習用枠を管理者に確認します。
:::

## 進め方

1. {{ch:s1}}の一時認証で、学習用アカウントとロールであることを確認する
2. DynamoDBに文字列の `id` をパーティションキーとするテーブルを作る。上の容量を設定する
3. Lambda関数を作り、上のコードと `TABLE_NAME` 環境変数、実行ロール、予約済み同時実行、タイムアウト、ログ保持期間を設定する
4. API Gatewayで空のHTTP APIとLambda統合を作り、ペイロード形式は `2.0` を指定する。認証なしの既定ルートを自動生成するクイック作成は使わない。Lambdaのリソースポリシーも、呼び出し元のAPI・ステージ・ルートに限定する
5. 以下のように、IAM認証付きのルートを作ってから、制限値付きの `dev` ステージを作る。`API_ID` と `INTEGRATION_ID` は自分の学習用資源のIDに置き換える。APIキーは認証手段として使わない

```bash
API_ID='自分の学習用APIのID'
INTEGRATION_ID='作成したLambda統合のID'
aws apigatewayv2 create-route --api-id "$API_ID" \
  --route-key 'GET /notes' --authorization-type AWS_IAM \
  --target "integrations/$INTEGRATION_ID"
aws apigatewayv2 create-route --api-id "$API_ID" \
  --route-key 'POST /notes' --authorization-type AWS_IAM \
  --target "integrations/$INTEGRATION_ID"
aws apigatewayv2 create-stage --api-id "$API_ID" --stage-name dev \
  --auto-deploy \
  --default-route-settings '{"ThrottlingRateLimit":1,"ThrottlingBurstLimit":2}'
```

6. `aws apigatewayv2 get-routes --api-id "$API_ID"` で、すべてのルートが `AWS_IAM` であることを確認する。既存APIを使う場合は認証なしルートが残っていないことを確認し、残っている場合は演習を止めて閉じる
7. 署名なしの `curl -i "https://自分のAPIのID.execute-api.ap-northeast-1.amazonaws.com/dev/notes"` が拒否されることを確認する（想定は403）。成功した場合は先に認証設定を直す
8. 署名したPOSTで登録し、1秒以上待って署名したGETで取得する。下の例はCloudShellの一時認証を使う。ローカルで実行する場合は{{ch:s1}}のSSOプロファイルを指定し、Boto3を用意する

次のコードを `call_api.py` として保存します。URLのAPI IDとリージョンは自分の値に置き換えます。署名先をAWSのAPI Gatewayのホストに限定し、リダイレクトは追いません。認証情報は表示・ファイル保存しません。

```python
import json, re, sys, urllib.request
import boto3
from botocore.auth import SigV4Auth
from botocore.awsrequest import AWSRequest

url = 'https://API_ID.execute-api.ap-northeast-1.amazonaws.com/dev/notes'
region = 'ap-northeast-1'
if not re.fullmatch(r'https://[a-z0-9]+\.execute-api\.' + re.escape(region)
                    + r'\.amazonaws\.com/dev/notes', url):
    raise ValueError('学習用APIのIDとリージョンを設定してください')
method = sys.argv[1] if len(sys.argv) == 2 else 'GET'
if method not in ('GET', 'POST'):
    raise ValueError('GET または POST を指定してください')
body = json.dumps({'text': '学習用の架空のメモ'}).encode() if method == 'POST' else None
credentials = boto3.Session().get_credentials()
if credentials is None:
    raise RuntimeError('CloudShellまたはSSOで学習用ロールにログインしてください')
request = AWSRequest(method=method, url=url, data=body,
                     headers={'Content-Type': 'application/json'})
SigV4Auth(credentials.get_frozen_credentials(), 'execute-api', region).add_auth(request)

class NoRedirect(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, req, fp, code, msg, headers, newurl):
        return None

opener = urllib.request.build_opener(NoRedirect)
with opener.open(urllib.request.Request(url, data=body, method=method,
                 headers=dict(request.headers)), timeout=10) as result:
    print(result.status, result.read().decode())
```

`python call_api.py POST` が201、`python call_api.py GET` が200となり、登録した架空のメモが含まれることを確かめます。429が返ったら少し待ち、繰り返しの連打や負荷試験は行いません。アクセスログではステータスとリクエストIDを確認し、本文や認証ヘッダーを出力しません。

:::ref
[HTTP APIのIAM認証](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-access-control-iam.html) ／ [HTTP APIのスロットリング](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-throttling.html)
:::

## 知っておく上限

サーバーレスの設計は、上限を知ることから始まります。Lambdaの主な上限は次のとおりです（[Lambdaのクォータ](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)）。

| 項目 | 値 | 設計への影響 |
|---|---|---|
| 1回の実行時間 | 最長900秒（15分）。既定の設定は3秒 | 長い処理は分割するか、コンテナなど別の方式にする |
| メモリ | 128MB〜10,240MB | メモリを増やすとCPUの性能も上がる。料金は、メモリの大きさと実行時間の掛け算で決まる |
| 同時に動く数 | 標準のアカウントクォータはリージョンごとに1,000。新規アカウントでは低い値から始まる場合があるため、自分のService Quotasで確認する | アカウント内のすべての関数で共有する。1つの関数の急増が、ほかの関数を止めることがある |
| 増え方 | 10秒ごとに1,000ずつ | 一瞬で数千に増えることはできない |
| 受け渡すデータの大きさ | 同期の呼び出しで6MB | 大きなファイルは関数を通さず、S3に直接置く |

API Gatewayにも、関数の応答を待つ時間に上限（30秒程度）があります。APIの裏で長い処理をする場合は、受け付けだけを先に返し、処理はキューを通じて後で行う形にします。

## つまずきやすい点

| 症状 | よくある原因 | 確かめ方 |
|---|---|---|
| ログに AccessDenied が出る | 関数の実行ロールに、そのテーブルへの操作の許可がない | エラーメッセージに、足りない操作と対象が書かれている |
| ログそのものが出ない | 実行ロールに、ログを書き込む権限（AWSLambdaBasicExecutionRole）がない | ロールの内容を確認する |
| KeyErrorや入力エラーになる | 環境変数が未設定、または入力が想定外 | `TABLE_NAME` と入力項目・型を確認する。ログに本文や認証情報を出力しない |
| 3秒でタイムアウトする | タイムアウトが既定の3秒のまま | 処理に必要な時間に合わせて延ばす。ただし、長くする前に、なぜ時間がかかるのかを確かめる |
| APIが500番台のエラーを返す | 統合の設定、呼び出し許可、関数の例外など | APIのアクセスログと関数ログをリクエストIDで照合する。HTTP APIのペイロード形式2.0では、`statusCode` を省略した有効なJSON応答を200として扱う場合もあるため、省略だけを原因と決めつけない |

## 確認ポイント

- 署名なしの呼び出しが拒否され、学習用ロールで署名したGET/POSTだけが成功する
- 不正なJSON、空のメモ、200文字を超えるメモが400になり、テーブルへ登録されない
- すべてのルートの認証設定と、スロットリング値を一覧で確認できる
- 演習終了時にAPIを含む資源を削除し、URLから利用できないことを確認した

- ステップ3の構成と比べて、管理するもの（OS、台数、パッチ適用）と、料金のかかり方の違いを説明できる
- このステップのLambda中心の構成と、EC2やFargateを使う構成を、処理時間、負荷の変動、費用、運用の手間の観点で比べられる。Fargateもサーバーレスの一種で、長時間の処理や常時の稼働にも使える

## 片付け

動作確認が終わったら、最初に学習用APIを削除して入口を閉じます。`aws apigatewayv2 delete-api --api-id "$API_ID"` は対象のIDを確認してから実行してください。その後、Lambda関数、学習用DynamoDBテーブル、ロググループ、関数用に作ったIAMロール、呼び出し用に追加した権限を削除します。共有ロールやほかの演習の資源は消しません。

APIのURLにもうアクセスできないことと、各サービスの一覧から対象資源が消えたことを確認します。削除エラーや、残ったログ・バックアップがないかも確認してください。IaCで作った場合は対応する削除手順を使います。呼び出していなくても、テーブル容量、保存済みデータやログには料金が発生し得ます。

## 本番ではどう変わるか

| 項目 | 学習での構成 | 本番で加わること |
|---|---|---|
| 認証 | IAM認証を必須にし、学習用ロールからの署名付き呼び出しに限定 | トークンを検証する仕組み（オーソライザー）を付ける。利用者の管理には Amazon Cognito などを使う |
| 呼び出しの制限 | 小さいスロットリング値、関数の予約済み同時実行、短時間実施と即時削除 | 呼び出しの頻度に上限を設ける。不正な大量アクセスにはAWS WAFを使う（WAFを直接関連付けられるのはREST API） |
| 失敗したとき | エラーを返すだけ | 非同期の処理では、再試行の回数と、失敗し続けたものの退避先（デッドレターキュー）を決める |
| 同じ処理が2回動く場合 | 考えていない | 再試行などで同じ依頼が2回届いても、結果が変わらないように作る（べき等性） |
| 応答の速さ | 気にしない | 最初の呼び出しが遅くなる現象（コールドスタート）が問題になる場合は、実行環境をあらかじめ用意する設定を検討する。待機の時間にも料金がかかる |
| リレーショナルデータベースとの接続 | 使っていない | 関数が増えると接続の数も増える。接続をまとめる仕組み（RDS Proxy）を挟む |

:::sum
- サーバーレスでは、OSや台数の管理がなくなる代わりに、権限、上限、失敗時の動きを設計する
- 関数の実行ロールには、必要なテーブルへの必要な操作だけを許可する
- 料金は、呼び出しの回数と、メモリの大きさ × 実行時間で決まる。使われない時間の計算料金はかからない
- Lambdaはサーバーレスの一部であって、すべてではない。長い処理や常時の稼働には Fargate などが向く
:::

## 章末問題

:::q 比較 | 管理するものと料金のかかり方
ステップ3の構成（ALB、EC2、Auto Scaling）と、このステップの構成（API Gateway、Lambda、DynamoDB）を、次の5つの観点で比べてください。

OSの修正プログラム、台数の調整、使われていない時間の料金、1回の処理時間の上限、起動直後の応答
:::a
| 観点 | ステップ3（サーバー） | ステップ6（サーバーレス） |
|---|---|---|
| OSの修正プログラム | 利用者が適用する（イメージを更新して入れ替える） | 事業者が行う |
| 台数の調整 | Auto Scalingの設定を利用者が決める | 自動。ただし、同時に動く数の上限がある |
| 使われていない時間の料金 | サーバーとALBが動いている限りかかる | 計算の料金はかからない。保存しているデータの料金はかかる |
| 1回の処理時間の上限 | 実質なし | 関数は最長15分。API経由なら、さらに短い |
| 起動直後の応答 | 起動済みのサーバーが応答するので安定 | 新しい実行環境の準備で、最初の応答が遅くなることがある |

どちらが優れているかではなく、処理の性質に合うかどうかで選びます。
:::

:::q 計算 | どこで費用が逆転するか
あるAPIの処理は、メモリ512MBの関数で平均0.2秒かかります。演習用の仮単価を、関数は1GB・秒あたり0.0000167ドルと、100万回の呼び出しあたり0.20ドルとします。比較対象のサーバー構成は、常時2台で月30ドル（仮）とします。

1. 月に100万回呼ばれる場合、関数の月額はいくらですか
2. 月に1億回呼ばれる場合はいくらですか
3. この結果から何が言えますか
:::a
1. 計算量：100万回 × 0.2秒 × 0.5GB = 10万GB・秒。10万 × 0.0000167ドル = 1.67ドル。呼び出し：0.20ドル。合計 約1.87ドル
2. すべて100倍になり、約187ドル
3. 呼び出しが少ないうちは関数のほうが大幅に安く、多くなるとサーバーのほうが安くなる。この仮単価では、月に1,600万回前後（30ドル ÷ 1.87ドル × 100万回）が分かれ目になる

実際の比較では、サーバー側にロードバランサーの費用と運用の手間が、関数側にAPI Gatewayとデータベースの費用が加わります。また、サーバー2台で1億回を処理できるとは限りません。「サーバーレスは安い」でも「高い」でもなく、呼び出しの量と波で決まることを、自分の数字で確かめるのが要点です。
:::

:::q 判断 | Lambdaに向かない処理
次の4つの処理のうち、Lambdaに向かないものを選び、理由と代わりの方式を答えてください。

1. 画像がアップロードされるたびに行う、数秒の縮小処理
2. 1本あたり30分かかる動画の変換
3. 利用者とつなぎ続けて、絶えずデータをやり取りするゲームのサーバー
4. 毎日午前3時に行う、5分で終わる集計
:::a
向かないのは2と3です。

- 2：1回の実行時間の上限（15分）を超える。コンテナ（ECSのFargateなど）で動かすか、動画変換のための専用サービスを使う。処理を短い単位に分割できるなら、分割して複数の関数で行う方法もある
- 3：接続を長時間保ち、状態を持ち続ける処理は、短時間で終わる関数の考え方と合わない。コンテナやサーバーで常時動かす

1は、件数に波がある短い処理で、関数に最も向く形です。4も、決まった時刻に起動して数分で終わるため、関数で問題ありません。時刻による起動には Amazon EventBridge を使います。
:::

:::q 設計 | 同じ依頼が2回届いたら
注文を登録するAPIがあります。利用者の通信が不安定で、同じ注文の依頼が2回届くことがあります。また、アプリ側の再試行でも、同じ依頼が2回届くことがあります。注文が二重に登録されないようにするには、どう作りますか。
:::a
依頼ごとに一意の番号を付け、同じ番号の依頼は1回だけ処理するように作ります。

1. 画面やアプリが、注文の操作ごとに一意の番号（べき等性のためのキー）を作り、依頼に付けて送る。再試行のときは、同じ番号を付ける
2. 関数は、その番号をキーにしてデータを登録する。このとき「同じキーのデータがまだないこと」を条件にして書き込む（DynamoDBの条件付き書き込み）
3. すでにあれば、新しく登録はせず、最初の依頼と同じ結果を返す

本文のコードのように、関数の中で毎回新しい番号（uuid）を作る書き方では、同じ依頼が2回届くと2件登録されます。「確認してから登録する」という2段階の処理も、2つの依頼が同時に届くと両方が「まだない」と判断するため、防げません。確認と登録を1回の操作で行う、条件付きの書き込みが必要です。

再試行は、サーバーレスに限らず、信頼性を高める仕組みのあちこちで自動的に行われます。「同じ依頼は2回届くことがある」を前提に作るのが、クラウドでの設計の基本です。
:::
