:::goal
- 症状から仮説を立て、通信や処理の流れに沿って、原因を絞り込める
- よくある障害の型と、その見分け方を知っている
- 復旧だけでなく、再発を防ぐ対策まで考えられる
:::

実務では、作る時間よりも、調べる時間のほうが長いことがあります。この章では、現場でよく起きる14の状況を題材に、切り分けの練習をします。どのシナリオも、次の順で考えてください。

1. 事実を整理する：何が、いつから、誰に、どのくらい起きているか。直前に変わったことは何か
2. 仮説を挙げる：考えられる原因を、複数挙げる。1つに決め打ちしない
3. 確かめる順を決める：通信や処理の流れに沿って、手前から。確かめやすく、可能性の高いものから
4. 影響を止める：原因がわからなくても打てる手（戻す、切り離す、増やす）を先に
5. 再発を防ぐ：同じことが、なぜ起こり得たのか。仕組みで防ぐ

解答を開く前に、自分の仮説と、確かめる順を書き出してください。表示されるメッセージや数値は、説明のための例です。

## シナリオ1：デプロイの後から、ときどき502になる

コンテナで動くWebアプリの新しい版を、昨日デプロイしました。それ以降、全体の0.5%ほどの依頼が、502のエラーになっています。失敗する依頼に、決まった画面や利用者の偏りはありません。ALBのアクセスログには、次のように記録されています。

```text
elb_status_code=502  target_status_code=-  request_processing_time=0.000
target_processing_time=-1  response_processing_time=-1
```

アプリのログには、対応するエラーが見当たりません。新しい版では、Webサーバーの設定を見直し、接続を保ち続ける時間（キープアライブ）を、75秒から5秒に短くしていました。ALBのアイドルタイムアウトは、既定の60秒です。

:::q 障害対応 | 原因と対策
何が起きていると考えられますか。どう確かめ、どう直しますか。
:::hint
ターゲットからの応答の状態コードが「-」で、アプリのログにも記録がありません。依頼は、アプリまで届いているでしょうか。ALBとアプリの間の接続は、依頼のたびに作られるとは限りません。
:::a
読み取れること：ALBは502を返しているが、ターゲットからの応答は受け取っていない（target_status_code が「-」）。アプリのログにもない。つまり、依頼は、アプリの処理に届く前に失敗している。

原因：ALBは、ターゲットとの接続を使い回します。ALBは60秒間、接続を保とうとしますが、新しい版のアプリは、5秒で接続を閉じます。アプリが閉じた直後の接続に、ALBが次の依頼を送ると、接続はすでに切れているため、ALBは502を返します。閉じるのと送るのが、たまたま重なったときだけ起きるので、一部の依頼だけが失敗します。

確かめ方：502が、デプロイの時刻から始まっていること。ALBの指標で、ALB自身が返した502（HTTPCode_ELB_502_Count）が増えていること。設定を元に戻した検証環境で、再現しなくなること。

対応：アプリ側の接続を保つ時間を、ALBのアイドルタイムアウトより長くする（例：75秒に戻す）。急ぐ場合は、前の版に戻す。

再発防止：ロードバランサーの後ろに置くアプリの、接続に関する設定の決まりを、文書にする。設定の変更も、コードの変更と同じく、検証環境で負荷をかけて確かめる。502の割合に、アラームを設定する。

同じ「デプロイの後の502」でも、入れ替えの途中だけ起きるなら、古いコンテナが、処理中の依頼を終える前に止められている可能性があります。いつ起きるか（常時か、入れ替えの間だけか）が、見分ける手がかりです。
:::

## シナリオ2：特定の画面だけ、ちょうど60秒で504になる

業務システムの「月次の集計」の画面だけが、月初に、504のエラーになります。ほかの画面は正常です。利用者によると、「ボタンを押して、ちょうど1分たつとエラーになる」とのことです。エラーの後、同じ操作を繰り返す利用者が多く、その時間帯は、データベースのCPU使用率が100%近くになっています。

:::q 障害対応 | 原因と対策
「ちょうど60秒」は、何を意味していますか。当面の対応と、根本的な対策を答えてください。
:::a
原因：60秒は、ALBのアイドルタイムアウトの既定値です。集計の処理が60秒を超え、その間、アプリが何も返さないため、ALBが待ちきれずに504を返しています。月初だけ起きるのは、集計の対象の件数が、月初に最も多くなるためと考えられます。

重要なのは、ALBが504を返しても、アプリとデータベースの処理は止まらないことです。利用者が操作を繰り返すたびに、重い集計が、並行していくつも動き、データベースの負荷を高め、さらに遅くなります。

当面の対応：

- 利用者に、繰り返し操作しないよう知らせる
- データベースで、動き続けている集計の問い合わせを確かめ、重複しているものを止める
- ALBのアイドルタイムアウトを延ばす。ただし、これは一時しのぎで、処理が延びれば、また同じことが起きる

根本的な対策：

- 集計を、画面の操作と切り離す。ボタンを押したら「受け付けました」とすぐに返し、処理はキューを通じて後ろで行い、終わったら結果を取りに来てもらう（{{ch:perf}}）
- 集計の問い合わせを見直す。索引、対象の絞り込み、あらかじめ集計した値の利用
- 重い集計は、読み取り用の複製や、分析用の置き場所で行い、業務の処理に影響させない
- 同じ利用者が、同じ集計を重ねて実行できないようにする

「決まった秒数で失敗する」ときは、どこかのタイムアウトの値と一致していないかを疑います。60秒（ALB）、30秒前後（API Gateway）、3秒（Lambdaの既定）、15分（Lambdaの上限）などが、よく出てくる数字です。
:::

## シナリオ3：サーバーに、Session Manager で入れない

費用を下げるため、検証環境のNATゲートウェイを削除し、代わりに、S3向けのゲートウェイ型のVPCエンドポイントを作りました。アプリは、外部との通信をしておらず、S3だけを使います。翌日、調査のためにサーバーへ入ろうとしたところ、Session Manager の接続先の一覧に、サーバーが表示されません。サーバーは動いており、アプリも正常に応答しています。

:::q 障害対応 | 原因と対策
なぜ入れなくなったのでしょうか。NATゲートウェイを戻さずに解決する方法を答えてください。
:::a
原因：Session Manager は、サーバーの中のエージェントが、Systems Manager のサービスへ、外向きに通信することで働きます。NATゲートウェイを削除したため、プライベートサブネットのサーバーから、Systems Manager へ届く経路がなくなりました。S3向けのエンドポイントは、S3への通信にしか使えません。

確かめ方：サーバーのIAMロールに、必要な権限（AmazonSSMManagedInstanceCore）があるか。これは変更していないので、問題ないはず。次に、プライベートサブネットのルートテーブルを見て、外部への経路がないことを確かめる。変更の履歴から、NATゲートウェイの削除と、時期が一致することを確かめる。

対応：Systems Manager 向けの、インターフェイス型のVPCエンドポイントを作ります。必要なのは、ssm、ssmmessages、ec2messages の3つです。エンドポイントのセキュリティグループで、サーバーからの443番を許可します。

判断：インターフェイス型のエンドポイントは、1つごとに、時間の料金がかかります。3つを、複数のAZに置くと、NATゲートウェイ1台より高くなることがあります。費用だけが目的なら、検証環境では、NATゲートウェイ1台のほうが安い場合もあります。本番では、インターネットを通らないことの価値と合わせて判断します。

再発防止：NATゲートウェイを削除する前に、それを通っている通信を洗い出す。VPCフローログで、NATゲートウェイを通る通信の宛先を確かめる。アプリの通信だけでなく、運用のための通信（Systems Manager、監視のエージェント、OSの更新、コンテナのイメージの取得）を、忘れない。

今回は入れないだけで済みましたが、同じ理由で、監視のエージェントが指標やログを送れなくなっている可能性があります。あわせて確かめます。
:::

## シナリオ4：NATゲートウェイを作り直したら、取引先のAPIだけつながらない

IaCの整理のため、週末に、NATゲートウェイを作り直しました。月曜の朝から、取引先のAPIを呼び出す処理だけが、タイムアウトで失敗しています。ほかの外部のサービス（パッケージの配布元など）には、正常に接続できます。取引先に問い合わせると、「こちらの仕組みには、問題はない」とのことです。

:::q 障害対応 | 原因と対策
原因として、最も可能性が高いものは何ですか。どう確かめ、どう防ぎますか。
:::a
原因：NATゲートウェイを作り直したとき、割り当てられた固定のIPアドレス（Elastic IP）が、新しいものに変わりました。取引先は、接続を許可する相手を、IPアドレスの一覧で管理しており、そこに登録されているのは、古いIPアドレスです。新しいIPアドレスからの通信は、取引先の側で、黙って捨てられています。ほかの外部のサービスは、接続元を制限していないため、影響がありません。

確かめ方：今のNATゲートウェイのIPアドレスを確かめ、作り直す前のものと比べる。取引先に、「許可の一覧に登録されているIPアドレス」を確かめてもらう。「問題はない」という回答は、「取引先の仕組みが動いている」という意味で、こちらが許可されているかどうかとは別です。具体的な項目を挙げて、確かめてもらいます。

対応：取引先に、新しいIPアドレスの登録を依頼する。登録に時間がかかるなら、古い Elastic IP がまだ解放されていなければ、それを新しいNATゲートウェイに割り当て直す。

再発防止：

- NATゲートウェイの Elastic IP を、NATゲートウェイとは別の資源として管理し、作り直しても同じIPアドレスを使い続けられるようにする。IaCで、Elastic IP を誤って削除しない設定にする
- 外部に登録しているIPアドレスを、一覧にして管理する。どの取引先に、どのIPアドレスを伝えているか
- NATゲートウェイが複数のAZにある場合は、すべてのIPアドレスを登録する。{{ch:uc}}のケース12のように、別のリージョンへ切り替える構成なら、そちらのIPアドレスも

変更の前に、「この資源の、何に、外部が依存しているか」を確かめる習慣が、この種の障害を防ぎます。
:::

## シナリオ5：台数を増やしたら、データベースにつながらなくなった

アクセスの増加に合わせて、アプリサーバーの台数の上限を、10台から30台に引き上げました。その日の夕方のピークで、台数が25台を超えたあたりから、次のエラーが大量に出るようになりました。

```text
FATAL: remaining connection slots are reserved for non-replication superuser connections
```

この文言は、PostgreSQL 15までのものです。16以降では、末尾が `reserved for roles with the SUPERUSER attribute` に変わっています。どちらも、一般の利用者が使える接続の枠を使い切ったことを示します。

データベース（RDS for PostgreSQL）のCPU使用率は、40%程度で、余裕があります。アプリは、サーバー1台につき、最大20本の接続を、ためて使い回す設定（コネクションプール）になっています。データベースの接続の上限は、400本ほどです。

:::q 障害対応 | 原因と対策
何が起きましたか。計算で示してください。当面の対応と、根本的な対策を答えてください。
:::a
原因：データベースの接続の数が、上限に達しました。サーバー1台あたり最大20本なので、25台で500本になり、上限の約400本を超えます。10台のときは、最大200本で、収まっていました。データベースのCPUには余裕がありますが、接続の数は、それとは別の上限です。

当面の対応：

- アプリサーバーの台数の上限を、接続の上限に収まる数に戻す（20本 × 20台 = 400本なので、18台程度まで）
- または、1台あたりの接続の上限を下げる（例：12本にすれば、30台で360本）。多くの場合、1台が20本を同時に使い切ることはない

根本的な対策：

- 接続をまとめる仕組み（RDS Proxy など）を、アプリとデータベースの間に置く。多数のアプリからの接続を、少数のデータベースへの接続にまとめる
- 接続の上限は、データベースのメモリの大きさで決まる。必要なら、データベースを大きくする。ただし、接続を増やすことそのものが、データベースの負担になる
- 接続の数（DatabaseConnections）を監視し、上限の8割で通知する

再発防止：台数を増やす変更の前に、「台数に比例して増えるものが、後ろの部品の上限に当たらないか」を確かめる。接続の数のほか、外部のAPIの呼び出しの頻度の上限、ライセンスの数などが、同じ形の問題を起こします。{{ch:perf}}で述べたとおり、台数の最大値は、後ろの部品が受けられる量から決めます。
:::

## シナリオ6：ファイルがないだけなのに、403になる

あるバッチ処理は、「S3に設定ファイルがあれば読み込み、なければ既定の値を使う」という作りです。新しい環境で動かしたところ、設定ファイルを置いていないのに、「ファイルが存在しない」ではなく、「アクセスが拒否された（403 AccessDenied）」というエラーで止まりました。バッチのロールには、そのバケットのオブジェクトの読み取り（s3:GetObject）が許可されています。設定ファイルを置くと、正常に読めます。

:::q 障害対応 | 原因と対策
読み取りの権限があるのに、なぜ403になるのでしょうか。どう直しますか。
:::a
原因：S3は、存在しないオブジェクトを読もうとしたとき、依頼した側に、そのバケットの一覧を取得する権限（s3:ListBucket）があるかどうかで、返すエラーを変えます。

- 一覧の権限がある：「存在しない（404）」を返す
- 一覧の権限がない：「拒否された（403）」を返す

一覧の権限がない相手に「存在しない」と答えると、どのような名前のオブジェクトがあるかを、探られてしまうためです。このバッチのロールには、読み取りの権限はあるものの、一覧の権限がないため、存在しないファイルが、403として返りました。バッチは、404なら既定の値を使う作りですが、403は想定しておらず、止まりました。

対応：ロールに、そのバケットに対する s3:ListBucket を追加する。必要なら、条件で、対象の場所（プレフィックス）を絞る。対象は、オブジェクトではなく、バケットそのもの（{{ch:s1}}の章末問題）。

再発防止：「なければ別の動きをする」という作りの処理には、一覧の権限が必要であることを、権限の設計の決まりに加える。環境ごとに権限がずれないよう、IaCで管理する。前の環境では動いていたのなら、そちらには一覧の権限があったはず。

S3の403には、ほかにも原因があります。バケットポリシーによる拒否、暗号化の鍵（KMS）を使う権限の不足、別のアカウントのバケットで、片方の許可しかない場合、などです。「読み取りの権限はあるのに」と思ったら、鍵と、もう一方の側のポリシーと、一覧の権限を確かめます。
:::

## シナリオ7：費用が、3日で1か月分に達した

月の途中で、コスト異常検出の通知が届きました。Cost Explorer を見ると、「EC2 その他」という分類が、3日前から、1日あたり約120ドルに跳ね上がっています。それまでは、1日5ドル程度でした。3日前に、新しいデータ加工のバッチの運用を始めています。バッチは、プライベートサブネットのサーバーで動き、S3から、1日に約2TBのデータを読み込みます。VPCには、NATゲートウェイがあり、VPCエンドポイントはありません。

:::q 障害対応 | 原因と対策
何に費用がかかっていますか。仮単価を、NATゲートウェイの通過データ1GBあたり0.06ドルとして、計算で確かめてください。対策も答えてください。
:::a
原因：バッチのサーバーが、S3からデータを読むとき、通信がNATゲートウェイを通っています。NATゲートウェイは、通過したデータの量に応じて課金されます。

計算：2TB = 2,000GB。2,000 × 0.06ドル = 120ドル。1日あたりの増加分と一致します。

確かめ方：Cost Explorer で、使用タイプ別に表示し、NATゲートウェイのデータ処理の項目が増えていることを確かめる。NATゲートウェイの指標で、通過したバイト数が、3日前から増えていることを確かめる。

対応：S3向けの、ゲートウェイ型のVPCエンドポイントを作り、バッチのサーバーがあるサブネットのルートテーブルに関連付けます。ゲートウェイ型のエンドポイントは無料で、S3への通信は、NATゲートウェイを通らなくなります。アプリの変更は要りません。

再発防止：

- 新しい処理を始める前に、「どのデータが、どの経路を、どれだけ通るか」を確かめ、費用を見積もる（{{ch:cost}}）
- S3やDynamoDBを使うVPCには、最初から、ゲートウェイ型のエンドポイントを作っておく。標準の構成にする
- コンテナのイメージの取得や、ログの送信など、量の多い通信が、NATゲートウェイを通っていないかを、定期的に確かめる

今回は、3日で気づけました。コスト異常検出を有効にしていなければ、月末の請求まで気づかず、30日分で約3,600ドルになっていたところです。
:::

## シナリオ8：1つの関数の急増で、ほかの関数まで止まった

注文の後の処理を、「SQSのキュー → Lambda関数 → RDS」で行っています。セールの日、キューに大量のメッセージがたまり、関数が多数、同時に動きました。すると、次の2つが、同時に起きました。

- データベースで、接続の数が上限に達し、エラーが多発した
- 同じアカウントにある、まったく別のAPIの関数が、次のエラーで、呼び出しに失敗し始めた

```text
TooManyRequestsException: Rate Exceeded
```

:::q 障害対応 | 原因と対策
2つの現象は、それぞれ、なぜ起きましたか。再発を防ぐ設定を、挙げてください。
:::a
原因：

- 1つ目：関数は、同時に動く数だけ、実行環境が作られ、それぞれがデータベースに接続します。キューの処理のために、関数が数百も同時に動き、データベースの接続の上限を超えました（シナリオ5と同じ構造）
- 2つ目：Lambdaの同時実行の数には、アカウントとリージョンごとに、全体の上限があります（標準のクォータは1,000。新しいアカウントでは、より小さい値から始まることがあります）。キューの処理の関数が、この枠の大半を使い切り、ほかの関数が動く余地がなくなりました。上限を超えた呼び出しは、制限されて失敗します

再発を防ぐ設定：

1. キューの処理の関数に、同時に動く数の上限を設ける。SQSとの連携の設定で、最大の同時実行の数を指定する。または、関数に、予約した同時実行の数を設定する。上限は、データベースが受けられる接続の数から決める
2. 止まってはいけないAPIの関数には、予約した同時実行の数を設定し、ほかの関数に枠を使い切られても、動けるようにする
3. データベースとの間に、接続をまとめる仕組み（RDS Proxy）を置く
4. アカウント全体の同時実行の数を監視し、上限に近づいたら通知する。必要なら、上限の引き上げを申請する

キューは、まさにこのような急増を、ためて吸収するためのものです。たまったメッセージを、できるだけ速く処理しようとするのではなく、後ろの部品が受けられる速さで、処理します。処理が遅れてもよいのか、どのくらいまで遅れてよいのかを、要件として確かめておきます。

重要なシステムと、そうでないシステムの関数が、同じアカウントで枠を取り合うことそのものが問題であれば、アカウントを分けます（{{ch:org}}）。
:::

## シナリオ9：切り替えたのに、古いサーバーにアクセスが来る

土曜の夜に、Webサイトを、古い環境から新しい環境へ、DNSの切り替えで移行しました。切り替えの直後、自分の端末では、新しい環境が表示されました。ところが、月曜になっても、古い環境のサーバーに、アクセスが届き続けています。利用者からは、「先週と同じ、古い画面が表示される」という問い合わせが来ています。切り替えの前、DNSのレコードのTTLは、86400秒でした。切り替えのときに、300秒に変更しました。

```text
$ dig +noall +answer www.example.com
www.example.com.  71523  IN  A  203.0.113.10    ← 古い環境のIPアドレス
```

:::q 障害対応 | 原因と対策
なぜ、古い環境にアクセスが届き続けるのでしょうか。いつまで続きますか。今できることと、次回の移行での対策を答えてください。
:::a
原因：TTLは、DNSの応答を、途中のDNSサーバーや端末が保存しておいてよい時間です。切り替えの前に、古い応答（古いIPアドレス、TTLは86400秒 = 24時間）を受け取っていたDNSサーバーは、その応答を、最大24時間、保存し続けます。切り替えのときにTTLを300秒に変えても、すでに保存されている古い応答には、効きません。新しいTTLが効くのは、保存の期限が切れて、問い合わせ直した後です。

コマンドの結果は、問い合わせたDNSサーバーが、古い応答を、あと71,523秒（約20時間）保存することを示しています。

いつまで続くか：仕組みの上では、切り替えから24時間で、ほとんどが新しい環境に向きます。月曜まで続いているのは、TTLを守らずに長く保存するDNSサーバーや、端末やアプリの側の保存、長時間つなぎ続けている接続などが、考えられます。

今できること：

- 古い環境を、止めずに動かしておく。止めると、古い応答を持つ利用者は、エラーになる
- 古い環境から、新しい環境へ、通信を転送する。または、古い環境の画面に、案内を出す
- 古い環境に届くアクセスの量を見張り、十分に減ってから、止める

次回の対策：

- 切り替えの数日前（今のTTLの時間より前）に、TTLを短く（60〜300秒）しておく。切り替えの時点で、世の中に保存されている応答が、すべて短いTTLのものになる
- 切り替えの後、落ち着いたら、TTLを元に戻す
- 切り替えの後も、古い環境を一定の期間動かしておくことを、計画に入れる
- 古い環境と新しい環境で、同じデータを見られるようにしておく。両方にアクセスが来る期間に、データが食い違わないように

「自分の端末では切り替わった」は、確認になりません。自分が使うDNSサーバーが、たまたま新しい応答を持っているだけです。
:::

## シナリオ10：サーバーが、起動しては消えるのを繰り返す

新しいアプリを、Auto Scalingグループで動かし始めました。構成は、IaCで作りました。サーバーは起動するのですが、4〜5分で終了され、また新しいサーバーが起動する、ということを、延々と繰り返しています。Auto Scalingの履歴には、次のように記録されています。

```text
Terminating EC2 instance: i-0abc...  Cause: an instance was taken out of service
in response to an ELB system health check failure.
```

アプリは、起動してから依頼を受けられるようになるまでに、約4分かかります。ロードバランサーのヘルスチェックは、30秒ごとに行われ、2回続けて失敗すると、異常と判定されます。IaCのコードでは、Auto Scalingのヘルスチェックの種類をELBにしていますが、猶予の時間は指定していません。

:::q 障害対応 | 原因と対策
なぜ、繰り返すのでしょうか。直し方を、2つ以上挙げてください。
:::a
原因：Auto Scalingには、起動した直後のサーバーについて、ヘルスチェックの結果を無視する時間（猶予期間）があります。コードで指定していないため、この時間が、非常に短い（0秒）設定になっています。アプリは、起動に4分かかりますが、その間、ロードバランサーのヘルスチェックには応答できません。Auto Scalingは、起動したばかりのサーバーを、ヘルスチェックに失敗した異常なサーバーとみなして終了し、新しいサーバーを起動します。新しいサーバーも、同じ理由で終了されます。

管理画面から作った場合は、猶予期間に、既定で数分の値が入ります。IaCやCLIで作ると、指定しない限り0になるため、管理画面で試したときには起きなかった問題が、IaCにしたときに現れます。

直し方：

1. 猶予期間を、アプリの起動にかかる時間より、長く設定する（例：360秒）
2. アプリの起動を速くする。必要なソフトウェアを、あらかじめイメージに入れておく。起動時の重い処理を、後に回す
3. ヘルスチェックに応答するものを、アプリの準備の状態と合わせる。準備ができるまでは、「準備中」と答え、準備ができたら「正常」と答える。ロードバランサーは、正常になるまで、通信を送らない
4. 起動の完了を、アプリの側から知らせる仕組み（ライフサイクルフック）を使い、準備ができてから、サービスに組み込む

再発防止：IaCでは、既定値に頼らず、動作に関わる値を、明示的に書く。新しい構成は、検証環境で、サーバーが安定して動き続けることを確かめてから、本番に適用する。短時間に、起動と終了が繰り返されていることを、通知で検知する。

この現象は、サーバーが1台も安定しないため、サービスが、まったく使えない状態になります。また、起動のたびに費用がかかり、気づかないと、無駄な費用が積み上がります。
:::

## シナリオ11：スタックの更新が失敗し、戻すこともできない

CloudFormationで管理している本番の環境に、小さな変更を適用しようとしました。更新は、途中で失敗し、自動的に、元の状態へ戻す処理が始まりました。ところが、その戻す処理も失敗し、スタックは、次の状態で止まりました。

```text
UPDATE_ROLLBACK_FAILED
```

イベントの一覧を見ると、あるセキュリティグループのルールを元に戻そうとして、「そのルールは存在しない」というエラーになっています。調べると、2週間前に、障害対応で、誰かが管理画面から、そのルールを手で削除していました。

:::q 障害対応 | 原因と対策
この状態から、どう回復しますか。同じことを防ぐには、どうしますか。
:::a
原因：CloudFormationは、自分が記録している状態を「正」として、更新や、元に戻す処理を行います。手で削除されたルールは、CloudFormationの記録の上では、まだ存在しています。元に戻す処理で、そのルールを操作しようとしましたが、実際にはないため、失敗しました。スタックは、更新も、元に戻すこともできない状態で止まっています。

回復の手順：

1. イベントの一覧で、元に戻す処理に失敗した資源と、理由を特定する
2. 原因を取り除く。この場合は、CloudFormationが期待する状態に合わせて、手でルールを作り直すか、次の手順で、その資源を飛ばす
3. 「元に戻す処理を続行する」操作を実行する。必要なら、失敗した資源を飛ばす指定をする。飛ばした資源は、CloudFormationの記録の上では、戻ったことになる。実際の状態とずれるため、後で必ず合わせる
4. スタックが、安定した状態（UPDATE_ROLLBACK_COMPLETE）に戻ったことを確かめる
5. ドリフト検出を実行し、記録と、実際の状態のずれを、すべて洗い出す。コードを直して、ずれを解消する
6. その後で、最初に適用しようとした変更を、もう一度行う

やってはいけないこと：あせって、スタックを削除する。本番の資源が、すべて削除されます。

再発防止：

- 管理画面からの手動の変更を、原則として禁止する。本番の権限から、変更の操作を外す
- 障害対応で、やむを得ず手で変更した場合は、その日のうちに記録し、コードに反映する（{{ch:s7}}の章末問題）
- ドリフト検出を、定期的に実行し、ずれを通知する
- 変更の適用の前に、差分に加えて、ドリフトがないことも確かめる

2週間前の手動の変更が、今日の、関係のない変更を止めました。手動の変更の代償は、変更した時点ではなく、後になって現れます。
:::

## シナリオ12：見覚えのないサーバーが、大量に動いている

月曜の朝、AWSから、「お客様のアクセスキーが、公開の場所で見つかりました」という内容のメールが届いていました。管理画面を確かめると、普段は使っていない海外のリージョンで、大きなサーバーが、数十台動いています。金曜の夜に、開発者の1人が、検証用のスクリプトを、公開のリポジトリにpushしていました。スクリプトの中には、IAMユーザーのアクセスキーが、書かれていました。

:::q 障害対応 | 最初の1時間
最初の1時間に行うことを、順に挙げてください。その後に行うことと、根本的な対策も答えてください。
:::a
最初の1時間：

1. 報告する。責任者と、セキュリティの担当に、わかっている事実を伝える。一人で対処しない
2. 漏れたアクセスキーを、無効にする。リポジトリからの削除は、対策にならない。公開された時点で、取得されている
3. そのキーを持つIAMユーザーの権限を確かめる。何ができる権限だったかで、被害の範囲の上限がわかる
4. 攻撃者が作った、入口を探す。新しいIAMユーザー、アクセスキー、ロール、ログイン用のパスワードが、作られていないか。作られていれば、無効にする。これを見落とすと、キーを無効にしても、別の入口から入られ続ける
5. 不正な資源を止める。すべてのリージョンを確かめる。サーバーのほか、関数、コンテナ、データベースなど。証拠として、情報を記録してから止める
6. 操作の記録（CloudTrail）で、そのキーが、いつから、何に使われたかを確かめる。データの読み出し（S3など）がなかったかを、特に確かめる

その後：

- AWSのサポートに連絡する。状況を伝え、対応の指示に従う。不正な利用による料金について、相談する
- 影響の範囲を確定する。データが読み出された可能性があれば、社内の手順に従い、関係者への報告を行う
- 同じキーや、同じ方法で管理されているほかのキーがないかを、確かめる
- 振り返りを行う

根本的な対策：

- 長く使えるアクセスキーを、なくす。人は、IAM Identity Center から、一時的な認証情報で入る。プログラムには、ロールを使う
- リポジトリで、秘密情報の検知を有効にし、pushの時点で止める
- 使わないリージョンを、SCPで塞ぐ（{{ch:org}}）
- 検知の仕組み（GuardDuty）、コスト異常検出、予算の通知を、有効にしておく。金曜の夜の出来事に、月曜の朝まで気づかなかったことも、課題

AWSが漏えいを検知すると、そのキーを持つユーザーに、一部の操作を制限するポリシーを、自動的に付けることがあります。これは、被害を抑えるための応急の措置で、対応が済んだことを意味しません。

開発者を責めても、何も解決しません。問うべきは、「なぜ、スクリプトに書けるような、長く使えるキーが存在したのか」です。
:::

## シナリオ13：急に、すべての依頼が500になった

EC2で動くWebアプリが、深夜2時ごろから、すべての依頼に500のエラーを返すようになりました。CPU使用率は低く、メモリにも余裕があります。サーバーに入って確かめると、次のようになっていました。

```text
$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p1   30G   30G   20K 100% /

$ tail -1 /var/log/app/error.log
OSError: [Errno 28] No space left on device
```

`/var/log/app` の下には、半年分のログが、圧縮されずに残っていました。

:::q 障害対応 | 原因と対策
復旧の手順と、再発を防ぐ対策を答えてください。
:::a
原因：ディスクが、ログでいっぱいになりました。アプリは、ログや一時ファイルを書けなくなり、依頼の処理に失敗しています。標準の監視には、ディスクの使用率が含まれないため、CPUやメモリを見ているだけでは、気づけませんでした。

復旧：

1. 空きを作る。古いログを、S3などに退避してから、削除または圧縮する。どれを消してよいか迷う場合は、まず圧縮する
2. アプリが、自動では回復しない場合は、再起動する
3. 動作を確かめる

台数が複数あり、Auto Scalingで動いているなら、もっと速い方法があります。このサーバーを切り離し、新しいサーバーに入れ替えます。ただし、ほかのサーバーも、同じ時期に起動していれば、まもなく同じ状態になります。全台のディスクの使用率を、すぐに確かめます。

ディスクそのものを大きくすることも、止めずにできます。EBSのボリュームを拡張した後、OSの側で、領域を広げる操作が必要です。ただし、これは原因への対処ではありません。

再発防止：

- ログを、サーバーの外に送る（CloudWatch Logs など）。サーバーの中には、短い期間の分だけを残す
- サーバーの中のログは、決めた世代で、自動的に削除・圧縮する（ログのローテーション）
- ディスクの使用率を、エージェントで取得して監視し、80%で通知する
- サーバーを、長く動かし続けない。定期的に、新しいイメージのサーバーに入れ替えていれば、半年分のログがたまることはない

容量には余裕があるのに、同じエラーが出ることもあります。小さなファイルが大量にあり、ファイルの数の上限に達している場合です。`df -i` で確かめられます。
:::

## シナリオ14：朝から、ブラウザに警告が出る

月曜の朝、利用者から、「サイトを開くと、『この接続は安全ではありません』という警告が出る」という問い合わせが、相次ぎました。サーバーも、アプリも、正常に動いています。ロードバランサーに設定されている証明書を確かめると、有効期限が、昨日で切れていました。この証明書は、2年前に、外部の発行元から購入し、AWS Certificate Manager に取り込んだものです。当時の担当者は、すでに異動しています。

:::q 障害対応 | 原因と対策
すぐに行う対応と、同じことを二度と起こさないための対策を答えてください。
:::a
原因：外部で発行して取り込んだ証明書は、自動では更新されません。期限の前に、新しい証明書を発行し、取り込み直す必要がありますが、その作業を覚えている人が、いませんでした。

すぐに行う対応：

- 最も速いのは、AWS Certificate Manager で、新しい証明書を発行し、ロードバランサーの証明書を、それに差し替えること。ドメインの所有の確認を、DNSで行う方式なら、DNSを自分で管理していれば、短時間で発行できる
- 証明書の種類に、特別な要件（組織の実在の証明など）がある場合は、元の発行元で、更新の手続きを行う。時間がかかるなら、その間の暫定として、上の方法を使えないかを確かめる
- 利用者に、状況と、復旧の見込みを知らせる。警告を無視して進むよう、案内してはいけない

再発防止：

- 証明書を、AWS Certificate Manager で発行する方式に切り替える。DNSによる確認にしておけば、期限の前に、自動で更新される
- ただし、自動の更新にも、条件がある。確認のために作ったDNSのレコードを、消してしまうと、更新に失敗する。そのレコードを、IaCで管理し、「不要なレコード」として消されないようにする
- 取り込んだ証明書を使い続ける場合は、期限までの日数を監視し、30日前、14日前、7日前に、チームの宛先へ通知する。個人の宛先や、個人の予定表に頼らない
- 証明書に限らず、「期限のあるもの」を一覧にする。ドメインの登録、外部のサービスの契約、APIの鍵、OSやデータベースの版の支援の期限。それぞれに、担当と、通知を決める

この障害の本当の原因は、技術ではなく、「2年に1回の作業が、人の記憶に頼っていた」ことです。めったに行わない作業ほど、自動にするか、通知で思い出せるようにします。
:::

## 切り分けの型をまとめる

14のシナリオに共通する、考え方の型を整理します。

| 型 | 内容 | 出てきたシナリオ |
|---|---|---|
| 直前の変更を疑う | 障害の直前に変更があれば、関係がなさそうに見えても、まず疑う | 1、3、4、5、10 |
| 決まった数字に注目する | ちょうど60秒、ちょうど上限の数、といった数字は、設定値や上限値を指している | 2、5、8、9 |
| どこまで届いたかを確かめる | 応答の有無、記録の有無から、処理が、どの部品まで進んだかを絞る | 1、3、6 |
| 上限は、1つではない | CPUに余裕があっても、接続の数、同時実行の数、ディスク、アドレスなど、別の上限に当たる | 5、8、13 |
| 見えていない依存を探す | 運用のための通信、外部に登録したIPアドレス、手動の変更、期限 | 3、4、11、14 |
| エラーの文言を、そのまま読む | 推測の前に、メッセージの全文を読む。答えが書かれていることが多い | 5、6、10、13 |
| 影響を止めてから、調べる | 戻す、切り離す、増やす。原因の究明は、その後 | 2、12、13 |
| 人ではなく、仕組みを直す | 誰の誤りかではなく、なぜ誤りが可能で、なぜ気づけなかったか | 11、12、14 |
