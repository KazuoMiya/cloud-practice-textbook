:::goal
- 構成から月額を見積もり、前提とともに示せる
- 費用を下げる4つの方法（止める、小さくする、買い方を変える、作りを変える）を使い分けられる
- 見落としやすい費用を挙げ、費用を継続して管理する仕組みを設計できる
:::

クラウドの費用は、設計の結果です。構成、台数、動かす時間、データの流れを決めた時点で、費用のほとんどは決まっています。請求が来てから下げようとするより、設計の段階で見積もり、選択肢を比べるほうが、はるかに効果があります。{{ch:secost}}で学んだ基本動作を、この章では設計と運用の仕組みに広げます。

## 見積もりの進め方

1. 部品を書き出す：構成図に出てくるものを、すべて表にする。図に描かれにくいもの（ログ、バックアップ、データ転送、NATゲートウェイ）を忘れない
2. 数量の前提を置く：台数、大きさ、動かす時間、データの量、リクエストの数。わからない数字は、幅を持たせて仮定する
3. 単価を調べて計算する：AWS Pricing Calculator を使う。リージョンによって単価が違う点に注意する
4. 環境ごとに分ける：本番、検証、開発。本番以外は、時間と大きさを減らせる
5. 前提と一緒に示す：数字だけでなく、「何を、どれだけ使う想定か」を必ず添える。前提が変われば、費用も変わる

見積もりは、当てるためではなく、判断するために作ります。「月に約20万円。その6割がデータベース」とわかれば、データベースの構成を見直す価値があると判断できます。

見落としやすい項目（外部へのデータ転送、NATゲートウェイ、パブリックIPv4アドレス、ログとバックアップの保存、AWSサポートの契約料金）は、後の節の表で確かめます。料金はドル建てのため、円で示すときは、前提の為替レートを明記します。

## 費用を下げる4つの方法

効果が大きく、危険が小さい順に検討します。

| 方法 | 内容 | 注意する点 |
|---|---|---|
| 止める | 使っていないものを消す。使わない時間帯は止める | 止めても料金が続くもの（ディスク、スナップショット、固定のIPアドレス）がある |
| 小さくする | 使用率を見て、大きさを実際の負荷に合わせる | 平均ではなく、ピーク時の使用率で判断する。メモリは標準の指標では見えない |
| 買い方を変える | 長く使う分を、割引の契約にする。中断されてもよい処理に、余っている処理能力を安く使う | 契約は、使わなくても支払いが続く。先に「止める」「小さくする」を済ませてから |
| 作りを変える | 管理の手間が少ないサービスに置き換える。キャッシュやCDNで、後ろの負荷と転送を減らす。データを安い保存クラスへ移す | 作り直しの費用と、得られる削減を比べる |

買い方の主な選択肢は次のとおりです。

| 選択肢 | 仕組み | 向いている使い方 |
|---|---|---|
| オンデマンド | 使った分だけ払う。約束なし | 変動する分、短期間の利用、始めたばかりで量が読めない時期 |
| Savings Plans（EC2、Fargate、Lambda向け） | 1年または3年、1時間あたり一定額の利用を約束する代わりに、割引を受ける。支払いは、全額前払い、一部前払い、前払いなしから選ぶ。割引の上限は種類で異なる。インスタンスの系列とリージョンを固定する EC2 Instance Savings Plans で最大72%、固定しない Compute Savings Plans で最大66% | 常に動いている土台の分。Compute Savings Plans は、EC2のほかFargateとLambdaにも適用される |
| Database Savings Plans | 1年、前払いなしで、データベースの利用に1時間あたり一定額を約束する。Aurora、RDS、DynamoDB、ElastiCacheなどに、エンジン、インスタンスの種類、リージョンをまたいで適用される（2025年12月に開始）。割引の上限は、サーバーレスで35%、インスタンスで20%。インスタンスは、第7世代以降が対象 | サーバーレスのデータベースの常時稼働分。インスタンスでは、エンジンや大きさ、リージョンを変える可能性があるもの。構成を変えないなら、リザーブドインスタンスのほうが割引は大きい |
| リザーブドインスタンス | 特定の種類の資源を、1年または3年使う約束をする。対象を固定する代わりに、3年の約束や前払いを選べる | 構成を変える予定のないデータベースなどの常時稼働分。Savings Plans の対象でないサービス |
| スポットインスタンス | 事業者の余っている処理能力を、大幅な割引で使う。必要になれば、2分前の通知で中断される | 中断されてもやり直せる処理（バッチ、検証、台数に余裕を持たせた一部のサーバー） |

対象のサービスと割引率は、追加や変更が続いています。契約の前に、料金のページと、Cost Explorer に表示される推奨で確認します（[Savings Plans の種類](https://docs.aws.amazon.com/savingsplans/latest/userguide/plan-types.html)）。

割引の契約は、「常に使っている最低限の量」に対して結びます。日中だけ増える分や、数か月後になくなるかもしれない分まで契約すると、使っていない時間の分も払うことになります。

## 見落としやすい費用

| 項目 | なぜ見落とすか | 確かめること |
|---|---|---|
| データ転送 | 構成図に描かれない | インターネットへ出る量。リージョンをまたぐ量。AZをまたぐ通信にも料金がかかる |
| NATゲートウェイ | 時間の料金に加え、通過したデータの量にも料金がかかる | AWSのサービスへの通信を、VPCエンドポイントに置き換えられないか |
| ログ | 取り込む量に料金がかかる。保存期間の既定が無期限のものがある | 出力する量を見直す。保存期間を決める |
| バックアップとスナップショット | 自動で増え続ける | 保持する世代を決める。不要になった資源のものが残っていないか |
| パブリックIPv4アドレス | 1つあたりは小さい | 数が多い構成では、積み上がる |
| サポートの契約 | 利用料に応じて増える | 契約の種類と計算の方法 |
| 本番以外の環境 | 本番と同じ大きさで、止めずに動いている | 検証や開発の合計が、本番を上回っていないか |

## 費用を、業務の単位で見る

月額の総額だけでは、増えたのが良いことなのか悪いことなのかがわかりません。利用者が2倍になって費用が1.5倍になったのなら、効率は良くなっています。「注文1件あたり」「利用者1人あたり」「処理1万件あたり」のように、業務の単位で割った費用を追うと、設計の良し悪しと、事業にとっての採算が見えるようになります。

## 続ける仕組み

費用の最適化は、一度の作業ではなく、続ける活動です。次の仕組みを、最初から設計に含めます。

- 誰の費用かがわかる：タグの決まりを作り、守らせる。アカウントを、システムや環境ごとに分ける（{{ch:org}}）
- 増えたら気づく：予算の通知と、異常の検知を設定する。通知の宛先は、その費用に責任を持つチームにする
- 定期的に見直す：月に一度、費用の内訳と、使用率の低い資源を確認する場を持つ
- 作る人が費用を知る：開発や構築の担当者が、自分の作ったものの費用を見られるようにする。費用を、経理や管理部門だけの関心事にしない

:::sum
- 費用は設計の結果。構成を決める段階で見積もり、前提とともに示す
- 下げる順は、止める、小さくする、買い方を変える、作りを変える
- 割引の契約は、常に使う最低限の量に対して結ぶ。先に無駄をなくしてから
- 総額だけでなく、業務の単位あたりの費用を追う。費用の管理は、続ける仕組みとして設計する
:::

## 章末問題

:::q 計算 | 月額を見積もる
次の構成の月額を、演習用の仮単価で見積もってください。1か月は730時間とします。

| 部品 | 数量 | 仮単価 |
|---|---|---|
| アプリサーバー | 4台、常時 | 1台1時間 0.10ドル |
| ロードバランサー | 1つ、常時 | 1時間 0.025ドル |
| データベース（マルチAZ） | 1組、常時 | 1時間 0.40ドル |
| データベースの保存領域 | 200GB | 1GBあたり月 0.25ドル |
| NATゲートウェイ | 2台、常時 | 1台1時間 0.06ドル、通過データ1GBあたり 0.06ドル |
| NATゲートウェイを通るデータ | 月300GB | 上記 |
| インターネットへのデータ転送 | 月500GB | 1GBあたり 0.11ドル |
| ログの取り込み | 月100GB | 1GBあたり 0.70ドル |

最も金額の大きい項目と、最初に見直す候補を挙げてください。
:::a
| 部品 | 計算 | 金額 |
|---|---|---|
| アプリサーバー | 4 × 730 × 0.10 | 292.0ドル |
| ロードバランサー | 730 × 0.025 | 18.3ドル |
| データベース | 730 × 0.40 | 292.0ドル |
| 保存領域 | 200 × 0.25 | 50.0ドル |
| NATゲートウェイ（時間） | 2 × 730 × 0.06 | 87.6ドル |
| NATゲートウェイ（データ） | 300 × 0.06 | 18.0ドル |
| データ転送 | 500 × 0.11 | 55.0ドル |
| ログ | 100 × 0.70 | 70.0ドル |
| 合計 | | 約883ドル |

最も大きいのは、アプリサーバーとデータベース（各292ドル）です。見直す候補の例：

- アプリサーバー：使用率を確かめ、大きさと台数が合っているか。夜間に減らせるか。常時動く分に割引の契約を使う
- ログ：月100GBは、出力しすぎの可能性がある。開発用の詳細なログが本番で出ていないか
- NATゲートウェイ：通過しているデータの中身を確かめる。S3などへの通信なら、VPCエンドポイントに置き換える
- データ転送：画像などをCDNから返せば、単価と量の両方が変わる

金額の大きい順に見ることと、「その数量は妥当か」を疑うことが要点です。
:::

:::q 判断 | どこまで割引の契約にするか
あるシステムは、アプリサーバーを常に10台動かし、平日の日中（月に約220時間）だけ、さらに10台を追加しています。割引の契約（1年の約束で、仮に30%引き）を、10台分にする案と、20台分にする案があります。1台1時間の単価を、仮に0.10ドルとします。1か月を730時間として、それぞれの月額を計算し、どちらが安いかを答えてください。
:::a
契約なしの場合：常時10台 = 10 × 730 × 0.10 = 730ドル。日中の追加10台 = 10 × 220 × 0.10 = 220ドル。合計950ドル。

10台分を契約する場合：常時10台 = 730 × 0.7 = 511ドル。追加の10台はオンデマンドで220ドル。合計731ドル。

20台分を契約する場合：契約は、使っても使わなくても、20台分を730時間分支払う。20 × 730 × 0.10 × 0.7 = 1,022ドル。

10台分の契約が最も安く、20台分の契約は、契約なしよりも高くなります。追加の10台は、月の約30%の時間しか動いていないため、30%引きの単価で730時間分を払うと、かえって損になります。割引の契約は、「ほぼ常に使っている量」までにとどめるのが原則です。
:::

:::q 計算 | 夜間と休日に止める効果
開発環境のサーバー6台（1台1時間 0.10ドルの仮単価）を、24時間365日動かしています。これを、平日の8時から20時だけ動かすようにします。1か月を730時間、平日を22日とします。

1. 変更の前後で、サーバーの月額はいくらになりますか
2. 止めている間も料金が続くものを、2つ挙げてください
:::a
1. 変更前：6 × 730 × 0.10 = 438ドル。変更後：6 × 22日 × 12時間 × 0.10 = 158.4ドル。約64%の削減
2. サーバーのディスク（EBS）の料金。割り当てたままの固定のパブリックIPアドレス。このほか、ロードバランサーやNATゲートウェイは、サーバーを止めても動き続ける。データベースを止めた場合も、保存領域とバックアップの料金は続く

開発環境や検証環境は、使う時間が全体の3分の1程度であることが多く、止めるだけで大きく下がります。止めて、起動し直しても正しく動くように作っておくことは、障害からの回復の練習にもなります。
:::

:::q 判断 | スポットに向く処理、向かない処理
次の4つのうち、スポットインスタンス（余っている処理能力を安く使う代わりに、2分前の通知で中断されることがある）に向くものと、向かないものを分けてください。

1. 途中から再開できる、夜間の動画の変換
2. 1台だけで動いている、社内の業務データベース
3. 20台で動くWebサーバー群のうちの一部
4. CI/CDで、コードの変更のたびに動く自動テスト
:::a
- 向く：1、3、4
- 向かない：2

1と4は、中断されてもやり直せる処理です。3は、一部が中断されても残りで処理を続けられるよう、台数に余裕を持たせ、オンデマンドや契約の分と混ぜて使います。複数の種類やAZに分散させると、同時に中断される危険を下げられます。

2は、中断されると業務が止まり、データを失うおそれもあります。状態を持ち、代わりのない部品には使いません。

判断の軸は「中断されたら、自動でやり直せるか」「1つが消えても、全体が動き続けるか」です。これは、{{ch:s3}}で学んだ「サーバーを、いつでも捨てて作り直せるものとして扱う」考え方そのものです。
:::
