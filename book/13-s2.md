:::goal
- VPCのアドレス設計を自分で書き、サブネット・ルートテーブル・ゲートウェイを1つずつ作れる
- ルートテーブルの中身だけを見て、サブネットの性質と通信の行き先を説明できる
- NATゲートウェイの置き方について、可用性と費用の兼ね合いを説明できる
:::

{{ch:net}}で学んだネットワークを、自分の手で組み立てます。管理画面には、VPCと必要な部品を一度に作る機能もありますが、1回目は部品を1つずつ作ってください。どの部品が何のためにあるのかは、自分でつないで初めて腑に落ちます。



## 先にアドレス設計を書く

作る前に、次のようなアドレス設計を自分で書いてください。この表を自分で埋められること自体が、設計の練習です。

| サブネット | AZ | CIDRの例 | ルートテーブル |
|---|---|---|---|
| パブリックA | AZ-a | 10.0.0.0/24 | 0.0.0.0/0 → IGW |
| パブリックC | AZ-c | 10.0.1.0/24 | 0.0.0.0/0 → IGW |
| アプリA | AZ-a | 10.0.10.0/24 | 0.0.0.0/0 → NAT |
| アプリC | AZ-c | 10.0.11.0/24 | 0.0.0.0/0 → NAT |
| DB-A | AZ-a | 10.0.20.0/24 | 外部への経路なし |
| DB-C | AZ-c | 10.0.21.0/24 | 外部への経路なし |

VPC全体は 10.0.0.0/16 とし、どのルートテーブルにも「10.0.0.0/16 → local」が自動で入ります。

## 進め方

1. 構成図を描き、上の表を自分で作る
2. VPCを作成し、サブネットを6つ作る。管理画面には一式をまとめて作る機能もあるが、1回目は部品を1つずつ作る
3. インターネットゲートウェイを作ってVPCに取り付け、パブリック用のルートテーブルに 0.0.0.0/0 → IGW を追加する
4. NATゲートウェイをパブリックサブネットに1つ作り、アプリ用のルートテーブルに 0.0.0.0/0 → NAT を追加する
5. 各サブネットに正しいルートテーブルを関連付ける

作ったものは、CLIでも確かめておきます。管理画面の表示と見比べると、どの画面の項目がどのAPIの値に当たるのかがわかります。

```bash
# VPCのルートテーブルと、その中の経路を表示する
aws ec2 describe-route-tables --filters Name=vpc-id,Values=vpc-xxxxxxxx

# サブネットごとの、AZとCIDRを一覧にする
aws ec2 describe-subnets --filters Name=vpc-id,Values=vpc-xxxxxxxx \
  --query 'Subnets[].[SubnetId,AvailabilityZone,CidrBlock]' --output table
```

## つまずきやすい点

| 症状 | よくある原因 | 確かめ方 |
|---|---|---|
| ルートを追加したのに効かない | サブネットをルートテーブルに関連付けていない。関連付けのないサブネットは、VPCの「メインルートテーブル」に従う | ルートテーブルの「サブネットの関連付け」を確認する |
| インターネットゲートウェイへの経路を追加できない | インターネットゲートウェイを作っただけで、VPCに取り付けていない | 状態が「取り付け済み（Attached）」かを確認する |
| プライベートサブネットから外に出られない | NATゲートウェイをプライベートサブネットに作ってしまった。NATゲートウェイ自身が外に出るには、インターネットゲートウェイへの経路があるサブネットに置く必要がある | NATゲートウェイのサブネットと、そのルートテーブルを確認する |
| サブネットを作れない | CIDRが、VPCの範囲の外にあるか、ほかのサブネットと重なっている | アドレス設計の表と見比べる |
| AZの名前が人によって違う | AZの名前（ap-northeast-1a など）と実際の拠点の対応は、AWSアカウントごとに異なることがある | アカウントをまたいで同じ拠点を指すときは、AZ ID（apne1-az4 など）で確認する |

## 確認ポイント

- ルートテーブルの中身だけを見て、各サブネットがパブリックかプライベートかを判定できる
- DB用サブネットに外部への経路を作らない理由を説明できる
- 本番ではNATゲートウェイをAZごとに置くことが多い理由（1つのAZの障害で外部への通信が止まらないように）を説明できる

:::warn 費用
NATゲートウェイは時間料金がかかります（{{ch:env}}）。学習では1つだけ作り、使う日だけにしてください。S3やDynamoDBへの通信だけなら、無料のゲートウェイ型VPCエンドポイントを使う方法もあります。
:::

## 実技の合格基準

次のすべてを、コマンドの出力や画面で示せたら合格です。

| 番号 | 確かめること | 合格の状態 |
|---|---|---|
| 1 | サブネットが設計どおりにできている | 6つあり、CIDRがアドレス設計の表と一致し、AZが2種類ある |
| 2 | すべてのサブネットが、意図したルートテーブルに関連付けられている | 6つのサブネットのIDが、いずれかのルートテーブルの Subnets に1回ずつ現れる。メインルートテーブルに任せたサブネットがない |
| 3 | 経路が設計どおりになっている | パブリック用は 0.0.0.0/0 → igw-、アプリ用は 0.0.0.0/0 → nat-、DB用は local だけ |
| 4 | NATゲートウェイがパブリックサブネットにある | State が available で、SubnetId がパブリックサブネットのものである |
| 5 | 片付けが済んでいる | NATゲートウェイが deleted になるか、一覧から消えている。学習用のElastic IPが残っていない |

```bash
VPC_ID='自分のVPCのID'

# 1
aws ec2 describe-subnets --filters Name=vpc-id,Values="$VPC_ID" \
  --query 'Subnets[].[SubnetId,AvailabilityZone,CidrBlock]' --output table
# 2、3
aws ec2 describe-route-tables --filters Name=vpc-id,Values="$VPC_ID" \
  --query 'RouteTables[].{Subnets:Associations[].SubnetId,Routes:Routes[].[DestinationCidrBlock,GatewayId,NatGatewayId]}'
# 4
aws ec2 describe-nat-gateways --filter Name=vpc-id,Values="$VPC_ID" \
  --query 'NatGateways[].[NatGatewayId,SubnetId,State]' --output table
# 5（片付けの後）
aws ec2 describe-nat-gateways --filter Name=vpc-id,Values="$VPC_ID" --query 'NatGateways[].State'
aws ec2 describe-addresses --query 'Addresses[].[PublicIp,AllocationId,AssociationId]' --output table
```

提出するもの：自分で書いたアドレス設計の表と構成図、1〜5の出力。

## わざと壊してみる

:::lab
アプリ用のルートテーブルから「0.0.0.0/0 → NATゲートウェイ」の経路を削除し、その状態のまま次のステップ3に進んでみてください。サーバーは起動しますが、Webサーバーのソフトウェアが入らず、Session Manager にもつながりません。サーバーが外部に出られないと何が起きるかを観察し、原因がルートテーブルにあることを、{{ch:net}}の「つながらないときの確認順」に沿って特定してから、経路を元に戻します。この体験は、{{ch:ts}}のシナリオ3と4の予習になります。
:::

## 片付け

NATゲートウェイを削除し、その後に残るElastic IPを解放します。VPCを丸ごと消す場合は、中の部品から順に削除します。

## 本番ではどう変わるか

| 項目 | 学習での構成 | 本番で検討すること |
|---|---|---|
| NATゲートウェイ | 1つのAZに1台 | AZごとに1台ずつ置く。1つのAZの障害で、ほかのAZのサーバーまで外部に出られなくなるのを防ぐ。1つで複数のAZにまたがって動くリージョナルNATゲートウェイという種類もある |
| AWSのサービスへの通信 | NATゲートウェイ経由 | VPCエンドポイントを使い、インターネットを通らずに届ける。S3とDynamoDB向けのゲートウェイ型は無料。それ以外のインターフェイス型は時間と通信量で課金される |
| アドレスの範囲 | 10.0.0.0/16 を自由に使う | 社内やほかのVPCと重ならない範囲を、管理者から割り当ててもらう |
| 通信の記録 | なし | VPCフローログを有効にし、許可・拒否された通信を記録する |
| AZの数 | 2つ | 3つを使う構成も多い。1つのAZが止まったとき、残りで負荷を受けきれるかで決める（{{ch:ha}}） |
| 複数のVPC | 1つだけ | アカウントや環境ごとにVPCを分け、必要に応じてつなぐ（{{ch:xnet}}） |

:::sum
- VPCは、アドレス設計を先に書いてから作る。範囲は後から変えにくい
- サブネットの性質は、関連付けたルートテーブルで決まる。関連付けを忘れるとメインルートテーブルに従う
- データベース用のサブネットには、外部への経路を作らない
- NATゲートウェイは置いてあるだけで費用がかかる。学習では使う日だけ作り、本番ではAZごとの配置を検討する
:::

## 章末問題

:::q 設計 | アドレスを割り当てる
VPCに 10.20.0.0/16 が割り当てられました。3つのAZを使い、それぞれに「パブリック」「アプリ」「DB」の3種類のサブネットを作ります。アプリ用のサブネットでは、将来コンテナを多数動かすため、1つのサブネットあたり1,000個以上のアドレスが必要です。9つのサブネットのCIDRを決めてください。
:::a
解答例：

| 種類 | AZ-a | AZ-c | AZ-d | 大きさ |
|---|---|---|---|---|
| パブリック | 10.20.0.0/24 | 10.20.1.0/24 | 10.20.2.0/24 | 各256個 |
| アプリ | 10.20.16.0/20 | 10.20.32.0/20 | 10.20.48.0/20 | 各4,096個 |
| DB | 10.20.8.0/24 | 10.20.9.0/24 | 10.20.10.0/24 | 各256個 |

考え方は次のとおりです。

- アプリ用は1,000個以上が必要なので、/22（1,024個、使えるのは1,019個）以上にする。余裕を見て /20 とした
- /20 の範囲は、第3オクテットが16の倍数（0、16、32、48…）から始まる。10.20.16.0/20 は 10.20.16.0〜10.20.31.255
- パブリックとDBは、置くものが少ないので /24 で足りる
- 種類ごとに範囲をまとめておくと、後から「アプリ用は 10.20.16.0〜10.20.63.255」のように説明しやすい
- 全体の半分以上を未使用のまま残してあり、将来の追加に備えられる

範囲が重なっていないこと、境界が正しいことを、必ず自分で計算して確かめてください。割り切れない位置から /20 を始める（例：10.20.10.0/20）ことはできません。
:::

:::q 判断 | NATゲートウェイを何台置くか
2つのAZにアプリサーバーを置く構成で、NATゲートウェイを1台にする案と、AZごとに1台ずつ計2台にする案があります。1台あたりの費用を月45ドル（演習用の仮単価、通信量の料金は除く）とします。

1. それぞれの月額はいくらですか
2. 1台の案で、NATゲートウェイのあるAZが止まると何が起きますか
3. どのような要件なら、1台の案を選んでもよいですか
:::a
1. 1台の案は45ドル、2台の案は90ドル
2. もう一方のAZのアプリサーバーは動き続けるが、外部への通信ができなくなる。外部のAPIを呼ぶ処理、更新プログラムの取得、VPCエンドポイントを使っていないAWSサービスへの通信が失敗する。新しいサーバーの起動時に外部からソフトウェアを取得する作りなら、台数の回復もできない
3. たとえば、検証環境や開発環境である場合、アプリが外部への通信を必要としない場合（AWSサービスへの通信はVPCエンドポイントで足りている場合）、外部への通信が一時的に止まっても業務に影響しない場合

差額は月45ドルです。「AZの障害時にも動き続ける」ことを要件にしているのに、NATゲートウェイだけが1台、という構成は、見落とされやすい単一障害点です。
:::

:::q 説明 | 経路のないサブネットとデータベースの保守
データベース用のサブネットには、外部への経路がありません。それでも、RDSの修正プログラムの適用やバックアップは行われます。なぜでしょうか。
:::a
RDSの保守（修正プログラムの適用、バックアップの取得、障害時の切り替えなど）は、事業者が管理する仕組みを通じて行われ、利用者のVPCのルートテーブルを通りません。利用者のサブネットに置かれるのは、アプリが接続するための出入口（ネットワークインターフェイス）だけです。

このため、マネージドサービスのデータベースは、外部への経路を持たないサブネットに置くことができます。一方、EC2に自分でデータベースを入れた場合は、OSやデータベースの更新プログラムを取得する経路を、利用者が用意しなければなりません。責任共有モデルの違いが、ネットワークの設計にも表れる例です。
:::

:::q 確認 | 関連付けを忘れたサブネット
新しく作ったサブネットを、どのルートテーブルにも関連付けませんでした。このサブネットはどのルートテーブルに従いますか。それが事故につながるのは、どのような場合ですか。
:::a
VPCのメインルートテーブルに従います。

事故につながるのは、メインルートテーブルにインターネットゲートウェイへの経路が入っている場合です。プライベートのつもりで作ったサブネットが、意図せずパブリックになります。逆に、メインルートテーブルに外部への経路がなければ、パブリックのつもりのサブネットが外部とつながらない、という不具合になります。

これを防ぐために、メインルートテーブルには外部への経路を入れず、すべてのサブネットを専用のルートテーブルに明示的に関連付ける、という決まりにしておくのが定石です。関連付けを忘れても、安全な側（外部につながらない）に倒れます。
:::
