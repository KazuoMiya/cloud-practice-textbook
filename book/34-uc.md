## ケース1：社内向けの申請システム

:::req
- 社員300人が、平日9時〜18時に使う。夜間と休日は使わない
- 止まっても半日以内に戻ればよい。データは前日の状態まで戻せればよい
- 氏名や所属などの個人情報を扱う
- 社外からは使わない（社内ネットワークかVPN経由のみ）
- 予算はできるだけ抑えたい
:::

:::think
- 復旧の目標が半日・前日分なら、マルチAZは本当に必要か
- 使わない夜間と休日の費用をどう減らすか
- インターネットに公開しないシステムを、どう社内からだけ使えるようにするか
:::

:::dir
内部向けのALB（インターネットに公開しない種類）と、Auto Scalingで最小1台のEC2、単一AZのRDS（自動バックアップあり）を、Site-to-Site VPNで社内ネットワークとつなぐ構成が考えられます。夜間と休日の費用は、次のように抑えます。EC2は、Auto Scalingのスケジュールされたスケーリングで、夜間と休日は最小・希望・最大の台数を0にし、業務開始前に日中の設定へ戻します。これは既存のEC2の停止と再開ではなく、終了と新規起動になるため、起動テンプレートとユーザーデータ（またはAMI）だけで環境が元どおりに立ち上がることが前提です。RDSは別途、停止と起動をスケジュールします。
:::

:::pit
費用のために可用性を下げる判断は、必ず記録し、利用部門の合意を取ってください。「止まっても半日以内に戻せればよい」は、実際に半日以内で戻せることを、復元の練習で確かめて初めて成り立ちます。また、Auto Scalingの配下にあるEC2を個別に停止すると、Auto Scalingが異常とみなして新しいEC2を起動します。夜間の停止は、台数の設定で行ってください。
:::

:::q 質問 | 顧客に確かめること
ケース1の要件を読んで、設計を始める前に顧客に確かめたいことを、5つ挙げてください。
:::a
解答例：

1. 「半日以内に戻ればよい」は、どの時間帯の障害でも同じか。月末や期末など、止まると特に困る時期はあるか
2. 社員はどこから使うか。本社だけか、支店や在宅からも使うか。社内のネットワークとVPNは、すでにあるか
3. 社員の認証はどうするか。会社の認証基盤（Microsoft Entra ID など）と連携するか
4. 申請に添付するファイルはあるか。大きさと、保存する期間は
5. データの保存期間と、削除の決まりはあるか。個人情報について、社内の規程で求められる管理（暗号化、操作の記録）は何か
6. 構築の後、誰が運用するか。夜間に起動と停止を自動で行うことに、支障はないか
7. 予算の上限は、月額でいくらか

要件に書かれた言葉（「半日」「前日」「できるだけ抑えたい」）を、条件と数字で確かめる質問になっているかを確認してください。
:::

## ケース2：キャンペーンの特設ページ

:::req
- 新商品キャンペーンの特設ページ。告知の直後の数時間に、平常時の数十倍のアクセスが集中する見込み
- 中身は画像とテキストが中心で、問い合わせフォームが1つある
- 公開期間は2か月
:::

:::think
- アクセスの急増に、サーバーの台数を増やして耐えるのか、サーバーを持たない仕組みで受けるのか
- フォームへのいたずらや大量送信をどう防ぐか
- 期間が終わった後の片付けをどう確実にするか
:::

:::dir
画像とページはS3とCloudFrontで配信し、フォームはAPI GatewayとLambda、DynamoDBのサーバーレスで受ける構成が向いています。このとき、API GatewayはREST APIを選び、APIのステージにAWS WAFを関連付けて、同じ相手からの大量送信を制限します。ステップ6で使ったHTTP APIには、WAFを直接関連付けられません。全体をIaCで管理すると、期間終了後の削除作業をまとめやすくなります。削除後は、保持設定で残ったもの、バックアップ、削除に失敗したもの（中身が残ったS3バケットなど）がないか確認してください。
:::

:::pit
Lambdaには、同時に動ける数の上限（アカウントごとの上限値）があります。告知前に上限値を確認し、必要なら引き上げを申請し、負荷試験で確かめてください。
:::

:::q 設計 | フォームへの大量送信を防ぐ
ケース2で、問い合わせフォームへのいたずらや、プログラムによる大量送信に備える手段を、層を分けて3つ以上挙げてください。
:::a
解答例：

| 層 | 手段 |
|---|---|
| 入口 | AWS WAFで、同じ相手からの短時間の大量のリクエストを制限する。プログラムによるアクセスを判定する機能を使う |
| API | API Gatewayで、全体の呼び出しの頻度に上限を設ける。上限を超えた分は、関数まで届かない |
| 画面 | 人による操作かどうかを確かめる仕組みを、フォームに入れる |
| 関数 | 入力の長さと形式を検査する。同じ内容の連続した送信を、受け付けない |
| 費用と量 | 関数が同時に動く数に、上限を設ける。予算の通知を設定する |

サーバーレスの構成は、アクセスの急増には強い一方、「来た分だけ処理して、来た分だけ課金される」ため、不正な大量送信が、そのまま費用になります。上限を設けることは、可用性のためだけでなく、費用を守るためでもあります。
:::

## ケース3：画像のアップロードとサムネイルの自動作成

:::req
- 利用者がアップロードした写真から、サムネイルを自動で作る
- 件数は1日に数百〜数千件で、時間帯によって波がある
- 元の画像は1年間保存し、その後は安く長期保存したい
:::

:::think
- アップロードされたことを、どうやって処理のきっかけにするか（イベント駆動）
- 処理に失敗した画像を、どうやって後からやり直すか
- 時間がたった画像を、安い保存方法へどう移すか
:::

:::dir
アプリは署名付きURLを発行し、利用者がS3へ直接アップロードします。S3のイベント通知をSQS（キュー）に送り、Lambdaがキューから取り出してサムネイルを作り、別のバケットに保存します。失敗が続いたものはデッドレターキューに分けて、後から調査・再処理します。保存期間は、S3のライフサイクルルールで、1年後に長期保存向けのストレージクラスへ自動で移します。
:::

:::pit
サムネイルの保存先を、元画像と同じバケットの同じ場所にすると、保存のたびにイベントが発生し、処理が無限に繰り返されます。保存先は必ず分けてください。
:::

{{fig:pipeline|ケース3の処理の流れ。キューを挟むことで、失敗したものをやり直せ、処理の速さも調整できる}}

:::q 説明 | なぜS3からLambdaを直接呼ばないのか
S3のイベント通知は、Lambdaを直接呼び出すこともできます。ケース3で、あえてSQSを間に挟む利点を、3つ挙げてください。
:::a
解答例：

1. やり直しやすい：処理に失敗したメッセージはキューに残り、再び処理される。失敗が続いたものは、デッドレターキューに分けて、原因を直した後に戻せる
2. 処理の速さを調整できる：一度に大量のアップロードがあっても、キューにためておき、関数が同時に動く数を抑えながら、順に処理できる。関数の同時実行の上限を使い切って、ほかの関数を止めることを防げる
3. 止めて直せる：関数に問題が見つかったとき、処理を一時的に止めても、メッセージはキューに残る。直してから再開すれば、取りこぼしがない

直接呼び出す形でも、失敗時の再試行と、失敗したイベントの退避先は設定できます。件数が少なく、処理が軽ければ、それで足ります。件数に波があり、失敗の調査とやり直しが重要なら、キューを挟みます。
:::

## ケース4：通販サイト

:::req
- 会員は10万人。平常時は毎秒30件ほどのアクセスがあり、月に一度のセールでは、開始から30分間、その10倍になる
- 決済は、外部の決済サービスを使う。カードの番号は、自社では保持しない
- 在庫を超えて売ってはいけない
- 注文の受け付けは、15分以内に復旧したい。受け付けた注文は、失えない
- 商品を、名前や特徴の言葉で検索できる
:::

:::think
- セールの開始の瞬間の急増に、どう備えるか
- 「在庫を超えて売らない」ことと、速さを、どう両立させるか
- 注文の後の処理（メール、出荷の連携）を、注文の受け付けと、どう切り離すか
:::

:::dir
入口にCloudFrontとAWS WAFを置き、画像と商品の一覧はCDNから返します。アプリは、ALBの後ろのコンテナ（ECSのFargate）で、複数のAZに分けて動かします。セールの前には、予定に合わせて台数を増やしておきます。データベースはAuroraのマルチAZ構成とし、商品の表示などの読み取りは、読み取り用の複製とキャッシュ（ElastiCache）に逃がします。在庫の引き当てと注文の確定だけは、プライマリのデータベースで、まとめて矛盾なく行います。注文が確定したら、その事実をキュー（SQS）に入れ、メールの送信や出荷の連携は、後ろの処理が自分の速さで行います。検索は、商品のデータの写しを、全文検索のサービス（OpenSearch Service）に持ちます。
:::

:::pit
キャッシュした在庫の数で、注文を確定してはいけません。画面の表示には使えますが、確定のときは、必ずデータベースで確かめます。また、決済サービスの応答が遅れて利用者がボタンを2回押す、アプリが再試行する、といった場合に、決済が二重に行われないよう、注文ごとに一意の番号を付けて、同じ番号の決済は1回だけにします。台数の自動調整は、数秒で10倍になる急増には追いつきません。
:::

:::q 計画 | セールの開始に備える
ケース4で、セールの開始に向けた準備を、「1週間前まで」「前日」「開始の1時間前」「開始後」に分けて挙げてください。
:::a
解答例：

- 1週間前まで：前回のセールの記録から、ピーク時の量を見積もる。本番に近い環境で負荷試験を行い、どの部品が最初に詰まるかを確かめる。上限値（クォータ）が、必要な最大の量を上回っているかを確かめ、足りなければ引き上げを申請する。データベースの接続の数が、台数を増やした後でも上限に収まるかを確かめる
- 前日：セールの商品の一覧と画像が、CDNにキャッシュされるようにしておく。当日の体制（誰が見張り、誰が判断するか）と、連絡の手段を確かめる。危険のある変更を、セールが終わるまで止める
- 1時間前：アプリの台数を、ピークに必要な数まで増やす。データベースの読み取り用の複製を増やす。ダッシュボードを開き、指標が平常であることを確かめる
- 開始後：エラーの割合、応答時間、データベースの負荷、キューにたまった件数を見張る。受けきれない場合に備え、利用者に順番に待ってもらう画面へ切り替える手段を、用意しておく。落ち着いたら、台数を戻す。振り返りを行い、実際の量と、見積もりの差を記録する

急増が予想できるなら、「増える仕組み」に頼らず、「先に用意する」のが基本です。
:::

## ケース5：複数の企業が使う業務SaaS

:::req
- 企業向けの業務アプリを、SaaSとして提供する。利用する企業（テナント）は、現在200社。3年で2,000社を見込む
- ある企業のデータが、ほかの企業から見えることは、絶対にあってはならない
- 大口の顧客の一部は、「自社のデータは、ほかの企業と分けて保存してほしい」と求めている
- 1社の大量の処理で、ほかの企業の応答が遅くなることは避けたい
- 企業ごとの利用量を把握し、料金に反映したい
:::

:::think
- 企業ごとに環境を分けるか、共有するか。その間に、どのような選択肢があるか
- 「どの企業の利用者か」を、どこで確かめ、どう伝えていくか
- 企業の数が10倍になったとき、運用の手間は、何に比例するか
:::

:::dir
分け方には、大きく3つあります。企業ごとに、アプリとデータベースを丸ごと用意する方式は、分離は強いものの、企業の数に比例して費用と運用が増えます。全企業で共有し、データに企業の番号を付けて区別する方式は、効率はよいものの、区別を誤ると漏えいにつながります。現実的には、標準の企業は共有の環境に置き、分離を求める大口の顧客だけを専用の環境に置く、という組み合わせにします。どの方式でも、利用者の認証の結果（トークン）に企業の番号を含め、アプリは、そこから得た番号だけを信用します。画面から送られてきた番号は、信用しません。企業ごとに、呼び出しの頻度の上限を設け、記録と指標にも企業の番号を付けて、利用量と、問題の切り分けに使います。
:::

:::pit
共有の方式で、企業の区別を、アプリの問い合わせの条件だけに頼ると、条件を1か所書き忘れただけで、他社のデータが見えます。データベースの側でも、企業の番号による行の制限をかけるなど、二重に守ります。また、専用の環境を個別の作り込みで増やすと、環境ごとに版や設定がずれ、運用できなくなります。専用の環境も、共有の環境と同じコードから、同じ手順で作れるようにします。
:::

:::q 比較 | 分け方を比べる
「企業ごとに丸ごと分ける」方式と、「全企業で共有する」方式を、分離の強さ、1社あたりの費用、企業を追加する手間、版の更新、1社の高負荷の影響、の5つの観点で比べてください。
:::a
| 観点 | 企業ごとに分ける | 全企業で共有する |
|---|---|---|
| 分離の強さ | 強い。環境やアカウントの境界で分かれる | アプリとデータベースの制御に依存する。誤りが漏えいに直結する |
| 1社あたりの費用 | 高い。小さな企業でも、最低限の資源が要る | 低い。資源を全体で分け合う |
| 企業を追加する手間 | 環境の作成が必要。自動化が前提 | 登録するだけ |
| 版の更新 | 環境の数だけ、適用が必要。段階的に適用しやすい反面、版がずれやすい | 1回で全体に適用される。問題があれば、全社に影響する |
| 1社の高負荷の影響 | ほかの企業に及ばない | 及ぶ。企業ごとの上限で抑える |

どちらかが優れているのではなく、顧客の求めと、料金に見合うかで選びます。専用の環境は、それに見合う料金の設定とセットで提供します。
:::

## ケース6：基幹システムの移行

:::req
- オンプレミスで動く販売管理システム。Windowsのサーバー15台と、Oracle Database
- 機器の保守が、10か月後に切れる
- 止められるのは、土曜と日曜だけ
- 月末の締めのバッチ処理に、現在8時間かかっている
- 全国の300の拠点から、社内のネットワーク経由で使っている
- ほかの社内システムとの連携が、20本ある
:::

:::think
- 10か月という期限の中で、どの移行戦略を選ぶか
- 300の拠点からの通信を、どうつなぐか。いつ手配を始めるか
- 20本の連携を、どう調べ、どの順で切り替えるか
:::

:::dir
期限が決まっているため、アプリは大きく変えずに移します（リホスト）。データベースは、運用の負担を減らすためにマネージドサービスへ置き換える案（リプラットフォーム）と、変更の危険を避けてそのまま移す案を、ライセンスの条件と、試験にかけられる期間で比べます。社内との接続は、Direct Connect を2つの拠点に引くか、1本とVPNの予備にします。回線の手配には時間がかかるため、最初に着手します。連携は、文書だけでなく、実際の通信の記録から洗い出します。データは、事前に写して変更を反映し続け、週末に切り替えます。切り替えの手順は、少なくとも2回、通しで練習します。
:::

:::pit
文書に載っていない連携が、切り替えの後に見つかります。深夜のファイルの受け渡しや、相手のシステムの設定に書き込まれたIPアドレスが典型です。Oracle のライセンスは、動かす環境によって必要な数が変わるため、早い段階で確かめます。月末のバッチは、保存領域の読み書きの速さに左右されることが多く、移行後に時間内に終わるかを、本番と同じ量のデータで試す必要があります。
:::

:::q 計画 | 10か月の工程を組む
ケース6について、10か月の大まかな工程を、月単位で組んでください。最初の月に始めるべきことを、特に挙げてください。
:::a
解答例：

| 時期 | 行うこと |
|---|---|
| 1か月目 | 棚卸し（サーバー、連携、実際の使用率）。回線の申し込み。ライセンスの確認。移行先の土台（アカウント、ネットワーク）の設計 |
| 2〜3か月目 | 土台の構築。検証環境への試験的な移行。データベースの移し方の決定。月末のバッチの性能の試験 |
| 4〜5か月目 | 回線の開通と、通信の試験。本番と同じ構成の環境の構築。監視、バックアップの用意 |
| 6〜7か月目 | アプリと連携の試験。利用部門による確認。データの事前の複製の開始。1回目の切り替えの練習 |
| 8か月目 | 2回目の練習。手順書と、判断の基準、切り戻しの条件の確定 |
| 9か月目 | 本番の切り替え（月末を避けた週末）。切り替え後の見守り。最初の月末のバッチの立ち会い |
| 10か月目 | 予備。旧環境のデータの保管と、機器の撤去の手配 |

最初の月に始めるべきは、時間が自分たちの努力では縮められないものです。回線の手配、ライセンスの確認、連携先のシステムの担当者への連絡がこれに当たります。また、最後の月を予備として空けておくこと、月末の締めを避けて切り替えることが要点です。
:::

## ケース7：工場の設備データの収集

:::req
- 5つの工場の、合計2,000台の設備から、1秒ごとに計測値を集める
- 工場とクラウドの間の回線は、ときどき切れる
- 設備の制御は、数ミリ秒の応答が必要で、止められない
- 異常の兆候を、数秒から数分で検知し、現場に知らせたい
- データは3年間保存し、後から分析に使う
:::

:::think
- 何を工場の中で行い、何をクラウドで行うか
- 回線が切れている間、データと制御はどうなるか
- 3年分のデータの量と、保存の費用は、どのくらいか
:::

:::dir
制御は、工場の中に置いたままにします。クラウドとの回線が切れても、生産が止まらないことが最優先です。工場ごとに中継の装置を置き、設備から計測値を集め、回線が切れている間は手元にため、つながったらまとめて送ります（AWS IoT Greengrass など）。クラウドでは、機器向けの入口（AWS IoT Core）で受け、流れてくるデータを処理する仕組み（Amazon Kinesis Data Streams、Amazon Data Firehose）を通して、S3に保存します。直近のデータは、すぐに読める置き場所にも入れ、異常の検知とダッシュボードに使います。即時性が求められる検知は、工場の中継の装置でも行います。
:::

:::pit
すべてのデータを、1秒ごとの細かさのまま、すぐ読める置き場所に3年間持つと、費用が膨らみます。直近は細かいまま、古いものは集約するか、安い保存クラスへ移します。機器の1台ごとの証明書の発行、更新、失効の管理は、台数が多いほど重い仕事になります。また、機器の時計がずれていると、データの前後関係が狂い、分析の結果が信用できなくなります。
:::

:::q 計算 | データの量を見積もる
ケース7で、1件の計測値を200バイトとします。

1. 1日に届く件数と、データの量はどのくらいですか
2. 3年間で、どのくらいの量になりますか
3. この結果から、保存の設計について、何を考えますか
:::a
1. 2,000台 × 86,400秒 = 1億7,280万件。1億7,280万 × 200バイト ≒ 34.6GB
2. 34.6GB × 365日 × 3年 ≒ 37.8TB
3. 考えること：
    - 形式を変えれば、量は大きく減る。計測値は、似た値が続くため、列ごとに保存する形式と圧縮がよく効く
    - 読む頻度で、置き場所を分ける。直近の数日は、すぐ読める置き場所に。それより前は、S3に。1年を過ぎたら、安い保存クラスへ
    - 古いデータは、1秒ごとの値が本当に必要かを確かめる。1分ごとの平均、最大、最小で足りるなら、量は数十分の1になる。ただし、後から細かい値が必要になる分析もあるため、利用する人と相談して決める
    - 件数が多い。1件ずつ小さなファイルにせず、まとめて保存する

量と件数を、最初に計算しておくと、「とりあえず全部ためる」ことの費用が見えます。
:::

## ケース8：データ分析基盤

:::req
- 販売、在庫、会員のデータベースと、Webのアクセスログを、1か所に集めて分析したい
- 毎朝7時までに、前日までのデータが、ダッシュボードに反映されていること
- 部門によって、見てよいデータが違う。会員の個人情報は、分析の担当者にも見せない
- 月に一度、過去3年分を使った集計を行う
:::

:::think
- 業務のデータベースに負荷をかけずに、どうデータを取り出すか
- 「毎朝7時まで」を守るために、何を見張り、遅れたらどうするか
- 個人情報を、どの段階で、どう扱うか
:::

:::dir
業務のデータベースからは、変更の記録を読み取る方式や、夜間の読み取り用の複製からの抽出で、負荷をかけずに取り込みます。取り込んだデータは、S3に、生のデータ、整えたデータ、目的別のデータの3つの層で持ちます。個人情報は、整える段階で、個人を特定できない形に変えるか、除きます。加工の処理は、順序と依存関係を管理する仕組みで実行し、各段階で、件数や値の検査を行います。提供は、Athenaやデータウェアハウスで行い、部門ごとに、見られる表と列を制御します。
:::

:::pit
分析のための重い問い合わせを、業務のデータベースに直接投げると、業務の処理が遅くなります。また、「売上」のような基本的な言葉でも、部門によって定義が違う（税を含むか、返品を引くか）ことがあり、数字が合わない原因になります。定義を、データと一緒に管理します。遅れて届くデータ（前日の分が、翌日の昼に届く）の扱いも、最初に決めておきます。
:::

:::q 設計 | 朝7時に間に合わないとき
ケース8で、夜間の加工の処理が失敗したり、遅れたりして、朝7時に間に合わない場合に備えた設計を、検知、対処、利用者への見せ方に分けて答えてください。
:::a
解答例：

- 検知：処理の失敗だけでなく、「決めた時刻までに終わっていない」ことを検知する。たとえば、午前5時の時点で、ある段階が終わっていなければ通知する。件数が、いつもより極端に少ない、または多い場合も通知する
- 対処：失敗した段階から、やり直せるようにする。同じ処理を2回実行しても、データが二重にならない作りにする。原因が元のデータにある場合は、問題のある部分だけを除いて先に進めるか、止めるかの基準を、あらかじめ決める
- 見せ方：ダッシュボードに、「いつの時点までのデータか」を表示する。間に合わなかったときは、前日までの古いデータを、その旨を示したうえで見せる。誤ったデータや、途中までのデータを、正しいものとして見せない

時間の余裕も、設計のうちです。処理に3時間かかるなら、午前4時ではなく、午前1時に始めます。やり直しの時間を、朝7時までの中に残しておきます。
:::

## ケース9：生成AIによる社内文書の検索

:::req
- 社内の規程とマニュアル、約2万件を対象に、質問に答える仕組みを作る
- 利用者は、社員3,000人。部門によって、見てよい文書が違う
- 答えには、根拠とした文書を示す
- 入力した内容や文書が、社外のモデルの学習に使われないこと
- 月額の費用に、上限がある
:::

:::think
- 見てはいけない文書の内容が、答えに混ざらないようにするには
- 答えの正しさを、公開の前と後で、どう確かめるか
- 費用が、利用の量に応じて増えすぎないようにするには
:::

:::dir
文書をS3に置き、Amazon Bedrock Knowledge Bases で、検索用のデータを作ります。文書には、見てよい部門を属性として付け、検索のときに、質問した人の所属で絞り込みます。利用者の認証は、会社の認証基盤と連携します。答えには出典を付け、関係する文書が見つからないときは、「わからない」と答えさせます。入力と出力には検査の層（Amazon Bedrock Guardrails）を置き、個人情報や、業務と関係のない話題を扱います。代表的な質問と、期待する答えの組を用意し、変更のたびに確かめます。利用者ごとの回数の上限と、費用の通知を設定します。
:::

:::pit
古い版や、重複した文書をそのまま取り込むと、答えが混乱します。仕組みを作る前に、文書の整理が必要です。権限の絞り込みを、モデルへの指示だけに頼ってはいけません。評価の仕組みがないまま公開すると、良くなったのか悪くなったのかがわからず、改善ができません。
:::

:::q 作成 | 公開の前に確かめる基準
ケース9で、全社に公開してよいかを判断するための基準を、5つ以上作ってください。それぞれ、どう測るかも答えてください。
:::a
解答例：

| 基準 | 測り方 |
|---|---|
| 正しく答えられる | 各部門から集めた代表的な質問（100問など）について、期待する答えと照らし、正答の割合が目標を超える |
| 根拠が示される | 答えに出典が付き、その文書に、答えの内容が実際に書かれている割合 |
| わからないときに、作らない | 文書に答えのない質問を混ぜ、「わからない」と答える割合 |
| 権限が守られる | 権限のない利用者として、制限された文書の内容を聞き出す質問を試し、1件も漏れない |
| 指示の乗っ取りに耐える | 指示を無視させる典型的な入力を試し、想定外の動きをしない |
| 応答が速い | 質問から答えまでの時間が、目標の秒数以内である割合 |
| 費用が収まる | 試行の期間の実績から、全社で使った場合の月額を見積もり、上限に収まる |

権限の基準だけは、「割合」ではなく、「1件も漏れない」とします。公開した後も、利用者が答えを評価できる仕組み（役に立った、立たなかった）を入れ、評価の低い質問を、次の改善の材料にします。
:::

## ケース10：金融機関の顧客向けシステム

:::req
- 顧客が、取引の履歴を照会するシステム
- 操作の記録を、7年間、改ざんできない形で保存する
- 本番への変更は、すべて、事前の承認と記録が必要
- 本番のデータを見る操作は、申請制とし、誰がいつ何を見たかを追える
- データは、国内のリージョンだけに置く。暗号化の鍵は、自社で管理する
- 東京が使えなくなった場合、1時間以内に大阪で再開する。失ってよいデータは、5分以内
:::

:::think
- 「できない」ことを、どの仕組みで保証するか
- 監査のときに、何を証拠として示せるか
- 緊急のときに、決まりを守ったまま、どう素早く動くか
:::

:::dir
アカウントを、本番、検証、記録の集約、セキュリティで分け、組織の決まり（SCP）で、国内のリージョン以外での操作と、記録の停止を禁止します。操作の記録は、組織全体の証跡として、記録用のアカウントのS3に集め、決めた期間、誰にも削除できない設定にします。暗号化には、自社で管理する鍵（KMSのカスタマー管理キー）を使い、鍵を使える人とプログラムを限定します。人は、通常は閲覧だけの権限で入り、本番の変更やデータの参照が必要なときは、申請と承認を経て、一時的な権限を得ます。変更は、CI/CDの中の承認を通してだけ適用します。大阪には、縮小した環境を常に動かし、データベースを複製しておきます。業界の基準への対応を、表にして示せるようにします。
:::

:::pit
記録を、記録される側と同じアカウントに置くと、そのアカウントの管理者が消せてしまいます。緊急のときに使う、強い権限を得る手順を決めていないと、障害の最中に、決まりを破るか、対応が遅れるかの二択になります。緊急用の手順も、使ったことが必ず記録され、後から確かめられる形で、あらかじめ用意します。開発者が、調査のために本番のデータを直接見る運用は、申請と記録の対象にします。
:::

:::q 説明 | 監査で求められたら
ケース10で、監査の担当者から、「先月、本番の顧客データに、誰が、いつ、何の目的でアクセスしたかを示してください」と求められました。何を示しますか。それを示せるために、設計の段階で用意しておくべきことは何ですか。
:::a
示すもの：

1. アクセスの申請と承認の記録：誰が、いつ、何の目的で申請し、誰が承認したか
2. 権限が付与された記録：その申請にもとづき、誰に、いつからいつまで、どの権限が与えられたか
3. 実際の操作の記録：その権限で、どのデータに、どの操作が行われたか。データベースへの問い合わせの記録や、S3のオブジェクトへのアクセスの記録
4. 1から3が、対応していること：申請のない操作がないこと

設計の段階で用意すること：

- 本番のデータへの経路を、申請を経たものだけに絞る。常に使える強い権限や、共有のアカウントをなくす
- 操作を、個人にひも付けて記録する。共有の利用者名で、データベースに入らない
- データへのアクセスの記録を、有効にする。管理の操作の記録（CloudTrail の既定の範囲）だけでは、「どのデータを見たか」まではわからない。データベースの監査の記録や、データイベントの記録を、別に設定する
- 記録を、改ざんできない場所に、必要な期間保存する
- 申請の記録と、操作の記録を、突き合わせられるようにする。申請の番号を、権限を得るときの情報に含めるなど

「記録はあるはず」ではなく、求められたときに、決まった時間で、実際に取り出して示せることを、あらかじめ試しておきます。
:::

## ケース11：海外への展開

:::req
- 日本で提供しているサービスを、北米と欧州にも提供する
- どの地域でも、主な画面の表示は1秒以内
- 欧州の利用者の個人データは、欧州の中に置く
- 運用は、当面、日本のチームが行う
:::

:::think
- 1つの大きな仕組みを世界で共有するか、地域ごとに独立した仕組みを持つか
- 地域をまたいで、共通にするものと、分けるものは何か
- 日本のチームが、欧州のデータを見ずに、どう運用するか
:::

:::dir
地域ごとに、アプリとデータベースを含む、独立したひとそろいの環境を持ちます。利用者は、登録のときに決まった地域の環境に振り分けます。個人データは、その地域の中だけに置き、ほかの地域へ複製しません。画像などは、CDNで世界に配信します。共通にするのは、コードと、IaC、デプロイの仕組み、監視の見方です。デプロイは、1つの地域で確かめてから、次の地域へ進めます。監視の指標と記録は、個人データを含まない形にして、日本から見られるようにします。
:::

:::pit
アプリの記録（ログ）や、エラーの報告に、個人データが混ざり、それが日本の監視の仕組みに集められて、結果として地域の外に出てしまうことがあります。記録に何を出すかを、設計の段階で決めます。日付と時刻、通貨、言語、住所の形式は、後から対応するのが難しいため、最初から、地域ごとに切り替えられる作りにします。また、すべての地域に同時にデプロイすると、同じ誤りで、世界中が同時に止まります。
:::

:::q 比較 | 世界で1つか、地域ごとか
ケース11について、「世界で1つのデータベースを共有する案」と、「地域ごとに独立した環境を持つ案」を比べ、どちらを勧めるかを、理由とともに答えてください。
:::a
| 観点 | 世界で1つを共有 | 地域ごとに独立 |
|---|---|---|
| データの置き場所の要件 | 満たしにくい。欧州のデータが、ほかの地域にも置かれる | 満たせる |
| 応答の速さ | 書き込みは、データベースのある地域まで届く必要があり、遠い地域では遅い | 近い地域で完結するため、速い |
| 障害の影響 | 全世界に及ぶ | その地域にとどまる |
| 地域をまたぐ機能 | 作りやすい。全利用者を対象にした検索や集計が、そのままできる | 別に仕組みが要る |
| 運用 | 対象は1つ | 対象が地域の数だけある。同じコードと手順で作ることが前提 |

このケースでは、欧州のデータを欧州の中に置く、という要件があるため、地域ごとに独立した案を勧めます。応答の速さと、障害の影響を限定できる点でも、有利です。

代償は、運用の対象が増えることと、地域をまたぐ機能が難しくなることです。前者は、IaCと、段階的なデプロイの仕組みで補います。後者については、「日本の利用者が、欧州の利用者とやり取りする」といった機能が必要かを、事業の側に確かめます。必要なら、やり取りに必要な最小限の情報だけを、地域をまたいで扱う設計を、法務の確認を得ながら行います。
:::

## ケース12：東京と大阪での災害対策

:::req
- 東京で動く受発注システム（ALB、コンテナ、Aurora）に、大阪での備えを加える
- 東京が使えなくなったら、30分以内に大阪で再開する。失ってよいデータは、1分以内
- 年に1回、実際に切り替える訓練を行う
- 追加の費用は、今の月額の半分まで
:::

:::think
- 4つの戦略のうち、どれが、目標と予算に合うか
- データベースのほかに、複製しておく必要があるものは何か
- 切り替えると決めるのは誰で、何を見て決めるか
:::

:::dir
30分という目標から、サーバーを一から作る方式では間に合わない可能性が高く、パイロットライトか、ウォームスタンバイを選びます。データベースは、Aurora Global Database で大阪へ複製します。複製の遅れは、通常1秒未満で、1分以内という目標に合います。コンテナのイメージ、S3のファイル、秘密情報、証明書も、大阪に複製しておきます。構成は、東京と同じIaCのコードから作ります。通信の切り替えは、DNSで行い、応答が保存される時間を短くしておきます。切り替えは、自動ではなく、責任者が、決めた基準にもとづいて判断します。判断から完了までを、手順書にし、訓練で時間を測ります。
:::

:::pit
大阪で使えないサービスや、資源の種類が、構成に含まれていることがあります。大阪の上限値（クォータ）が、東京より小さいままになっていることもあります。連携先のシステムが、こちらのIPアドレスを許可の一覧に登録している場合、大阪のIPアドレスも登録しておかないと、切り替えた後に、連携だけがつながりません。そして、切り替えた後に、東京へ戻す手順が、設計から抜けがちです。
:::

:::q 計画 | 訓練で何を確かめるか
ケース12で、年に1回の切り替えの訓練の計画を立ててください。確かめる項目を6つ以上挙げ、訓練そのものが障害にならないための注意も答えてください。
:::a
確かめる項目の例：

1. 切り替えの判断から、大阪で業務を再開するまでの時間。30分以内に収まるか
2. 切り替えた時点での、データの複製の遅れ。失われたデータがないか
3. 大阪のアプリが、必要な台数まで起動するか。上限値に当たらないか
4. 利用者の通信が、大阪に向くまでの時間。古い宛先に、いつまで通信が届くか
5. 連携先のシステムとの通信が、大阪からもつながるか
6. 監視と通知が、大阪の環境でも働くか
7. 手順書のとおりに実行できたか。書かれていない作業、権限の不足はなかったか
8. 東京へ戻す手順。データを失わずに戻せるか。かかる時間は
9. 連絡の流れ。責任者に連絡がつき、判断できたか

訓練が障害にならないための注意：

- 最初は、利用の少ない時間帯に、計画的な切り替え（データを失わない方式）で行う
- 利用部門と、連携先に、事前に知らせる
- 中止の基準と、中止したときに東京へ戻す手順を、先に決めておく
- 段階を踏む。1年目は、大阪の環境の起動と、検証用の通信での確認まで。2年目に、本番の通信の切り替え、というように広げる

訓練の結果は、時間と、見つかった問題と、その対応を記録し、次の年の訓練で、直ったことを確かめます。訓練で問題が見つかるのは、成功です。本当の災害のときに見つかるより、はるかによいからです。
:::
