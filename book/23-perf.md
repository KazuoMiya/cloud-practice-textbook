:::goal
- 応答時間、処理量、同時に処理している数の関係を使って、必要な台数を概算できる
- 負荷を、入口に近い場所から順に減らす設計ができる
- キャッシュ、キュー、再試行を、それぞれの注意点を踏まえて使い分けられる
:::

性能の設計は、「速いサーバーを選ぶこと」ではありません。目標の数字を決め、負荷がシステムのどこにかかるかを見きわめ、減らせる場所で減らし、増えたときに追いつく仕組みを用意することです。目標のない性能改善は、終わりがありません。

## 3つの数字で考える

| 数字 | 意味 | 見るときの注意 |
|---|---|---|
| 応答時間 | 依頼してから結果が返るまでの時間 | 平均ではなく、パーセンタイルで見る。「95%の依頼が1秒以内」のように決める |
| 処理量（スループット） | 1秒あたりに処理できる依頼の数 | 平常時とピーク時を分けて考える |
| 同時に処理している数 | ある瞬間に、処理の途中にある依頼の数 | 処理量 × 応答時間で概算できる |

平均が当てにならないのは、遅い依頼が少数あっても、平均にはほとんど表れないためです。100件のうち99件が0.1秒、1件が10秒かかった場合、平均は約0.2秒ですが、100人に1人は10秒待たされています。利用者の不満は、この「遅いほうの端」から生まれます。

3つ目の関係は、台数の見積もりに使えます。毎秒300件の依頼があり、1件に平均0.2秒かかるなら、同時に処理している数は 300 × 0.2 = 60 です。サーバー1台が同時に20件を無理なく処理できるなら、最低3台が必要になります。応答時間が0.4秒に延びると、同じ処理量でも同時に処理している数は120になり、必要な台数は倍になります。遅くなると、さらに混む、という悪循環が起きるのはこのためです。

## 入口に近い場所から減らす

{{fig:reqpath|リクエストの通り道と、負荷を減らす場所。入口に近いところで減らすほど、後ろの部品すべてが楽になる}}

| 場所 | 手段 | 効果 |
|---|---|---|
| CDN | 画像やスクリプトを配信する。変化の少ない応答をキャッシュする | サーバーに届く通信そのものが減る。利用者に近い拠点から返すので速い |
| ロードバランサー | 複数台に振り分ける | 1台あたりの負荷を下げる |
| アプリ | 状態を外に出し、台数を増減する。よく読むデータをキャッシュに置く | 負荷に合わせて処理能力を変えられる |
| データベース | 索引（インデックス）と問い合わせを見直す。読み取りを複製へ逃がす | 多くの場合、ここが最後の詰まりどころになる |
| キュー | すぐに結果を返さなくてよい処理を、後ろに回す | 急増を吸収し、後ろの部品を自分の速さで動かせる |

性能の問題で、最初に確かめたいのは、データベースへの問い合わせです。台数を増やす前に、遅い問い合わせを特定し、索引を付ける、取得する件数を絞る、同じ問い合わせを繰り返さない、といった改善を先に行います。アプリのサーバーを増やしても、データベースが詰まっていれば、詰まりがひどくなるだけです。

## 台数を増減する仕組み

| 方式 | 動き | 向く場面 |
|---|---|---|
| 目標値を保つ（ターゲット追跡） | CPU使用率などの指標が目標値になるように、台数を自動で調整する | ゆるやかに増減する負荷。最初に選ぶ方式 |
| 予定に合わせる | 決まった時刻に、台数を変える | 始業時や、告知の時刻など、増える時期がわかっている場合 |
| 過去の傾向から予測する | 周期的な負荷を学習し、増える前に台数を増やす | 曜日や時間帯で、同じ波を繰り返す負荷 |

設計で決めるのは、次の4つです。

- 何を目標にするか：CPU使用率が一般的だが、処理の内容によっては、1台あたりの依頼の数や、キューにたまった件数のほうが適している
- 最小と最大：最小は、AZを1つ失っても足りる台数（{{ch:ha}}）。最大は、費用の上限と、後ろの部品（データベースの接続数など）が受けられる量から決める
- 増えるまでの時間：新しいサーバーが依頼を受けられるようになるまでの時間。これより速い急増には、台数の自動調整では追いつかない
- 上限値（クォータ）：アカウントごとに、起動できる台数などの上限がある。必要な最大の台数が上限を超えていないかを、事前に確認する

## キャッシュ

キャッシュは、一度得た結果を保存しておき、次からはそれを返す仕組みです。性能への効果は大きい一方、「古い内容を返す」ことを設計に持ち込みます。

| 決めること | 考え方 |
|---|---|
| 何をキャッシュするか | 読まれる回数が多く、変わる頻度が低いもの。利用者ごとに違う内容や、常に最新でなければならないもの（在庫の最終確認、残高）は対象にしない |
| どれだけ保存するか | 古い内容を何秒まで許せるか、で決める。数秒のキャッシュでも、集中したアクセスには大きく効く |
| 更新されたらどうするか | 保存の期限が切れるのを待つか、更新のときにキャッシュを消すか |
| キャッシュが空のときどうなるか | 再起動の直後や、期限が一斉に切れたときに、すべての依頼がデータベースに集中する。期限をずらす、段階的に戻す、といった備えをする |

アプリの中で使うキャッシュには、Amazon ElastiCache などのインメモリのデータストアを使います。よく使われる形は、まずキャッシュを見て、なければデータベースから読み、結果をキャッシュに書く、というものです。キャッシュが止まってもデータベースから読めるように作っておけば、キャッシュの障害は「遅くなる」だけで済みます。

## キューで後ろに回す

注文の受け付けのように、すぐに返す必要があるのは「受け付けました」という応答だけ、という処理は多くあります。メールの送信、帳票の作成、ほかのシステムへの連携は、キューに入れて後ろで処理できます。

Amazon SQS を使うときに、設計で押さえる値は次のとおりです（[SQSのクォータ](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html)）。

| 項目 | 値 | 設計への影響 |
|---|---|---|
| 可視性タイムアウト | 既定30秒、最大12時間 | 取り出したメッセージが、ほかの処理から見えなくなる時間。処理にかかる時間より長くしないと、処理中に別の処理が同じメッセージを取り出し、二重に処理される |
| メッセージの保持期間 | 既定4日、最大14日 | 処理する側が止まっていても、この期間は失われない |
| メッセージの大きさ | 最大1MiB | 大きなデータはS3に置き、メッセージには場所だけを入れる |
| 1回に取り出せる数 | 最大10件 | まとめて取り出すと、効率がよい |

標準のキューでは、同じメッセージが2回届くことがあり、順序も保証されません。処理する側を、同じメッセージを2回処理しても結果が変わらないように作ります（{{ch:s6}}の章末問題）。何度処理しても失敗するメッセージは、デッドレターキューに移し、ほかの処理を止めないようにします。

## 混雑を広げない作法

1つの部品が遅くなったとき、それを呼ぶ側の作り方によって、障害が全体に広がるか、その部品だけで済むかが決まります。

| 作法 | 内容 |
|---|---|
| タイムアウトを付ける | 応答を待つ時間に上限を設ける。上限がないと、遅い相手を待つ処理がたまり、自分も応答できなくなる |
| 再試行は、間隔を空けて、回数を限る | 失敗したら、待つ時間を倍々に延ばしながら数回だけ試す。待つ時間には、ばらつきを加える。全員が同じ間隔で再試行すると、波になって相手を襲う |
| 見込みのない相手を呼ばない | 失敗が続いている相手への呼び出しを、しばらく止める（サーキットブレーカー）。相手の回復を助け、自分も待たされない |
| 受ける量を制限する | 処理できる量を超えた依頼は、早めに断る。全員を待たせて全員が時間切れになるより、一部を断って残りを確実に処理する |

## 負荷試験で確かめる

設計した数字は、試験で確かめて初めて根拠になります。

- 目的を分ける：想定のピークに耐えるか。どこまで増やすと壊れるか。急に数倍になったらどうなるか。長時間続けて問題が出ないか
- 本番に近い条件で行う：データの件数が少ない環境では、データベースの遅さが表れない
- 壊れ方を見る：限界を超えたとき、ゆるやかに遅くなるのか、突然全体が止まるのか。どの部品が最初に詰まるか
- 事前に確認する：上限値（クォータ）、事業者の負荷試験に関する規定、試験の通信がほかのシステムに影響しないか

:::sum
- 性能は、応答時間（パーセンタイル）、処理量、同時に処理している数の3つで考える。目標を数字で決める
- 負荷は、入口に近い場所から減らす。台数を増やす前に、データベースへの問い合わせを見直す
- キャッシュは「古さをどこまで許すか」、キューは「二重の処理と順序」を設計に持ち込む
- タイムアウト、間隔を空けた再試行、受ける量の制限で、混雑が広がるのを防ぐ
:::

## 章末問題

:::q 計算 | 必要な台数を見積もる
あるAPIは、ピーク時に毎秒400件の依頼を受け、1件の処理に平均0.15秒かかります。負荷試験の結果、サーバー1台は、同時に15件までなら応答時間を保てることがわかりました。

1. ピーク時に、同時に処理している数はいくつですか
2. 最低で何台が必要ですか
3. 2つのAZに置き、1つのAZを失ってもピークに耐えるには、合計で何台を動かしますか
4. 処理の遅延で平均の処理時間が0.3秒になると、何が起きますか
:::a
1. 400 × 0.15 = 60
2. 60 ÷ 15 = 4台
3. 各AZに4台、合計8台
4. 同時に処理している数が 400 × 0.3 = 120 になり、必要な台数が8台に倍増する。4台のままでは1台あたり30件を抱え、応答時間がさらに延び、同時に処理している数がさらに増える。最後には時間切れのエラーが続出する

実際には、余裕を見て台数を上乗せします。4の悪循環は、障害の現場でよく見られます。原因（処理の遅延）を取り除かない限り、台数を増やしても後ろの部品をさらに混ませるだけ、ということもあります。
:::

:::q 分析 | 平均は良いのに苦情が来る
ダッシュボードでは、応答時間の平均は0.2秒で安定しています。しかし、利用者から「ときどき、画面が10秒近く固まる」という苦情が続いています。何を確認しますか。
:::a
平均ではなく、遅いほうの端を確認します。応答時間の99パーセンタイルや最大値をグラフにすると、平均には表れない遅い依頼が見えます。

遅い依頼があるとわかったら、次のように絞り込みます。

- いつ起きるか：決まった時刻なら、バッチ処理やバックアップとの重なり。不定期なら、特定の操作やデータ
- どの操作か：特定のURLや機能に偏っていないか。件数の多い利用者の一覧表示など、データ量に比例して遅くなる処理はないか
- どのサーバーか：特定の1台に偏っていれば、そのサーバーの問題。起動直後のサーバーなら、準備が終わる前に依頼を受けている可能性がある
- 後ろの部品：データベースの遅い問い合わせの記録、ロックの待ち、外部のAPIの遅延

監視の目標も、「平均が0.5秒以内」ではなく「99%が1秒以内」のように、パーセンタイルで決めておくと、この種の問題に通知で気づけます。
:::

:::q 原因 | メッセージが二重に処理される
SQSのキューからメッセージを取り出して、帳票を作る処理があります。可視性タイムアウトは既定の30秒のままです。帳票の作成には、大きいもので2分かかります。同じ帳票が2回、3回と作られる問題が起きています。原因と対策を答えてください。
:::a
原因：取り出したメッセージは、可視性タイムアウトの間だけ、ほかの処理から見えなくなります。30秒たっても処理が終わらず、メッセージが削除されていないと、メッセージは再びキューに現れ、別の処理（または同じ処理）がもう一度取り出します。2分かかる帳票では、処理が終わるまでに何度も取り出されます。

対策：

1. 可視性タイムアウトを、処理にかかる最長の時間より十分に長くする。Lambdaで処理する場合は、関数のタイムアウトの6倍以上にすることが推奨されている
2. 長くかかりそうなときは、処理の途中で、そのメッセージの可視性タイムアウトを延長する
3. 同じメッセージを2回処理しても結果が変わらないように作る。たとえば、帳票の識別子で、作成済みかどうかを確かめてから作る
4. 何度も失敗するメッセージが、ほかを妨げ続けないよう、デッドレターキューを設定する

1だけでは不十分です。標準のキューは、仕組みの上で、まれに同じメッセージを2回届けることがあります。3の作りが、根本の備えになります。
:::

:::q 設計 | 何を、どこで、どれだけキャッシュするか
通販サイトの次の4つの情報について、キャッシュするかどうか、する場合はどこで、どのくらいの時間かを答えてください。

1. 会社概要のページ
2. 商品の一覧と説明
3. 在庫の数
4. 利用者ごとの買い物かごの中身
:::a
解答例：

1. CDNで長くキャッシュする（数時間から1日）。めったに変わらず、全員に同じ内容を返す。更新したときは、キャッシュを無効化する
2. CDNまたはアプリのキャッシュで、短めにキャッシュする（数分）。全員に同じ内容で、読まれる回数が非常に多い。数分の古さは許容できることが多い。価格の変更など、すぐに反映したい更新があるなら、更新時にキャッシュを消す仕組みを加える
3. 一覧に表示する目安の数は、短くキャッシュしてよい（数秒から数十秒）。ただし、注文を確定するときの在庫の確認は、キャッシュを使わず、必ずデータベースで行う
4. CDNではキャッシュしない。利用者ごとに内容が違い、誤ってキャッシュすると、他人の買い物かごが表示される事故になる。アプリのサーバーが状態を持たないよう、インメモリのデータストアやデータベースに保存する

4のような事故を防ぐため、CDNでは「キャッシュしてよいもの」を明示的に指定し、それ以外はキャッシュしない設定を基本にします。
:::

:::q 対策 | 再試行が障害を長引かせる
あるサービスのデータベースが、一時的に遅くなりました。すると、呼び出し側のアプリがすべて、失敗した依頼をすぐに3回まで再試行する作りだったため、データベースへの依頼が急増し、回復までに長い時間がかかりました。何が起きたのかを説明し、対策を3つ挙げてください。
:::a
起きたこと：遅くなって時間切れになった依頼を、全員がすぐに再試行したため、データベースに届く依頼が最大で4倍（最初の1回と再試行3回）になりました。遅さの原因が負荷であれば、再試行はその負荷をさらに増やします。遅くなる、時間切れが増える、再試行が増える、さらに遅くなる、という循環に入り、元の原因が解消しても、自力では回復しにくくなります。

対策：

1. 再試行の間隔を空ける：待つ時間を倍々に延ばし、さらにばらつきを加える。全員の再試行が同じ瞬間に重ならないようにする
2. 再試行の回数と総量を限る：回数を減らす。失敗が続いている間は再試行そのものを止める（サーキットブレーカー）
3. 受ける側で量を制限する：処理できる量を超えた依頼は、すぐに断る。待たせて時間切れにするより、早く断るほうが、呼び出し側も次の手を打てる
4. 再試行する層を1つにする：画面、アプリ、ライブラリのそれぞれが3回ずつ再試行すると、掛け算で27回になる

再試行は、一時的な失敗には有効ですが、過負荷に対しては逆効果になります。「再試行は、相手にとっては追加の負荷である」ことを前提に設計します。
:::
