用語は、「基本の用語」と「設計・運用・上級の用語」に分けています。左の検索欄に用語を入力すると、本文で使われている箇所も探せます。

案件の打ち合わせや設計書でよく出てくる用語を、意味が近いものごとにまとめています。

## 基本の用語

| 用語 | 意味 |
|---|---|
| マネージドサービス | OSやミドルウェアの保守を事業者に任せられるサービス。RDSやLambdaなど |
| リージョン／AZ | データセンター群の地域単位と、その中の独立した拠点（{{ch:mech}}） |
| エッジロケーション | CDNが利用者の近くにコンテンツを置くための拠点。リージョンより数が多い |
| インスタンス | 起動した仮想サーバー1台のこと。「インスタンスタイプ」はそのスペック |
| AMI・イメージ | 仮想サーバーを起動するためのOSとソフトの雛形 |
| オートスケーリング | 負荷に応じて台数を自動で増減する仕組み |
| 冗長化 | 同じ役割の部品を複数用意し、1つが壊れても止まらないようにすること |
| フェイルオーバー | 障害時に予備系へ自動で切り替えること |
| SLA | サービス水準に関する合意。稼働率などの条件を定め、未達の場合は申請によりサービスクレジット（将来の利用料への充当）などが適用されることがある。自動的な現金返金とは限らない |
| RTO | 障害発生から復旧までに許容できる時間（目標復旧時間） |
| RPO | 障害時にどの時点までのデータを取り戻せればよいか（目標復旧時点） |
| DR（災害対策） | 別リージョンなどに予備環境を用意し、大規模災害でも業務を続ける対策 |
| エンドポイント | サービスに接続するためのURLやアドレス |
| ARN・リソースID | クラウド上の部品を一意に識別する名前（ARNはAWSでの呼び方） |
| IAMロール | 人やプログラムが引き受ける権限のまとまり。一時的な認証情報が発行されるため、長期アクセスキーをコードに埋め込んだり保管したりせずに済む |
| MFA | パスワードに加えてスマホアプリなどで本人確認する多要素認証 |
| VPCピアリング | 2つのVPCを直接つなぐこと |
| デプロイ | 作ったプログラムを実行環境に配置して動かすこと |
| ブルー／グリーンデプロイ | 新旧2つの環境を用意し、切り替えで無停止リリースする手法 |
| IaC | インフラ構成をコードで管理すること。Terraform、CloudFormationなど |
| コンテナイメージ | アプリと実行環境をひとまとめにしたパッケージ。Dockerで作る |
| オーケストレーション | 多数のコンテナの配置・再起動・増減を自動管理すること。Kubernetesが代表 |
| サーバーレス | サーバーの管理を意識せず、コードや設定だけで動かす方式 |
| コールドスタート | 新しい実行環境の準備・初期化のため、応答に追加の時間がかかる現象。長時間使われなかった後の最初の実行や、アクセス急増で実行環境が増えるときに起きる |
| リフト＆シフト | 既存のアプリケーションを大きく変更せずにクラウドへ移す方法（AWSの移行戦略では「リホスト」）。移行後に別途最適化する場合がある。国内で使われる「クラウドリフト（まず移す）後にクラウドシフト（最適化する）」という段階的移行の説明とは区別する |
| モダナイゼーション | 古いシステムをクラウドに適した構成（コンテナ、マネージドサービス等）に作り直すこと |
| ベンダーロックイン | 特定事業者の独自機能に依存しすぎて、他社へ移れなくなる状態 |
| エグレス（データ転送アウト） | クラウドから外部へ出ていく通信。課金対象になることが多い |
| FinOps | クラウド費用を可視化し、組織横断で最適化する取り組み |
| ISMAP | 政府が安全性を評価したクラウドサービスの登録制度。官公庁案件で求められる |

## 設計・運用・上級の用語

第2部以降で出てくる用語です。括弧の中は、詳しく扱っている章です。

| 用語 | 意味 |
|---|---|
| ステートレス | サーバーが、利用者ごとの状態を、自分の中に持たない作り。どのサーバーが処理しても同じ結果になり、台数を自由に増減できる（{{ch:mech}}） |
| べき等性 | 同じ操作を、何度実行しても、結果が変わらない性質。再試行や、重複した依頼に備えるための、基本の作法（{{ch:s6}}） |
| コントロールプレーン／データプレーン | 作成や変更の依頼を受け付ける管理の系と、実際に通信や処理を運ぶ系（{{ch:mech}}） |
| 静的安定性 | 障害が起きても、何も操作せずに、動き続けられる性質。障害時に、新しく作ることに頼らない（{{ch:ha}}） |
| 単一障害点 | そこが止まると、全体が止まる箇所（{{ch:pattern}}） |
| ポイントインタイムリカバリ | バックアップと変更の記録から、任意の時点の状態を復元する機能（{{ch:s4}}） |
| ヘルスチェック | 部品が、正常に応答するかを、定期的に確かめる仕組み。振り分けの停止や、入れ替えのきっかけになる（{{ch:s3}}） |
| 起動テンプレート | サーバーを起動するときの設定（イメージ、種類、ロール、起動時のスクリプト）をまとめたもの（{{ch:s3}}） |
| ドリフト | コードに書かれた構成と、実際の構成の、ずれ。手動の変更で生じる（{{ch:s7}}） |
| 変更セット／plan | IaCで、適用の前に、何が追加・変更・置き換え・削除されるかを示す差分（{{ch:s7}}） |
| OIDC | 外部のサービスが、長く使える鍵を持たずに、一時的な認証情報を受け取るための連携の方式（{{ch:s8}}） |
| タスク定義 | ECSで、どのイメージを、どの設定で動かすかを書いたもの（{{ch:s8}}） |
| ADR | 設計の判断の記録。検討した案、選んだ理由、受け入れたデメリットを残す（{{ch:req}}） |
| 非機能要件 | 機能そのものではなく、可用性、性能、運用、セキュリティなどについての要件（{{ch:req}}） |
| パーセンタイル | 値を小さい順に並べたとき、指定した割合の位置にある値。「95パーセンタイルが1秒」は、95%の依頼が1秒以内、という意味（{{ch:perf}}） |
| スロットリング | 上限を超えた依頼を、制限して断ること（{{ch:s6}}） |
| クォータ | アカウントやサービスごとに決められた、資源の数や、呼び出しの頻度の上限。上限値、サービスクォータとも呼ぶ（{{ch:perf}}） |
| コネクションプール | データベースへの接続を、ためて使い回す仕組み（{{ch:ts}}） |
| 可視性タイムアウト | キューから取り出したメッセージが、ほかの処理から見えなくなる時間（{{ch:perf}}） |
| デッドレターキュー | 何度処理しても失敗するメッセージを、退避しておくキュー（{{ch:perf}}） |
| サーキットブレーカー | 失敗が続く相手への呼び出しを、しばらく止める仕組み（{{ch:perf}}） |
| パーティションキー／ソートキー | DynamoDBで、データの置き場所と、並び順を決めるキー（{{ch:data}}） |
| 結果整合性 | 書き込みの直後は、古い内容が読まれることがあるが、やがて最新にそろう、という性質（{{ch:data}}） |
| ライフサイクルルール | S3で、時間の経過に応じて、保存クラスの変更や削除を自動で行う設定（{{ch:data}}） |
| Savings Plans | 一定の利用を約束する代わりに、割引を受ける契約（{{ch:cost}}） |
| スポットインスタンス | 余っている処理能力を、安く使う代わりに、中断されることがある買い方（{{ch:cost}}） |
| Well-Architected Framework | AWSが公開する、設計の指針。6つの柱で、構成を確かめる（{{ch:review}}） |
| ランディングゾーン | 多数のアカウントを、安全に、ばらつきなく作るための土台（{{ch:org}}） |
| OU | 組織の中で、アカウントをまとめる入れ物（{{ch:org}}） |
| SCP | OUやアカウントに付けて、できることの上限を決めるポリシー。権限は与えない（{{ch:org}}） |
| ガードレール | 決まりを守らせる柵。できないようにする予防と、見つけて知らせる発見がある（{{ch:org}}） |
| Transit Gateway | 多数のVPCと、社内のネットワークを、中央でつなぐ中継点（{{ch:xnet}}） |
| PrivateLink | 特定のサービスだけを、相手のVPCの中に、出入口として見せる仕組み（{{ch:xnet}}） |
| BGP | ネットワーク同士が、経路の情報を交換する仕組み。専用線やVPNの、経路の切り替えに使う（{{ch:xnet}}） |
| 7つのR | 移行の7つの戦略。リタイア、リテイン、リホスト、リロケート、リパーチェス、リプラットフォーム、リファクタリング（{{ch:mig}}） |
| カットオーバー | 古い環境から、新しい環境への、本番の切り替え（{{ch:mig}}） |
| SLI／SLO | 利用者から見た良し悪しを測る指標と、その目標値（{{ch:sre}}） |
| エラーバジェット | 目標の範囲で、許される失敗の量。変更を進めるか、止めるかの判断に使う（{{ch:sre}}） |
| カナリアリリース | 通信の一部だけを、新しい版に流し、問題がなければ広げる方式（{{ch:sre}}） |
| 機能フラグ | 配置した機能を、設定で、有効・無効に切り替える仕組み（{{ch:sre}}） |
| ポストモーテム | 障害の後の、振り返りと、その文書。人ではなく、仕組みを問う（{{ch:sre}}） |
| ランブック | 通知や障害の種類ごとに、確認と対処の手順を書いたもの（{{ch:sre}}） |
| カオスエンジニアリング | 管理された形で、意図的に障害を起こし、備えを確かめる取り組み（{{ch:sre}}） |
| Pod | Kubernetesで、動かす最小の単位（{{ch:k8s}}） |
| マニフェスト | Kubernetesで、あるべき状態を宣言した文書（{{ch:k8s}}） |
| マイクロサービス | システムを、独立して変更・公開できる、小さなサービスに分ける作り方（{{ch:k8s}}） |
| データレイク | さまざまなデータを、形を変えずに、まとめて保存しておく置き場所（{{ch:dataai}}） |
| パーティション | データを、日付などで分けて置くこと。必要な範囲だけを読めるようにする（{{ch:dataai}}） |
| RAG | 質問に関係する文書を検索し、それを根拠に、生成AIに答えさせる仕組み（{{ch:dataai}}） |
| ベクトルストア | 文章の意味を表す数値を保存し、意味の近いものを探せる保存先（{{ch:dataai}}） |
| トークン | 生成AIが文章を扱う単位。料金や、入力の長さの上限は、この数で決まる（{{ch:dataai}}） |
| プロンプトインジェクション | 入力や文書に紛れ込ませた指示で、生成AIの動きを乗っ取ろうとする攻撃（{{ch:dataai}}） |
| TTL | 保存しておいてよい時間。DNSの応答や、キャッシュ、データの自動の削除などで使う（{{ch:ts}}） |
| フェイルバック | 切り替えた先から、元の環境へ戻すこと（{{ch:ha}}） |
