:::goal
- 守りを1か所に頼らず、層を重ねる形で設計できる
- 複数のポリシーが重なったとき、ある操作が許可されるかどうかを判定できる
- 最小権限、暗号化、検知の仕組みを、具体的なサービスと設定に結びつけて選べる
:::

{{ch:secost}}では、セキュリティの基本原則を学びました。この章では、それを設計に落とし込みます。出発点は、「何を、誰から守るのか」をはっきりさせることです。守る対象が決まらないまま対策を積み上げると、費用と手間ばかりが増え、肝心の場所が抜けます。

## 守るものと、入口から考える

設計の最初に、次の4つを書き出します。

1. 何を守るか：個人情報、取引のデータ、認証情報、サービスが動き続けること
2. 誰から守るか：外部の攻撃者、権限を持った内部の人の誤りや不正、乗っ取られたアカウントやプログラム
3. どこから入れるか：インターネットに公開された入口、管理用の経路、開発や運用に使う端末、CI/CD、連携先
4. 入られたら何ができるか：その場所の権限で、どこまで届くか

4つ目が最も大切です。侵入を完全に防ぐことはできないと考え、1か所を破られても被害が広がらないようにします。これが、層を重ねる守り（多層防御）の考え方です。

| 層 | ねらい | 主な手段 |
|---|---|---|
| ID・権限 | 必要な人とプログラムだけが、必要な操作だけをできる | IAMロール、最小権限、多要素認証、一時的な認証情報 |
| ネットワーク | 届く必要のない場所には、通信が届かない | プライベートサブネット、セキュリティグループ、VPCエンドポイント |
| 入口 | 不正なリクエストを、アプリに届く前に落とす | AWS WAF、CloudFront、大量アクセスへの制限 |
| アプリとOS | 既知の弱点を残さない | 修正プログラムの適用、イメージの検査、入力の検証 |
| データ | 持ち出されても読めない。消されても戻せる | 暗号化（KMS）、バックアップ、公開ブロック |
| 検知と記録 | 起きたことに気づき、後から追える | CloudTrail、AWS Config、Amazon GuardDuty、Security Hub CSPM |
| 対応 | 気づいた後、被害を広げずに動ける | 連絡の体制、隔離や無効化の手順、訓練 |

## 権限はどう判定されるか

AWSでは、1つの操作に対して、複数の種類のポリシーが同時に関わります。それぞれの役割は、「許可を与えるもの」と「上限を決めるもの」に分かれます。

| ポリシーの種類 | 付ける先 | 役割 |
|---|---|---|
| IDベースのポリシー | ユーザー、グループ、ロール | 許可を与える |
| リソースベースのポリシー | S3バケットなどの資源 | 許可を与える。誰（どのアカウント、どのサービス）に許可するかを書ける |
| アクセス許可の境界 | ユーザー、ロール | 上限を決める。境界の外の操作は、IDベースで許可しても通らない |
| サービスコントロールポリシー（SCP） | 組織、OU、アカウント | 上限を決める。そのアカウントの中の人とロールに効く |
| リソースコントロールポリシー（RCP） | 組織、OU、アカウント | 上限を決める。そのアカウントの中の資源に効く |

{{fig:iameval|権限の判定の流れ（同じアカウントの中での簡略図）。明示的な拒否が最優先で、どこにも許可がなければ拒否される}}

覚えておく規則は3つです。

1. 明示的な拒否（Deny）は、ほかのどの許可よりも優先される
2. 上限を決めるものは、それ自体では何も許可しない。「許可を与えるもの」と「すべての上限」の両方で認められた操作だけが通る
3. どこにも許可が書かれていない操作は、拒否される（暗黙の拒否）

別のアカウントの資源を操作する場合は、条件がもう1つ増えます。操作する側のアカウントのIDベースのポリシーと、操作される側のアカウントのリソースベースのポリシーの、両方に許可が必要です。片方だけでは通りません。

:::ref
判定の正確な順序と例外は、公式ドキュメントの「[ポリシーの評価論理](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html)」で確認できます。権限のエラーで詰まったときに、立ち返る場所です。
:::

## 最小権限を現実に進める

最小権限は、最初から完璧にはできません。次の順で近づけます。

1. 人とプログラムを分ける：人は IAM Identity Center から、役割に応じたロールで入る。プログラムには、それぞれ専用のロールを付ける。1つのロールを使い回さない
2. 長く使える認証情報を作らない：アクセスキーを発行せず、ロールによる一時的な認証情報を使う。外部のサービス（CI/CDなど）にはOIDCで連携する（{{ch:s8}}）
3. 操作と対象を絞る：Action に「*」を使わず、必要な操作を列挙する。Resource も、特定のバケットやテーブルに限定する
4. 条件で絞る：特定のVPCエンドポイント経由のときだけ、特定のタグが付いた資源だけ、のように条件（Condition）を付ける
5. 使われていない権限を削る：IAM Access Analyzer は、使われていないロールや権限、外部に共有されている資源を検出する。記録にもとづいて、実際に使った操作だけのポリシーを作ることもできる
6. 強い権限は、必要なときだけ使う：本番を変更できる権限は、申請して一時的に得る形にする

特定の場所だけを読めるようにするポリシーの例を示します。一覧の取得（ListBucket）はバケットに対する操作で、読み取り（GetObject）はオブジェクトに対する操作であるため、文を分けて書きます。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::example-bucket",
      "Condition": { "StringLike": { "s3:prefix": "reports/*" } }
    },
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-bucket/reports/*"
    }
  ]
}
```

## ネットワークと入口を守る

- 公開する面を最小にする：インターネットから直接届くのは、CloudFrontやロードバランサーだけにする。サーバーとデータベースは、プライベートサブネットに置く
- セキュリティグループは、相手のセキュリティグループを指定する：IPアドレスの範囲で広く許可しない（{{ch:net}}）
- AWSのサービスへは、VPCエンドポイントで届ける：インターネットを通らず、エンドポイントのポリシーで、使える相手を絞ることもできる
- 入口でWAFを使う：よく知られた攻撃の型（SQLインジェクションなど）や、同じ相手からの大量のリクエストを落とす。WAFを関連付けられるのは、CloudFront、ALB、API GatewayのREST APIなど
- 管理用の経路を別に考える：サーバーへは Session Manager で入り、管理用のポートを開けない

## データを守る

暗号化には、保存しているデータの暗号化と、通信の暗号化があります。

| 対象 | 手段 | 設計で決めること |
|---|---|---|
| 保存データ | AWS KMS の鍵で暗号化する。S3、EBS、RDSなど、多くのサービスが設定で対応する | 鍵を、事業者が用意するものにするか、自分で管理するもの（カスタマー管理キー）にするか。後者は、誰がその鍵を使えるかを鍵のポリシーで制御でき、利用の記録も残る |
| 通信 | TLSで暗号化する。証明書は AWS Certificate Manager で発行・更新できる | どの区間を暗号化するか。利用者からロードバランサーまでか、その先のサーバーやデータベースとの間までか |
| 秘密情報 | Secrets Manager や Parameter Store に置き、実行時に取り出す | 誰が読めるか。定期的に更新するか |

暗号化は、「権限のない人が、保存先の機器やデータを直接手に入れても読めない」ことを守ります。権限のある人やプログラムが正規の手順で読み出せば、データは復号されて返ります。したがって、暗号化は権限の設計の代わりにはなりません。S3では、アカウント全体で公開ブロックを有効にし、暗号化と合わせて使います。

## 気づく仕組みを持つ

| 知りたいこと | 使うサービス |
|---|---|
| 誰が、いつ、どの操作をしたか | AWS CloudTrail。管理の操作は直近90日分を確認できる。長期保存や、S3のファイル操作などのデータイベントの記録には、証跡などの設定が必要 |
| 設定が、いつ、どう変わったか。決まりに反していないか | AWS Config。資源の設定の履歴を残し、ルールに照らして評価する |
| 不審な動きがないか | Amazon GuardDuty。記録や通信の情報から、普段と違う挙動や、既知の悪意ある相手との通信を検出する |
| 推奨される設定から外れていないか | AWS Security Hub CSPM。基準に照らして、設定の不備を一覧にする |
| 外部に共有されている資源はないか | IAM Access Analyzer |

検知の仕組みは、通知の行き先と、通知を受けた人の動きが決まっていて、初めて役に立ちます。組織全体で記録と検知をまとめる方法は、{{ch:org}}で扱います。

:::sum
- 守るものと入口を書き出し、1か所を破られても広がらないように層を重ねる
- 権限の判定は、明示的な拒否が最優先。許可を与えるものと、すべての上限の両方で認められて、初めて通る
- 最小権限は、人とプログラムを分け、長く使える認証情報をなくし、使われていない権限を削ることで近づける
- 暗号化は権限の設計の代わりにならない。記録と検知は、通知の後の動きまで決めておく
:::

## 章末問題

:::q 判定 | 重なったポリシーを読む
同じアカウントの中で、あるロールに「S3のすべての操作（s3:*）を、すべての資源に対して許可する」IDベースのポリシーが付いています。次のそれぞれの場合、このロールで、バケット data-bucket にファイルをアップロード（s3:PutObject）できますか。

1. ほかに関係するポリシーがない
2. アカウントに、s3:DeleteBucket だけを拒否するSCPが適用されている
3. ロールに、s3:GetObject だけを許可するアクセス許可の境界が設定されている
4. data-bucket のバケットポリシーに、このロールからの s3:PutObject を拒否（Deny）する文がある
:::a
1. できる。IDベースのポリシーで許可されている
2. できる。SCPが拒否しているのは s3:DeleteBucket だけで、s3:PutObject はSCPの上限の中にある（SCPで、ほかの操作が許可されている前提）
3. できない。境界は上限を決める。s3:PutObject は境界の中にないため、IDベースのポリシーで許可していても通らない
4. できない。明示的な拒否は、どの許可よりも優先される

3と4は、「許可しているのに通らない」という問い合わせの典型です。権限のエラーが出たら、許可を足す前に、上限を決めるものと、明示的な拒否がないかを確認します。エラーメッセージには、どの種類のポリシーで拒否されたかが書かれていることが多いので、全文を読みます。
:::

:::q 設計 | 別のアカウントのバケットを読む
アカウントAのアプリ（ロール app-role で動く）が、アカウントBにあるS3バケット shared-data のファイルを読み取る必要があります。必要な設定を、どちらのアカウントで何をするかに分けて答えてください。データがKMSのカスタマー管理キーで暗号化されている場合に、追加で必要なことも答えてください。
:::a
- アカウントA：app-role のIDベースのポリシーで、shared-data のオブジェクトに対する s3:GetObject を許可する
- アカウントB：shared-data のバケットポリシーで、アカウントAの app-role からの s3:GetObject を許可する

別のアカウントをまたぐ操作は、両方に許可があって初めて通ります。

暗号化されている場合：ファイルを読むには、復号の権限も必要です。アカウントBの鍵のポリシーで、アカウントAの app-role に復号（kms:Decrypt）を許可し、アカウントAの app-role のIDベースのポリシーでも、その鍵に対する復号を許可します。S3の許可だけを設定して「読めない」となるのは、よくあるつまずきです。

許可する相手は、アカウント全体ではなく特定のロールに絞ります。さらに、組織の外からのアクセスを許可しない条件を付けておくと、設定の誤りによる外部への公開を防げます。
:::

:::q 設計 | 3層構成に層を重ねる
CloudFront、ALB、EC2（Auto Scaling）、RDS、S3で構成されたWebシステムがあります。本文の多層防御の表の7つの層について、この構成で行う対策を1つずつ挙げてください。
:::a
解答例：

| 層 | 対策 |
|---|---|
| ID・権限 | EC2に専用のIAMロールを付け、必要なバケットとシークレットだけを許可する。人は IAM Identity Center から入り、多要素認証を必須にする |
| ネットワーク | EC2とRDSをプライベートサブネットに置く。RDSは、アプリ用のセキュリティグループからの通信だけを許可する |
| 入口 | CloudFrontにAWS WAFを関連付ける。ALBは、CloudFrontからの通信だけを受け付けるようにする |
| アプリとOS | 修正プログラムを当てたイメージを定期的に作り、サーバーを入れ替える。依存するライブラリの脆弱性を検査する |
| データ | RDSとS3を暗号化する。S3の公開ブロックを有効にする。バックアップを別のアカウントにも複製する |
| 検知と記録 | CloudTrailの証跡を長期保存する。GuardDutyを有効にする。ALBとWAFの記録を保存する |
| 対応 | 連絡の体制と、サーバーを隔離する手順、認証情報を無効にする手順を用意し、練習する |

どれか1つを完璧にするより、すべての層に最低限の対策がある状態を先に作ります。
:::

:::q 説明 | 暗号化すれば公開されても安全か
ある担当者が「S3のバケットはKMSで暗号化しているので、仮に公開設定になっても中身は読めないはずだ」と言っています。この理解は正しいですか。
:::a
正しいとは言えません。暗号化が守るのは、保存先の機器やデータを直接手に入れられた場合です。正規のAPIを通じた読み出しでは、読み出す側に必要な権限があれば、S3が自動的に復号して中身を返します。

公開設定になったときに何が起きるかは、暗号化に使う鍵の種類によって変わります。S3が管理する鍵による暗号化の場合、読み出しに鍵の権限は要らないため、公開されれば誰でも読めます。KMSのカスタマー管理キーの場合は、読み出す側に鍵を使う権限も必要になるため、権限のない外部の相手は読めません。この場合は、鍵が追加の守りとして働きます。

いずれにしても、暗号化は権限と公開範囲の設計の代わりにはなりません。「公開されない」ことを公開ブロックとバケットポリシーで守り、そのうえで暗号化を重ねる、という順で考えます。
:::

:::q 選択 | どの仕組みで気づけるか
次の4つの出来事に、最も早く気づける（または後から調べられる）仕組みを、本文の表から選んでください。

1. 誰かが、セキュリティグループで22番ポートを 0.0.0.0/0 に開けた
2. あるロールの認証情報が、普段とは違う国から使われている
3. 3週間前に、誰がこのデータベースを削除したのかを知りたい
4. 組織の外のアカウントから読める状態になっているバケットがある
:::a
1. AWS Config のルール、または Security Hub CSPM。設定が決まりから外れたことを検出する。検出したら自動で元に戻す仕組みを組むこともできる
2. Amazon GuardDuty。普段と違う場所からの利用を、不審な動きとして検出する
3. AWS CloudTrail。直近90日以内なので、イベント履歴で、削除のイベントから操作した人と時刻を確認できる
4. IAM Access Analyzer。外部からアクセスできる資源を一覧にする

1つの出来事を、複数の仕組みで捉えられることもあります。たとえば1は、CloudTrailにも「誰が変更したか」が記録されています。Configで気づき、CloudTrailで経緯を調べる、という組み合わせになります。
:::
