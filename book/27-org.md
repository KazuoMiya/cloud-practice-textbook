:::goal
- AWSアカウントを分ける理由を、権限・費用・影響の範囲の3点で説明できる
- 組織、OU、SCPの関係を理解し、SCPで「できること」と「できないこと」を説明できる
- 複数のアカウントにまたがる、人のアクセス、記録の集約、費用の管理の基本形を設計できる
:::

第2部と第3部では、1つのAWSアカウントの中での設計を扱いました。しかし、実際の企業では、数十から数百のアカウントを使うのが普通です。規模が大きくなると、問いは「このシステムをどう作るか」から、「多数のシステムを、安全に、ばらつきなく作れる土台をどう用意するか」に変わります。この土台は、ランディングゾーンと呼ばれます。

## なぜアカウントを分けるのか

AWSアカウントは、AWSの中で最も強い境界です。1つのアカウントに複数のシステムや環境を同居させると、次の問題が起きます。

| 観点 | 1つのアカウントに同居させた場合 | アカウントを分けた場合 |
|---|---|---|
| 権限 | 開発者に検証環境の権限を与えると、本番にも届かないよう、細かい条件で縛る必要がある。誤りが起きやすい | アカウントの境界で分かれる。検証のアカウントで何をしても、本番には届かない |
| 影響の範囲 | 誤操作や侵害の影響が、すべてのシステムに及ぶ。上限値（クォータ）も共有するため、1つのシステムの急増がほかを止める | 影響はそのアカウントの中にとどまる |
| 費用 | タグを付け忘れた資源は、誰の費用かわからない | アカウントごとに、費用が自動的に分かれる |
| 取り違え | 本番と検証の資源が同じ画面に並ぶ | ログインするアカウントが違うため、取り違えにくい |

基本の方針は、「システムごと、環境ごとに、アカウントを分ける」です。アカウントの数は増えますが、後で述べる仕組みを使えば、管理の手間は数に比例しません。

## 組織とOU

AWS Organizations は、複数のアカウントを1つの「組織」としてまとめ、一括で管理する仕組みです。

{{fig:org|組織の構成例。アカウントをOU（組織単位）にまとめ、OUごとに決まりを適用する}}

| 用語 | 役割 |
|---|---|
| 管理アカウント | 組織を作ったアカウント。請求をまとめ、組織の設定を行う。強い権限を持つため、業務のシステムは置かず、使う人もごく少数に限る |
| メンバーアカウント | 組織に属する、そのほかのアカウント |
| OU（組織単位） | アカウントをまとめる入れ物。決まり（ポリシー）を、OUごとに適用できる |

AWSは、次のようなOUの構成を勧めています。最初に作るのは、基盤となるSecurityとInfrastructureの2つです。

| OU | 置くアカウント |
|---|---|
| Security | 組織全体の操作の記録を集めるアカウント（ログ集約）。セキュリティの検知と監査に使うアカウント |
| Infrastructure | ネットワークの中継点、共通の基盤サービスを置くアカウント |
| Workloads | 業務のシステムのアカウント。本番と、それ以外を、さらに下のOUで分ける |
| Sandbox | 個人が自由に試すためのアカウント。社内のネットワークにはつながず、支出を制限する |
| そのほか | 利用をやめたアカウントを隔離するOU、決まりを試すためのOU、デプロイの仕組みを置くOUなど |

## SCP：できることの上限を決める

サービスコントロールポリシー（SCP）は、OUやアカウントに付けて、その中で「できることの上限」を決めるポリシーです。次の4つの性質を、正確に押さえてください（[SCPの解説](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html)）。

1. 権限を与えるものではない：SCPで許可されていても、IAMのポリシーで許可されていなければ、操作できない
2. 管理アカウントには効かない：管理アカウントの中の人とロールは、SCPの制限を受けない。業務のシステムを管理アカウントに置かない理由の1つ
3. メンバーアカウントのルートユーザーにも効く：IAMのポリシーでは制限できないルートユーザーも、SCPで制限できる
4. サービスにひも付いた特別なロール（サービスリンクロール）には効かない

SCPは、「このOUの中では、誰であっても、これはできない」という、予防のための柵として使います。よく使われる例は次のとおりです。

- 使わないリージョンでの操作を禁止する
- 操作の記録（CloudTrail）や、検知の仕組み（GuardDuty など）の停止や設定変更を禁止する
- アカウントが組織から離脱することを禁止する
- 特定の高価な種類の資源の作成を禁止する

使うリージョンを東京と大阪に限定するSCPの例を示します。リージョンに属さないサービス（IAMなど）を除外するために、NotAction を使っています。この例の除外は、仕組みを示すための最小限のものです。そのまま適用すると、後の注意書きのとおり、必要な操作まで止まります。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideAllowedRegions",
      "Effect": "Deny",
      "NotAction": ["iam:*", "organizations:*", "route53:*", "cloudfront:*", "support:*", "sts:*"],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["ap-northeast-1", "ap-northeast-3"] }
      }
    }
  ]
}
```

:::warn この例を、そのまま使わない
リージョンを絞るSCPでは、除外するサービスの選び方で、事故が起きます。

- バージニア北部（us-east-1）でしか作れない資源がある。CloudFrontに付ける証明書（ACM）と、CloudFront用のAWS WAFは、us-east-1 に作る。上の例は `acm:*` と `wafv2:*` を除外していないため、CloudFrontの独自ドメインの設定や、WAFの設定ができなくなる
- AWS Control Tower が用意しているリージョン拒否のコントロールでは、請求と費用の確認（Cost Explorer、AWS Budgets）、AWS Health、AWS KMS など、数十の項目が除外されている
- 同じコントロールは、組織の管理に使うロールまで止めないよう、特定のロールを対象から外している

除外するサービスは、公式の例を出発点にして、自社で使うサービスに合わせて決めます。一覧は更新されるため、写したままにせず、見直します（[リージョンにもとづいてアクセスを拒否する例](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_examples_aws_deny-requested-region.html) ／ [AWS Control Tower のリージョン拒否](https://docs.aws.amazon.com/controltower/latest/userguide/ou-region-deny.html)）。
:::

:::warn SCPは、試してから広げる
SCPは強力で、誤ると、配下のすべてのアカウントで必要な操作までできなくなります。新しいSCPは、まず試験用のOUで確かめ、次に影響の小さいOUへ、最後に本番のOUへ、と段階を踏んで適用します。
:::

## 予防する柵と、見つける柵

決まりを守らせる方法は、2種類あります。

| 種類 | 仕組み | 向いている決まり |
|---|---|---|
| 予防（できないようにする） | SCP、RCP | 例外がなく、破られると重大なもの。記録の停止の禁止、使わないリージョンの禁止など |
| 発見（見つけて知らせる、直す） | AWS Config のルール、Security Hub CSPM | 例外があり得るもの、状況によって判断が必要なもの。暗号化されていない保存領域、広く開いたセキュリティグループなど |

すべてを予防で縛ると、正当な作業まで止めてしまいます。「絶対に許さないこと」は少数に絞って予防し、それ以外は発見して是正する、という組み合わせにします。AWS Control Tower は、この章で述べる組織、OU、柵、記録の集約を、まとめて設定・管理するサービスです。

## 人はどう入るか

アカウントごとにIAMユーザーを作ると、アカウントの数だけ、ユーザーとパスワードが増えます。そこで、人の入口を1つにまとめます。

- AWS IAM Identity Center を使い、会社の認証基盤（Microsoft Entra ID など）と連携する。入社、異動、退職が、会社の認証基盤の操作だけでAWSの権限に反映される
- 「閲覧のみ」「開発者」「管理者」のような権限のまとまりを定義し、「誰が、どのアカウントに、どの権限で入れるか」を割り当てる
- 本番のアカウントは、通常は閲覧のみとし、変更が必要なときだけ、申請して一時的に強い権限を得る

## 記録と検知を集める

アカウントが多数あると、記録や検知の結果が分散します。組織の機能を使って、まとめて有効にし、一か所に集めます。

- 操作の記録：組織全体を対象にした証跡（組織の証跡）を作り、ログ集約アカウントのS3に保存する。各アカウントの管理者にも消せないよう、保存先のアカウントを分けるのが要点
- 検知：GuardDuty や Security Hub CSPM は、組織全体で有効にし、結果をセキュリティ用のアカウントに集める。新しく作られたアカウントにも、自動で適用される
- 設定の記録：AWS Config の結果も、同じように集約する

## アカウントを、型から作る

新しいシステムのためのアカウントを、依頼のたびに手作業で作っていては、設定がばらつきます。アカウントの作成を型にし、作った時点で次のものが入っているようにします。

- 所属するOUと、それに伴うSCP
- 記録と検知の設定
- 標準のネットワーク（VPCと、社内や共通基盤への接続。{{ch:xnet}}）
- 人が入るための権限の割り当て
- 予算と、通知の宛先
- 名前とタグの決まり

これらをコードで定義しておくと、依頼から短時間で、安全な初期状態のアカウントを渡せます。開発チームは、土台の上で、自分のシステムに集中できます。

:::sum
- アカウントは最も強い境界。システムごと、環境ごとに分けると、権限、影響の範囲、費用が自然に分かれる
- SCPは上限を決める柵で、権限は与えない。管理アカウントには効かず、メンバーアカウントのルートユーザーには効く
- 絶対に許さないことは予防で、それ以外は発見して是正する
- 人の入口、記録、検知を組織でまとめ、新しいアカウントは型から作る
:::

## 章末問題

:::q 判定 | SCPは誰に効くか
Workloads OU に、「東京と大阪以外のリージョンでの操作を拒否する」SCPを適用しました。次の3人は、バージニア北部リージョンでEC2を起動できますか。

1. Workloads OU の中のアカウントで、管理者権限（AdministratorAccess）のロールを使っている人
2. Workloads OU の中のアカウントの、ルートユーザー
3. 組織の管理アカウントで、管理者権限のロールを使っている人
:::a
1. できない。IAMのポリシーで許可されていても、SCPの拒否が優先される
2. できない。SCPは、メンバーアカウントのルートユーザーにも効く
3. できる。SCPは、管理アカウントには効かない。また、このSCPは Workloads OU に付けたもので、管理アカウントはそのOUの中にない

3が示すとおり、管理アカウントは柵の外にあります。だからこそ、管理アカウントに入れる人を最小限にし、業務のシステムを置かず、多要素認証と操作の監視を特に厳しくします。
:::

:::q 原因 | SCPで許可したのに操作できない
ある担当者が、「OUに、S3のすべての操作を許可（Allow）するSCPを付けた。それなのに、配下のアカウントの開発者がS3を操作できない」と困っています。何を確認しますか。
:::a
SCPは、権限を与えるものではありません。SCPの許可は「この範囲までなら、IAMのポリシーで許可してよい」という上限を示すだけです。開発者がS3を操作するには、開発者のロールのIAMのポリシーで、S3の操作が許可されている必要があります。

確認すること：

1. 開発者が使っているロールのIAMのポリシーに、必要なS3の操作の許可があるか
2. 上位のOUや組織のルートに付いたSCPで、拒否されていないか。SCPは、ルートからそのアカウントまでの、すべての階層で許可されている必要がある
3. アクセス許可の境界や、バケットポリシーで拒否されていないか

なお、許可するものを列挙する形のSCPに切り替えると、列挙していないサービスはすべて使えなくなります。多くの組織は、既定のすべてを許可するSCPを残したまま、禁止したいことだけを拒否する形で使っています。
:::

:::q 設計 | アカウントの分け方を決める
ある会社は、3つの業務システム（受注、在庫、会員）を持ち、それぞれに本番、検証、開発の環境があります。現在は、すべてが1つのAWSアカウントに入っています。組織とOU、アカウントの構成を提案してください。移行の順序についても、考えを述べてください。
:::a
解答例：

- 管理アカウント：請求と組織の管理だけ。業務のシステムは置かない
- Security OU：ログ集約アカウント、セキュリティ用のアカウント
- Infrastructure OU：ネットワーク用のアカウント
- Workloads OU
    - Prod OU：受注の本番、在庫の本番、会員の本番（3アカウント）
    - NonProd OU：受注、在庫、会員それぞれの検証と開発。検証と開発を1つのアカウントにまとめるか分けるかは、チームの体制で決める（3〜6アカウント）
- Sandbox OU：個人の検証用

Prod と NonProd でOUを分けるのは、適用する決まりが違うためです。本番には、資源の削除の制限や、変更の手順に関する厳しい決まりを適用します。

移行の順序：

1. 組織を作り、基盤（記録の集約、検知、人の入口）を先に整える
2. 新しく作るシステムや環境から、新しいアカウントに作る
3. 既存のものは、開発、検証、本番の順に移す。IaCで管理されていれば、新しいアカウントに作り直して切り替える形が取りやすい
4. 元のアカウントは、空になったら利用をやめる

現在の1つのアカウントを、そのまま組織の管理アカウントにするのは避けます。業務のシステムが管理アカウントに残ってしまうためです。新しく管理用のアカウントを作り、既存のアカウントをメンバーとして招待する形にします。
:::

:::q 選択 | 予防か、発見か
次の4つの決まりについて、予防（SCP）と発見（Config のルールなど）のどちらで守らせるのが適切かを答えてください。

1. 操作の記録（CloudTrail）を、誰にも止めさせない
2. S3のバケットは、原則として暗号化する
3. 東京と大阪以外のリージョンは使わない
4. セキュリティグループで、22番ポートを 0.0.0.0/0 に開けない
:::a
1. 予防。例外がなく、破られると、その後の不正を追えなくなる
2. 発見（または、既定の設定で対応）。S3は、新しいオブジェクトを既定で暗号化する。どの鍵を使うかといった決まりは、発見して是正する形が扱いやすい
3. 予防。使わないリージョンを塞ぐことで、乗っ取られたときに、気づきにくい場所に資源を作られる危険を減らせる。ただし、リージョンに属さないサービスの除外を誤ると、必要な操作まで止まるため、試してから適用する
4. 発見と、自動の是正。SCPでは「開ける範囲」のような細かい条件を表しにくい。Config のルールで検出し、通知するか、自動でルールを削除する

判断の軸は、「例外が一切ないか」「条件を単純に書けるか」「誤って止めたときの影響が許容できるか」です。
:::
