:::goal
- ステップ2〜4の構成をTerraformのコードで定義し、削除した状態からコマンド1つで作り直せる
- 適用の前に plan を読み、何が作られ、何が変更・置き換え・削除されるかを説明できる
- ステートの役割を説明でき、手動の変更とコードのずれ（ドリフト）を検出して解消できる

ステップ2〜4の構成をコードで定義し、何度でも同じ環境を作り直せるようにします。ここまでのステップで、同じ構成を何度か手で作り直してきたはずです。その手間と、「前回と同じに作れたか自信がない」という不安を、コードで解消します。



端末から操作する前に、{{ch:s1}}の「手元の端末は一時的な認証情報で操作する」を実施します。`aws sts get-caller-identity --profile cloudbook-lab` で対象を確認し、IaCにも同じ学習用プロファイルを指定してください。アクセスキーをIaCファイルやステートへ書き込みません。

## ツールを選ぶ

| ツール | 特徴 | 向いている場面 |
|---|---|---|
| AWS CloudFormation | AWS公式。YAMLかJSONで書き、追加のツールが要らない | AWSだけを使う案件、IaCの仕組みの理解 |
| AWS CDK | TypeScriptやPythonで書き、CloudFormationに変換して実行する | プログラミングに慣れた開発チーム |
| Terraform | AWS以外のクラウドやサービスも同じ書き方で扱える | 複数のクラウドを使う案件、すでに採用している案件 |

案件で使われているツールを優先して学ぶのが効率的です。決まっていなければ、この章の実習で使うTerraformから始めてください。完成形のコード（参考実装）をこの本のリポジトリに置いてあり、自分のコードと見比べられます。CloudFormationやCDKを使う案件に入る場合も、考え方は共通しています。

| 考え方 | CloudFormation | Terraform |
|---|---|---|
| あるべき構成を書いたファイル | テンプレート | 設定ファイル（.tf） |
| 1回の適用でまとめて管理される単位 | スタック | ステート（state）で管理される範囲 |
| 適用前の差分の確認 | 変更セット | terraform plan |
| 適用 | スタックの作成・更新 | terraform apply |
| 実際の構成とのずれの検出 | ドリフト検出 | terraform plan で差分として表示される |
| 消えては困る資源の保護 | DeletionPolicy、スタックの終了保護 | lifecycle の prevent_destroy、資源ごとの削除保護 |

「手順」ではなく「あるべき状態」を書く、という点が要です。ツールは、今の状態とあるべき状態を比べ、差を埋めるために必要な操作を自分で決めます。

## 段階1：VPCを書いて、作って、消す

最初に、版の指定と、プロバイダーの設定を書きます。

```hcl
# labs/terraform/versions.tf
terraform {
  required_version = ">= 1.11.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
```

```hcl
# labs/terraform/providers.tf
locals {
  # 資源の名前の先頭に付ける。例：cloudbook-lab
  name = "${var.project}-${var.env}"

  # すべての資源に付けるタグ。費用の内訳と、消し忘れの確認に使う
  tags = {
    Project   = var.project
    Env       = var.env
    ManagedBy = "terraform"
  }
}

provider "aws" {
  region = var.region

  default_tags {
    tags = local.tags
  }
}
```

`required_providers` は、AWSを操作するための部品（プロバイダー）と、その版の範囲です。`~> 6.0` は「6.x の中で新しいもの」を表します。`default_tags` に書いたタグは、タグを付けられる資源に自動で付きます。費用の内訳を見るときと、消し忘れを探すときに使います。

環境ごとに変える値は、変数にします。

```hcl
# labs/terraform/variables.tf
variable "project" {
  description = "資源の名前とタグに使う、システムの名前"
  type        = string
  default     = "cloudbook"

  validation {
    condition     = can(regex("^[a-z][a-z0-9-]{1,14}$", var.project))
    error_message = "project は、英小文字で始まる2〜15文字（英小文字、数字、ハイフン）にしてください。"
  }
}

variable "env" {
  description = "環境の名前。同じコードから別の環境を作るときに変える"
  type        = string
  default     = "lab"

  validation {
    condition     = contains(["lab", "dev", "stg", "prod"], var.env)
    error_message = "env は lab、dev、stg、prod のいずれかにしてください。"
  }
}

variable "region" {
  description = "作成先のリージョン"
  type        = string
  default     = "ap-northeast-1"
}
```

`validation` は、値の決まりを書く場所です。決まりに合わない値を渡すと、何も作る前にエラーになります。

次に、{{ch:s2}}のアドレス設計を、そのままコードにします。

```hcl
# labs/terraform/network.tf
data "aws_availability_zones" "available" {
  state = "available"

  # Local Zone など、別に申し込みが要る場所は除く
  filter {
    name   = "opt-in-status"
    values = ["opt-in-not-required"]
  }
}

# アドレス設計。第13章の表と同じ内容を、1か所にまとめて書く
locals {
  # 使えるAZのうち、先頭の2つを使う（東京リージョンでは 1a と 1c になることが多い）
  azs = slice(data.aws_availability_zones.available.names, 0, 2)

  subnets = {
    public-a = { tier = "public", az = local.azs[0], cidr = "10.0.0.0/24" }
    public-c = { tier = "public", az = local.azs[1], cidr = "10.0.1.0/24" }
    app-a    = { tier = "app", az = local.azs[0], cidr = "10.0.10.0/24" }
    app-c    = { tier = "app", az = local.azs[1], cidr = "10.0.11.0/24" }
    db-a     = { tier = "db", az = local.azs[0], cidr = "10.0.20.0/24" }
    db-c     = { tier = "db", az = local.azs[1], cidr = "10.0.21.0/24" }
  }
}

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "${local.name}-vpc"
  }
}

# 表の1行が、サブネット1つになる
resource "aws_subnet" "this" {
  for_each = local.subnets

  vpc_id            = aws_vpc.main.id
  availability_zone = each.value.az
  cidr_block        = each.value.cidr

  tags = {
    Name = "${local.name}-${each.key}"
    Tier = each.value.tier
  }
}
```

読み方は、次のとおりです。

- `data` は、すでにあるものを調べる。ここでは、このアカウントで使えるAZの一覧。`filter` で、Local Zone のように別に申し込みが要る場所を除いている。除かないと、申し込んだアカウントでは、名前の並び順で、それが先頭に来ることがある
- `locals` は、コードの中で使う、名前を付けた値。アドレス設計の表を、1か所にまとめている
- `resource` は、作るもの。`aws_vpc.main.id` のように、ほかの資源を名前で参照する。Terraformは、この参照から、作る順番（VPCが先、サブネットが後）を自分で決める
- `for_each` は、表の1行ごとに、資源を1つ作る。作られたサブネットは、`aws_subnet.this["public-a"]` のように、表の名前で指す

書けたら、次の順に実行します。

```bash
terraform init      # プロバイダーを取得する。最初の1回と、版の指定を変えたときに実行する
terraform fmt       # 書式をそろえる
terraform validate  # 文法と、項目の名前や型の誤りを調べる
terraform plan      # 何が起きるかを表示する。まだ何も作らない
terraform apply     # plan をもう一度表示する。yes と答えると作る
```

`terraform plan` の最後に、次の1行が出ます。VPCが1つと、サブネットが6つです。

```text
Plan: 7 to add, 0 to change, 0 to destroy.
```

`apply` の後、管理画面と{{ch:s2}}のCLIで、手で作ったときと同じものができていることを確かめます。確かめたら `terraform destroy` で消し、もう一度 `terraform apply` で作ります。この「作成 → 削除 → 作成」を、手順を見ずにできるまで繰り返してください。

### plan の読み方

plan は、資源ごとに、先頭の記号で、何が起きるかを示します。

| 記号 | 意味 | 注意すること |
|---|---|---|
| `+` | 作る | 作ってみるまで決まらない値（IDなど）は、`(known after apply)` と表示される |
| `~` | 今ある資源を、そのまま変更する | 項目によっては、変更の間に通信が途切れる |
| `-/+` | 今ある資源を削除し、新しく作り直す（置き換え） | 原因になった項目に `# forces replacement` と表示される。データを持つ資源では、データを失う |
| `-` | 削除する | コードから消した資源は、削除される |

次の2つを試し、plan の違いを見比べてください。どちらも、plan を見たら適用せずに、コードを元に戻します。

1. VPCの `Name` タグの値を変える。`~`（そのまま変更）になる
2. サブネット `app-a` のCIDRを `10.0.12.0/24` に変える。`-/+`（置き換え）になり、CIDRの行に `# forces replacement` が付く

差分は、「何行変わったか」ではなく、「資源ごとに、追加・変更・置き換え・削除のどれか」で読みます。最後の `Plan:` の行で、置き換えと削除の数が予想と合っているかを、必ず確かめます。

## 段階2：経路、サーバー、ロードバランサーを足す

### 経路

インターネットゲートウェイ、NATゲートウェイ、3つのルートテーブルを足します。まず、NATゲートウェイです。

```hcl
# labs/terraform/network.tf
# NATゲートウェイは、パブリックサブネットに置く。置いてある間、時間料金がかかる
resource "aws_nat_gateway" "main" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.this["public-a"].id

  tags = {
    Name = "${local.name}-nat"
  }

  # インターネットゲートウェイが付く前に作ると、外へ出られない
  depends_on = [aws_internet_gateway.main]
}
```

`depends_on` は、参照からは読み取れない順番を、Terraformに伝える書き方です。NATゲートウェイのコードは、インターネットゲートウェイを参照していません。しかし、インターネットゲートウェイが付く前に作っても、外へは出られません。このように、「参照はないが、順番はある」関係にだけ使います。

次に、DB用のルートテーブルと、関連付けです。

```hcl
# labs/terraform/network.tf
# DB用は、外部への経路を持たない。空であることを明示し、手で足された経路を差分として検出する
resource "aws_route_table" "db" {
  vpc_id = aws_vpc.main.id
  route  = []

  tags = {
    Name = "${local.name}-db"
  }
}

locals {
  route_table_ids = {
    public = aws_route_table.public.id
    app    = aws_route_table.app.id
    db     = aws_route_table.db.id
  }
}

# 関連付けを忘れたサブネットは、メインルートテーブルに従ってしまう。6つすべてを関連付ける
resource "aws_route_table_association" "this" {
  for_each = local.subnets

  subnet_id      = aws_subnet.this[each.key].id
  route_table_id = local.route_table_ids[each.value.tier]
}
```

- DB用のルートテーブルは、`route = []` で、経路を持たないことを明示している。この行を省略すると、Terraformは経路を管理の対象から外し、だれかが手で足した経路に気づけなくなる
- 関連付けは、6つのサブネットすべてに作る。{{ch:s2}}で見たとおり、関連付けを忘れたサブネットは、メインルートテーブルに従ってしまう

### セキュリティグループ

```hcl
# labs/terraform/security.tf
resource "aws_security_group" "app" {
  name        = "${local.name}-app"
  description = "App: HTTP from ALB only"
  vpc_id      = aws_vpc.main.id

  tags = {
    Name = "${local.name}-app"
  }
}

# 送信元は、IPアドレスではなくALBのセキュリティグループで指定する。22番（SSH）は開けない
resource "aws_vpc_security_group_ingress_rule" "app_from_alb" {
  security_group_id            = aws_security_group.app.id
  description                  = "HTTP from ALB"
  referenced_security_group_id = aws_security_group.alb.id
  ip_protocol                  = "tcp"
  from_port                    = 80
  to_port                      = 80
}
```

送信元を、IPアドレスではなく、ALBのセキュリティグループで指定しています（`referenced_security_group_id`）。{{ch:net}}の設定例と同じ考え方です。ルールは、セキュリティグループとは別の資源として、1つずつ書きます。

### サーバーとロードバランサー

サーバーの中身を作るスクリプトは、{{ch:s3}}と同じものを `user_data.sh` というファイルに置き、起動テンプレートから読み込みます。

```hcl
# labs/terraform/compute.tf
resource "aws_launch_template" "app" {
  name_prefix            = "${local.name}-app-"
  image_id               = nonsensitive(data.aws_ssm_parameter.al2023.value)
  instance_type          = var.instance_type
  vpc_security_group_ids = [aws_security_group.app.id]
  user_data              = filebase64("${path.module}/user_data.sh")
  update_default_version = true

  iam_instance_profile {
    arn = aws_iam_instance_profile.app.arn
  }

  # サーバーの中から認証情報を取り出す経路（IMDS）は、v2だけを許可する
  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required"
    http_put_response_hop_limit = 1
  }

  # default_tags は、Auto Scaling が起動するサーバーには付かない。ここで付ける
  tag_specifications {
    resource_type = "instance"

    tags = merge(local.tags, {
      Name = "${local.name}-app"
    })
  }
}
```

```hcl
# labs/terraform/compute.tf
resource "aws_autoscaling_group" "app" {
  name                = "${local.name}-app"
  min_size            = var.app_min_size
  max_size            = var.app_max_size
  vpc_zone_identifier = [aws_subnet.this["app-a"].id, aws_subnet.this["app-c"].id]
  target_group_arns   = [aws_lb_target_group.app.arn]

  # ALBが異常と判断したサーバーを入れ替える。猶予期間は、起動にかかる時間より長くする
  health_check_type         = "ELB"
  health_check_grace_period = 120

  launch_template {
    id      = aws_launch_template.app.id
    version = aws_launch_template.app.latest_version
  }

  # 起動テンプレートを変えたら、サーバーを半分ずつ入れ替える
  instance_refresh {
    strategy = "Rolling"

    preferences {
      min_healthy_percentage = 50
    }
  }

  # サーバーは起動時に外へ出て、ソフトウェアを取得する。経路ができる前に起動させない
  depends_on = [aws_route_table_association.this]
}
```

ここにも `depends_on` があります。サーバーは起動時に、NATゲートウェイを通って外へ出て、Webサーバーのソフトウェアを取得します。経路ができる前にサーバーが起動すると、取得に失敗します。{{ch:s2}}の「わざと壊してみる」で体験した状態が、作る順番によって起きるということです。手で作るときは人が順番を守りますが、コードでは、順番を書いておかなければなりません。参考実装では、ALBにも同じ理由で `depends_on` を書いています。

作った後に使う値は、出力にします。

```hcl
# labs/terraform/outputs.tf
output "alb_url" {
  description = "ブラウザや curl で開くURL"
  value       = "http://${aws_lb.main.dns_name}"
}
```

```bash
terraform apply
# サーバーが起動して、正常と判定されるまで、数分待つ
for i in $(seq 10); do curl -s "$(terraform output -raw alb_url)"; echo; done
```

ホスト名が2種類以上表示されれば、{{ch:s3}}と同じ構成ができています。

## 段階3：データベースを足す

```hcl
# labs/terraform/database.tf
resource "aws_db_instance" "main" {
  identifier     = "${local.name}-db"
  engine         = "postgres"
  engine_version = var.db_engine_version
  instance_class = var.db_instance_class

  allocated_storage = 20
  storage_type      = "gp3"
  storage_encrypted = true

  db_name  = "appdb"
  username = "postgres"

  # パスワードは書かない。RDSが生成して、Secrets Manager に保管する
  manage_master_user_password = true

  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.db.id]
  publicly_accessible    = false
  multi_az               = var.db_multi_az

  backup_retention_period = 1
  apply_immediately       = true

  # 学習用の設定。本番では、削除保護を有効にし、削除時に最終スナップショットを残す
  deletion_protection = false
  skip_final_snapshot = true
}
```

- パスワードを書く場所がない。`manage_master_user_password = true` を指定すると、RDSがパスワードを生成し、Secrets Manager に保管する。Terraformが知るのは、保管先（シークレットのARN）だけである
- `password` という項目に値を渡す書き方もあるが、その値は、ステートに読める形で残る。この章では使わない
- `deletion_protection` と `skip_final_snapshot` は、何度も作り直すための、学習用の設定。本番では、どちらも逆にする

アプリサーバーには、このデータベースの接続情報だけを読む権限を付けます。

```hcl
# labs/terraform/database.tf
# アプリサーバーに、このデータベースの接続情報だけを読む権限を付ける
resource "aws_iam_role_policy" "app_read_db_secret" {
  name = "read-db-secret"
  role = aws_iam_role.app.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect   = "Allow"
        Action   = "secretsmanager:GetSecretValue"
        Resource = aws_db_instance.main.master_user_secret[0].secret_arn
      },
    ]
  })
}
```

`Resource` に「すべて」を表す `*` ではなく、このデータベースのシークレットのARNだけを書いています。{{ch:s1}}の最小権限を、コードで表した形です。

データベースの作成には、10分以上かかることがあります。`apply` が終わったら、{{ch:s4}}と同じ手順で、アプリサーバーから接続できることを確かめます。エンドポイントとシークレットのARNは、`terraform output` で表示できます。

## ステートを知る

Terraformは、「コードのどの資源が、実際のどの資源（ID）に当たるか」を、ステートというファイルに記録します。何も設定しなければ、作業用のフォルダの `terraform.tfstate` です。

{{fig:tfflow|コード、ステート、実際の構成の関係}}

```bash
terraform state list                            # 管理している資源の一覧
terraform state show 'aws_subnet.this["db-a"]'  # 1つの資源について、記録されている内容
```

ステートについて、次のことを守ります。

- 手で編集しない。Gitに追加しない。チャットやメールで送らない。資源のIDや設定の値が入っており、資源によっては秘密の値も入る
- 失わない。ステートを失うと、Terraformは「まだ何も作っていない」と判断する。実際の資源は残っているため、次の `apply` は、同じ名前の資源を作ろうとして失敗するか、二重に作る。元に戻すには、資源を1つずつステートへ取り込み直す作業（インポート）が要る
- 手元に置くのは、1人で学習する間だけにする

チームで使うときは、ステートを共有の場所に置き、同時に適用できないようにロックします。AWSでは、S3に置く設定がよく使われます。

```hcl
terraform {
  backend "s3" {
    bucket       = "example-tfstate-111122223333"
    key          = "cloudbook/lab/terraform.tfstate"
    region       = "ap-northeast-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

`use_lockfile = true` は、S3だけでロックを行う設定です。以前は、ロックにDynamoDBのテーブルを使っていましたが、その方式は非推奨になりました。古い記事や既存の案件には、DynamoDBを使う設定（`dynamodb_table`）が残っています。バケットは、バージョニングを有効にし（壊したときに、前の版へ戻せる）、読み書きできる人を絞ります。

:::note 2つの「ロック」
`.terraform.lock.hcl` は、プロバイダーの版を固定するファイルで、Gitに追加します。ステートのロックは、2人が同時に適用するのを防ぐ仕組みです。名前は似ていますが、別のものです。
:::

## テストで設計の決まりを守る

「データベースにパブリックアクセスを許可しない」「サーバーは2台以上にする」といった決まりは、人がレビューで見るだけでは、いつか見落とします。Terraformには、決まりをコードで書き、自動で確かめる仕組みがあります。

```hcl
# labs/terraform/tests/design.tftest.hcl
run "database_is_private_and_has_no_password_in_code" {
  command = plan

  assert {
    condition     = aws_db_instance.main.publicly_accessible == false
    error_message = "データベースに、パブリックアクセスを許可しない"
  }

  assert {
    condition     = aws_db_instance.main.manage_master_user_password == true
    error_message = "管理者パスワードは、Secrets Manager に管理させる"
  }

  assert {
    condition     = aws_db_instance.main.storage_encrypted == true
    error_message = "データベースの保存領域を暗号化する"
  }
}
```

```bash
terraform test
```

参考実装のテストは、AWSに接続しない設定（`mock_provider`）で動きます。費用はかからず、数秒で終わります。確かめられるのは「コードにどう書かれているか」までで、実際に作られた資源の状態ではありません。作った後の確認は、「実技の合格基準」で行います。自分のコードで使うときは、テストの中の資源の名前を、自分のコードに合わせます。

## 進め方

1. 準備をし、段階1のVPCを「作成 → 削除 → 作成」できるようにする
2. 段階2、段階3を、少しずつ足す。足すたびに plan を読み、予想と合っていることを確かめてから適用する
3. 変更のたびに、Gitにコミットする。コミットの前に、`terraform fmt` と `terraform validate` を通す
4. 参考実装と見比べ、違いを説明する
5. 「わざと壊してみる」で、手動の変更がどう見えるかを確かめる
6. その日のうちに、`terraform destroy` で消す

## つまずきやすい点

| 症状 | よくある原因 | 対処 |
|---|---|---|
| `No valid credential sources found` と表示される | プロファイルを選んでいない。セッションが切れた。ツールが、ログインの方式に対応していない | `aws sts get-caller-identity` が通るかを確かめる。通るのにTerraformだけ失敗するなら、「準備」の `credential_process` の設定を使う |
| `Inconsistent dependency lock file` と表示される | プロバイダーの版の指定を変えた。`.terraform` フォルダーがない | `terraform init` を実行する。版を上げる場合は `terraform init -upgrade` を実行し、変わった `.terraform.lock.hcl` をコミットする |
| `apply` が途中で失敗した | 一部の資源だけが作られた状態。作られた分は、ステートに記録されている | エラーを読んでコードを直し、もう一度 `apply` する。途中まで作られた資源を、管理画面から手で消さない |
| 小さな変更のつもりが、資源が作り直された | 変更した項目が、置き換えを伴う種類だった | 適用の前に、plan に `-/+` と `# forces replacement` がないかを必ず確認する |
| 管理画面で直した設定が、次の適用で元に戻った | コードに書かれた状態が「正」として適用された | 手で直した内容は、コードにも反映する |
| `Error acquiring the state lock` と表示される | ほかの人が適用している。または、前回の実行が途中で止まり、ロックが残った | ほかの人が実行していないことを確かめてから、`terraform force-unlock` でロックを外す |
| `destroy` が、VPCやサブネットの削除で止まる | Terraformの管理外の資源（手で作ったサーバーなど）が、VPCの中に残っている | 残っている資源を管理画面で探して消し、もう一度 `destroy` する |
| （CloudFormation）初回の作成に失敗し、スタックが ROLLBACK_COMPLETE のまま更新できない | 最初の作成に失敗したスタックは、更新できない | イベントの一覧で、最初に失敗した資源とその理由を読む。スタックを削除し、テンプレートを直して作り直す |

## 設計の問い

コードで書けるようになると、次は「どう分けるか」が問いになります。

- 何を1つの単位にまとめるか：ネットワーク、データベース、アプリのように、変更の頻度と影響の範囲が違うものは分ける。毎日変わるアプリの設定と、めったに変えないVPCを同じ単位にすると、アプリの変更のたびにネットワークまで差分の確認が必要になる。参考実装は、学習のために1つにまとめてある
- 環境の違いをどう表すか：開発・検証・本番で同じコードを使い、違いは変数で渡す。環境ごとにコードを複製すると、やがて内容がずれていく
- 消えては困るものをどう守るか：データベースやバケットには、削除保護や、削除時に残す設定（Terraformの `prevent_destroy`、CloudFormationの DeletionPolicy）を付ける
- 秘密情報をどう扱うか：パスワードはコードにも変数にも書かず、Secrets Manager に生成・管理させて参照する

## 確認ポイント

- すべて削除した状態から、コマンド1つで同じ環境を作り直せる
- 適用前に、何が作られ、何が変更・削除されるかを確認できる
- パスワードなどの秘密情報をコードに書いていない
- ステートに何が記録されているか、失うと何が起きるかを説明できる

## 実技の合格基準

次のすべてを、コマンドの出力で示せたら合格です。

| 番号 | 確かめること | 合格の状態 |
|---|---|---|
| 1 | 書式と文法が整っている | `terraform fmt -check -recursive` が何も表示せずに終わり、`terraform validate` が成功する |
| 2 | コードと実際の構成が一致している | `apply` の直後の `terraform plan` が `No changes.` と表示する |
| 3 | 作り直せる | `destroy` の後、`apply` だけで同じ構成ができ、ALBのURLがホスト名を返す。かかった時間を記録している |
| 4 | 秘密の値と、残してはいけないファイルが、Gitにない | パスワードやアクセスキーがコードにない。ステート、`.terraform`、`terraform.tfvars` がGitの管理下になく、`.terraform.lock.hcl` はある |
| 5 | 決まりをテストで確かめている | 自分のコードに合わせたテストを1つ以上書き、`terraform test` が成功する |
| 6 | 手動の変更の見え方を説明できる | 「わざと壊してみる」の3つについて、plan の表示と、その理由を説明できる |
| 7 | 片付けが済んでいる | `terraform state list` が何も表示せず、タグでの検索にも資源が残っていない |

```bash
# 1
terraform fmt -check -recursive
terraform validate
# 2
terraform plan
# 3
terraform destroy
time terraform apply -auto-approve
curl -s "$(terraform output -raw alb_url)"
# 4
git grep -n -i -E 'password|secret_access_key|AKIA' -- '*.tf' '*.tfvars'
git ls-files
# 5
terraform test
```

4の1つ目のコマンドで表示されてよいのは、`manage_master_user_password` の行と、その説明だけです。`-auto-approve` は、確認を省いて適用する指定です。時間を計るために使っています。学習用の環境以外では使いません。

提出するもの：自分のリポジトリ（コードとテスト）、1〜5の出力、6の説明、作り直しにかかった時間。

## わざと壊してみる

:::lab
`apply` が済んだ状態で、管理画面から、次の3つの変更を手で加えます。1つ加えるたびに、結果を予想してから `terraform plan` を実行し、表示を記録してください。

1. アプリ用のセキュリティグループに、受信ルールを1つ足す（例：自分のIPアドレスからの8080番）
2. DB用のルートテーブルに、経路を1つ足す（例：0.0.0.0/0 → インターネットゲートウェイ）
3. VPCの `Name` タグを、別の値に書き換える

参考実装の書き方では、2と3は差分として表示され、1は表示されません。なぜ1だけ表示されないのかを、説明してください。手がかりは、Terraformが見ているのは「コードに書いた資源」だけだという点と、ルールをセキュリティグループとは別の資源として書いている点です。

次に、コードを変えずに `terraform apply` を実行し、3つの変更がそれぞれどうなったかを確かめます。最後に、1で足したルールを手で消します。案件で「手動の変更がいつの間にか消えた（消えなかった）」ときの理解に役立ちます。差分に出ない変更を見つける手段（{{ch:s5}}のCloudTrail、{{ch:sec}}のAWS Config）も、あわせて考えてください。
:::

## 片付け

IaCで作ったものは、必ずIaCのコマンドで削除します（`terraform destroy`、CloudFormationならスタックの削除）。管理画面から個別に消すと、ツールの記録と実際の構成がずれ、次の操作が失敗します。

```bash
terraform destroy
terraform state list   # 何も表示されなければ、Terraformの管理下に残っている資源はない

# タグで、消し残しを探す（削除した直後の資源が、しばらく表示されることがある）
aws resourcegroupstaggingapi get-resources --tag-filters Key=Project,Values=cloudbook \
  --query 'ResourceTagMappingList[].ResourceARN'
```

「わざと壊してみる」で手で足したものは、Terraformの管理外です。`destroy` の前に、手で消しておきます。

## 本番ではどう変わるか

| 項目 | 学習での進め方 | 本番で加わること |
|---|---|---|
| 適用する人 | 自分の端末から自分で適用する | CI/CDから適用する。人の端末には、本番を変更できる権限を持たせない |
| レビュー | なし | コードの変更と、適用前の差分の両方を、ほかの人が確認してから適用する |
| ステート | 手元のファイル | 共有の場所に置き、ロック、暗号化、バージョニングを有効にする。読み書きできる人を絞る |
| 版の固定 | 入れた版をそのまま使う | Terraformとプロバイダーの版を固定し、上げるときは差分を確認する。`.terraform.lock.hcl` をレビューの対象にする |
| コードの分け方 | 1つのフォルダー | ネットワーク、データ、アプリなどに分ける。繰り返し使う部分は、モジュールにする |
| 手動の変更 | 自由 | 原則として禁止。障害対応でやむを得ず行った場合は、後で必ずコードに反映する |
| ずれの検出 | 気づいたときに | 定期的に plan を実行し、ずれが見つかったら通知する |
| 既存の資源 | すべて新しく作る | 手で作られた既存の資源を、コードの管理下に取り込む作業（インポート）が発生する |

:::sum
- IaCは「手順」ではなく「あるべき状態」を書く。ツールが差分から必要な操作を決める
- 適用の前に必ず差分を確認する。特に「置き換え」と「削除」を見落とさない
- 変更の入口をコードに一本化する。手動の変更は、ずれと事故のもとになる
- ステートは、コードと実際の資源を結び付ける記録。失わず、漏らさず、同時に書き換えさせない
- 変更の頻度と影響の範囲で単位を分け、環境の違いは変数で表す
:::

## 章末問題

:::q 読み取り | 差分に「置き換え」が出た
本番のデータベース（RDS）の設定を1か所変更するため、テンプレートを直して変更セットを作りました。差分を見ると、RDSの資源に「置き換え：True」と表示されています。このまま適用すると何が起きますか。どうすべきですか。
:::a
「置き換え」は、今の資源を変更するのではなく、新しい資源を作り、古い資源を削除することを意味します。データベースの場合、新しい空のデータベースが作られ、データの入った古いデータベースが削除されます。削除時に残す設定をしていなければ、データを失います。

すべきこと：

1. 適用しない
2. どの項目の変更が置き換えを引き起こしているかを、公式ドキュメントの各項目の説明（更新時の動作）で確認する。データベースの識別子、暗号化の有無、サブネットグループなどが該当しやすい
3. その変更が本当に必要かを見直す。必要なら、スナップショットからの復元や、データの移行を含む手順を別に計画する

変更セットや plan は、この種の事故を防ぐための仕組みです。差分は「何行変わったか」ではなく、「追加・変更・置き換え・削除のどれか」を資源ごとに読みます。あわせて、データベースには削除保護と、削除時にスナップショットを残す設定を付けておきます。
:::

:::q 対応 | 障害対応で手動変更をした後
深夜の障害対応で、通信を通すために、管理画面からセキュリティグループのルールを1つ追加して復旧させました。この環境はIaCで管理されています。翌朝、何をすべきですか。
:::a
1. 手動で行った変更を記録する：いつ、誰が、何を、なぜ変えたか。障害報告書にも書く
2. その変更が恒久的に必要かを判断する：一時的な回避策だったのか、もともとコードに欠けていた設定だったのか
3. 必要な変更であれば、コードに反映する：コードを直し、レビューを受け、差分を確認する。このとき、差分が「変更なし」になれば、コードと実際の構成が一致したことになる
4. 不要な変更であれば、元に戻す：これもコードの適用を通じて行うのが望ましい

放置すると、次に誰かがコードを適用したときに、手動で追加したルールが消えて同じ障害が再発する、あるいは残り続けて「誰も理由を知らないルール」になります。緊急時の手動変更そのものは、やむを得ない場合があります。問題は、変更したことではなく、コードに戻さないことです。
:::

:::q 設計 | 1つの巨大なテンプレート
ある案件では、VPC、データベース、アプリのサーバー、監視の設定まで、すべてが1つのテンプレートに書かれています。アプリの設定を毎日変更するたびに、全体の差分を確認して適用しています。どのような問題が起きやすいですか。どう分けますか。
:::a
起きやすい問題：

- 影響の範囲が広い：アプリの小さな変更の適用で、誤ってネットワークやデータベースまで変更する危険がある
- 差分が読みにくい：毎回、関係のない資源まで確認の対象になり、重要な差分を見落としやすい
- 権限を分けられない：アプリの担当者にも、ネットワークやデータベースを変更できる権限が必要になる
- 適用に時間がかかり、失敗したときの巻き戻しも大きくなる

分け方の例：

| 単位 | 中身 | 変更の頻度 |
|---|---|---|
| ネットワーク | VPC、サブネット、ルートテーブル、ゲートウェイ | まれ |
| データ | データベース、バケット | まれ。削除からの保護を付ける |
| アプリ | サーバーやコンテナ、ロードバランサー、アプリ用の権限 | 頻繁 |
| 監視 | アラーム、ダッシュボード | ときどき |

単位の間では、VPCのIDのような値を出力として公開し、ほかの単位から参照します。分ける基準は「一緒に変更されるものは一緒に、別々に変更されるものは別々に」です。
:::

:::q 防止 | スタックを消したらデータベースも消えた
検証環境の整理のつもりでスタックを削除したところ、それは本番のスタックで、データベースも一緒に削除されてしまいました。同じ事故を防ぐ設定や仕組みを、3つ以上挙げてください。
:::a
解答例：

1. 削除時の動作を指定する：データベースの資源に、スタックの削除時にスナップショットを残す、または資源そのものを残す設定（DeletionPolicy）を付ける
2. データベースの削除保護を有効にする：有効な間は、データベースを削除する操作そのものが失敗する
3. スタックの削除保護（終了保護）を有効にする：本番のスタックは、保護を外さない限り削除できない
4. 権限で防ぐ：本番のスタックを削除できる権限を、日常の作業用の権限から外す
5. 環境を取り違えにくくする：本番と検証でAWSアカウントを分ける（{{ch:org}}）。スタックの名前に環境名を入れる
6. バックアップを別に持つ：自動バックアップは、データベースの削除と一緒に消える設定になっていることがある。AWS Backup などで、別に管理されたバックアップを持つ

1つの対策に頼らず、何重にも防ぐのが基本です。特に5の「アカウントを分ける」は、取り違えそのものを起こりにくくする、最も効果の大きい対策です。
:::

:::q 読み取り | count で作ったサブネットを1つ減らす
同僚のコードは、サブネットを次のように作っています。一覧から、真ん中の `10.0.11.0/24` を消して `terraform plan` を実行すると、何が表示されますか。なぜですか。どう書けば避けられますか。

```hcl
variable "cidrs" {
  default = ["10.0.10.0/24", "10.0.11.0/24", "10.0.12.0/24"]
}

resource "aws_subnet" "app" {
  count      = length(var.cidrs)
  vpc_id     = aws_vpc.main.id
  cidr_block = var.cidrs[count.index]
}
```
:::a
`count` は、資源を番号（0、1、2）で区別します。真ん中を消すと、一覧は2つになり、番号1の中身が `10.0.11.0/24` から `10.0.12.0/24` に変わります。plan には、次の2つが表示されます。

- 番号1のサブネット：CIDRが変わるため、置き換え（`-/+`）
- 番号2のサブネット：一覧にないため、削除（`-`）

消したかったのは `10.0.11.0/24` だけなのに、`10.0.12.0/24` のサブネットまで作り直されます。そのサブネットにサーバーがあれば、削除できずに適用が失敗するか、サーバーごと止まります。

避けるには、`for_each` を使い、番号ではなく名前（キー）で区別します。この章の参考実装の書き方です。表から1行を消せば、その行の資源だけが削除されます。

すでに動いている環境で `count` から `for_each` へ書き換えるときは、`moved` ブロックで「同じ資源である」ことをTerraformに伝え、plan が「変更なし」になることを確かめてから適用します。
:::

:::q 判断 | ステートをGitで共有する提案
3人のチームで、Terraformを使い始めました。同僚が「`terraform.tfstate` をGitに入れれば、全員で共有できる」と提案しています。どのような問題がありますか。代わりに、どうしますか。
:::a
問題：

- 秘密の値が漏れる：ステートには、資源の設定が読める形で入る。資源によっては、パスワードや鍵も入る。Gitの履歴に一度入ると、後から消すのは難しい
- 同時に適用できてしまう：2人が同時に `apply` すると、それぞれが古いステートをもとに動き、資源が二重に作られたり、ステートが壊れたりする。Gitには、適用の間だけほかの人を待たせる仕組みがない
- 古いステートで適用してしまう：`git pull` を忘れると、ほかの人が作った資源を知らないまま適用することになる
- 競合を直せない：2人の変更がぶつかると、ステートを手で直すことになる。ステートは、手で編集してはいけない

代わりにすること：

1. ステートを、共有の保存場所（S3など）に置く。保存時の暗号化と、バージョニングを有効にする
2. ロックを有効にし、同時に適用できないようにする
3. ステートを読み書きできる人とロールを絞る
4. 適用は、人の端末からではなく、CI/CDから行う形に移していく

コードはGitで、ステートは専用の保存場所で管理する、と分けて覚えます。
:::
