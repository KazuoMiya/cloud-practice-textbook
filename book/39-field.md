:::goal
- 案件に参画した最初の週に、確かめることと、その理由を説明できる
- 本番環境での作業の決まりを守り、想定外のときに、止めて報告できる
- 相手がすぐに答えられる形で、質問と報告ができる
:::

学習環境と実際の案件の最大の違いは、自分の操作が顧客の業務に直接影響することです。案件に入ってからの動き方を、あらかじめ型として身につけておきましょう。

## 参画した最初の週に確認すること

- [ ] システム構成図と各部品の役割（どれが最新版か）
- [ ] AWSアカウントの分け方（本番・検証・開発が別のアカウントか）と、自分に付与された権限
- [ ] 自分が作業してよい環境と、触ってはいけない環境
- [ ] 名前の付け方とタグのルール
- [ ] 変更の手順（申請、承認、作業してよい時間帯、手順書の書式）
- [ ] IaCのリポジトリの場所と、管理画面での手動変更が許されているか
- [ ] 監視の仕組みと、障害時の連絡体制（誰に、どの手段で）
- [ ] 費用を管理している人と、予算
- [ ] 質問してよい相手と、質問の窓口

## 本番環境で作業するときのルール

1. 手順書を事前に作り、レビューを受ける。実行するコマンド、結果の確認方法、元に戻す手順（切り戻し）まで書く
2. 作業の前に、現在の状態を記録し、必要なバックアップを取る
3. 実行する人と確認する人の2人で作業し、手順を読み合わせながら進める
4. 操作のたびに、画面右上のアカウント名とリージョンを確認する
5. 手順書にない作業はしない。想定と違う結果が出たら、その場で止めて報告する
6. 実行したコマンドと結果を、作業ログとして残す

想定外のときに「止めて報告する」のは失敗ではなく、事故を防ぐ正しい行動です。

手順書は、次のような形で作ります。書式は案件ごとに決まっていますが、含めるべき内容は共通です。

```text
作業名    アプリ用セキュリティグループへの受信ルールの追加
目的      新しい監視サーバーからの、ヘルスチェックの通信を許可する
対象      本番アカウント（1111-2222-3333）／東京リージョン／sg-0abc...（app-sg）
実施日時  2026-11-20 22:00〜22:30   実施者 ○○   確認者 △△
影響      なし（ルールの追加のみ。既存の通信には影響しない）

事前確認
  1. 画面右上のアカウントとリージョンが、対象と一致していること
  2. 現在の受信ルールを記録する（コマンドと、出力の保存先）

作業手順
  3. 受信ルールを追加する（実行するコマンド。値は、すべて埋めておく）
  4. 追加されたことを確かめる（コマンドと、期待する出力）

事後確認
  5. 監視サーバーから、ヘルスチェックが成功すること
  6. 既存の通信（ALBからの通信）に、エラーが増えていないこと

切り戻し  手順3で追加したルールを削除する（実行するコマンド）
中止の基準  手順1、2で、想定と異なる状態だった場合。手順4で、期待する出力と異なる場合
```

よい手順書は、「その作業を初めて行う人が、判断を加えずに実行できる」ものです。コマンドの中の値を、当日に考えて埋めるようでは、誤りが入り込みます。

## 質問と報告のしかた

質問するときは、次の5点をそろえると、相手がすぐに答えられます。

1. 何をしようとしているか（目的）
2. 何をしたか（手順と設定値）
3. 何が起きたか（エラーメッセージの全文と時刻）
4. 自分で調べたこと、試したこと
5. 何を教えてほしいか

一人で長く抱え込まないことも大切です。15〜30分調べても進まなければ相談する、のように自分なりの目安を決めておきましょう。報告は結論から伝え、障害のときは「影響の範囲」「今の状況」「次に報告する時刻」を最初に伝えます。

質問の例を示します。5点がそろっていると、相手は、読んですぐに、答えるか、追加で聞くべきことを判断できます。

```text
【質問】検証環境のアプリサーバーから、RDSに接続できません

目的    検証環境で、新しい版のアプリの動作を確かめたい
したこと アプリサーバー（i-0abc...）に Session Manager で入り、
        psql -h app-stg.xxxx.ap-northeast-1.rds.amazonaws.com -U app -d appdb を実行
起きたこと 約30秒後に、次のエラーになります（11/20 14:05ごろ）
        psql: error: connection to server at "app-stg..." (10.0.20.15), port 5432 failed:
        Connection timed out
調べたこと ・名前解決はできている（10.0.20.15 が返る）
        ・RDSのセキュリティグループ（sg-0def...）の受信ルールは、
          sg-0123...（旧アプリ用）からの5432番だけを許可している
        ・このサーバーのセキュリティグループは sg-0456...（新アプリ用）
知りたいこと RDSのセキュリティグループに、sg-0456... からの許可を
        追加してよいでしょうか。追加の申請の手順があれば、教えてください
```

この例では、調べるうちに、原因の見当がついています。質問を書く作業そのものが、切り分けになることは、よくあります。

## 情報の追い方

| 情報源 | 使い方 |
|---|---|
| AWS公式ドキュメント（各サービスのユーザーガイド） | 仕様の一次情報。迷ったら最初にここを確認する |
| AWS What's New（新機能・変更のお知らせ） | 新しい機能や仕様変更の把握。週に15分眺めるだけでも、案件での会話の理解が変わる |
| AWS Black Belt Online Seminar（日本語） | サービスごとの体系的な解説資料と動画 |
| AWS Hands-on for Beginners（日本語） | 動画に沿って手を動かすハンズオン |
| AWS Skill Builder | AWS公式の学習サイト。無料のコースも多い |
| AWS re:Post | 質問と回答のコミュニティ。よくある問題の解説（ナレッジセンター）もある |
| JAWS-UG（日本のAWSユーザーコミュニティ） | 勉強会への参加、他社の事例や知見の収集 |

## 最初の3か月の過ごし方

| 時期 | 目標 | 行うこと |
|---|---|---|
| 1か月目 | 全体を知る | 構成図と、設計書を読む。わからない部品と用語を一覧にし、1つずつ調べる。検証環境で、実際の資源を見て、図と照らし合わせる。小さな作業を、手順書を書いて、レビューを受けて行う |
| 2か月目 | 任された範囲を、確実に行う | 定型の作業を、一人で行えるようになる。通知と、問い合わせの対応に加わる。過去の障害の記録を読む |
| 3か月目 | 改善を提案する | 手作業を1つ、自動にする。古くなった手順書を1つ、直す。気づいた弱点を、事実・リスク・提案の形で伝える（{{ch:review}}） |

参画したばかりの人には、長くいる人には見えなくなったものが、見えます。「なぜ、こうなっているのですか」という問いは、理由を教わる機会であると同時に、理由のない慣習を見つける機会でもあります。

:::sum
- 最初の週に、構成、権限、触ってよい範囲、変更の手順、連絡の体制を確かめる
- 本番の作業は、手順書、レビュー、2人での実施、記録が基本。想定外のときは、止めて報告する
- 質問は、目的、したこと、起きたこと、調べたこと、知りたいことをそろえる。抱え込まない
- 報告は、結論から。障害のときは、影響の範囲、今の状況、次の報告の時刻を先に
:::

## 章末問題

:::q 判断 | 手順書と違う結果が出た
本番環境で、手順書に沿って、設定の変更を行っています。手順4の確認のコマンドを実行したところ、手順書に書かれた「期待する出力」と、1か所だけ違う値が表示されました。害はなさそうに見えます。予定の時間は、あと10分で終わります。どうしますか。
:::a
作業を止めて、確認者と、作業の責任者に報告します。

- 「害はなさそう」は、その場の推測にすぎない。手順書を作ったときの想定と、実際の環境が違っている、ということは、ほかの前提も違っている可能性がある
- 手順書にない判断を、その場で加えない。続行するかどうかは、自分ではなく、責任者が、事実にもとづいて決める
- 報告では、手順のどこまで進んだか、期待する出力と、実際の出力の違い、今の状態（変更が適用済みか）を、そのまま伝える
- 続行しないと決まったら、切り戻しの手順に従う。時間が足りなければ、今の状態で安全に止められるかを確かめる

時間の制約は、判断を急がせる圧力になりますが、時間内に終わらせることは、作業の目的ではありません。止めたことを、責める現場であってはなりませんし、止めた人は、正しいことをしています。後で、違いの原因を調べ、手順書を直して、改めて実施します。
:::

:::q 書き直し | 答えやすい質問にする
次の質問を、本文の5点をそろえた形に、書き直してください。足りない情報は、自分で補ってかまいません。

「デプロイがうまくいきません。エラーが出ています。どうすればいいですか」
:::a
解答例：

「【質問】検証環境へのデプロイで、ECSのタスクが起動しません

- 目的：会員検索の機能の修正（チケット番号 ○○）を、検証環境で確かめたい
- したこと：本日15:10に、mainブランチへマージしました。GitHub Actionsは、イメージの作成と、ECRへの登録までは成功しています
- 起きたこと：ECSのサービスの更新で、新しいタスクが、起動してから約1分で停止することを繰り返しています。停止の理由には、『Task failed ELB health checks』と表示されています
- 調べたこと：コンテナのログを見ると、起動時に『環境変数 SEARCH_ENDPOINT が設定されていません』と出力されています。今回の修正で、この環境変数を新しく使うようにしました。タスク定義には、まだ追加されていません
- 知りたいこと：タスク定義の環境変数は、どのリポジトリの、どのファイルで管理されていますか。変更の手順（レビューの依頼先）を、教えてください」

元の質問では、相手は、「どの環境の」「何の」「どんなエラーか」を、聞き返すところから始めることになります。エラーのメッセージは、要約せず、そのまま貼ります。
:::

:::q 判断 | 初日に、強い権限を渡された
案件に参画した初日に、「とりあえず、これを使って」と、本番環境の管理者権限のある利用者を渡されました。前任者と、共有で使っていたもののようです。どうしますか。
:::a
受け取ったままにせず、次のことを、案件の責任者に確かめ、相談します。

- 自分専用の利用者を、発行してもらえないか。共有の利用者では、誰が何をしたかが、記録の上で区別できない。何かあったとき、自分の操作でないことも、証明できない
- 自分の担当に、管理者権限が、本当に必要か。必要な範囲の権限にしてもらえないか。少なくとも、当面は、閲覧だけの権限で足りないか
- 多要素認証は、設定されているか
- 本番の変更の手順は、どうなっているか。手順を知る前に、変更できる権限を持つことは、自分にとっても危険

言い出しにくい場面ですが、「自分の誤操作で、ご迷惑をかけたくないので」という言い方なら、角が立ちません。現場の事情で、すぐには変えられないこともあります。その場合でも、懸念を伝えたうえで、強い権限を使う操作は、手順とレビューを経たものに限る、と自分で決めておきます。

{{ch:rev}}の演習4は、まさに、このような現場を、どう立て直すかを考える題材です。
:::
