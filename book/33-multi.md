:::goal
- 複数のリージョンを使う理由を、災害対策・応答の速さ・データの置き場所の3つに分けて説明できる
- 複数のリージョンでデータを持つときの、整合性と遅れの問題を説明できる
- マルチクラウドの利点と代償を整理し、採否を、理由を持って判断できる
:::

複数のリージョンや、複数のクラウドを使う構成は、最も複雑で、最も費用のかかる選択です。それに見合う理由があるかどうかを見きわめることが、この章の主題です。「念のため」「将来に備えて」は、理由になりません。

## 複数のリージョンを使う3つの理由

| 理由 | 内容 | 求められること |
|---|---|---|
| 災害対策 | リージョン全体の障害でも、業務を続ける | 別のリージョンに、データと、動かせる環境を持つ（{{ch:ha}}のDRの戦略） |
| 応答の速さ | 世界の各地の利用者に、近い場所から応答する | 利用者の近くのリージョンで、処理を行う |
| データの置き場所 | 法令や契約で、特定の国や地域の中にデータを置く必要がある | 地域ごとに、データを分けて持つ。地域をまたいで複製しない |

3つは、求める設計が違います。災害対策なら、同じデータを複数の場所に持ちます。データの置き場所の規制なら、逆に、データを地域の外に出さないことが求められます。どの理由で複数のリージョンを使うのかを、最初にはっきりさせます。

なお、応答の速さだけが目的なら、複数のリージョンを使う前に、CDNを検討します。画像や、変化の少ない応答は、CDNの拠点から返せば、処理を行うリージョンが1つでも、多くの利用者には十分に速くなります。

## 構成の型

| 型 | 動き | データ | 難しさ |
|---|---|---|---|
| 待機型（アクティブ/パッシブ） | 平常時は、1つのリージョンだけが通信を受ける。障害時に、もう1つへ切り替える | 主のリージョンから、待機のリージョンへ複製する | 切り替えの手順と、訓練。待機の側が、本当に動くかの確認 |
| 読み取りの分散 | 読み取りは、利用者に近いリージョンで行う。書き込みは、1つのリージョンに集める | 書き込むリージョンから、ほかへ複製する。読み取りには、複製の遅れがある | 書き込みが遠いリージョンになる利用者は、書き込みが遅い。古い内容を読むことがある |
| 複数での書き込み（マルチアクティブ） | すべてのリージョンで、読み書きを受ける | 互いに複製し合う。同じデータが、複数の場所で同時に書き換えられることがある | 書き込みの衝突をどう扱うか。アプリの設計から考える必要がある |

下の行ほど、得られるものは大きくなりますが、難しさも、桁違いに増えます。多くのシステムには、待機型で十分です。

## データの複製には、遅れと衝突がある

リージョンの間は、物理的に離れています。複製には、どうしても時間がかかります。

| サービス | 複数のリージョンでの動き |
|---|---|
| Aurora Global Database | 1つのリージョンで書き込み、ほかのリージョン（最大10か所）へ複製する。複製の遅れは、通常1秒未満。計画的な切り替え（データを失わない）と、障害時の切り替え（遅れの分を失う可能性がある）がある |
| DynamoDB のグローバルテーブル | 複数のリージョンで書き込める。既定では、同じ項目が複数の場所でほぼ同時に書き換えられた場合、後から書かれたほうが残る |
| S3 のリージョン間の複製 | オブジェクトを、別のリージョンのバケットへ複製する。複製には、遅れがある |

「後から書かれたほうが残る」という動きは、衝突したもう一方の書き込みが、黙って消えることを意味します。在庫の数を、東京と別のリージョンで同時に1ずつ減らすと、2減るべきところが、1しか減りません。複数の場所で書き込む設計では、次のような工夫で、衝突そのものを避けます。

- データごとに、書き込むリージョンを決める。たとえば、利用者のデータは、その利用者の住む地域のリージョンだけで書き込む
- 上書きではなく、追記にする。「在庫を5にする」ではなく、「1つ引き当てた」という記録を追加し、後で集計する
- 衝突が許されない処理（決済、在庫の最終的な引き当て）は、1つのリージョンに集める

## 通信を振り分ける

| 手段 | 動き | 向く用途 |
|---|---|---|
| Route 53 のルーティング | DNSの応答で、振り分ける。応答時間の短いリージョン、利用者のいる地域、正常なリージョン、といった条件で選べる | 多くの場合の基本。切り替えは、DNSの応答が保存される時間（TTL）の分だけ遅れる |
| AWS Global Accelerator | 変わらないIPアドレスを入口にし、AWSのネットワークを通じて、正常で近いリージョンへ届ける | 切り替えの速さが重要な場合。DNSの保存の影響を受けない |
| CloudFront | 利用者に近い拠点で受け、内容に応じて、後ろのリージョンへ届ける | Webの通信。キャッシュと組み合わせる |

## 複数のリージョンを、運用する

構成を作ることより、運用し続けることのほうが難しくなります。

- 同じ状態に保つ：2つのリージョンの構成、設定、上限値（クォータ）、アプリの版が、ずれないようにする。すべてをIaCで管理し、同じコードから作る。手で直したものは、片方だけに残る
- 段階的に変更する：変更を、すべてのリージョンに同時に適用しない。1つのリージョンで確かめてから、次へ進む。同時に適用すると、同じ誤りで、すべてが同時に止まる
- 外から見張る：リージョンの中の監視は、そのリージョンの障害では働かない。別の場所から、見張る
- 使えるサービスを確かめる：リージョンによって、使えるサービスや、資源の種類が違う。国内では、東京と大阪の組み合わせがよく使われるが、大阪で使えないものが、構成に含まれていないかを確かめる
- 切り替えを、定期的に実行する：{{ch:ha}}で述べたとおり、試していない切り替えは、動かないものと考える

## マルチクラウドを判断する

複数の事業者のクラウドを使う理由と、その代償を整理します。

| よく挙げられる理由 | 検討すること |
|---|---|
| それぞれの得意分野を使いたい | 業務はA社、データ分析はB社、のように、用途で分けるのは、現実的で、よくある形。事業者をまたぐデータの転送の費用と時間を、見積もる |
| 買収や統合で、結果として複数になった | 無理に1つに寄せる必要はない。権限、監視、費用の管理を、どう横断的に行うかを決める |
| 顧客や規則で、指定されている | 従う。指定の範囲を、正確に確かめる |
| 1社への依存を避けたい。価格の交渉力を持ちたい | 「移れる」状態を保つための費用と、それによって得られる利益を、比べる。次の項を参照 |
| 事業者の全面的な障害に備えたい | 同じシステムを、2社で同時に動かせるように保つのは、非常に高くつく。先に、1社の中での複数のリージョンで足りないかを検討する |

代償は、次のとおりです。

- 技能が分散する：事業者ごとに、仕組みも、用語も、運用の方法も違う。それぞれに詳しい人が必要になる
- 最も低い共通の部分に、合わせることになる：どの事業者でも動くように作ると、各社の独自の便利な機能が使えない。自分で作り、運用するものが増える
- 境界が弱点になる：権限、ネットワーク、監視、記録が、事業者ごとに分かれる。その境界で、漏れや、見落としが起きやすい
- 通信に費用と遅れがかかる：事業者をまたぐ通信は、外部へのデータ転送として課金される

現実的な進め方は、「すべてを、どの事業者でも動くようにする」ことではなく、次のようなものです。

- システムごとに、主となる事業者を決める。1つのシステムを、複数の事業者にまたがらせない
- 横断して共通にするのは、人の認証、監視と記録の集約、IaCの道具、費用の管理、といった土台の部分
- データを、標準的な形式で、いつでも持ち出せるようにしておく。持ち出しにかかる費用と時間を、把握しておく

## 依存をどう考えるか

特定の事業者の独自の機能に頼ること（ロックイン）は、避けるべき悪ではなく、費用と利益の釣り合いの問題です。独自の機能を使えば、早く作れ、運用の手間も減ります。その代わり、ほかへ移るときの費用は増えます。

考えるべきは、「移る可能性は、どのくらいあるか」「移るとしたら、何にどれだけかかるか」「独自の機能を使わないことで、今、何を失うか」です。移る可能性が低いのに、移りやすさのために、日々の開発と運用の効率を大きく犠牲にするのは、割に合いません。一方、データの形式と、持ち出しの手段だけは、どの場合でも確保しておきます。データさえ持ち出せれば、時間をかけて作り直すことはできます。

:::sum
- 複数のリージョンを使う理由は、災害対策、応答の速さ、データの置き場所の3つ。理由によって、設計が変わる
- リージョン間の複製には、遅れがある。複数の場所で書き込むなら、衝突を避ける設計が要る
- 複数のリージョンは、同じ状態に保ち、段階的に変更し、切り替えを定期的に実行して、初めて役に立つ
- マルチクラウドは、用途で分けるのが現実的。依存は、費用と利益の釣り合いで判断し、データの持ち出しは常に確保する
:::

## 章末問題

:::q 選択 | 構成の型を選ぶ
次の3つのシステムに、合う構成を選んでください。複数のリージョンが不要な場合は、そう答えてください。

1. 国内の利用者だけが使う、社内の業務システム。大きな災害のときも、翌日には使えるようにしたい
2. 世界中に読者がいる、ニュースの配信サイト。記事の投稿は、日本の編集部だけが行う
3. 日本と欧州に利用者がいる、会員制のサービス。欧州の利用者の個人データは、欧州の中に置く必要がある
:::a
1. 待機型で、復旧の目標に合った、最も簡素な形。翌日でよいなら、別のリージョン（大阪など）にバックアップを複製し、障害時にIaCで環境を作って復元する方式（バックアップ＆リストア）で足りる可能性がある。訓練で、実際に翌日までに戻せることを確かめる
2. まずCDN。記事は全員に同じ内容で、変化も少ないため、CDNの拠点から返せば、世界中に速く届く。処理を行うリージョンは、1つでよい。それでも足りない場合に、読み取りの分散を検討する。書き込みは日本だけなので、衝突の問題は起きない
3. 地域ごとに、データを分けて持つ構成。欧州の利用者のデータは、欧州のリージョンだけに置き、日本のリージョンへ複製しない。利用者がどちらの地域に属するかで、通信を振り分ける。これは、同じデータを複数の場所に持つ災害対策の構成とは、逆の方向の設計になる

3で、欧州のデータの災害対策が必要なら、欧州の中の別のリージョンを使います。どの範囲の情報が規制の対象か、日本にいる運用の担当者が欧州のデータを見てよいか、といった点は、技術者だけで判断せず、法務の担当者に確認します。
:::

:::q 説明 | 同時に書き換えると、何が起きるか
在庫の数を、DynamoDBのグローバルテーブルに保存しています。ある商品の在庫が10のとき、東京のリージョンと、米国のリージョンで、ほぼ同時に、それぞれ「在庫を読み、1引いて、書き戻す」処理が動きました。既定の設定では、結果はどうなりますか。どう設計すれば、防げますか。
:::a
どちらのリージョンも、在庫10を読み、9を書き込みます。2つの書き込みは、互いのリージョンへ複製され、衝突します。既定では、後から書かれたほうが残るため、在庫は9になります。実際には2つ売れたのに、1しか減っていません。

防ぐ方法の例：

- 在庫の引き当ては、1つのリージョンだけで行う。ほかのリージョンからの注文も、引き当ての処理だけは、そのリージョンへ送る。最も確実
- 地域ごとに、在庫を分けて持つ。東京の在庫と、米国の在庫を、別の項目にし、それぞれのリージョンだけが書き換える
- 上書きではなく、「1つ引き当てた」という記録を追加する形にする。記録は、項目が別なので、衝突しない。在庫の数は、記録を集計して求める。ただし、集計に遅れがあるため、売りすぎが起こり得る

なお、1つのリージョンの中でも、「読んで、計算して、書き戻す」処理は、同時に動くと同じ問題を起こします。こちらは、条件付きの書き込みや、数値を直接増減する操作で防げます。複数のリージョンにまたがると、その保護が、リージョンの間では効かなくなる、という点が要です。
:::

:::q 評価 | すべてを2社で動かす案
ある役員から、「1社のクラウドの全面的な障害に備え、すべてのシステムを、2社のクラウドで同時に動かせるようにしたい」という方針が示されました。この方針について、利点と課題を整理し、代わりの案を提案してください。
:::a
利点：

- 1社の全面的な障害でも、業務を続けられる可能性がある
- 価格や条件の交渉で、選択肢を持てる

課題：

- 費用：2つの環境の利用料に加え、両方で動くように作り、試験し、運用し続ける人の費用がかかる。切り替えの訓練も、定期的に必要
- 機能の制約：両方で同じように動かすには、各社の独自の機能を避けることになる。マネージドサービスに任せていた部分を、自分で作って運用することになり、かえって信頼性が下がるおそれがある
- データ：2社の間で、データを常に同期する必要がある。遅れと、衝突と、転送の費用の問題が生じる
- 共通の弱点：認証、DNS、デプロイの仕組み、アプリのバグなど、2社に共通する部分が止まれば、両方が止まる。ここは、2社に分けても冗長にならない

代わりの案：

1. まず、障害の単位ごとに、今の備えを確かめる。多くの場合、先に対処すべきは、変更の誤りや、1つのリージョンの中の単一障害点
2. リージョン全体の障害には、同じ事業者の、別のリージョンで備える。道具と技能が共通で、はるかに安い
3. 本当に止められない、ごく少数のシステムに限って、別の事業者での備えを検討する。その場合も、同時に動かすのではなく、データのバックアップを別の事業者にも置き、時間をかけて立ち上げられるようにする、といった段階から始める
4. どのシステムについても、データを標準的な形式で持ち出せる状態は、保つ

方針を否定するのではなく、守りたいもの（業務の継続）を確かめ、それに対して、費用と効果の釣り合う手段を、段階を付けて示します。
:::

:::q 計算 | 待機の環境には、いくらかかるか
東京のリージョンで動くシステムのために、大阪のリージョンに、ウォームスタンバイの環境を持ちます。演習用の仮単価で、月額を概算してください。1か月は730時間とします。

- 縮小した規模のアプリサーバー2台（1台1時間 0.10ドル）
- 複製を受けるデータベース1台（1時間 0.20ドル）
- データベースの保存領域200GB（1GBあたり月 0.25ドル）
- ロードバランサー1つ（1時間 0.025ドル）
- 東京から大阪への複製の転送。1日あたり40GB（1GBあたり 0.09ドル）

東京の本番の月額が約880ドルだとすると、待機の環境は、その何%に当たりますか。
:::a
| 項目 | 計算 | 金額 |
|---|---|---|
| アプリサーバー | 2 × 730 × 0.10 | 146.0ドル |
| データベース | 730 × 0.20 | 146.0ドル |
| 保存領域 | 200 × 0.25 | 50.0ドル |
| ロードバランサー | 730 × 0.025 | 18.3ドル |
| 複製の転送 | 40 × 30日 × 0.09 | 108.0ドル |
| 合計 | | 約468ドル |

本番の約53%に当たります。縮小した規模でも、本番の半分程度の費用が、使われない環境に、毎月かかり続けます。このほかに、2つのリージョンを同じ状態に保つ作業と、切り替えの訓練の、人の費用がかかります。

この数字を、「1時間止まったときの損失」や、「復旧までの時間を、半日から数分に縮める価値」と比べて、初めて、採否を判断できます。パイロットライト（サーバーを止めておく）なら、アプリサーバーの分が、ほぼなくなります。目標の復旧時間と、費用を並べて、選びます。
:::
