:::goal
- 何を監視し、どの状態を異常とみなすかを、利用者への影響から決められる
- アラームから通知までを作り、通知を受けた後の動きまで決められる
- 「誰が、いつ、何をしたか」を記録から調べ、障害報告書を書ける
:::

システムの異常に気づき、原因を追える状態にします。ここまでのステップで作ったものは「動く」状態ですが、「運用できる」状態ではありません。止まったことに利用者からの連絡で気づく、原因を調べようにも記録がない、という状況をなくすのがこのステップです。

## 何を監視するかを決める

監視する項目は、資源の内側（CPU使用率など）からではなく、利用者に近い側から決めます。利用者にとっての異常は「エラーになる」「遅い」の2つで、まずそれを直接測ります。資源の指標は、その原因を調べるために使います。

| 層 | 主な指標（CloudWatchのメトリクス名） | 異常とみなす例 |
|---|---|---|
| 入口（ALB） | 5xxエラーの数（HTTPCode_ELB_5XX_Count、HTTPCode_Target_5XX_Count）、応答時間（TargetResponseTime） | エラーが5分間に一定数を超えた。応答時間が平常時の数倍になった |
| 入口（ALB） | 正常なターゲットの数（HealthyHostCount） | 最小台数を下回った |
| サーバー（EC2） | CPU使用率（CPUUtilization）、状態チェックの失敗（StatusCheckFailed） | 高い状態が続く。状態チェックに失敗した |
| サーバー（EC2） | メモリ使用率、ディスク使用率 | 上限に近づいた。標準では取得されず、CloudWatchエージェントを入れて送る必要がある |
| データベース（RDS） | CPU使用率、接続数（DatabaseConnections）、空き容量（FreeStorageSpace）、空きメモリ（FreeableMemory） | 接続数が上限に近づいた。空き容量が残り少ない |

:::note 通知は「人が動く必要があるもの」だけにする
アラームを増やしすぎると、通知が日常の風景になり、本当に重要な通知が見過ごされます。人に通知するのは、利用者に影響が出ている、または放置すると影響が出るものに絞ります。それ以外は、ダッシュボードで見られるようにしておけば十分です。通知には「何が起きたか」「まず何を確認するか」を書き添えます。
:::



## 進め方

1. CloudWatchで、EC2・ALB・RDSの主な指標（CPU使用率、ALBの5xxエラー数、正常なターゲットの数、DBの接続数や空き容量）を確認し、ダッシュボードにまとめる
2. CloudWatchエージェントで、Webサーバーのアクセスログを CloudWatch Logs に送る。ロググループには保存期間を設定する
3. アラームを作り、SNSでメールに通知する（例：正常なターゲットが1台以下になったら）
4. CloudTrailで、自分が行った操作（誰が、いつ、何をしたか）の記録を検索する
5. AWS Backupで、RDSとEC2のバックアップ計画を作る

## つまずきやすい点

| 症状 | よくある原因 | 確かめ方 |
|---|---|---|
| アラームが鳴ってもメールが届かない | SNSの宛先の登録時に届く確認メールを、承認していない | SNSのサブスクリプションの状態が「確認済み」かを見る |
| アラームが「データ不足」のまま | メトリクスの名前や対象の指定が違う。エラーが0件のときにデータが送られない指標を使っている | グラフにデータが表示されるかを確かめる。データがないときの扱い（正常とみなすか、異常とみなすか）を設定する |
| ログが CloudWatch Logs に届かない | サーバーのIAMロールに、ログを送る権限がない。エージェントの設定で、ファイルの場所が違う | ロールの権限（CloudWatchAgentServerPolicy など）と、エージェント自身のログを確認する |
| CloudTrailに操作が出てこない | 記録が表示されるまでに数分から十数分かかる。見ているリージョンが違う | 少し待つ。操作したリージョンで検索する |

## 障害報告書の型

報告書は、責任を追及するためのものではなく、同じ問題を繰り返さないためのものです。次の項目を、事実と時刻にもとづいて書きます。

```text
件名      Webサーバー停止による一部エラーの発生（学習環境）
発生時刻  2026-11-20 14:02    復旧時刻  2026-11-20 14:09
影響      約7分間、アクセスの一部がエラー、または遅延。データの損失はなし
経過      14:02 アプリサーバー（AZ-a）でWebサーバーのプロセスが停止
          14:03 ALBがこのサーバーを異常と判定し、振り分けを停止
          14:04 「正常なターゲットが1台以下」のアラームが通知される
          14:05 Auto Scalingが異常なサーバーを終了し、新しいサーバーを起動
          14:09 新しいサーバーがヘルスチェックに合格し、2台に回復
原因      検証のため、手動でWebサーバーのプロセスを停止した
対応      自動回復を確認。手動の対応は不要だった
再発防止  （本番を想定して）プロセスが異常終了した原因をログから特定できるよう、
          アプリのログをサーバーの外に送る。回復中の1台で負荷に耐えられるかを確認する
```

## 確認ポイント

- 何を監視し、どの状態を異常とみなすかを、理由とともに説明できる
- 通知を受けた人が最初に何を確認し、誰に連絡するかを決めている。監視は、通知の後の動きまで決めて初めて役に立つ

## わざと壊してみる

:::lab
ステップ3でElastic Load Balancingのヘルスチェックを有効にした状態で、アプリサーバーのWebサーバーを停止し、「ヘルスチェック失敗 → アラーム通知 → Auto Scalingによる入れ替え」までの流れを、時刻付きで記録します。そのまま簡単な障害報告書（発生時刻、影響、原因、対応、再発防止）を書いてみると、現場での報告の練習になります。
:::

## 片付け

アラーム、ダッシュボード、SNSのトピック、ロググループ、バックアップ計画を削除します。バックアップ計画を削除しても、取得済みのバックアップ（復旧ポイント）は残るため、バックアップボールトから別に削除してください。CloudTrailのイベント履歴は、設定しなくても見られる機能で、費用はかかりません。証跡（トレイル）を作った場合は、証跡と、保存先のS3バケットを削除します。

## 本番ではどう変わるか

| 項目 | 学習での構成 | 本番で加わること |
|---|---|---|
| 外からの確認 | なし | 利用者と同じように外から定期的にアクセスし、応答を確かめる（外形監視）。内側の指標が正常でも、外から使えないことはある |
| 通知先 | 自分のメール | チームのチャットや、当番の担当者を呼び出す仕組みにつなぐ。夜間や休日に誰が受けるかを決める |
| 通知の後の動き | 自分で考える | アラームごとに、最初に確認することと連絡先を書いた手順（ランブック）を用意する |
| 操作の記録 | イベント履歴（直近90日） | 証跡を作り、長期保存する。記録を消されないよう、別のアカウントのS3に集める（{{ch:org}}） |
| ログの保存 | 既定のまま | 保存期間を決める。長期保存が必要なものは、安価な保存先へ移す |
| 目標 | なし | 「どの程度使える状態を保つか」を数字で決め、それに照らして判断する（{{ch:sre}}） |

:::sum
- 監視は、利用者に近い側（エラーと遅さ）から決め、資源の指標は原因の調査に使う
- 通知は、人が動く必要があるものだけに絞り、受けた後の動きまで決めておく
- 操作の記録（CloudTrail）と、アプリのログ（CloudWatch Logs）は役割が違う。両方を残す
- 障害報告書は、事実と時刻で書く。目的は再発を防ぐこと
:::

## 章末問題

:::q 判断 | 通知するもの、記録だけでよいもの
次の5つのうち、夜間でも担当者に通知すべきものと、記録やダッシュボードでの確認で足りるものを分けてください。前提は、利用者が24時間使うWebサービスで、サーバーは最小2台です。

1. ALBが返す5xxエラーが、5分間で全体の5%を超えた
2. サーバー1台のCPU使用率が、一時的に80%になった
3. 正常なターゲットの数が0になった
4. データベースの空き容量が、残り10%を切った
5. Auto Scalingが、サーバーを1台入れ替えた
:::a
- 通知すべきもの：1、3。利用者にエラーが返っている、またはまったく使えない状態で、すぐに人が動く必要がある
- 通知するが、夜間に起こすかは状況による：4。放置すると書き込みができなくなり、全体が止まる。ただし、数時間の余裕があることが多い。増え方が速い場合は夜間でも通知し、ゆるやかなら営業時間内の対応でよい。しきい値を2段階（注意と緊急）にする方法もある
- 記録で足りるもの：2、5。2は、台数を増やす仕組みが働いていれば正常な動き。5は、自動回復が働いた結果で、利用者への影響がなければ翌朝の確認で足りる。ただし、5が短時間に何度も起きているなら、別の問題の兆候なので通知の対象にする

判断の軸は「今、利用者に影響があるか」「放置するとどのくらいで影響が出るか」「人が動かないと直らないか」です。
:::

:::q 調査 | 資源の指標は正常なのに遅い
利用者から「午後2時ごろ、画面の表示が遅かった」という連絡がありました。サーバーのCPU使用率は、その時間帯も30%程度で正常でした。次に何を見ますか。確認する順に3つ以上挙げてください。
:::a
解答例：

1. ALBの応答時間（TargetResponseTime）：実際に遅かったのか、いつからいつまでかを確かめる。サーバーが応答を返すまでの時間が延びていれば、サーバーより後ろに原因がある
2. データベースの指標：CPU使用率、接続数、読み書きの待ち時間。アプリは、データベースの応答を待っている間はCPUを使わないため、サーバーのCPU使用率は低く見える
3. アプリのログ：その時間帯に、時間のかかった処理や、外部のサービスの呼び出しの遅延が記録されていないか
4. サーバーのメモリとディスク：メモリが足りずに処理が遅くなっていないか。標準の指標には含まれないため、エージェントで取得しているかも確認する
5. 外部の要因：呼び出している外部のAPIの遅延、NATゲートウェイの通信量、同じ時間に動いていたバッチ処理

CPU使用率が低いことは、「サーバーは待たされていた」ことの手がかりになります。何を待っていたのかを、後ろの部品へ順にたどります。
:::

:::q 調査 | 誰が設定を変えたか
今朝から、あるサーバーに外部からアクセスできなくなりました。調べると、セキュリティグループの受信ルールが1つ消えていました。誰がいつ消したのかを調べる手順を答えてください。
:::a
CloudTrailのイベント履歴で調べます。

1. 操作が行われたリージョンで、イベント履歴を開く
2. イベント名で絞り込む。受信ルールの削除は RevokeSecurityGroupIngress、追加は AuthorizeSecurityGroupIngress という名前で記録される。または、リソース名にセキュリティグループのIDを指定して絞り込む
3. 該当するイベントを開き、時刻、操作した人（ユーザーやロールの名前）、接続元のIPアドレス、変更の内容を確認する

操作した「人」がロールの名前になっている場合は、そのロールを誰が（または何のツールが）引き受けたのかを、セッションの名前などからさらにたどります。IaCのツールやCI/CDが変更したのであれば、どのコードの変更がきっかけかを、リポジトリの履歴と照らし合わせます。イベント履歴で見られるのは直近90日分なので、それより前の操作を調べるには、証跡による保存が必要です。
:::

:::q 作成 | 報告の第一報を書く
本番のWebサービスで、午前10時15分から画面がエラーになっています。原因はまだわかっていません。あなたは10時25分に、関係者へ第一報を送ります。伝えるべき項目を挙げ、短い文面を書いてください。
:::a
第一報では、原因よりも「影響の範囲」「今の状況」「次に報告する時刻」を先に伝えます。

解答例：

「【障害・第一報】10時15分ごろから、○○サービスの画面でエラーが発生しています。現在、利用者の大半が画面を表示できない状態です。データへの影響は確認中です。原因は調査中で、現在、直前の変更の有無と、サーバーおよびデータベースの状態を確認しています。次の報告は10時45分に行います。問い合わせは△△までお願いします」

要点：

- わかっていることと、わかっていないことを分けて書く。推測を事実のように書かない
- 原因がわからなくても、第一報は送る。報告が遅れるほど、関係者は状況を把握できず、問い合わせが増える
- 次に報告する時刻を必ず書き、その時刻に、進展がなくても報告する
:::
