:::goal
- 障害を「どの単位で起きるか」に分け、それぞれへの備えを選べる
- RTOとRPOを業務への影響から決め、それに合う冗長化とバックアップを設計できる
- DRの4つの戦略を、復旧の速さと費用の兼ね合いで選べる
- 「切り替えられる」ことと「切り替えたことがある」ことの違いを説明できる
:::

可用性の設計とは、「何が壊れても止まらないようにする」ことではありません。「何が壊れたら、どのくらい止まり、どこまでデータを失うか」をあらかじめ決め、その範囲に収まるように作ることです。備えを増やせば費用と複雑さが増えるため、どこまで備えるかは要件から決めます。

## 障害の単位で考える

障害は、影響の範囲が小さいものほど頻繁に起きます。備えは、範囲の小さいものから順に考えます。

| 障害の単位 | 例 | 主な備え |
|---|---|---|
| プロセス | アプリの異常終了、メモリ不足 | 自動で再起動する。ヘルスチェックで異常なものを外す |
| サーバー | ハードウェアの故障 | 複数台を動かす。壊れたものを自動で入れ替える（{{ch:s3}}） |
| AZ | 電源や回線の障害 | 複数のAZに置く。1つのAZを失っても足りる台数にする |
| リージョン | 大規模な災害、広範囲のサービス障害 | 別のリージョンに備えを持つ（DR） |
| データ | 誤った削除や更新、アプリのバグによる破損、不正な暗号化 | バックアップと、任意の時点への復元。冗長化では防げない |
| 依存先 | 外部のAPI、認証の基盤、DNS | タイムアウトと再試行。依存先が止まっても主要な機能は動く作りにする |
| 変更 | 設定の誤り、問題のある版のデプロイ | 少しずつ適用する。すぐに戻せるようにする（{{ch:sre}}） |

見落とされやすいのは、下の2行、つまり依存先と変更です。機器の冗長化だけを考えていると、ここが抜けます。

## RTOとRPOを決める

RTO（目標復旧時間）は、障害が起きてから業務を再開するまでに許される時間です。RPO（目標復旧時点）は、どの時点までのデータを取り戻せればよいか、言い換えると、どれだけのデータを失ってよいかです。

2つは別々に決めます。たとえば、入力し直せるデータなら、RPOは長くてもかまいません。一方、決済のように失うと取り返しがつかないデータは、復旧に時間がかかってもよいから失わないこと、つまりRPOが優先されます。

| システムの例 | RTO | RPO | 理由 |
|---|---|---|---|
| 社内の申請システム | 半日 | 前日 | 止まっても紙やメールで代替でき、当日分は入力し直せる |
| 通販サイトの注文 | 15分 | ほぼ0 | 止まると売上を失う。受けた注文は失えない |
| 夜間の集計バッチ | 翌朝まで | 再実行できる | 元のデータが残っていれば、やり直せる |

すべてのシステムを同じ水準にする必要はありません。重要度で段階を分け、段階ごとに標準の構成を決めておくと、判断が速くなります。

:::note 目標と実力は別のもの
RTOとRPOは目標です。実際に何分で戻せるか（実力）は、復元の練習をして測るまでわかりません。「バックアップは毎日取っている」は、RPOが最大24時間であることを示すだけで、RTOについては何も言っていません。
:::

## 冗長化の基本形

状態を持たない層（Webやアプリのサーバー）は、複数のAZに置き、ロードバランサーで振り分けます。考える点は、1つのAZを失ったときに、残りで負荷を受けきれるかです。ピーク時に6台が必要なら、2つのAZでは各AZに6台（合計12台）、3つのAZでは各AZに3台（合計9台）を置けば、どのAZを失っても6台が残ります。AZの数が多いほど、余分に持つ台数の割合は小さくなります。

状態を持つ層（データベース）は、同じデータを複数の場所に複製します。AWSのリレーショナルデータベースの主な選択肢は次のとおりです。

| 構成 | 仕組み | 切り替えの目安 | 特徴 |
|---|---|---|---|
| RDS 単一AZ | 1台だけ | 復元が必要 | 安価。検証環境や、長い停止を許容できる場合 |
| RDS マルチAZ（DBインスタンス） | 別のAZに待機用を1台。同期して複製する | 通常60〜120秒 | 待機用は読み取りには使えない |
| RDS マルチAZ（DBクラスター） | 別のAZに、読み取りにも使える待機用を2台 | 通常35秒未満 | 待機用で読み取りを分散できる |
| Aurora | 保存領域そのものが3つのAZにまたがり、6つの複製を持つ | レプリカがあれば通常60秒未満（多くは30秒未満） | レプリカがない場合は、通常10分未満 |

切り替えの時間は公式ドキュメントに示された目安で、データベースの負荷や状態によって変わります。どの構成でも、切り替えの間は接続が切れるため、アプリ側で接続し直す作りが必要です（{{ch:pattern}}）。

:::tip 障害の最中に、新しく作ることに頼らない
AZの障害が起きると、多くの利用者が同時に、残りのAZで新しいサーバーを起動しようとします。その結果、起動に時間がかかったり、失敗したりすることがあります。重要なシステムでは、障害時に台数を増やすのではなく、最初から必要な台数を動かしておきます。障害が起きても何も操作せずに動き続ける、という性質を「静的安定性」と呼びます。
:::

## バックアップは冗長化の代わりにならず、冗長化もバックアップの代わりにならない

複製は、誤った削除や更新も忠実に複製します。マルチAZ構成のデータベースでテーブルを誤って削除すれば、待機側からも同時に消えます。データそのものの事故には、過去の時点に戻せるバックアップが必要です。

| 決めること | 選択肢と考え方 |
|---|---|
| 頻度と保持期間 | RPOから頻度を、業務や規則から保持期間を決める。任意の時点に戻せる機能（ポイントインタイムリカバリ）を使えば、数分単位で戻せる |
| 置き場所 | 元のデータと同じ場所に置かない。別のリージョン、別のアカウントにも複製する。アカウントが乗っ取られても消されないようにするため |
| 消されない工夫 | 一定期間、誰にも削除や変更をさせない設定（AWS Backup のボールトロック、S3 のオブジェクトロック）を使う |
| 復元の確認 | 定期的に実際に復元し、データが使えることと、かかる時間を確かめる |

「復元を試したことのないバックアップは、バックアップではない」と言われます。取得の成功は、復元の成功を保証しません。

## リージョンをまたぐ備え：DRの4つの戦略

リージョン全体の障害や、広い範囲の災害に備えるのがDR（災害対策）です。AWSは、4つの戦略に整理しています。

{{fig:dr4|DRの4つの戦略。右へ行くほど復旧は速くなり、平常時の費用と運用の手間は大きくなる}}

| 戦略 | 平常時に別リージョンで動いているもの | 復旧時に行うこと | 向いている要件 |
|---|---|---|---|
| バックアップ＆リストア | バックアップのデータだけ | 環境をIaCで作り、データを復元する | RTOが数時間以上でよい |
| パイロットライト | データの複製と、最小限の中核部分。サーバーは止めておく | サーバーを起動し、台数を増やす | RTOが数十分 |
| ウォームスタンバイ | 縮小した規模で、全体が動いている | 台数を本番の規模に増やす | RTOが数分 |
| マルチサイト（アクティブ/アクティブ） | 本番と同じものが動き、通信も受けている | 障害のあるリージョンへの振り分けを止める | 停止をほぼ許容できない |

どの戦略でも、次の3つを決めます。

- データをどう複製するか：データベースは、リージョン間の複製機能（Aurora Global Database など）を使う。複製は非同期で、通常は1秒未満の遅れがあるため、切り替えの瞬間に、その遅れの分のデータを失う可能性がある。ファイルはS3のリージョン間の複製を使う
- 通信をどう切り替えるか：DNS（Route 53）で、正常なリージョンへ向け直す方法が一般的。DNSの応答が保存される時間（TTL）の分だけ、切り替えは遅れる
- 誰が切り替えを決めるか：自動で切り替えるか、人が判断するか。誤って切り替えると、かえって停止やデータの不整合を招くため、人の判断を挟むことが多い。その場合、判断にかかる時間もRTOに含める

そして、見落とされがちなのが「戻す」手順です。障害が収まった後、元のリージョンへ、データを失わずに戻す手順まで設計して、初めて完成です。

:::warn 動かしたことのない切り替えは、動かない
切り替えの手順は、定期的に実際に行って確かめます。手順書の誤り、権限の不足、複製されていなかった設定、上限値（クォータ）の違いなどは、実際に切り替えて初めて見つかります。年に1回でも、本番に近い形で訓練する日を決めておきます。
:::

## SLAを正しく読む

事業者のSLA（サービス水準に関する合意）は、設計の材料にはなりますが、自分のシステムの稼働率を保証するものではありません。

- 対象と条件が決まっている：たとえばEC2のSLAは、複数のAZを使う構成を前提にしたリージョン単位の水準（99.99%）と、インスタンス1台ごとの水準（99.5%）を分けて定めている。1台だけで動かしているシステムに、高いほうの数字は当てはまらない
- 未達のときの補償は、利用料の一部の充当：申請が必要で、失った売上や信用を補うものではない
- 自分のシステムの稼働率は、自分の設計と運用で決まる：部品を直列につなげば下がり、アプリのバグや設定の誤りはSLAの対象外

:::sum
- 可用性の設計は、障害の単位ごとに「どのくらい止まり、どこまで失うか」を決めること
- RTOとRPOは業務への影響から別々に決め、実力は練習で測る
- 冗長化は機器や拠点の障害に、バックアップはデータの事故に備える。どちらも他方の代わりにならない
- DRは4つの戦略から、復旧の速さと費用で選ぶ。切り替えと、戻す手順を、実際に動かして確かめる
:::

## 章末問題

:::q 選択 | DRの戦略を選ぶ
次の4つのシステムについて、リージョン障害への備えとして合う戦略を、4つの中から選んでください。理由も答えてください。

1. 社内向けの文書管理。数日止まっても、業務は続けられる。文書は失えない
2. 会員向けの予約サイト。1時間以内に再開したい。直前の数分の予約は、失った場合に個別に連絡して対応できる
3. 決済の処理。数分以上の停止は許されず、受け付けた取引は失えない
4. 社内の開発環境
:::a
1. バックアップ＆リストア。RTOは長くてよく、守るべきはデータ。バックアップを別のリージョンに複製し、環境はIaCから作り直せるようにしておく
2. パイロットライト、またはウォームスタンバイ。1時間以内なら、データを常に複製し、サーバーを起動して規模を増やす方式で間に合う可能性がある。訓練で実際の時間を測って決める
3. マルチサイト、または本番に近い規模のウォームスタンバイ。データを失わないことについては、リージョン間の複製が非同期である点を踏まえ、遅れの分をどう扱うか（取引の記録を別の経路でも残すなど）を別に設計する
4. 備えは不要、または、コードとデータのバックアップだけ。作り直せるものに、費用をかけて備える必要はない

4のように「備えない」と決めることも、設計の判断です。その判断を記録に残しておきます。
:::

:::q 計算 | AZを1つ失っても足りる台数
あるシステムは、ピーク時にアプリサーバーが8台必要です。1つのAZが止まっても、ピーク時の負荷を受けきれるようにします。

1. 2つのAZを使う場合、合計で何台を動かしておく必要がありますか
2. 3つのAZを使う場合は、合計で何台ですか
3. 「AZが止まったら、Auto Scalingで残りのAZに台数を増やせばよい」という案には、どのような危険がありますか
:::a
1. 各AZに8台、合計16台。1つを失うと8台が残る
2. 各AZに4台、合計12台。1つを失うと8台が残る
3. 障害時に新しいサーバーを起動できるとは限らない。多くの利用者が同時に起動しようとして、時間がかかったり、失敗したりすることがある。また、起動してアプリが準備できるまでの数分間は、残った台数だけでピークの負荷を受けることになり、過負荷で続けて止まるおそれがある

3つのAZを使うと、余分に持つ台数は8台から4台に減ります。費用を抑えるために台数を減らす場合は、「AZ障害時には性能が落ちる」ことを、要件として合意しておきます。
:::

:::q 原因 | マルチAZなのに5分止まった
RDSのマルチAZ構成（DBインスタンス）で、切り替えが起きました。データベースの切り替えは90秒で終わりましたが、アプリのエラーは5分以上続きました。考えられる原因を2つ以上挙げてください。
:::a
解答例：

- アプリが、切れた接続を使い続けた：接続をためておく仕組み（コネクションプール）が、切れた接続を検知して捨てる設定になっていない。古い接続でエラーになり続ける
- アプリやOSが、データベースの古いIPアドレスを覚えていた：エンドポイントのDNS名は切り替え後に新しいIPアドレスを指すが、アプリの実行環境が名前解決の結果を長く保存していると、古い宛先に接続し続ける
- タイムアウトが長すぎる：応答しない接続を、長い時間待ち続けた。待っている処理がたまり、アプリ全体が応答しなくなった
- 再接続が一斉に起き、データベースの負荷が跳ね上がった：切り替え直後に全サーバーが同時に接続を作り直し、新しいプライマリが応答しきれなくなった

データベースの切り替え時間は、システムの停止時間の一部にすぎません。切り替えを実際に起こし、アプリの側が何秒で回復するかを測ることが必要です（{{ch:s4}}）。
:::

:::q 指摘 | バックアップの設計を見直す
あるシステムのバックアップは、次のとおりです。考えられるリスクを4つ挙げ、それぞれの改善策を答えてください。

「データベースのスナップショットを毎日午前3時に取得し、7世代を保持する。保存先は本番と同じアカウント、同じリージョン。取得の成功は毎朝メールで確認している。復元は、構築時に一度試した」
:::a
| リスク | 改善策 |
|---|---|
| アカウントが乗っ取られる、または管理者が誤ると、本番とバックアップを同時に消される | 別のアカウントにも複製する。一定期間は削除できない設定にする |
| リージョン全体の障害で、本番とバックアップの両方が使えなくなる | 別のリージョンにも複製する |
| 最大で24時間分のデータを失う。業務の要件と合っているか不明 | RPOを確認する。必要なら、任意の時点に戻せる機能を有効にする |
| 8日以上前の誤りに気づいた場合、戻せない | 保持期間を見直す。月次のバックアップを長く残すなど、段階をつける |
| 復元を構築時に一度試しただけで、今のデータ量でかかる時間がわからない | 定期的に復元を試し、時間を記録する。手順書を最新に保つ |

「取得の成功を確認している」ことは良い運用ですが、確認しているのは取得だけです。備えとして数えられるのは、復元まで確かめたものだけです。
:::

:::q 対話 | 「停止もデータの損失もゼロに」と言われたら
顧客から「このシステムは重要なので、RTOもRPOもゼロにしてほしい」と要望されました。どのように進めますか。
:::a
解答例：

1. 要望の背景を聞く：「止まると何が起きるか」「どのデータを失うと何が困るか」を、機能ごとに確認する。システムのすべての機能が同じ重要度であることは少ない
2. 段階と費用を示す：バックアップ＆リストアからマルチサイトまでの選択肢について、復旧の目安と、おおよその費用、運用の負担を並べて示す。ゼロに近づけるほど、費用と複雑さが大きく増えることを共有する
3. 厳密なゼロの意味を説明する：リージョン間の複製には遅れがあり、データの損失を完全にゼロにするには、処理のたびに複数の拠点への書き込みを待つ必要があり、応答が遅くなる。停止ゼロも、切り替えの検知と実行に時間がかかる以上、厳密には達成できない
4. 機能ごとに目標を分ける：たとえば「取引の受け付けはRTO 5分・RPOほぼ0、帳票の出力はRTO半日」のように分け、重要な部分に費用を集中する
5. 合意した内容と、受け入れたリスクを記録する

「できません」でも「わかりました」でもなく、選択肢と費用を示して一緒に決める、という進め方が要点です。
:::
