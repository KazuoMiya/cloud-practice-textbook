- 各ステップの合格を、人によらず同じ基準で判定し、記録に残せる

この付録は、この本を使って、後輩やチームのメンバーを指導する人に向けたものです。研修の担当者、勉強会の進行役、配属先で新人を受け持つ人を想定しています。1人で学ぶ人は、「合格の判定と記録」と「費用の管理と、無料で進められる範囲」を、自分の進み具合の確かめに使えます。

この本は、読むだけでは身につかないように作ってあります。作る、壊す、直す、説明する、文書に残す。この繰り返しを、受講者が最後までやり切れるかどうかは、指導役の関わり方で大きく変わります。

## 指導役の役割

指導役の仕事は、教えることよりも、確かめることと、問いかけることです。知識は、本文と公式ドキュメントに書いてあります。指導役にしかできないのは、次のことです。

| 指導役が行うこと | 指導役が行わないこと |
|---|---|
| 受講者の出力と文書を見て、合格かどうかを判定する | 受講者の代わりに、設定を直す |
| 説明を聞き、「なぜ」「変えるとどうなるか」を問う | 質問される前に、答えを言う |
| つまずいているときに、次に見る場所を問いかける | 画面やキーボードを取り上げて、操作する |
| 作業の前に、手順書やアドレス設計をレビューする | 手順を省略させて、先へ進ませる |
| 片付けと費用を、受講者と一緒に確かめる | 費用の確認を、受講者だけに任せる |
| 障害の演習で、出題し、観察し、振り返りを進める | 演習の途中で、原因を教える |

受講者が自分で原因にたどり着いた経験は、指導役が教えた10個の知識より、長く残ります。指導役が黙って待つ時間は、指導の一部です。

## 始める前に決めること

最初の回までに、次のことを決め、受講者に伝えます。

- [ ] 使うアカウント：会社の検証用アカウントか、個人のアカウントか（{{ch:env}}の「どのアカウントで学ぶか」）。個人のアカウントを使わせる場合は、費用を誰が負担するかを、先に決める
- [ ] 権限の渡し方：受講者ごとに、学習用のロールか、IAM Identity Center の利用者を用意する。アクセスキーは発行しない（{{ch:s1}}）
- [ ] 予算と通知：予算アラートの宛先に、指導役を加える。金額の目安と、超えたときに誰が何をするかを決める
- [ ] リージョン：東京（ap-northeast-1）に固定する
- [ ] 提出の場所：出力、構成図、文書を置く場所（社内のリポジトリや共有フォルダー）。秘密の値と、アカウント番号などの固有の情報を載せない決まりを、最初に伝える
- [ ] 定例の時間：週に1回、30分。5分の説明と質疑、合格の判定、次の週の確認に使う
- [ ] 質問の経路：どこで、どの形で質問するか。{{ch:field}}の「質問と報告のしかた」の5点をそろえて書く練習を、研修の中で始める
- [ ] 持ち込まないもの：会社や顧客の本物のデータ、本番の設定の写し
- [ ] 研修で使える時間：業務と並行する場合は、週に何時間を学習に使えるかを、受講者の上長と合意する

{{ch:env}}の「最初の30分で必ずやること」は、受講者に任せきりにせず、最初の回に、画面を見ながら一緒に確かめてください。ルートユーザーの多要素認証、予算アラート、コスト異常検出のどれかが抜けたまま、ステップ1へ進ませないことが、指導役の最初の仕事です。

## 期間の目安と、段階ごとの計画

業務と並行して、週に5〜7時間を学習に使う場合の計画です。{{ch:road}}の「学習の進め方」と、同じ区切りにしています。

| 段階 | 週 | 範囲 | 次へ進む条件 | 指導役が行うこと |
|---|---|---|---|---|
| 全体像 | 1〜2 | 序章、第1部、{{ch:env}} | 第1部の章末問題に、自分の言葉で答えられる。学習環境の安全の設定が済んでいる | 開始の面談。安全の設定を、画面で確かめる |
| 構築 | 3〜8 | {{ch:map}}、ステップ1〜4（{{ch:s1}}〜{{ch:s4}}） | 各ステップの「実技の合格基準」と「確認ポイント」を満たす | 毎週の判定。アドレス設計とパラメータシートを、作る前にレビューする |
| 運用と自動化 | 9〜13 | ステップ5〜8（{{ch:s5}}〜{{ch:s8}}）、{{ch:ts}} | 各ステップの合格基準を満たす。環境をすべて消した状態から、コードで作り直せる。障害の演習で、原因を特定して報告書を書ける | 作業手順書を、実施の前にレビューする。障害の演習を運営する |
| 設計 | 14〜19 | 第3部、{{ch:uc}}のケース1〜8、{{ch:rev}}、{{ch:calc}} | ケースを1つ選び、構成と判断を、チームの前で説明できる | 設計のレビューで、質問する側に回る。ほかの受講者にも、指摘をさせる |
| 総合 | 20〜 | {{ch:cap}}、担当する案件に近い第4部の章 | {{ch:cap}}の「評価の基準」で、すべての観点が「合格」に届く | 発表を聞き、評価の表で講評する |

第2部（{{ch:env}}を読む2週目から、13週目まで）は、{{ch:env}}に書いた目安の12週間に当たります。ステップ2、3、7、8は、ほかのステップより時間がかかります。1週間で終わらなくても、遅れとは扱わないでください。合格基準を満たさないまま次へ進むほうが、後で大きな遅れになります。

第4部のうち、{{ch:xnet}}、{{ch:mig}}、{{ch:k8s}}には、手元のPCで通せる実習があります。AWSの費用がかからないため、設計の段階と並行して、いつでも取り組めます。

研修として、日中の時間をまとめて使える場合の例です。1日6時間、20日間で、第2部の終わりまでを通し、設計の入口までを扱います。

| 週 | 範囲 | 区切りで確かめること |
|---|---|---|
| 1 | 第1部、{{ch:env}}、ステップ1〜2 | 安全の設定。ステップ1〜2の合格 |
| 2 | ステップ3〜5 | ステップ3〜5の合格。作業手順書と障害報告書 |
| 3 | ステップ6〜8、{{ch:ts}}の実機の演習 | コードからの作り直し。障害の演習の報告書 |
| 4 | 第3部の要点、{{ch:uc}}から2〜3ケース、発表 | 構成と判断の説明 |

設計の演習の残り（{{ch:uc}}のほかのケース、{{ch:rev}}、{{ch:calc}}、{{ch:cap}}）は、配属の後に、週1回の勉強会として続けます。

日程を詰めると、手は動きますが、定着のための間隔が取れません。集中して行った場合は、終了の1か月後に、ステップ3か4を、手順を見ずに作り直す回を設けてください。そこで作れなければ、身についていません。

## 合格の判定と記録

### 判定の決まり

各ステップの章には、「実技の合格基準」（できているかを、出力で示す）と、「確認ポイント」（理由を説明できるか）があります。判定は、次の4つがそろったときに、合格とします。

1. 合格基準の表の、すべての番号について、出力や画面が提出されている
2. 5分の説明と、その後の質問に、自分の言葉で答えられる
3. そのステップで求めている文書（{{ch:docs}}のひな形）が、実際の値と一致している
4. 片付けが済み、翌日以降に、請求の画面を確かめている

判定は、3つに分けます。

| 判定 | 状態 | 次に行うこと |
|---|---|---|
| 合格 | 4つがそろっている | 次のステップへ進む |
| 条件つき | 動いているが、説明、文書、片付けのどれかが足りない | 足りない点を伝え、次の定例までに出し直す。次のステップに、並行して進んでよい |
| やり直し | 合格基準の出力が出せない。または、なぜ動いているかを説明できない | 一度すべて消して、作り直す。手順のどこを見ながら作ったかを、振り返る |

{{fig:mentorloop|1つのステップの進め方。判定は、次へ進む前に行う}}

「動いたので合格」にしないでください。手順を写して動かしただけの状態と、理解して作った状態は、出力だけでは区別できません。区別できるのは、説明と、壊したときの対応です。

### 説明を聞くときの質問

5分の説明の後に、次の3種類の質問を、1つずつ行います。答えられなかった質問は、次の回の宿題にします。

| 質問の種類 | 例 |
|---|---|
| なぜ、そうしたか | アプリサーバーのセキュリティグループの送信元を、IPアドレスの範囲ではなく、ALBのセキュリティグループにしたのは、なぜですか |
| 変えると、どうなるか | このルートテーブルから、NATゲートウェイへの経路を消すと、何が、どの順に起きますか |
| 本番では、どう変わるか | この構成を、止められないシステムで使うとしたら、どこを変えますか |

2つ目の質問は、その場で実際に試させると、最も効果があります。各ステップの「わざと壊してみる」が、その題材です。

### ステップごとの、見落としやすい点

合格基準の出力がそろっていても、次の点は、指導役が自分の目で確かめてください。

| ステップ | 確かめる点 |
|---|---|
| 1（{{ch:s1}}） | 出力のARNが、学習用のロールのものか。ルートユーザーや、権限の広すぎる利用者で作業していないか。バケットを公開して動かした形跡がないか |
| 2（{{ch:s2}}） | アドレス設計の表に、範囲を決めた理由が書かれているか。メインルートテーブルに任せたままのサブネットがないか |
| 3（{{ch:s3}}） | セキュリティグループの送信元が、IPアドレスの範囲になっていないか。回復にかかった時間を、実際に測っているか |
| 4（{{ch:s4}}） | パスワードが、コマンドの履歴、提出物、チャットに残っていないか。復元を、実際に行っているか |
| 5（{{ch:s5}}） | 通知が、実際に届いているか（届いたメールを見る）。作業手順書を、作業の前に書いているか |
| 6（{{ch:s6}}） | 認証のないルートがないか。スロットリングを設定しているか。関数の同時実行の上限を設定しているか（設定できないアカウントでは、その理由を説明できるか） |
| 7（{{ch:s7}}） | ステートと変数のファイルが、Gitに入っていないか。テストを、自分で1つ以上書いているか。手で加えた変更が、plan でどう見えるかを説明できるか |
| 8（{{ch:s8}}） | アクセスキーを、どこにも置いていないか。信頼ポリシーの条件が、自分のリポジトリと環境に、完全一致で絞られているか |

### 記録のひな形

判定は、受講者ごとに、1つの表に残します。後から、どこで時間がかかったか、何が苦手かを、読み取れるようにします。

| ステップ | 提出日 | 合格基準 | 説明 | 文書 | 片付けと費用 | 判定 | 所見 |
|---|---|---|---|---|---|---|---|
| 2 | 11/20 | 5/5 | メインルートテーブルの説明に詰まった | パラメータシートあり。理由の欄が空 | 済み。翌日0.31ドル | 条件つき | 理由の欄を埋めて再提出。経路の関連付けを、もう一度説明してもらう |
| 2（再） | 11/27 | 5/5 | 説明できた | 理由の欄を記入 | 済み | 合格 | NATゲートウェイを置くサブネットを、自分で図に描いて説明できた |

所見には、できなかったことだけでなく、できるようになったことを書きます。受講者に見せる前提で書いてください。

## つまずいたときの関わり方

### 答えを渡さずに、段階を踏む

受講者が止まっているときは、次の順に、関わり方を強めていきます。1つ進めるたびに、数分は待ちます。

| 段階 | 指導役が行うこと | 例 |
|---|---|---|
| 1 | 起きていることを、事実で言い直してもらう | 「何をしたら、何が表示されましたか。エラーの文を、そのまま読んでください」 |
| 2 | どこまで届いているかを、問う | 「利用者からデータベースまでの間で、どこまでは正常だと、確かめられていますか」 |
| 3 | 見る場所を、示す | 「ターゲットグループの画面で、異常の理由の欄には、何と書いてありますか」 |
| 4 | 原因を伝え、理由を説明してもらう | 「セキュリティグループの送信元です。なぜそれで、この症状になるのかを、説明してみてください」 |

多くの場合、段階1で、受講者が自分で気づきます。エラーの文を読んでいない、見ている場所が違う、思い込みで操作を重ねた、のどれかであることが多いためです。段階4まで進んだ場合も、原因を伝えて終わりにせず、理由の説明までを、受講者に行わせます。

質問を受けたときは、{{ch:field}}の5点（目的、したこと、起きたこと、調べたこと、知りたいこと）がそろっているかを、先に見ます。そろっていなければ、足りない項目を聞き返します。質問を書き直す途中で、受講者が自分で解決することは、よくあります。それは、指導がうまくいっている状態です。

抱え込みにも、注意します。15〜30分調べて進まなければ質問する、という目安を、最初に伝えておきます。黙って半日止まっている受講者には、指導役から声をかけます。

### よくあるつまずきと、最初の問いかけ

各ステップの「つまずきやすい点」に、症状と原因の表があります。指導役は、原因を知っていても、表の「確かめ方」の列へ、受講者を導く問いかけから始めます。

| 症状 | 最初の問いかけ | 導く先 |
|---|---|---|
| CloudFrontのURLが403になる | 「S3のURLと、CloudFrontのURLで、結果は同じですか」 | バケットポリシーの条件と、ディストリビューションのIDの照合（{{ch:s1}}） |
| ルートを追加したのに、効かない | 「そのサブネットは、どのルートテーブルに従っていますか」 | サブネットの関連付け。メインルートテーブル（{{ch:s2}}） |
| ターゲットが unhealthy のまま | 「理由の欄には、何と書いてありますか。サーバーの中からは、応答しますか」 | ヘルスチェックの理由と、`curl localhost`（{{ch:s3}}） |
| Session Manager の一覧に、サーバーが出ない | 「サーバーは、外へ出られますか。何で確かめられますか」 | IAMロールと、外部への経路（{{ch:s3}}） |
| データベースに接続できない | 「待たされてから失敗しますか。すぐに失敗しますか」 | エラーの出方で、届いている範囲を分ける（{{ch:s4}}） |
| アラームが鳴ったのに、メールが届かない | 「SNSの宛先は、どういう状態ですか」 | サブスクリプションの確認（{{ch:s5}}） |
| 関数が AccessDenied になる | 「エラーの文に、足りない操作と対象は、書かれていますか」 | 実行ロールの権限（{{ch:s6}}） |
| `apply` が途中で失敗した | 「何が作られ、何が作られていませんか。ステートには、何がありますか」 | エラーを読んで直し、もう一度適用する。手で消さない（{{ch:s7}}） |
| GitHub Actionsで、ロールを引き受けられない | 「信頼ポリシーの条件の文字列と、実際のリポジトリ名を、並べて見比べましたか」 | 条件の完全一致（{{ch:s8}}） |

思いついた設定を、順に変えて試す受講者には、手を止めさせます。変えた設定を戻し忘れ、原因が増えていくためです。{{ch:s3}}の「症状からではなく、通信の順に確かめる」に戻し、「どこまで届いているか」を、1つずつ確かめさせます。

### 避けたい関わり方

- 画面を見て、すぐに原因を言う。受講者は、次も、指導役を待つようになる
- 「前にも言った」と言う。聞いて知っていることと、自分で使えることは、別である。使えるまで、形を変えて問う
- うまくいっている受講者を、放っておく。手順を写して進んでいるだけのことがある。「変えると、どうなるか」を、必ず問う
- 遅れている受講者に、合格基準を緩める。基準はそのままにし、時間を足す

## 障害の演習の進め方

{{ch:ts}}には、文章で考える14のシナリオと、実際の環境に障害を入れて調べる演習があります。

### 読んで考えるシナリオ

- 解答を開く前に、仮説を2つ以上と、それぞれの確かめ方を、紙に書かせる
- 2人1組にし、1人が調べる役、もう1人が「なぜ、そこを見るのか」を問う役にすると、考えが言葉になる
- 解答と同じ原因に、たどり着いたかどうかだけで、評価しない。確かめる順番が、利用者に近い側から進んでいたかを見る

### 実機の演習の準備

実機の演習は、{{ch:s7}}の参考実装で作った環境を使います。ステップ7に合格した後に行います。

1. 学習用のアカウントで、参考実装を適用し、ページが表示されることを確かめる
2. 受講者に見えないところで、障害を入れる。名前を指定するか、`random` を使う
3. 「届いた連絡」と、待つ時間（2分か10分）が表示される。その時間だけ待つ。障害の影響が、外から見えるようになるまでの時間である
4. 受講者には、「届いた連絡」だけを伝える

```bash
cd labs/terraform
../faults/inject.sh list
../faults/inject.sh target-group-detached
```

障害は5つあります。次の順に出すと、やさしいものから、難しいものへ進みます。

| 順 | 障害の名前 | 難しさ | この障害で身につくこと |
|---|---|---|---|
| 1 | target-group-detached | すぐにエラーになり、原因が1か所にある | 利用者の側から、順に確かめる |
| 2 | app-sg-closed | 待たされてから、エラーになる。サーバーの中は正常 | エラーの出方から、届いている範囲を分ける |
| 3 | web-stopped | 調べ始めたときには、直っている | 記録から、過去に起きたことを組み立てる |
| 4 | health-path | 利用者には、何も見えていない | 利用者に見えない異常を、指標と履歴から見つける |
| 5 | no-egress-route | サーバーに入れず、中から調べられない | 外から見える事実だけで、原因にたどり着く |

### 当日の進め方

1回の演習は、60〜75分を目安にします。

| 時間 | 行うこと |
|---|---|
| 始める前 | 障害を入れ、表示された時間（2分か10分）を待つ |
| 5分 | 出題。届いた連絡を伝える。調査の記録を取ることを、もう一度伝える |
| 30〜40分 | 調査と復旧。指導役は、観察し、記録する。口は出さない |
| 10分 | 受講者が、原因、証拠、復旧の方法を報告する |
| 15分 | 振り返り。答え合わせ（`reveal` と、`terraform plan` の表示）。観察したことを伝える |

制限時間を過ぎても原因にたどり着けない場合は、前の節の段階1から、順に関わります。時間内に解けたかどうかより、調べ方が身についたかどうかを見ます。

### 観察する点

調査の間、指導役は、次の点を記録します。振り返りで、具体的な場面を挙げて伝えます。

| 観点 | よい動き | 直したい動き |
|---|---|---|
| 事実と推測 | 届いた連絡から、わかることと、わからないことを分けて書いている | 最初の思いつきを、原因と決めて進む |
| 仮説 | 2つ以上を挙げ、確かめ方を決めてから動く | 仮説を言葉にせず、画面を次々に開く |
| 順番 | 利用者に近い側から、どこまで届いているかを確かめる | 知っている設定から、順に見て回る |
| 証拠 | 原因と判断した根拠を、出力や記録で示せる | 「たぶん、これです」で復旧に進む |
| 変更 | 調査の間は、設定を変えない。変えるときは、何を変えるかを先に言う | 試しに設定を変え、元に戻し忘れる |
| 復旧の確認 | 利用者の側から、直ったことを確かめる | コマンドが成功したところで、終わりにする |
| 報告 | 影響、原因、対応、再発を防ぐ仕組みを、分けて書く | 対応した操作の列挙で終わる |

演習の後は、{{ch:s5}}の型で、障害報告書を書かせます。自動で直った障害（web-stopped）でも、報告書は省略しません。

### 演習の後の片付け

演習に使った環境は、その日のうちに `terraform destroy` で消します。障害を入れたままの環境を残すと、サーバーの入れ替えが続き、費用がかかり続けるものがあります（health-path、no-egress-route）。消した後、タグでの検索で、資源が残っていないことを、受講者と一緒に確かめます。

## 費用の管理と、無料で進められる範囲

### AWSの費用がかかる範囲と、かからない範囲

この本は、AWSの費用がかかる作業を、第2部と、その環境を使う演習に集めています。それ以外は、費用をかけずに進められます。

| 範囲 | AWSの費用 | 進め方 |
|---|---|---|
| 第1部、第3部、第6部、付録 | かからない | 読む。章末問題を解く |
| {{ch:uc}}、{{ch:rev}}、{{ch:calc}}、{{ch:cap}} | かからない | 紙と図で設計し、説明する |
| {{ch:ts}}の、読んで考えるシナリオ | かからない | 仮説を書いてから、解答を開く |
| {{ch:xnet}}、{{ch:mig}}、{{ch:k8s}}の、手元の実習 | かからない | 手元のPCのDockerで動かす |
| ステップ1〜8（{{ch:s1}}〜{{ch:s8}}） | かかる | 作った日のうちに片付ける。翌日に請求を確かめる |
| {{ch:ts}}の、実機の演習 | かかる | 参考実装を作り、演習の後に消す |
| 第4部で触れた、EKS、Transit Gateway、VPN、移行のサービスを、AWSの上で試すこと | かかる | 任意。試した日のうちに消す |

構築の力（{{ch:road}}のレベル2と3）は、AWSの実機で手を動かさなければ、身につきません。第2部の費用は、省く対象ではなく、管理する対象です。個人のアカウントで学ぶ受講者には、{{ch:env}}の「プラン：無料プランと有料プラン」を読ませ、クレジットの範囲と期限を、自分の請求の画面で確かめさせてください。

### 費用を小さく保つ進め方

- 作る日を決める。週の中の作業日にまとめて作り、その日のうちに片付ける。読む日と、作る日を分ける
- 時間で料金がかかるもの（NATゲートウェイ、ロードバランサー、データベース、サーバー）を、翌日に持ち越さない
- ステップ7に合格した後は、コードで作って、終わったら消す。{{ch:s7}}の参考実装は、作ってから片付けるまでを2時間で終えれば、費用の目安は1ドル未満である
- 東京以外のリージョンに、誤って作ったものがないかを、月に1回確かめる

### 指導役が確かめること

| 時期 | 確かめること |
|---|---|
| 作業日の終わり | {{ch:env}}の「毎回の片付けチェックリスト」を、受講者が実施したか |
| 作業日の翌日 | 請求の画面で、前日の費用が、想定の範囲か |
| 毎週の定例 | 学習ログの「かかった費用」の欄。予算アラートの通知が出ていないか |
| 予算アラートが届いたとき | 通知は、上限ではない。その日のうちに、何が動いているかを、受講者と一緒に確かめる |
| 研修の終わり | すべてのリージョンで、残っている資源がないか。個人のアカウントを使った場合は、アカウントを残すか閉じるかを、受講者と決める |

費用の事故は、受講者の失敗ではなく、仕組みの不足として扱います。責めると、次から報告が遅れます。{{ch:ts}}のシナリオ7を、起きる前に読ませておくと、費用の通知を受けたときの動き方の練習になります。

## 研修の終わりに

- {{ch:road}}の「5つのレベル」と「分野別のチェック」で、到達を確かめる。記録の表と照らし、できるようになったことと、残っている課題を、受講者に伝える
- 案件で構築を任せられる目安は、レベル3（手順なしで構築し、問題を切り分けられる）である。届いていない場合は、どのステップを、いつ、やり直すかを決める
- 配属の前に、{{ch:field}}の「参画した最初の週に確認すること」と「本番環境で作業するときのルール」を、一緒に読む。学習用の環境で許されていた試し方は、本番では許されない
- 研修で書いた構成図、パラメータシート、手順書、障害報告書は、受講者の手元に残す。配属先で、最初に文書を書くときの見本になる
- 指導役自身の振り返りを残す。どのステップで時間がかかったか、どの問いかけが効いたかは、次の研修の計画になる

:::sum
- 指導役の仕事は、教えることよりも、確かめることと、問いかけること。設定を代わりに直さない
- 合格は、出力、説明、文書、片付けの4つで判定する。「動いた」だけでは、合格にしない
- つまずきには、事実の言い直し、届いている範囲、見る場所、原因の順に、段階を踏んで関わる
- 障害の演習では、解けたかどうかより、調べ方を観察し、具体的な場面を挙げて振り返る
- 第2部と実機の演習のほかは、費用をかけずに進められる。第2部の費用は、省かずに、管理する
:::
