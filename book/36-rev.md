## 演習1：創業したばかりの会社の、最初の構成

要件：創業して3か月の会社が、サービスの最初の版を、来月公開する。開発者は3人。まず少数の利用者で試し、反応を見て作り直す前提。利用者の個人情報（氏名とメールアドレス）を預かる。費用は、月に2万円以内に抑えたい。

設計：

- EC2を1台。その中で、Webサーバー、アプリ、データベース（MySQL）を、すべて動かす
- サーバーはパブリックサブネットに置き、固定のIPアドレスを付ける。80番、443番、22番、3306番を、0.0.0.0/0 に開ける
- デプロイは、開発者がSSHで入り、最新のコードを取得して、アプリを再起動する
- データベースのバックアップは、「そのうち考える」
- 全員が、ルートユーザーのパスワードを共有して、作業している

:::q レビュー | 段階に合った指摘をする
指摘を挙げてください。「今すぐ直すべきこと」と、「利用者が増えてからでよいこと」を分けてください。
:::a
この段階の会社に、複数のAZや、自動の台数調整を求めるのは、過剰です。作り直す前提で、費用も限られています。指摘は、「取り返しがつかないこと」に絞ります。

今すぐ直すべきこと（必須）：

- データベースのポート（3306番）を、インターネットに開けている。同じサーバーの中で使うだけなら、外部に開ける必要はない。閉じる。個人情報の漏えいに、直結する
- SSH（22番）を、すべての相手に開けている。Session Manager に切り替えて閉じるか、少なくとも、接続元を限定する
- ルートユーザーを共有している。誰が何をしたかが追えず、1人の端末が侵害されると、すべてを失う。ルートユーザーに多要素認証を設定して封印し、各自の利用者を作る
- バックアップがない。サーバーが壊れるか、誤って消すと、利用者のデータを、すべて失う。作り直せないのは、データだけ。最低限、EBSのスナップショットを毎日、自動で取り、復元を一度試す
- 予算の通知を設定する。月に2万円という上限があるなら、なおさら

推奨：

- データベースを、RDSの最小の構成に出す。バックアップと、修正プログラムの適用を任せられる。サーバーを作り直しやすくなる。費用との兼ね合いで判断する
- デプロイの手順を、スクリプトにして、リポジトリに入れる。3人が、同じ手順で行えるように

利用者が増えてからでよいこと：

- 複数台と、ロードバランサー、複数のAZ
- IaCによる管理、CI/CD
- 監視の作り込み

レビューでは、「正しい構成」を押し付けるのではなく、「この会社が、来月、取り返しのつかない事故を起こさないために、何が必要か」を考えます。単一のサーバーであること自体は、この段階では、合理的な選択です。
:::

## 演習2：サーバーレスの注文API

要件：モバイルアプリから呼ばれる、注文のAPI。平常時は毎秒10件、昼の1時間は毎秒200件。注文は、失えない。応答は、95%が1秒以内。

設計：

- API Gateway（HTTP API）→ Lambda → RDS（PostgreSQL、単一AZ、小さいサイズ）
- Lambdaは、RDSと同じVPCのプライベートサブネットに置く。関数は、呼び出しのたびに、データベースへの接続を新しく作る
- 関数のタイムアウトは、最大の900秒。「長いほうが安全なので」
- 関数の実行ロールには、「AmazonRDSFullAccess」と「AdministratorAccess」を付けている。「権限のエラーで困らないように」
- データベースのパスワードは、関数の環境変数に、そのまま設定している
- 認証は、アプリに埋め込んだ、共通のAPIキーで行う

:::q レビュー | サーバーレスの落とし穴を見つける
指摘を、重要度を付けて挙げてください。
:::a
必須：

- 接続の数が、上限を超える。毎秒200件で、1件に0.2秒かかるなら、同時に40の関数が動く。遅延が起きれば、すぐに数百になる。それぞれが接続を作るため、小さいデータベースの接続の上限を超える。接続をまとめる仕組み（RDS Proxy）を置き、関数の同時実行の数に上限を設ける。接続は、呼び出しのたびではなく、実行環境ごとに1つ作って使い回す
- データベースが単一AZ。「注文は失えない」という要件に対し、障害時は、バックアップからの復元になり、その間、注文を受けられない。直前の注文も、失う可能性がある。マルチAZ構成にする
- 実行ロールに、管理者権限が付いている。関数に脆弱性があれば、アカウントのすべてを操作される。そもそも、関数がデータベースに接続するのに、IAMの「RDSFullAccess」は要らない（これは、データベースの作成や削除の権限）。必要な権限だけにする
- パスワードが、環境変数に、そのまま入っている。関数の設定を見られる人、全員に見える。Secrets Manager に置く
- 共通のAPIキーを、アプリに埋め込んでいる。アプリを解析すれば取り出せるため、認証にならない。利用者ごとに認証し、トークンを検証する

推奨：

- タイムアウトが900秒。API Gatewayは、30秒ほどで応答を打ち切るため、それ以上待つ意味がない。問題のある処理が、長時間動き続け、同時実行の枠と、接続を占有する。数秒から十数秒にする
- 同じ注文が、2回届いた場合の扱いが、書かれていない。モバイルの回線では、再送がよく起きる。注文ごとの一意の番号で、二重の登録を防ぐ
- 昼のピークでは、新しい実行環境の準備で、応答が遅れる可能性がある。応答時間の目標（95%が1秒以内）を、負荷試験で確かめる

質問：

- データベースに、リレーショナルを選んだ理由は。注文の登録と、番号での取得が中心なら、DynamoDBのほうが、この構成に合う。ほかの表との結合や、集計の要件があるのか
- 不正な大量のアクセスへの備えは。HTTP APIには、WAFを直接関連付けられない

「エラーで困らないように、広い権限を」「安全のために、長いタイムアウトを」という判断は、どちらも、問題を隠して、大きくします。
:::

## 演習3：夜間バッチの基盤

要件：毎晩1時に、取引先から届いた受注のファイル（数百件）を取り込み、在庫を引き当て、出荷の指示を作る。朝6時の出荷の開始までに、必ず終わっていること。失敗したら、すぐに担当者が気づけること。

設計：

- EC2を1台。常時動かす。OSの定期実行の仕組み（cron）で、1時にスクリプトを起動する
- スクリプトは、ファイルを上から順に処理する。途中で失敗したら、そこで止まる。再実行すると、最初から処理する
- 処理の結果は、サーバーの中のログファイルに書く。担当者が、毎朝、サーバーに入って確かめる
- 取引先のファイルは、サーバーのディスクで、直接受け取る

:::q レビュー | バッチに特有の観点で見る
指摘を挙げてください。特に、「朝6時までに、必ず」と、「失敗したら、すぐに気づける」に注目してください。
:::a
必須：

- 再実行すると、最初から処理する。途中まで処理した後で失敗し、再実行すると、前半の受注について、在庫の引き当てと、出荷の指示が、二重に行われる。処理済みのファイルや受注を記録し、再実行しても、未処理の分だけが処理されるようにする
- 失敗に気づく手段が、「毎朝、人がログを見る」だけ。夜中の1時5分に失敗しても、気づくのは朝。6時に間に合わない。失敗したら通知する。さらに、「決めた時刻までに、正常に終わっていない」ことを検知して通知する。サーバーが止まっていて、バッチが起動すらしなかった場合、失敗の通知は来ない
- サーバーが1台で、それが止まると、バッチが動かない。代わりに動かす手段がない。別の環境で、すぐに実行できるようにする

推奨：

- 1日に数時間しか動かない処理のために、サーバーを常時動かしている。時刻になったら起動する仕組み（EventBridge のスケジュール）から、コンテナ（ECSのFargate）や、処理の流れを管理する仕組み（Step Functions）で実行する形にすれば、サーバーの保守がなくなり、どこでも動かせる
- 取引先のファイルを、サーバーのディスクで受け取っている。サーバーが壊れると、ファイルを失う。S3で受け取る。届いたことを、きっかけにもできる
- ログが、サーバーの中にしかない。サーバーの外に送る
- 1件のデータの不正で、全体が止まる。不正な1件を飛ばして記録し、残りを処理するのか、全体を止めるのかを、業務の側と決める

質問：

- 処理に、今、どのくらいの時間がかかっているか。件数が増えたときに、6時に間に合うか。やり直しの時間の余裕は
- ファイルが届かなかった場合、または、2回届いた場合は、どうするか
- 在庫の引き当ては、日中の画面からの操作と、同じデータを更新する。同時に動いた場合の扱いは

バッチの設計で、最初に問うのは、「途中で止まったら、どうやり直すか」です。何度実行しても、結果が同じになる作りにしておけば、失敗したときの判断は、「もう一度実行する」だけで済みます。
:::

## 演習4：権限とアカウントの運用

要件：開発者15人、運用担当3人の会社。3つのサービスを運営している。来年、取引先から、セキュリティの監査を受ける予定がある。

現状：

- AWSアカウントは1つ。本番、検証、開発が、すべて入っている。名前の先頭で区別している
- 全員に、IAMユーザーがあり、全員が「AdministratorAccess」を持つ
- 多要素認証は、「各自に任せている」
- CI/CD用に、アクセスキーを持つIAMユーザーが1つあり、キーは、3年前に発行したまま。同じキーが、複数の仕組みと、何人かの開発者の端末にも設定されている
- 退職者のIAMユーザーは、「気づいたときに」削除している
- CloudTrailは、設定していない。「既定で見られるので」

:::q レビュー | 監査の前に、何から直すか
問題点を挙げ、対応の優先順位を付けてください。すべてを一度に直すことはできない前提で、最初の1か月に行うことを、3つ選んでください。
:::a
問題点：

- 全員が管理者で、誰でも、本番のすべてを変更・削除できる。誤操作と、1人の端末の侵害が、そのまま全体の事故になる
- 多要素認証が、必須になっていない
- 3年間、同じアクセスキーが、複数の場所で使われている。どこから漏れてもわからず、交換しようにも、どこに設定されているかがわからない。退職者も、このキーを知っている可能性がある
- 退職者の利用者が、残っている
- 操作の記録が、90日しか残らない。監査で、半年前の操作を示せない。データへのアクセスの記録もない
- 本番と、それ以外が、同じアカウントにある。取り違えが起きやすく、権限も分けにくい

最初の1か月に行うこと（効果が大きく、すぐにできる順）：

1. 多要素認証を、全員に必須にする。あわせて、退職者の利用者を、今すぐ棚卸しして、削除する。今日からできる
2. CloudTrailの証跡を作り、記録を、長期保存する。記録は、作った日からしか残らない。監査が来年なら、早く始めるほど、示せる期間が長くなる
3. 共有のアクセスキーを、廃止する計画を立て、着手する。まず、どこで使われているかを、記録から洗い出す。CI/CDは、OIDCによる連携に切り替える。切り替えが終わったものから、古いキーを使えなくしていく

その次に行うこと：

- 人の入口を、IAM Identity Center に移し、役割に応じた権限にする。日常は、本番を変更できない権限で作業し、必要なときだけ、強い権限を得る
- アカウントを、本番と、それ以外に分ける。さらに、サービスごとに分ける（{{ch:org}}）
- 検知の仕組み（GuardDuty、Security Hub CSPM）を有効にする

優先順位の考え方は、「今、起きたら、最も被害が大きく、最も簡単に防げるもの」からです。アカウントの分割は、効果は大きいものの、時間がかかります。先に、多要素認証と、記録と、キーの廃止を進めます。
:::

## 演習5：見積もりのレビュー

要件：動画の学習サービス。利用者は、月に、1人あたり平均10時間の動画を見る。利用者は5,000人。動画は、1時間あたり約1GB。

提出された見積もり（月額）：

| 項目 | 内容 | 金額 |
|---|---|---|
| アプリサーバー | 4台、常時 | 300ドル |
| データベース | マルチAZ | 300ドル |
| ロードバランサー | 1つ | 20ドル |
| 動画の保存 | S3、2TB | 50ドル |
| 合計 | | 670ドル |

備考には、「本番環境の費用。為替は考慮していない。動画は、S3からCloudFrontで配信する」と書かれています。

:::q レビュー | 見積もりの穴を見つける
この見積もりに、抜けている項目を挙げてください。最も影響の大きいものについて、仮単価（インターネットへの転送1GBあたり0.10ドル）で、金額を概算してください。
:::a
最も影響の大きい抜け：動画の配信の、データ転送の料金。

- 5,000人 × 10時間 × 1GB = 月に50,000GB（50TB）
- 50,000GB × 0.10ドル = 5,000ドル

見積もりの合計（670ドル）の、7倍以上の金額が、抜けています。動画や、大きなファイルを配信するサービスでは、サーバーやデータベースではなく、データ転送が、費用の大半を占めます。実際の単価は、量が増えるほど下がり、配信の事業者との契約によっても変わりますが、桁が変わることはありません。

そのほかの抜け：

- 本番以外の環境（検証、開発）
- NATゲートウェイ（時間と、通過するデータ）
- ログの取り込みと保存。動画の配信の記録は、量が多い
- バックアップ、スナップショット
- 動画の変換の処理（アップロードされた動画を、配信用の形式にする）
- 監視、WAF、証明書などの周辺
- サポートの契約
- 動画の保存の増加。2TBは、今の量。毎月、どれだけ増えるか

備考について：

- 「為替は考慮していない」。円で予算を立てるなら、前提のレートを明記し、変動した場合の幅を示す
- 数量の前提（利用者の数、視聴の時間）が、見積もりの表の中に書かれていない。利用者が2倍になると、どの項目が、どう増えるかが、読み取れない

対策の方向：

- 動画の画質を、回線や端末に合わせて切り替える。全員に、最高の画質で送らない
- 利用者あたりの費用（この場合、転送だけで1人あたり月1ドル）を、料金の設計と比べる

見積もりのレビューでは、「この構成で、最も量が多いものは何か」を、最初に考えます。図に描かれた箱ではなく、箱の間を流れるものに、費用がかかります。
:::

## 演習6：災害対策の設計

要件：東京で動く予約システム。東京が使えなくなった場合、2時間以内に、大阪で再開する。失ってよいデータは、15分以内。

設計の説明：

- 大阪には、平常時は、何も動かしていない。災害のときに、担当者が、手順書に沿って、管理画面から環境を作る
- データベースは、毎日午前3時に、スナップショットを大阪へ複製している
- 利用者がアップロードしたファイル（S3）は、「S3は耐久性が高いので」、複製していない
- DNSのレコードのTTLは、86400秒
- 切り替えの手順書は、2年前に作った。訓練は、「業務への影響があるため」、行っていない
- 手順書と、構成の資料は、東京のリージョンにある、社内のWikiに置いている

:::q レビュー | 目標を満たせるかを確かめる
要件（2時間以内、15分以内）に照らして、この設計が満たせない点を、すべて挙げてください。
:::a
必須（要件を満たせない点）：

- データを失う量が、最大24時間。毎日のスナップショットの複製では、15分以内という目標を、満たせない。データベースを、大阪へ継続的に複製する（リージョン間の複製の機能を使う）
- 再開までの時間が、2時間に収まらない可能性が高い。管理画面から、手作業で環境を作るのに、何時間かかるかが、わかっていない。2年前の手順書は、今の構成と合っていない可能性が高い。環境をIaCで作れるようにし、実際に作って、時間を測る
- DNSのTTLが24時間。切り替えても、利用者の通信が大阪に向くまで、最大24時間かかる。短くする
- アップロードされたファイルが、大阪にない。S3の耐久性の高さは、リージョンの中での話。東京のリージョンが使えなければ、ファイルを読めない。大阪へ複製する
- 手順書が、東京にある。東京が使えないときに、手順書を読めない。災害のときに使える場所にも置く
- 訓練をしていない。手順が働くか、何時間かかるかが、わからない。目標を満たせると、言える根拠がない

推奨：

- 2時間という目標なら、最低限の中核（複製を受けるデータベースなど）を、大阪で常に動かしておく方式（パイロットライト）が、現実的。何もない状態から2時間で再開するのは、IaCがあっても、余裕が少ない
- 大阪で、必要な資源の種類と量を、災害のときに確保できるか。上限値（クォータ）は、東京と同じになっているか
- 秘密情報、証明書、コンテナのイメージは、大阪にあるか

質問：

- 切り替えると決めるのは、誰か。その人に、夜間や休日に、連絡がつくか
- 連携している外部のシステムは、大阪からの通信を、受け付けるか
- 東京が復旧した後、どう戻すか

この設計は、「大阪にスナップショットがある」ことで、災害対策ができているように見えます。しかし、目標の数字と、1つずつ照らし合わせると、どちらの目標も満たせていません。災害対策のレビューでは、「目標の時間の中で、誰が、何を見て、どの手順を、どの順に実行するか」を、時刻を追って、たどってみることが有効です。
:::
