:::goal
- 複数のVPCをつなぐ方法（ピアリング、Transit Gateway、PrivateLink、VPCの共有）を使い分けられる
- 会社のネットワークとクラウドを、冗長性と暗号化を考えてつなげる
- 名前解決とアドレスの管理を、複数のVPCと社内にまたがって設計できる
- 手元に作ったネットワークで、経路の不足を見つけて直し、回線の切り替わりにかかる時間を測れる
:::

アカウントを分けると、VPCも増えます。{{ch:s2}}で作ったVPCは1つでしたが、数十のVPCと、社内のネットワーク、複数の拠点がつながる環境では、「どことどこが通信でき、どこが通信できないか」を、全体として設計する必要があります。

## VPCが増えると起きること

| 問題 | 内容 |
|---|---|
| 接続の数が増える | 1対1でつなぐと、VPCが10個で45本、20個で190本の接続が必要になる |
| アドレスが重なる | 各チームが自由に範囲を決めると、同じ範囲のVPCができ、つなげなくなる |
| 経路の管理が分散する | どのVPCからどこへ届くかが、多数のルートテーブルに散らばる |
| 出口と入口が増える | VPCごとにNATゲートウェイやインターネットへの入口があると、費用がかさみ、通信の検査も行き届かない |
| 名前を引けない | あるVPCや社内から、別のVPCの中の名前を解決できない |

## つなぎ方を選ぶ

| 方法 | 仕組み | 向いている場面 | 注意する点 |
|---|---|---|---|
| VPCピアリング | 2つのVPCを直接つなぐ | つなぐVPCが少ない。2つのVPCの間で大量に通信する | 通り抜けはできない。AとB、BとCをつないでも、AからCへは届かない |
| Transit Gateway | 中央の中継点に、VPCや社内との接続を集める | VPCが多い。社内とも広くつなぐ。経路を一か所で管理したい | 時間の料金と、通過したデータの量の料金がかかる |
| PrivateLink | 特定のサービスだけを、相手のVPCの中に出入口として見せる | 別の会社やチームに、1つのサービスだけを提供する。アドレスの範囲が重なっていても使える | ネットワーク全体をつなぐものではない。提供する側から始める通信には使えない |
| VPCの共有 | 1つのVPCのサブネットを、複数のアカウントで共有して使う | ネットワークは専門のチームが一元管理し、各チームはその中に資源を置く | 同じVPCの中にいるため、分離はセキュリティグループなどで行う |

{{fig:tgw|ハブ・アンド・スポーク構成の例。接続を中央に集め、どこからどこへ通すかを中央の経路表で決める}}

Transit Gateway を使う構成では、中央の経路表を複数持つことで、通信の分離を表現します。たとえば、「本番のVPCと検証のVPCは、互いに通信できない。どちらも、共通サービスのVPCと社内には届く」という決まりを、経路表の組み合わせで実現します。つなぐことよりも、「何をつながないか」を決めることが設計の中心です。

## 出口と入口をまとめる

インターネットへの出口を、VPCごとではなく、専用のVPCにまとめる構成があります。各VPCからインターネット宛ての通信を、Transit Gateway 経由で出口のVPCに集め、そこでファイアウォール（AWS Network Firewall など）による検査と、NATゲートウェイによる変換を行います。

| 利点 | 代償 |
|---|---|
| 通信の検査と記録を、一か所で行える。許可する宛先の一覧を、全体で統一できる | 出口のVPCが、全体の単一障害点になり得る。複数のAZで冗長にする |
| NATゲートウェイの数を減らせる | Transit Gateway を通過するデータの量に料金がかかる。通信量が多いと、かえって高くなる |

S3やDynamoDBなど、AWSのサービスへの通信は、各VPCのVPCエンドポイントから直接届けるほうが、安くて速いことが多くあります。すべてを中央に集めるのではなく、通信の種類ごとに経路を決めます。

## 会社のネットワークとつなぐ

| 方法 | 特徴 | 設計で決めること |
|---|---|---|
| Site-to-Site VPN | インターネットの上に、暗号化した通り道を作る。数日で始められる | 1つの接続は、2本のトンネルで構成される。両方を使えるように、社内側の機器を設定する。通信の速さと安定性は、インターネットの状況に左右される |
| Direct Connect | 専用の回線でつなぐ。通信の品質が安定し、大量の通信では転送の料金も下がる | 開通までに、数週間から数か月かかる。1本では、回線や接続拠点の障害で切れる。標準では暗号化されない |

重要なシステムをつなぐ場合の基本形は、次のとおりです。

- Direct Connect を、2つの異なる接続拠点に、1本ずつ引く。1つの拠点の障害で両方が切れないようにする
- 費用を抑えたい場合は、Direct Connect を1本にし、VPNを予備にする。切り替わったときに、通信の速さが落ちることを、利用部門と合意しておく
- 暗号化が必要なら、Direct Connect の上でVPNを使うか、回線の区間を暗号化する機能（MACsec）を使う。「専用線だから安全」とは限らない
- どの経路を優先するか、障害時にどう切り替わるかは、BGP（経路の情報を交換する仕組み）の設定で決まる。切り替えを、実際に回線を止めて試す

回線の手配は、設計の中で最も時間がかかる部分です。プロジェクトの早い段階で、回線の事業者と社内のネットワークの担当者を交えて始めます。

## 名前解決をつなぐ

通信の経路がつながっても、名前を引けなければ使えません。たとえば、社内のサーバーから、VPCの中のデータベースのエンドポイント（プライベートな名前）は、そのままでは解決できません。

| 向き | 仕組み |
|---|---|
| 社内から、VPCの中の名前を引く | VPCに、問い合わせを受け付ける出入口（Route 53 Resolver のインバウンドエンドポイント）を作る。社内のDNSサーバーに、「この名前は、ここへ問い合わせる」という転送の設定をする |
| VPCから、社内の名前を引く | VPCに、問い合わせを送り出す出入口（アウトバウンドエンドポイント）と、「この名前は、社内のDNSサーバーへ送る」という規則を作る。規則は、ほかのアカウントのVPCにも共有できる |
| VPC同士で、プライベートな名前を引く | プライベートホストゾーンを、複数のVPCに関連付ける |

「つながらない」の原因が、経路や許可ではなく、名前解決にあることは、珍しくありません。{{ch:net}}の確認順のとおり、最初に名前解決を確かめます。

## アドレスを管理する

アドレスの範囲の重複は、後から直すのが最も難しい問題です。次の決まりを、最初に作ります。

- 全体の計画を持つ：社内、各リージョン、各環境に、重ならない大きな範囲を割り当てる。たとえば、東京の本番は 10.16.0.0/12 の中から、というように決める
- 払い出しを一元化する：新しいVPCの範囲は、台帳から払い出す。Amazon VPC IP Address Manager（IPAM）を使うと、払い出しと、重複の検出を自動化できる
- 将来の分を残す：買収した会社との接続、新しいリージョン、コンテナの増加など、今は見えていない需要のために、未使用の範囲を残しておく

すでに重複してしまったネットワーク同士をつなぐ必要が出た場合は、PrivateLink で必要なサービスだけを見せる、アドレスを変換する仕組み（プライベートNATゲートウェイ）を挟む、といった回避策を使います。いずれも、構成が複雑になります。

## 手元で通す：社内とクラウドをつなぐ

複数のVPCと社内をつなぐ構成は、AWSの上で試すと、Transit Gateway やVPNに、作った時点から時間の料金がかかります。一方、この章で扱った考え方の中心は、経路です。経路が行きと戻りの両方に要ること、つながない設計を経路表で表すこと、細かい経路が優先されること、名前解決にも転送の設定が要ること、回線が切れたときの切り替わり方。これらは、手元のPCで、費用をかけずに確かめられます。

ここでは、1つのコンテナの中に、機器7台分のネットワークを作ります。実習に使うファイルは、この本のリポジトリの [labs/network](https://github.com/KazuoMiya/cloud-practice-textbook/tree/main/labs/network) にあります。この節の手順は、変更のたびに、最初から最後まで動かして確かめています。

{{fig:netlab|実習で作るネットワーク。四角1つが機器1台。wan2 は、最後の実習で足す}}

| 機器 | 役割 | アドレス | AWSで当たるもの |
|---|---|---|---|
| pc | 社内の端末 | 192.168.210.10 | 社内の利用者の端末 |
| dns-office | 社内のDNSサーバー | 192.168.210.53 | 社内のDNSサーバー |
| router-office | 社内のルーター | 社内側 192.168.210.254、回線側 192.168.255.1 | 社内側の接続機器（カスタマーゲートウェイ） |
| hub | クラウド側の中継点 | 回線側 192.168.255.2、本番側 10.210.1.254、検証側 10.210.2.254 | Transit Gateway |
| web-prod | 本番のサーバー | 10.210.1.10 | 本番のVPCのサーバー |
| dns-cloud | クラウド側のDNSサーバー | 10.210.1.53 | Route 53 Resolver のインバウンドエンドポイント |
| web-dev | 検証のサーバー | 10.210.2.10 | 検証のVPCのサーバー |

### 準備

Dockerを使います。`docker compose version` が表示されれば、準備はできています。

```bash
cd labs/network
docker compose up -d --build
docker compose exec lab bash
```

2つ目のコマンドは、初回だけ、道具を入れたイメージを作ります。1〜2分かかり、このときだけ、インターネットへの接続が要ります。会社のPCで使う場合は、Docker Desktop の利用条件と、社内の決まりを、先に確かめてください。

3つ目のコマンドで、実習用のコンテナの中に入ります。この節のコマンドは、片付けを除いて、すべてこの中で実行します。途中で、通信を観察するために、端末をもう1つ使います。別の端末でも、同じ3つ目のコマンドで中に入れます。

:::warn 実習用のコンテナは、特権つきで動く
このコンテナは、中に仮想のネットワークを作るために、特権つき（privileged）で動かします。外のネットワークにはつないでいないため、中の機器からインターネットや社内のネットワークへは、出られません。学習用の端末で使い、終わったら、この節の最後の手順で片付けてください。
:::

構成を作ります。機器の中でコマンドを実行するには、機器の名前を先頭に付けます。`pc ip route` は、「機器 pc の中で、`ip route` を実行する」という意味です。

```bash
lab static
hub ip -br addr
pc ip route
router-office ip route
```

`hub` には、回線側（wan1）、本番側（to-prod）、検証側（to-dev）の3つの口があります。`pc` の経路表には、同じネットワークの中（192.168.210.0/24）と、それ以外をすべて `router-office` へ送る既定の経路（default）があります。`router-office` の経路表には、自分が直接つながっている2つの範囲しかありません。

この構成は、経路が足りない状態で始まります。足りない場所を、順に見つけていきます。どのコマンドも、実行する前に、何が表示されるかを予想してください。何度でもやり直せます。`lab static` を実行すると、最初の状態に戻ります。

### 経路がなければ、届かない

社内の端末から、本番のサーバーへ ping を送ります。

```bash
pc ping -c 2 -W 1 10.210.1.10
```

```text
From 192.168.210.254 icmp_seq=1 Destination Net Unreachable
```

返事をしたのは、本番のサーバーではなく、社内のルーター（192.168.210.254）です。`pc` は、既定の経路に従って、`router-office` へ送りました。`router-office` は、10.210.1.10 への経路を知らないため、「行き先がない」と返しました。

AWSのルートテーブルに経路がない場合は、この返事も返りません。通信は黙って捨てられ、利用者には、時間切れとして見えます。

### 行きの経路だけでは、返事が戻らない

`router-office` に、「クラウド側の範囲（10.210.0.0/16）は、回線の向こうの `hub` へ送る」という経路を足します。

```bash
router-office ip route add 10.210.0.0/16 via 192.168.255.2
pc ping -c 2 -W 1 10.210.1.10
```

今度は、何も返ってこなくなります（100% packet loss）。どこまで届いているかを調べます。もう1つの端末でコンテナに入り、本番のサーバーに届く通信を表示させます。その状態で、最初の端末から、もう一度 ping を送ります。表示は、Ctrl+C で止めます。

```bash
web-prod tcpdump -ni eth0 icmp
```

```text
10:35:56.148078 IP 192.168.210.10 > 10.210.1.10: ICMP echo request, id 162, seq 1, length 64
10:35:57.163467 IP 192.168.210.10 > 10.210.1.10: ICMP echo request, id 162, seq 2, length 64
```

依頼（echo request）は、本番のサーバーまで届いています。返事（echo reply）が、出ていません。`web-prod ip route` を見ると、自分のネットワーク（10.210.1.0/24）の経路しかありません。返事の宛先（192.168.210.10）へ、どこから送ればよいかを知らないのです。サーバーに、「外への通信は、中継点へ送る」という経路を足します。

```bash
web-prod ip route add default via 10.210.1.254
```

もう一度 ping を送っても、まだ返ってきません。観察する場所を、1つ手前の `hub` に移します。

```bash
hub tcpdump -ni to-prod icmp
```

```text
10:36:01.388090 IP 192.168.210.10 > 10.210.1.10: ICMP echo request, id 182, seq 1, length 64
10:36:01.388121 IP 10.210.1.10 > 192.168.210.10: ICMP echo reply, id 182, seq 1, length 64
10:36:01.388136 IP 10.210.1.254 > 10.210.1.10: ICMP net 192.168.210.10 unreachable, length 92
```

今度は、返事が `hub` まで届いています。しかし、3行目で、`hub`（10.210.1.254）が、サーバーに「192.168.210.10 への行き先がない」と返しています。`hub` も、社内への戻り方を知りません。足します。

```bash
hub ip route add 192.168.210.0/24 via 192.168.255.1
pc ping -c 2 -W 1 10.210.1.10
pc curl -s -m 3 http://10.210.1.10/
```

ping に返事が返り、`curl` は、サーバーの名前（web-prod）を表示します。返事の `ttl=62` は、途中で機器を2つ通ったことを表しています（64から始まり、機器を1つ通るたびに1減る）。

経路は、行きと戻りの両方に、通るすべての場所で要ります。「こちらからは設定したのに、つながらない」ときは、戻りの経路を疑います。調べ方は、ここで行ったとおりです。観察する場所を1つずつ動かし、「どこまで届き、どこで止まっているか」を確かめます。

AWSの構成では、次の3か所が、これに当たります。1か所でも欠けると、同じ症状になります。

| この実習で足した経路 | AWSで当たる設定 |
|---|---|
| `router-office` の、クラウド宛ての経路 | 社内のルーターの経路。BGPで受け取るか、手で設定する |
| `web-prod` の、外への経路 | VPCのサブネットのルートテーブル。社内宛てを、Transit Gateway などへ向ける |
| `hub` の、社内宛ての経路 | Transit Gateway のルートテーブル。社内宛てを、VPNや Direct Connect の接続へ向ける |

AWSでは、経路に加えて、セキュリティグループとネットワークACLの許可も要ります。通信を観察する手段は、VPCフローログと、Reachability Analyzer です。

### つないだだけでは、すべてが通る

検証のサーバー（web-dev）と、クラウド側のDNSサーバー（dns-cloud）には、外への経路を、あらかじめ入れてあります。本番のサーバーから、検証のサーバーへ接続してみます。

```bash
web-prod curl -s -m 3 http://10.210.2.10/
```

`web-dev` と表示されます。本番から検証へ、届いています。`hub` が、つながっているすべての範囲を、1つの経路表で転送しているためです。中継点につなぐと、何も決めなければ、すべてが互いに通信できます。

「本番と検証は、互いに通信させない。どちらも、社内には届く」という決まりを、経路表で表します。`hub` に、本番側から入ってきた通信が引く経路表（101）と、検証側から入ってきた通信が引く経路表（102）を作ります。どちらにも、社内への経路だけを載せ、ほかの宛先は捨てます。

```bash
hub ip route add 192.168.210.0/24 via 192.168.255.1 table 101
hub ip route add blackhole default table 101
hub ip rule add iif to-prod lookup 101
hub ip route add 192.168.210.0/24 via 192.168.255.1 table 102
hub ip route add blackhole default table 102
hub ip rule add iif to-dev lookup 102
hub ip rule
hub ip route show table 101
```

```text
0:	from all lookup local
32764:	from all iif to-dev lookup 102
32765:	from all iif to-prod lookup 101
32766:	from all lookup main
32767:	from all lookup default
```

`ip rule` の表示は、「どの口から入ってきた通信が、どの経路表を引くか」の一覧です。上から順に調べます。最初の local は、この機器自身に宛てた通信のための経路表です。to-prod から入った通信は101を、to-dev から入った通信は102を引きます。回線側（wan1）から入った通信は、どちらにも当てはまらないため、もとの経路表（main）を引きます。4つの組み合わせを確かめます。

```bash
web-prod curl -s -m 3 http://10.210.2.10/
web-dev curl -s -m 3 http://10.210.1.10/
pc curl -s -m 3 http://10.210.1.10/
pc curl -s -m 3 http://10.210.2.10/
```

最初の2つは、3秒待っても何も表示されません。後の2つは、サーバーの名前を表示します。本番と検証の間は届かず、社内からは両方に届く状態になりました。

Transit Gateway では、「どの口から入った通信が、どの経路表を引くか」を関連付け（アソシエーション）と呼び、経路表に載せる経路を、伝播（プロパゲーション）か、手での登録で決めます。ここで行ったことと、同じ考え方です。許可と拒否の規則を並べるのではなく、「経路表に載っていない宛先へは、届かない」ことで、分離を表します。

確かめてください。検証のサーバーから、クラウド側のDNSサーバー（10.210.1.53）へは、届くでしょうか。`web-dev nslookup -timeout=2 web.dev.cloud.internal 10.210.1.53` を実行すると、応答がなく、数秒で時間切れになります。DNSサーバーが、本番のネットワークにあるためです。認証、DNS、監視のように、どの環境からも使うものは、本番にも検証にも置かず、共通サービス用のVPCに置きます。そのうえで、どの経路表にも、共通サービスへの経路を載せます。

### 細かい経路が勝つ

`hub` に、本番のサーバー1台だけを指す経路を足します。向け先は、社内側です。

```bash
hub ip route add 10.210.1.10/32 via 192.168.255.1
pc ping -c 2 -W 1 10.210.1.10
```

```text
From 192.168.255.2 icmp_seq=1 Time to live exceeded
```

さきほどまで届いていたサーバーへ、届かなくなりました。`hub` の経路表には、10.210.1.10 に当てはまる経路が、2つあります。直接つながっている 10.210.1.0/24 と、いま足した 10.210.1.10/32 です。宛先に当てはまる経路が複数あるときは、範囲が狭いほう（/32）が選ばれます。これを、最長一致と呼びます。

`hub` は、この通信を社内側へ送ります。`router-office` は、「10.210.0.0/16 は `hub` へ」の経路に従って、送り返します。通信は、2台の間を回り続け、通れる機器の数の上限（TTL）を使い切って、捨てられました。表示された Time to live exceeded は、経路が輪になっているときの、典型的な表示です。

```bash
hub ip route del 10.210.1.10/32
pc ping -c 2 -W 1 10.210.1.10
```

AWSのルートテーブルも、Transit Gateway のルートテーブルも、最長一致で経路を選びます。現場では、次の場面で、この動きが問題になります。

- アドレスの範囲が重なったネットワーク同士を、一部だけ通そうとして、細かい経路を足した。その結果、もともと同じアドレスを使っていた側へ、届かなくなった
- 回線の相手から、想定より細かい経路がBGPで流れ込み、通信の向きが変わった
- 既定の経路（0.0.0.0/0）を中央の出口へ向けたが、より細かい経路が別にあり、一部の通信だけが検査を通らずに出ていた

経路を足すときは、「その宛先に当てはまる経路が、ほかにないか」を、足す前に確かめます。

### 経路はあるのに、名前で届かない

社内の端末から、本番のサーバーの名前を引きます。

```bash
pc nslookup web.prod.cloud.internal
pc nslookup web.prod.cloud.internal 10.210.1.53
```

```text
** server can't find web.prod.cloud.internal: REFUSED
```

1つ目は、社内のDNSサーバーに聞いています。答えは、REFUSED（答えられない）です。2つ目は、クラウド側のDNSサーバー（10.210.1.53）に、直接聞いています。こちらは、10.210.1.10 を返します。経路はつながっていて、クラウド側のDNSサーバーは答えを知っています。足りないのは、「社内のDNSサーバーが、この名前を、どこへ聞きに行くか」の設定です。

社内のDNSサーバーに、「cloud.internal で終わる名前は、10.210.1.53 へ聞く」という転送の設定を足し、読み込ませます。

```bash
echo 'server=/cloud.internal/10.210.1.53' > /etc/dnsmasq-office.forward
kill -HUP "$(cat /run/dns-office.pid)"
pc nslookup web.prod.cloud.internal
pc curl -s -m 5 http://web.prod.cloud.internal/
grep forwarded /var/log/dns-office.log
```

名前が引け、名前を使って、サーバーに接続できます。最後のコマンドは、社内のDNSサーバーの記録です。問い合わせを 10.210.1.53 へ転送したことが、残っています。

本文の「名前解決をつなぐ」の表の、1行目に当たります。`dns-cloud` が、Route 53 Resolver のインバウンドエンドポイントです。社内のDNSサーバーの転送の設定は、社内の担当者が行う作業です。依頼するときは、転送する名前の範囲と、転送先のIPアドレスを伝えます。エンドポイントのIPアドレスは、2つ以上を、別々のAZに用意します。

名前解決の問い合わせも、通信です。DNSサーバーの間に、経路と、53番（UDPとTCP）の許可が要ります。ここで転送が通ったのは、先に経路を足してあったからです。

### 回線を2本にして、切り替わりを測る

ここまでの経路は、すべて手で入れました。手で入れた経路は、送り先の機器や回線が止まっても、消えません。回線を2本にしても、切れた回線へ、送り続けます。

回線を冗長にするときは、BGPを使います。BGPでは、回線の両端の機器が、自分の側にある範囲を知らせ合い、相手が動いていることを、定期的に確かめ続けます。相手からの知らせが途絶えると、その相手から受け取った経路を捨て、残っている経路に切り替えます。

回線を2本にし、2台のルーターでBGPを動かす構成に、作り直します。

```bash
lab bgp
vtysh -N router-office -c 'show bgp summary'
vtysh -N router-office -c 'show ip bgp'
router-office ip route
```

`vtysh` は、ルーターの設定や状態を見るための画面です。`-N` で、どの機器を見るかを選びます。相手とつながるまでに、5秒ほどかかります。次のように表示されるまで、何度か実行してください。

```text
Neighbor        V         AS   …   Up/Down State/PfxRcd   PfxSnt Desc
192.168.255.2   4      64512   …  00:00:02            1        2 wan1
192.168.255.6   4      64512   …  00:00:02            1        2 wan2
```

```text
     Network          Next Hop            Metric LocPrf Weight Path
 *>  10.210.1.0/24    192.168.255.2            0    200      0 64512 i
 *                    192.168.255.6            0             0 64512 i
 *>  192.168.210.0/24 0.0.0.0                  0         32768 i
```

1つ目の表示は、BGPの相手の一覧です（途中の列は、省いています）。State/PfxRcd の列が数字なら、相手とつながり、その数だけ経路を受け取っています。Connect や Active と表示されている間は、つながっていません。

2つ目の表示は、受け取った経路の一覧です。本番の範囲（10.210.1.0/24）への経路を、2本の回線の両方から受け取っています。`>` が付いているのが、選ばれた経路です。LocPrf（ローカルプリファレンス）の値が大きいほうが、選ばれます。`ip route` の表示では、選ばれた経路が、`proto bgp` として、経路表に入っています。手では、何も足していません。

`router-office` の設定は、次のとおりです。`hub` にも、向きを逆にした、同じ形の設定があります。

```text
! labs/network/frr/router-office/frr.conf
hostname router-office
log file /var/log/frr/router-office.log
!
! wan1 から受け取った経路を優先する（値が大きいほうが選ばれる。既定は100）
route-map PRIMARY permit 10
 set local-preference 200
!
router bgp 65010
 bgp router-id 192.168.210.254
 ! 学習用：受け取る経路と知らせる経路を、絞り込まない
 no bgp ebgp-requires-policy
 ! 1秒ごとに生存を知らせ、3秒届かなければ、相手が落ちたとみなす
 timers bgp 1 3
 neighbor 192.168.255.2 remote-as 64512
 neighbor 192.168.255.2 description wan1
 neighbor 192.168.255.2 timers connect 5
 neighbor 192.168.255.6 remote-as 64512
 neighbor 192.168.255.6 description wan2
 neighbor 192.168.255.6 timers connect 5
 !
 address-family ipv4 unicast
  ! 社内の範囲を、相手に知らせる
  network 192.168.210.0/24
  neighbor 192.168.255.2 route-map PRIMARY in
 exit-address-family
!
```

| 設定 | 意味 |
|---|---|
| `router bgp 65010` | 自分の側のAS番号（経路をやり取りする組織の番号）。社内で使える範囲（64512〜65534）から選ぶ |
| `neighbor … remote-as 64512` | 相手のアドレスと、相手のAS番号。64512は、AWSの仮想プライベートゲートウェイや Transit Gateway の、既定のAS番号でもある |
| `network 192.168.210.0/24` | 相手に知らせる範囲 |
| `timers bgp 1 3` | 1秒ごとに生存を知らせ、3秒届かなければ、相手が止まったとみなす（保持時間）。学習用に、短くしている |
| `route-map PRIMARY` と `local-preference 200` | wan1 から受け取った経路を、優先する。どちらを主にするかは、設定で決める |
| `no bgp ebgp-requires-policy` | 受け取る経路と、知らせる経路を、絞り込まない。学習用の設定。実際の機器では、受け取る範囲と知らせる範囲を、必ず絞り込む |

通信を続けながら、主の回線を切ります。もう1つの端末で、0.2秒おきに60回（12秒間）、ping を送ります。送り始めて2〜3秒たったら、最初の端末で、回線を切ります。

```bash
pc ping -i 0.2 -c 60 -W 1 10.210.1.10
```

```bash
lab cut wan1
```

```text
60 packets transmitted, 46 received, 23.3333% packet loss, time 12268ms
```

ping が終わると、結果が表示されます。この例では、60回のうち14回が失われました。0.2秒おきなので、通信が途切れた時間は、約3秒です。自分の結果を、記録してください。

```bash
vtysh -N router-office -c 'show bgp summary'
router-office ip route show 10.210.1.0/24
pc ping -c 2 -W 1 10.210.1.10
```

wan1 の相手は Connect や Active になり、経路は、wan2 の相手（192.168.255.6）を通るものに、入れ替わっています。人は、何もしていません。

`lab cut` は、回線を途中で切ります。両端の機器から見ると、自分の口はつながったままで、相手からの知らせだけが届かなくなります。機器は、保持時間（3秒）が過ぎて、はじめて相手が止まったと判断します。途切れた時間が約3秒だったのは、このためです。保持時間は、最後の知らせを受け取った時点から数えるため、切ったタイミングによって、2秒から3秒の間で変わります。保持時間は、「切れてから、気づくまでの最大の時間」であり、そのまま、通信が途切れる時間になります。

実際の回線では、保持時間は数十秒から数分に設定されていることが多く、何もしなければ、その間は通信が途切れます。短くするには、保持時間を短くするか、より短い間隔で相手を確かめる仕組み（BFD）を、併用します。どこまで短くできるかは、回線の事業者と、機器の対応によります。要件の「何秒まで途切れてよいか」と、照らし合わせて決めます。

回線を戻します。

```bash
lab restore wan1
vtysh -N router-office -c 'show bgp summary'
router-office ip route show 10.210.1.0/24
```

数秒から十数秒で、wan1 の相手と再びつながり、経路は、wan1 を通るものに戻ります。優先する回線を設定で決めてあるため、切り戻しも自動です。

本文の「切り替えを、実際に回線を止めて試す」は、ここで行ったことを指しています。予備の回線は、用意しただけでは、働くかどうかがわかりません。主の回線を止め、途切れた時間を測り、切り替わった後の通信の速さで業務に支障がないかを、確かめます。

### 実技の合格基準

次のすべてを、コマンドの出力と、記録で示せたら合格です。

| 番号 | 確かめること | 合格の状態 |
|---|---|---|
| 1 | 行きと戻りの経路を、足せる | 3か所に経路を足し、社内の端末から本番のサーバーへ届く。足す前の各段階で、どこまで届き、どこで止まっていたかを、tcpdump の出力で示せる |
| 2 | つながない設計を、経路表で表せる | 社内からは本番と検証の両方に届き、本番と検証の間は届かない。その理由を、`ip rule` と経路表の出力で説明できる |
| 3 | 最長一致を説明できる | 1台分の経路を足したときに起きたことを、経路表を示して説明できる。経路を消して、元どおり届くことを確かめている |
| 4 | 名前解決の転送を設定できる | 転送の設定の前と後の、nslookup の出力を示せる。DNSサーバーの記録に、転送が残っている |
| 5 | 回線の切り替わりを測れる | 回線を切ったときに失われた回数と、そこから計算した途切れた時間を、記録している。切り替わった後と、戻した後の経路を示せる |
| 6 | AWSの構成に読み替えられる | 1〜5のそれぞれが、AWSのどの設定に当たるかを、説明できる |
| 7 | 片付けが済んでいる | `docker compose ps` に、何も表示されない |

提出するもの：1〜5の出力、記録した時間、6の説明。

### AWSで試す場合の費用

この実習で行ったことを、AWSの上で試す場合に、費用がかかるものと、かからないものを分けておきます。料金は、東京リージョンの目安です。試す前に、料金のページで確かめてください。

| この実習で行ったこと | AWSで使うもの | 費用 |
|---|---|---|
| 経路を足す | VPCのルートテーブル | かからない |
| 2つのネットワークを、直接つなぐ | VPCピアリング | 接続を作ることには、かからない。同じAZの中の通信にも、かからない。AZをまたぐ通信には、データの量に応じてかかる |
| AWSのサービスへの出入口を作る | S3とDynamoDBのゲートウェイエンドポイント | かからない |
| 中継点に集め、経路表を分ける | Transit Gateway | 接続（アタッチメント）1つにつき、1時間あたり0.07ドル。通過したデータ1GBあたり0.02ドル |
| 社内とつなぐ | Site-to-Site VPN | 接続1本につき、1時間あたり0.048ドル。社内側に、対応する機器も要る |
| 名前解決を転送する | Route 53 Resolver のエンドポイント | エンドポイントのIPアドレスごとに、時間の料金がかかる |
| 届くかどうかを調べる | Reachability Analyzer | 分析1回ごとにかかる（バージニア北部の料金表で0.10ドル） |

料金の出典は、[VPCピアリングの説明](https://docs.aws.amazon.com/vpc/latest/peering/what-is-vpc-peering.html)と[ゲートウェイエンドポイントの説明](https://docs.aws.amazon.com/vpc/latest/privatelink/vpce-gateway.html)（AWS）、[東京と大阪を3つの方法でつないだ記事](https://builder.aws.com/content/3GNzLkyg6VGZQUSfTZeLNhjJAdF/experiment-three-ways-to-connect-aws-tokyo-and-osaka-over-a-closed-network-how-much-does-speed-actually-differ?lang=ja)（AWS Builder Center。Transit Gateway の東京リージョンの単価）、[ISSOHの解説](https://www.issoh.co.jp/tech/details/17655/)（2026年9月の料金表。VPNの東京リージョンの単価）です。最新の料金は、[Transit Gateway](https://aws.amazon.com/transit-gateway/pricing/)、[VPN](https://aws.amazon.com/vpn/pricing/)、[VPC](https://aws.amazon.com/vpc/pricing/)の料金のページで確かめてください。

費用をかけずにAWSの上で確かめられるのは、表の上の3つです。任意の課題として、次のことを試せます。道具は、コンソール、CLI、Terraform のどれでもかまいません。

1. アドレスの範囲が重ならないVPCを、2つ作る（例：10.210.0.0/16 と 10.211.0.0/16）。それぞれに、サブネットを1つ作る
2. 2つのVPCを、VPCピアリングでつなぐ。両方のルートテーブルに、相手の範囲への経路を足す。片方にしか足さなかった場合に何が起きるかは、この実習で確かめたとおり
3. 片方のVPCに、S3のゲートウェイエンドポイントを作る。ルートテーブルに、S3のアドレスの一覧（プレフィックスリスト）を宛先とする経路が、自動で入ることを確かめる。ゲートウェイエンドポイントを使えるのは、作ったVPCの中からだけで、ピアリングの相手や社内からは使えない
4. 確かめたら、ピアリング、エンドポイント、VPCを消す

```bash
VPC_ID='自分のVPCのID'
aws ec2 describe-vpc-peering-connections \
  --query 'VpcPeeringConnections[].[VpcPeeringConnectionId,Status.Code]' --output table
aws ec2 describe-route-tables --filters Name=vpc-id,Values="$VPC_ID" \
  --query 'RouteTables[].Routes[].[DestinationCidrBlock,DestinationPrefixListId,VpcPeeringConnectionId,GatewayId]' --output table
```

ピアリングの状態が active で、ルートテーブルに、相手の範囲への経路（pcx- で始まる向け先）と、プレフィックスリスト（pl- で始まる宛先）への経路（vpce- で始まる向け先）が表示されれば、設定はできています。

サーバーを置かなければ、通信は流れず、費用もかかりません。実際に通信を流して確かめるには、両方のVPCにサーバーを置くか、Reachability Analyzer を使います。どちらも費用がかかるため、試すかどうかは任意とし、試した日のうちに消してください。Transit Gateway とVPNも、同じ扱いにします。

:::sum
- VPCが増えたら、接続を中央に集め、何をつなぎ、何をつながないかを経路表で表す
- つなぎ方は、ネットワーク全体をつなぐのか、1つのサービスだけを見せるのかで選ぶ
- 社内との接続は、冗長性、暗号化、切り替えの試験までを設計する。回線の手配は早く始める
- 名前解決とアドレスの計画は、経路と同じ重みで設計する。重複は後から直せない
- 経路は、行きと戻りの両方に、通るすべての場所で要る。届かないときは、観察する場所を動かして、止まっている場所を見つける
- 予備の回線は、実際に主の回線を止めて、途切れる時間を測って、はじめて当てにできる
:::

## 章末問題

:::q 計算 | 接続の数を数える
12個のVPCがあり、すべてのVPCが互いに通信できるようにします。

1. VPCピアリングだけで実現する場合、接続は何本必要ですか
2. Transit Gateway を使う場合、VPCとの接続（アタッチメント）はいくつ必要ですか
3. 13個目のVPCを追加するとき、それぞれの方法で、新たに必要な作業は何ですか
:::a
1. 12 × 11 ÷ 2 = 66本
2. 12個
3. ピアリング：新しいVPCと、既存の12個のVPCとの間に、12本の接続を作る。さらに、既存の12個のVPCすべてのルートテーブルに、新しいVPCへの経路を追加する。Transit Gateway：新しいVPCを1つ接続し、中央の経路表に関連付ける。既存のVPCのルートテーブルが、あらかじめ「社内やほかのVPC宛ては Transit Gateway へ」という大きな範囲の経路になっていれば、変更は要らない

VPCの数が増えるほど、差は広がります。一方、VPCが2つか3つで、今後も増えない場合は、ピアリングのほうが単純で、通過するデータへの料金もかかりません。
:::

:::q 判定 | 通り抜けはできるか
VPC-A と VPC-B、VPC-B と VPC-C が、それぞれVPCピアリングでつながっています。VPC-A のサーバーから、VPC-C のサーバーへ通信できますか。また、VPC-B がNATゲートウェイを持っている場合、VPC-A のサーバーは、VPC-B のNATゲートウェイを通ってインターネットへ出られますか。
:::a
どちらもできません。VPCピアリングは、つないだ2つのVPCの間の通信だけを運びます。ほかのVPCを経由した通り抜けや、相手のVPCのゲートウェイ（インターネットゲートウェイ、NATゲートウェイ、VPN）を借りることはできません。

VPC-A から VPC-C へ通信させるには、AとCの間にもピアリングを作るか、Transit Gateway で3つをつなぎます。出口を1か所にまとめたい場合も、Transit Gateway を使った構成にします。
:::

:::q 選択 | つなぎ方を選ぶ
次の3つの状況に合うつなぎ方を、本文の4つの方法から選んでください。

1. 自社のサービスのAPIを、顧客のVPCから、インターネットを通らずに使えるようにしたい。顧客のアドレスの範囲は、こちらでは決められず、自社と重なることもある
2. 全社で40個のVPCがあり、どれも社内のネットワークとつなぐ。本番と検証は、互いに通信させない
3. 分析用のVPCが、業務用のVPCのデータベースから、毎日大量のデータを読み出す。ほかにつなぐ予定のVPCはない
:::a
1. PrivateLink。顧客のVPCの中に、自社のAPIだけにつながる出入口を作る。ネットワーク全体はつながらないため、顧客のほかの資源には届かず、顧客から見ても安心。アドレスが重なっていても使える
2. Transit Gateway。接続を中央に集め、本番用と検証用の経路表を分けて、互いに届かないようにする。社内との接続も、1か所につなげば全体で使える
3. VPCピアリング。2つのVPCの間だけで、通信の量が多い。ピアリングは、通過するデータに対する中継の料金がかからない

1つの環境の中で、3つを併用することも普通にあります。全体は Transit Gateway でつなぎ、通信量の多い特定の組だけをピアリングで直結する、といった形です。
:::

:::q 指摘 | 専用線の設計を見直す
基幹システムのために、会社とAWSを次のようにつなぐ計画があります。指摘を3つ以上挙げてください。

「Direct Connect を1本引く。専用線なので暗号化は不要。回線の開通は、システムの構築が終わるころに申し込めば間に合う。障害時の切り替えは、回線が1本なので検討していない」
:::a
解答例：

- 【必須】回線が1本で、回線や接続拠点の障害、保守の作業で、基幹システムとの通信が止まる。別の接続拠点にもう1本引くか、少なくともVPNを予備にする
- 【必須】暗号化が不要という根拠がない。Direct Connect は、標準では通信を暗号化しない。扱うデータと、社内の規程に照らして要否を判断する。必要なら、回線の上でVPNを使うか、回線の区間を暗号化する機能を使う。アプリの層でTLSを使っているなら、それで足りるかを整理する
- 【必須】開通の申し込みが遅い。回線の開通には、数週間から数か月かかる。構築と並行して、早い段階で申し込む。開通が遅れた場合に備え、当面はVPNで始められるようにしておく
- 【推奨】切り替えの試験を計画に入れる。予備の経路を用意しても、切り替えが働くかどうかは、実際に主の経路を止めて確かめないとわからない。切り替わったときの通信の速さで、業務に支障がないかも確かめる
- 【質問】必要な通信の速さと量は、見積もられているか。データの移行のように、一時的に大量の通信が必要な時期はないか

「専用線」という言葉が、冗長性と暗号化についての思い込みを生みやすい、という例です。
