:::goal
- 「止まらないように」「速く」といったあいまいな要望を、数字の要件に置き換えられる
- 稼働率と停止時間を相互に換算し、部品を組み合わせたときの稼働率を概算できる
- 構成案を2つ以上出して比べ、判断とその理由を記録できる
:::

ハンズオンで「作れる」ようになったら、次は「なぜその構成にするのか」を説明できる力をつけます。設計とは、要件を整理し、選択肢を比べ、判断を記録する作業です。

## 設計の進め方

{{fig:designflow|設計の進め方。5つの段階を進み、検証の結果で前の段階へ戻る}}

初心者が陥りがちなのは、最初に思いついた1つの構成をそのまま作ることです。少なくとも2つの案（例：EC2で作る案と、サーバーレスで作る案）を出し、要件・費用・運用の手間で比べてから決めます。

設計を始める前に、動かせない条件（制約）を確かめます。制約は、検討できる案の範囲を最初に決めてしまうためです。

| 制約の種類 | 確かめること |
|---|---|
| 期限 | いつまでに動いている必要があるか。機器の保守切れ、法改正、事業上の日程など、動かせない日付はあるか |
| 予算 | 初期費用と月額の上限。誰が承認するか |
| 体制 | 構築後に誰が運用するか。その人たちが扱える技術か。夜間や休日の対応はできるか |
| 既存の環境 | つなぐ相手のシステム、社内のネットワーク、すでに使っているクラウドや契約 |
| 規則 | 社内の規程、業界の基準、契約上の条件。データを置ける場所の指定 |

「運用する人が扱えるか」は、技術的な優劣よりも優先されることがあります。最新の構成を作っても、運用する人が障害時に調べられなければ、止まる時間はかえって長くなります。

## 非機能要件を数字で聞く

「止まらないように」「速く」といったあいまいな言葉は、必ず数字に置き換えます。日本の案件では、IPA（情報処理推進機構）の「[非機能要求グレード](https://www.ipa.go.jp/archive/digital/iot-en-ci/jyouryuu/hikinou/hikinou20190328.html)」の6つの大項目で整理されることが多いため、この枠組みで聞く習慣をつけておくと、要件定義の会話についていけます。

| 大項目 | 決めること | 質問の例 | AWSでの主な手段 |
|---|---|---|---|
| 可用性 | どれだけ止まってよいか | 使う時間帯は？止まったら何時間で戻せばよい？データはどの時点まで戻ればよい？ | マルチAZ、Auto Scaling、バックアップ、別リージョンへの複製 |
| 性能・拡張性 | 速さと、利用の増加への備え | 同時に何人使う？ピークはいつ？1年後に利用は何倍になる？ | インスタンスの選定、Auto Scaling、キャッシュ、CDN |
| 運用・保守性 | 監視・バックアップ・保守の体制 | 障害時は誰が何分以内に対応する？保守で止めてよい時間帯は？ | CloudWatch、AWS Backup、Systems Manager |
| 移行性 | 今のシステムからの移し方 | いつ切り替える？データ量は？止められる時間は？ | Database Migration Service、各種のデータ転送サービス |
| セキュリティ | 守るべき情報と守り方 | 個人情報を扱う？誰がどこから使う？操作の記録は必要？ | IAM、暗号化（KMS）、WAF、CloudTrail |
| システム環境・エコロジー | 制約条件（法令、設置場所など） | データを国内に置く必要は？利用する地域は？ | リージョンの選択 |

### あいまいな言葉を数字にする

| 要望の言葉 | 数字にするための質問 | 数字の例 |
|---|---|---|
| 止まらないように | 止まると、誰の、何の業務が、どのくらい困るか。何分までなら待てるか | 平日8時〜20時の稼働率99.9%。復旧は30分以内 |
| データは消えないように | どの時点まで戻せれば業務を続けられるか。失った分を入力し直せるか | 障害の5分前までのデータを復元できる |
| 速く | どの画面の、どの操作か。今は何秒で、何秒なら満足か | 検索結果の表示は、95%が1秒以内 |
| たくさんの人が使う | 登録者数ではなく、同時に操作している人数は。最も集中するのはいつか | 平常時は毎秒20件、月末は毎秒200件 |
| 安全に | どの情報を扱うか。漏れたら何が起きるか。従うべき基準はあるか | 個人情報を扱う。操作の記録を1年保存する |
| 安く | 月にいくらまでか。何と比べて安ければよいか | 月額30万円以内。現行の保守費を下回る |

質問のコツは、技術の数字を直接聞かないことです。「稼働率は99.99%が必要ですか」と聞くと、多くの人は「高いほうがよい」と答えます。「平日の昼に1時間止まると、何が起きますか」と聞けば、業務への影響が具体的にわかり、そこから必要な数字を一緒に決められます。

### 稼働率と停止時間

稼働率は、停止してよい時間に置き換えると実感しやすくなります。

| 稼働率 | 1か月（30日）に止まってよい時間 | 1年に止まってよい時間 |
|---|---|---|
| 99% | 約7.2時間 | 約3.7日 |
| 99.9% | 約43分 | 約8.8時間 |
| 99.95% | 約22分 | 約4.4時間 |
| 99.99% | 約4.3分 | 約53分 |
| 99.999% | 約26秒 | 約5.3分 |

99.9%と99.99%の差は、数字の上ではわずかですが、止まってよい時間は10分の1になります。月に4分しか止まれないなら、人が通知を受けてから対応を始めていては間に合わず、自動で回復する仕組みが前提になります。9が1つ増えるごとに、必要な仕組みと費用は大きく増えます。

部品を組み合わせたときの稼働率は、次のように概算します。

- 直列（どれか1つが止まると全体が止まる）：それぞれの稼働率を掛ける。99.9%の部品を2つ直列にすると、0.999 × 0.999 ≒ 99.8%。部品が増えるほど下がる
- 並列（どちらか一方が動いていればよい）：「両方が同時に止まる確率」を1から引く。99%の部品を2つ並列にすると、1 − 0.01 × 0.01 = 99.99%

この計算は、部品が互いに無関係に故障し、切り替えが一瞬で終わることを前提にした目安です。実際には、同じ原因で両方が止まること（設定の誤り、同じバグ）や、切り替えにかかる時間があるため、計算どおりにはなりません。

## 設計判断を記録する

大きな判断ごとに、次の項目を短く記録します。後から参加した人が「なぜこうなっているのか」を理解でき、自分自身の説明の準備にもなります。

| 項目 | 記入例 |
|---|---|
| 決めたこと | DBはRDS for PostgreSQLのマルチAZ構成にする |
| 背景と要件 | 平日の日中に止まると業務が止まる。許容できる停止は10分以内 |
| 検討した案 | EC2上に自分でDBを構築、RDSの単一AZ、RDSのマルチAZ |
| 選んだ理由 | 運用の手間を抑えながら、可用性の要件を満たせる |
| 受け入れたデメリット | 費用は単一AZの約2倍。切り替え時に数分の停止は発生しうる |
| 見直す条件 | 利用者が今の3倍を超えたら、構成を再検討する |

:::tip 判断の記録は短く、その場で
この記録は、ADR（Architecture Decision Record）とも呼ばれます。立派な文書にする必要はなく、1つの判断につき10行程度で十分です。大切なのは、決めたその日に書くことです。後から書こうとすると、検討した案や、選ばなかった理由を思い出せなくなります。コードと同じリポジトリに置くと、構成の変更と一緒に履歴が残ります。
:::

:::sum
- 設計は、要件を聞く、数字にする、案を出す、比べて決める、見積もって確かめる、の繰り返し
- あいまいな要望は、業務への影響を聞くことで数字に置き換える
- 稼働率は停止時間に直して考える。直列は掛け算で下がり、並列は上がるが、計算は目安にすぎない
- 判断は、検討した案、選んだ理由、受け入れたデメリット、見直す条件とともに記録する
:::

## 章末問題

:::q 計算 | 直列の稼働率
ロードバランサー、アプリサーバー群、データベースが直列につながるシステムがあります。それぞれの稼働率を、仮に99.99%、99.9%、99.95%とします。

1. システム全体の稼働率は、およそ何%ですか
2. 1か月（30日）に止まる時間は、およそ何分ですか
3. 全体の稼働率を上げるには、どの部品から手を付けるのが効果的ですか
:::a
1. 0.9999 × 0.999 × 0.9995 ≒ 0.9984。約99.84%
2. 30日は43,200分。43,200 × 0.0016 ≒ 69分
3. 最も稼働率の低いアプリサーバー群（99.9%）。直列では、最も弱い部品が全体を決める。ほかの部品をいくら高めても、全体は99.9%を超えない

個々の部品の数字がどれも高く見えても、直列につなぐと全体は下がります。「各部品のSLAが99.9%以上だから、システムも99.9%」とは言えない理由です。
:::

:::q 計算 | 並列の稼働率と、その前提
稼働率99%のサーバーを2台並べ、どちらか一方が動いていればサービスを続けられる構成にします。

1. 計算上の稼働率は何%ですか
2. 実際にはこの数字にならない理由を、3つ挙げてください
:::a
1. 1 − 0.01 × 0.01 = 0.9999。99.99%
2. 解答例：
    - 同じ原因で両方が止まる：同じアプリのバグ、同じ設定の誤り、同時に適用した更新、同じAZへの配置など。2台は互いに無関係に故障するわけではない
    - 切り替えに時間がかかる：異常の検知と振り分けの停止には、数十秒かかる。その間はエラーが出る
    - 残った1台で負荷を受けきれない：1台が止まると、もう1台に2倍の負荷がかかる。耐えられなければ、続けて止まる
    - 2台の前後にある部品（振り分ける仕組み、データベース）が止まれば、全体が止まる

冗長化の効果は、「同時に止まる原因をどれだけ取り除けるか」で決まります。別のAZに置く、更新を1台ずつ行う、といった工夫は、そのためのものです。
:::

:::q 変換 | 要望を質問に直す
顧客との最初の打ち合わせで、次の3つの要望が出ました。それぞれ、数字の要件にするために、あなたが聞き返す質問を2つずつ挙げてください。

1. 「24時間365日、絶対に止まらないようにしてほしい」
2. 「今のシステムは遅いので、速くしてほしい」
3. 「将来、利用者が増えても大丈夫なようにしてほしい」
:::a
解答例：

1. 「深夜や休日には、どなたがどのような操作をされますか」「仮に平日の昼に30分止まった場合、どのような影響が出ますか。深夜の場合はどうですか」。時間帯ごとの影響の違いがわかれば、保守に使える時間帯や、必要な稼働率が決まる。あわせて、複数の構成案とそれぞれの費用を示し、選んでもらう
2. 「特に遅いと感じるのは、どの画面のどの操作ですか」「その操作は今、何秒くらいかかっていて、何秒なら業務に支障がありませんか」。全体を漠然と速くするのではなく、対象と目標を絞る
3. 「現在の利用者数と、同時に使う人数はどのくらいですか」「1年後、3年後に、何倍になる見込みですか。その根拠（事業の計画など）はありますか」。見込みの幅がわかれば、最初から大きく作るか、増えたときに拡張できる作りにするかを判断できる

いずれも、顧客の言葉を否定せず、業務の具体的な場面に引き寄せて聞くのが要点です。
:::

:::q 作成 | 判断を記録する
検証環境のNATゲートウェイを、AZごとの2台から1台に減らすことにしました。本文の「設計判断を記録する」の6つの項目に沿って、この判断の記録を書いてください。数字は自分で仮定してかまいません。
:::a
解答例：

| 項目 | 内容 |
|---|---|
| 決めたこと | 検証環境のNATゲートウェイを、AZ-aの1台だけにする |
| 背景と要件 | 検証環境の月額を下げたい。検証環境は平日の日中だけ使い、数時間止まっても業務への影響はない |
| 検討した案 | (1) AZごとに2台のまま (2) 1台にする (3) NATゲートウェイをなくし、VPCエンドポイントだけにする |
| 選んだ理由 | (2)で月額が約45ドル下がる。(3)は、外部のパッケージ配布元への通信が必要なため採れない |
| 受け入れたデメリット | AZ-aの障害時、AZ-cのサーバーも外部へ通信できなくなる。本番環境とは構成が異なるため、AZ障害時の動作は検証環境では確認できない |
| 見直す条件 | 検証環境でAZ障害の試験を行うことになった場合。検証環境を夜間の自動試験にも使うようになった場合 |

「受け入れたデメリット」と「見直す条件」が具体的に書かれているかを確認してください。この2つがあると、後から読んだ人が「知らずにこうなっている」のではなく「わかったうえで選んだ」と理解できます。
:::
