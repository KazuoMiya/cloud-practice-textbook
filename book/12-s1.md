:::goal
- 「今、誰として操作しているか」を確認でき、ユーザー・ロール・ポリシーの違いを説明できる
- 管理画面とCLIが同じAPIを呼んでいることを、自分の操作で確かめる
- S3を非公開のまま、CloudFront経由でだけ配信する構成を作り、その理由を説明できる
:::

最初のステップでは、AWSの操作の基本（権限、管理画面とCLIの関係、公開範囲）を体験します。作るものは小さいですが、ここで身につける「誰が、何に対して、何をできるか」という見方は、この先のすべてのステップの土台になります。

## 権限の基本を押さえる

AWSでは、すべての操作がAPIの呼び出しで、そのたびに「この呼び出しは許可されているか」が判定されます。判定の材料になるのが、次の4つです。

| 用語 | 何か | 使いどころ |
|---|---|---|
| IAMユーザー | 人やプログラムに発行する、長く使う認証情報 | 最小限にする。会社の環境では、人は IAM Identity Center から入るのが一般的 |
| IAMグループ | ユーザーをまとめ、同じ権限を付けるための入れ物 | 「開発者」「閲覧のみ」のように役割で分ける |
| IAMロール | 人やサービスが一時的に引き受ける権限のまとまり | EC2やLambdaに権限を持たせる。別のアカウントや外部のサービスに操作を許可する |
| ポリシー | 何を許可し、何を拒否するかを書いた文書（JSON） | ユーザー・グループ・ロール、またはS3バケットなどの資源に付ける |

ポリシーは、次の3つを読めば意味がわかります。Effect（許可か拒否か）、Action（どの操作か）、Resource（どの資源に対してか）です。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::example-bucket/*"
    }
  ]
}
```

このポリシーは「example-bucket の中のオブジェクトを読み取ることを許可する」という意味です。書かれていない操作は、すべて許可されません。許可は書いたものだけ、という点が最小権限の出発点です。評価の詳しい順序は{{ch:sec}}で扱います。



## 手元の端末は一時的な認証情報で操作する

第18章のIaCや第19章のコンテナ操作でも、長期間使えるアクセスキーを発行して保存する手順には進みません。手元の端末から操作するときは、有効期限のある一時的な認証情報を使います。入り方は、学習環境によって2通りあります。どちらの場合も、ルートユーザーでは実行しません。

| 学習環境 | 入り方 | 用意するもの |
|---|---|---|
| 会社や研修で用意された環境 | IAM Identity Center（`aws sso login`） | 管理者が用意した開始URL、リージョン、学習用アカウントと権限セット |
| 個人のアカウント | 管理画面と同じサインイン（`aws login`） | {{ch:env}}で作った作業用ユーザー（MFAを設定済み）と、AWS CLI 2.32.0 以降 |

このステップから{{ch:s6}}までは、ブラウザ上のCloudShellだけでも進められます。CloudShellは、管理画面にログインしている利用者の権限でそのまま動くため、端末の設定は要りません。手元の端末の設定が必要になるのは、{{ch:s7}}からです。

この本では、ここで確認する「学習用のアカウントで、作業に使う利用者」を、学習用ロールと呼びます。会社の環境では IAM Identity Center で割り当てられたロール、個人のアカウントでは作業用ユーザーが、これに当たります。

### 会社や研修で用意された環境の場合

管理者が用意した開始URL、リージョン、学習用アカウントと権限セットを確認します。これらがない場合は管理者に準備を依頼し、用意できるまではCloudShellから操作します。

```bash
aws configure sso --profile cloudbook-lab
aws sso login --profile cloudbook-lab
aws sts get-caller-identity --profile cloudbook-lab
```

セッションが切れたら `aws sso login --profile cloudbook-lab` をやり直します。作業を終えたら `aws sso logout` でローカルのSSOセッションキャッシュを消します。すでに発行済みの一時認証情報すべてを即座に無効にする操作ではありません。

### 個人のアカウントの場合

IAM Identity Center でAWSアカウントに入る構成には、AWS Organizations が必要です。{{ch:env}}で見たとおり、無料プランのアカウントでは、AWS Organizations を使い始めると有料プランに切り替わり、元に戻せません。個人のアカウントでは、代わりに `aws login` を使います（2025年11月に追加されたコマンドです）。管理画面と同じサインイン（ユーザー名、パスワード、MFA）をブラウザで行うと、AWS CLI が一時的な認証情報を受け取ります。アクセスキーは作りません。

準備は2つです。

1. AWS CLI を 2.32.0 以降にする。`aws --version` で確認する
2. 作業用ユーザーに、このサインインを許可する。AWSの管理ポリシー SignInLocalDevelopmentAccess を付ける。すべての操作を許可するポリシー（AdministratorAccess）を付けているユーザーでは、この許可も含まれている

```bash
aws login --profile cloudbook-lab
aws sts get-caller-identity --profile cloudbook-lab
```

初回はリージョンを聞かれるので、`ap-northeast-1` と入力します。ブラウザが開いたら、作業用ユーザーでサインインし、端末に戻ります。ブラウザを開けない端末では `aws login --remote` を使い、表示されたURLを別の端末で開いて、そこに出た認証コードを入力します。

認証情報は15分ごとに自動で更新され、最長12時間でセッションが切れます。切れたら、同じコマンドでやり直します。作業を終えたら `aws logout --profile cloudbook-lab` で、端末に保存されたセッションを消します。

`aws login` はルートユーザーでも実行できますが、使いません。ルートユーザーの権限は絞れないため、端末に置く認証情報としては強すぎます。

### どちらの場合も守ること

`aws sts get-caller-identity` で、表示されたアカウントと利用者が学習用であることを確認します。以後のAWS CLIは `--profile cloudbook-lab` を付けます。TerraformなどSDKの認証設定を使うツールでは、実行するターミナルで `export AWS_PROFILE=cloudbook-lab` として同じプロファイルを選びます。`aws login` に対応していない古い版のツールでは、公式の手順にある `credential_process` の設定で、AWS CLI から認証情報を受け渡します。環境変数に以前のアクセスキーが残っていると、想定と違う認証情報が使われることがあります。認証元を確認し、混在させないでください。

認証情報のキャッシュ（`~/.aws` の下に保存される）や `.aws/credentials` をGitに追加したり、共有端末から持ち出したりしません。

:::ref
[公式：AWS CLIのIAM Identity Center認証](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html) ／ [公式：管理画面の認証情報でAWS CLIにログインする（aws login）](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html)
:::

## 進め方

1. 学習用ロール（個人のアカウントでは作業用ユーザー）で管理画面にログインし、CloudShell（ブラウザ上で使えるターミナル）で `aws sts get-caller-identity` を実行して、「今、誰として操作しているか」を確認する
2. AWS CLIでS3バケットを作り、簡単なHTMLファイルをアップロードする
3. CloudFrontを作り、S3バケットを配信元（オリジン）に指定する。S3バケットは非公開のままにし、CloudFrontからだけ読めるようにする（オリジンアクセスコントロール）
4. CloudFrontのURLでページが表示されることを確認する

手順3でS3バケットに設定するバケットポリシーは、次の形になります。「CloudFrontというサービスからの読み取りを、指定したディストリビューションに限って許可する」という内容です。Principal（誰に許可するか）と Condition（条件）が加わっている点に注目してください。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-bucket/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/EXAMPLEID"
        }
      }
    }
  ]
}
```

## つまずきやすい点

| 症状 | よくある原因 | 確かめ方 |
|---|---|---|
| バケットを作れない | バケット名が、世界中の誰かにすでに使われている | 名前に案件名や日付などを加えて、ほかと重ならないものにする |
| CloudFrontのURLを開くと403になる | バケットポリシーの許可がない、またはディストリビューションのARNが違う | バケットポリシーの Condition の値と、実際のディストリビューションのIDを見比べる |
| ファイル名を付ければ表示されるが、URLの末尾を「/」にすると403になる | 既定のルートオブジェクトを設定していない | ディストリビューションの設定で、index.html を指定する |
| 作った直後にアクセスできない | CloudFrontの設定は、世界中の拠点に行き渡るまで数分かかる | 状態が「デプロイ済み」になるのを待つ |
| ファイルを更新したのに古い内容が出る | CloudFrontや手元のブラウザに、古いファイルが保存されている | キャッシュを無効化する。ブラウザは再読み込みか、別のブラウザで確かめる |

## 確認ポイント

- S3のURLに直接アクセスすると拒否され、CloudFront経由なら表示される理由を説明できる
- 管理画面の操作もCLIの操作も、内部では同じAPIを呼んでいることを説明できる

## わざと壊してみる

:::lab
バケットポリシーからCloudFrontへの許可を外します。CloudFrontに保存済み（キャッシュ済み）のファイルは表示され続けることがあるため、対象ファイルのキャッシュを無効化して完了を待つか、まだ一度も開いていない別のファイルを開いて、エラー（403）の出方を確認します。許可を元に戻した後も、エラーの応答がしばらくキャッシュされることがある点に注意してください。
:::

## 片付け

CloudFrontを無効化してから削除し、S3バケットを空にしてから削除します。

## 本番ではどう変わるか

| 項目 | 学習での構成 | 本番で加わること |
|---|---|---|
| ドメインと証明書 | CloudFrontが発行するURLをそのまま使う | 独自ドメインを割り当て、証明書を設定する。CloudFrontに設定する証明書は、バージニア北部リージョン（us-east-1）で発行する決まりがある |
| 更新の反映 | 手動でキャッシュを無効化する | ファイル名に版を表す文字列を入れ、古いファイルと新しいファイルが混ざらないようにする。保存する時間（TTL）をファイルの種類ごとに決める |
| 保護 | なし | AWS WAFで不正なアクセスを制限する。アクセスの記録を保存する |
| 誤った上書きや削除への備え | なし | バケットのバージョニングを有効にし、前の版に戻せるようにする |
| 作り方 | 管理画面とCLI | IaCで管理する（{{ch:s7}}） |

:::sum
- すべての操作はAPIの呼び出しで、そのたびに権限が判定される。まず「誰として操作しているか」を確かめる
- ポリシーは、Effect・Action・Resourceを読む。書かれていない操作は許可されない
- S3は非公開のままにし、CloudFrontからの読み取りだけをバケットポリシーで許可する
- キャッシュは速さの源であり、「変更が反映されない」原因にもなる
:::

## 章末問題

:::q 読み取り | ポリシーを読む
本文の1つ目のポリシー（example-bucket への s3:GetObject の許可）だけが付いたロールがあります。このロールで、次の操作はできますか。

1. example-bucket の中の report.pdf をダウンロードする
2. example-bucket にファイルをアップロードする
3. other-bucket の中のファイルをダウンロードする
4. example-bucket の中のファイルの一覧を表示する
:::a
1. できる。s3:GetObject が、バケットの中のオブジェクトに対して許可されている
2. できない。アップロードは s3:PutObject という別の操作で、許可されていない
3. できない。Resource が example-bucket に限られている
4. できない。一覧の取得は s3:ListBucket という別の操作で、対象もバケットそのもの（arn:aws:s3:::example-bucket）になる

4は見落としやすい点です。「読めるのに一覧が出ない」ときは、まずこれを確かめます。操作ごとに、対象がバケットなのか、その中のオブジェクトなのかが決まっています。
:::

:::q 説明 | なぜS3を直接公開しないのか
同僚から「S3のバケットを公開設定にすれば、CloudFrontなしでも静的サイトを公開できる。なぜわざわざCloudFront経由にするのか」と聞かれました。理由を3つ挙げてください。
:::a
解答例：

1. 公開設定の事故を防げる：バケットを非公開に保ち、公開ブロックの設定も有効のままにできる。「公開してよいバケット」という例外を作らずに済むため、誤って別のファイルを公開する事故が起きにくい
2. HTTPSと独自ドメインを使える：CloudFrontに証明書を設定し、暗号化された通信で配信できる
3. 速く、安定して配信できる：利用者に近い拠点からキャッシュを返すため、応答が速く、アクセスが集中してもS3への負荷が増えにくい

このほか、AWS WAFによる保護や、アクセスの記録、地域による制限など、入口でまとめて行える制御が増える点も利点です。
:::

:::q 対応 | 更新が反映されない
静的サイトの index.html を修正してS3にアップロードしましたが、CloudFrontのURLを開くと古い内容のままです。原因と、対処の方法を2つ以上挙げてください。
:::a
原因は、CloudFrontの拠点（または手元のブラウザ）に、古い index.html が保存されているためです。保存する時間（TTL）が切れるまでは、S3に問い合わせずに古い内容を返します。

対処の方法：

1. CloudFrontで、対象のパスのキャッシュを無効化する。すぐに反映したいときの方法。完了まで少し時間がかかる
2. 画像やスクリプトなどのファイルは、名前に版を表す文字列を入れる（例：app.3f2a1c.js）。名前が変われば別のファイルとして扱われるため、無効化が要らない
3. index.html のように名前を変えられないファイルは、保存する時間を短く設定しておく

実務では2と3を組み合わせ、1は緊急時の手段にします。確認のときは、ブラウザ自身のキャッシュにも注意してください。
:::

:::q 確認 | CLIと管理画面の違い
CLIで作ったS3バケットと、管理画面で作ったS3バケットに、違いはありますか。また、「誰がいつ作ったか」は、後からどこで確認できますか。
:::a
違いはありません。どちらも内部では同じAPI（この場合はバケットを作成するAPI）を呼んでおり、指定した設定が同じなら、できあがるものも同じです。違うとすれば、管理画面が既定で選んでくれる設定値と、CLIで省略したときの既定値が異なる場合があることです。

誰がいつ作ったかは、CloudTrailのイベント履歴で確認できます。管理画面からの操作も、CLIからの操作も、IaCのツールからの操作も、同じように記録されます（{{ch:s5}}）。
:::
