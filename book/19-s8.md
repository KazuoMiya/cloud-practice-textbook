:::goal
- アプリをコンテナにし、ECS（Fargate）でロードバランサーの後ろに動かせる
- コードの変更が、テストを通って自動で届く流れを作り、失敗したら止まることを確かめる
- 問題のある版を出したとき、前の版に戻す手順を説明できる
:::

アプリの変更を、安全に自動で本番まで届ける流れを作ります。ここまでは「環境を作る」ことが中心でしたが、実際の案件では、作った環境の上でアプリが毎日のように変わります。変更のたびに人が手作業で配置していては、時間がかかり、手順の誤りも起きます。このステップは発展的な内容で、時間がかかってもかまいません。

## コンテナとECSの用語

| 用語 | 意味 |
|---|---|
| コンテナイメージ | アプリと、動かすのに必要なものをひとまとめにしたもの。Dockerfile から作る |
| ECR | イメージの置き場（レジストリ） |
| タスク定義 | どのイメージを、どれだけのCPUとメモリで、どの設定で動かすかを書いたもの。変更するたびに新しい版（リビジョン）ができる |
| タスク | タスク定義から起動された、動いているコンテナの集まり |
| サービス | タスクを決まった数だけ動かし続ける仕組み。減れば補い、新しい版への入れ替えも行う |
| クラスター | サービスやタスクをまとめる入れ物 |
| Fargate | コンテナを動かすサーバーを、事業者が用意・管理する実行方式 |

## 参考実装

完成形は、この本のリポジトリの [labs/delivery](https://github.com/KazuoMiya/cloud-practice-textbook/tree/main/labs/delivery) にあります。題材のアプリ（画面と、ヘルスチェック用の `/health` を返すだけの小さなWebアプリ）とそのテスト、Dockerfile、GitHub Actions のワークフロー、デプロイと戻しのスクリプト、AWS側の資源を作るTerraformがそろっています。この章に載せたファイルは、そこにあるものそのままです。1行目に、どのファイルかを書いてあります。

参考実装は、変更のたびに、次の検査を通しています。コンテナを作って読み取り専用で動かし、画面とヘルスチェックの応答を確かめる。デプロイのスクリプトを、偽の `aws` と `docker` のコマンドで通しで動かす。Terraform の書式、文法、設計のテストを行う。実際のアカウントで確かめた状況は、[labs/delivery の README](https://github.com/KazuoMiya/cloud-practice-textbook/tree/main/labs/delivery) に書いてあります。

| 範囲 | 費用 |
|---|---|
| 手元でのテストとコンテナの起動。GitHub に自分のリポジトリを作り、PRのたびにテストが動き、失敗したらマージできないところまで | 無料（公開リポジトリの GitHub Actions は無料。非公開でも毎月の無料枠で足りる） |
| AWSで動かし、main に入った変更を承認の後に届け、前の版に戻す | 時間料金がかかる（任意）。ALB、Fargate のタスク、パブリックIPv4アドレスは、置いてあるだけで課金される。その日のうちに片付ける |

AWSを使えない場合も、無料の範囲で、テストで止まる仕組みと、承認を挟む設定までは確かめられます。届ける部分は、この章のスクリプトと、偽のコマンドで動かすテストを読んで、何がどの順で呼ばれるかを追ってください。

Dockerfile を示します。小さな土台のイメージを使うこと、必要なファイルだけを入れること、管理者以外のユーザーで動かすことが、基本の作法です。

```dockerfile
# labs/delivery/app/Dockerfile
FROM public.ecr.aws/docker/library/python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
# 必要なファイルだけを入れる（COPY . . は、テストや手元の設定まで入れてしまう）
COPY app.py .
ARG APP_VERSION=local
ENV APP_VERSION=$APP_VERSION PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
USER 1000
EXPOSE 8080
# ファイルシステムを読み取り専用にして動かすため、gunicorn の作業用ファイルはメモリ上（/dev/shm）に置く
CMD ["gunicorn", "-b", "0.0.0.0:8080", "--workers", "2", "--worker-tmp-dir", "/dev/shm", "--access-logfile", "-", "app:app"]
```

`COPY . .` で全部を入れると、テストや手元の設定ファイル、場合によっては秘密情報まで、イメージに入ってしまいます。タスク定義では、コンテナのファイルシステムを読み取り専用にします（`readonlyRootFilesystem`）。乗っ取られても、中のプログラムを書き換えられにくくするためです。書き込みが必要なもの（ここでは gunicorn の作業用ファイル）は、メモリ上の場所に逃がします。手元でも `docker run --read-only` で同じ条件にして動かします（`make run`）。

## 進め方

1. 題材のアプリ（`labs/delivery/app`）をコンテナにし、手元のPCで動かす。ステップ3で動かしたアプリを、同じ形でコンテナにしてもよい
2. ECR（コンテナイメージの置き場）にイメージを登録する
3. ECSのFargateでサービスを作り、ALBの後ろで動かす。ステップ3のEC2と比べ、何を管理しなくてよくなったかを整理する
4. GitHub Actionsで、コードをpushしたら「テスト → イメージ作成 → ECRに登録 → ECSを更新」まで進む流れを作る
5. GitHub ActionsからAWSへの認証は、アクセスキーを保存せず、OIDC（一時的な認証情報を受け取る仕組み）で行う

プライベートサブネットでFargateを動かす場合、ECRからイメージを取得するための経路（NATゲートウェイかVPCエンドポイント）が必要です。

GitHub ActionsからAWSを操作する部分は、次のように書きます。アクセスキーはどこにも保存せず、実行のたびに、決められたロールの一時的な認証情報を受け取ります。

ワークフローの全体です。先に、main のブランチ保護（PRと、このワークフローの `test` の合格を必須にする）と、`production` 環境（承認者と、デプロイできるブランチを `main` だけにする設定）を作っておきます。

```yaml
# labs/delivery/workflow/app-delivery.yml
# リポジトリの直下に、labs/delivery の app/、deploy.sh、render-taskdef.jq を置いた前提。
# 先に、main のブランチ保護（PRと、このワークフローの test を必須にする）と、
# production 環境（承認者と、デプロイできるブランチを main だけにする設定）を作っておく。
name: App delivery

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: app-delivery-${{ github.ref }}
  cancel-in-progress: false

jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - name: Unit tests
        run: make -C app test

  deploy:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    needs: test
    runs-on: ubuntu-24.04
    environment: production
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: aws-actions/configure-aws-credentials@e1253824e5c10ff9df46874f81ed3ec929e19cfd # v6.3.0
        with:
          role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ap-northeast-1
      - name: Build, push and deploy
        env:
          AWS_REGION: ap-northeast-1
          ECR_REPOSITORY: cloudbook-app
          ECS_CLUSTER: cloudbook
          ECS_SERVICE: cloudbook-app
          IMAGE_TAG: ${{ github.sha }}
        run: bash deploy.sh
```

引き受けるロールは、リポジトリの変数 `AWS_DEPLOY_ROLE_ARN` から読みます。ロールのARNは秘密情報ではないため、Secrets ではなく Variables に置きます。AWS側のロールの信頼ポリシー（参考実装の `infra/github.tf`）では、GitHubのOIDCプロバイダーを指定し、`aud` を `sts.amazonaws.com`、`sub` を `repo:OWNER/REPOSITORY:environment:production` に完全一致で絞ります（`OWNER/REPOSITORY` は自分の対象に置き換える）。環境を指定したジョブの `sub` はブランチ形式ではなく環境形式です。そのため、GitHub側でも `production` へのデプロイを `main` だけに制限する必要があります。ロールの操作権限も、対象ECR・ECSなど必要な資源と操作だけに絞ります。

PRのテストにはOIDC権限を与えません。未確認のPRコードを、権限の強い `pull_request_target` などで実行しないでください。アクションは変更可能なタグだけで指定せず、公式リポジトリで確認した完全なコミットIDに固定します（例のコミットIDは、2026年11月時点の版のものです）。更新時は差分と検証結果をレビューして固定値を更新します。コンテナの基底イメージも、本番では検証したダイジェストに固定して更新を管理します。

:::ref
[公式：GitHub Actionsの安全な利用](https://docs.github.com/en/actions/reference/security/secure-use) ／ [公式：AWSへのOIDC接続](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
:::

## デプロイのスクリプトがしていること

`deploy.sh` は、3つのことを順に行います。

1. イメージを、コミットIDをタグにして作り、ECRに登録する。ECRは同じタグの上書きを禁止する設定にしてあるため、同じ名前で中身の違うイメージは存在できない
2. サービスが今使っているタスク定義を取り出し、イメージだけを差し替えた新しい版を登録する。CPUとメモリ、ロール、ログの設定は、前の版をそのまま引き継ぐ
3. サービスを新しい版に切り替え、安定するまで待ち、本当に新しい版で動いているかを確かめる

2の差し替えは、次の処理で行います。取り出したタスク定義には、登録のときに指定できない項目（版の番号や登録日時など）が含まれるため、それを取り除いてから登録します。

```text
# labs/delivery/render-taskdef.jq
# 登録済みのタスク定義から、登録のときに指定できない項目を除き、
# 名前が app のコンテナのイメージだけを、新しいものに差し替える
del(.taskDefinitionArn, .revision, .status, .requiresAttributes, .compatibilities,
    .registeredAt, .registeredBy, .deregisteredAt, .deleteRequestedAt)
| .containerDefinitions |= map(if .name == "app" then .image = $image else . end)
```

3の最後の確認には理由があります。参考実装のサービスは、新しい版のタスクが起動に失敗し続けると、入れ替えを止めて前の版に自動で戻す設定（デプロイのサーキットブレーカー）にしてあります。前の版に戻った状態も「安定」なので、待つだけでは、失敗に気づけません。スクリプトは、動いている版が登録した版と同じで、入れ替えが完了（`COMPLETED`）していることを確かめ、違えば失敗として止まります。

戻すときは、前の版のタスク定義を指定します。`deploy.sh` は、最後に戻すためのコマンドを表示します。

```bash
export ECS_CLUSTER=cloudbook ECS_SERVICE=cloudbook-app
aws ecs list-task-definitions --family-prefix cloudbook-app --sort DESC --max-items 3
bash rollback.sh cloudbook-app:6
```

戻した後に main へ新しい変更を入れると、また新しい版が届きます。戻した原因を直す変更を、PRで入れます。

## つまずきやすい点

| 症状 | よくある原因 | 確かめ方 |
|---|---|---|
| タスクが起動せず、イメージを取得できないというエラーになる | プライベートサブネットからECRへの経路がない。タスク実行ロールに、イメージを取得する権限がない | 停止したタスクの「停止の理由」を読む。NATゲートウェイかVPCエンドポイントがあるか |
| タスクが起動と停止を繰り返す | ヘルスチェックに合格する前に、異常と判定されている。アプリが起動に失敗している | コンテナのログと、ターゲットグループのヘルスチェックの設定を確認する |
| ALB経由でつながらない | コンテナが待ち受けるポートと、タスク定義やターゲットグループのポートが合っていない | 3か所のポート番号を見比べる |
| コンテナのログが見られない | タスク定義に、ログを CloudWatch Logs へ送る設定がない | タスク定義のログの設定を確認する |
| GitHub Actionsで、ロールを引き受けられない | 信頼ポリシーの条件（リポジトリ名やブランチ名）が、実際と合っていない | エラーメッセージと、信頼ポリシーの条件の文字列を見比べる |

:::note 2種類のロール
ECSのタスクには、役割の違う2つのロールがあります。タスク実行ロールは、ECSがタスクを起動するために使うもので、イメージの取得やログの送信に必要です。タスクロールは、コンテナの中のアプリがAWSのサービスを呼ぶために使うもので、S3の読み書きなど、アプリに必要な権限を付けます。権限のエラーが出たら、どちらのロールの話かを最初に切り分けます。
:::

## 確認ポイント

- 本番反映の前に人の承認を挟む「継続的デリバリー」と、自動で反映する「継続的デプロイ」の違いを説明できる
- 問題のある版を出してしまったとき、前の版に戻す手順を説明できる

## 実技の合格基準

次のすべてを、コマンドの出力や画面で示せたら合格です。

| 番号 | 確かめること | 合格の状態 |
|---|---|---|
| 1 | サービスが安定して動いている | status が ACTIVE で、desiredCount と runningCount が同じ。最新のデプロイの rolloutState が COMPLETED |
| 2 | イメージを、一意の名前で指定している | image の末尾が `latest` ではなく、コミットIDなどのタグか、ダイジェストになっている |
| 3 | アクセスキーを使わずに認証している | 信頼ポリシーの条件で、aud が sts.amazonaws.com、sub が自分のリポジトリと環境に、完全一致で絞られている。GitHubのシークレットにも、IAMユーザーにも、アクセスキーがない |
| 4 | push から反映までが自動で進む | 画面の文言を変えて push すると、人の操作は承認だけで、ALBのURLに反映される。かかった時間を記録している |
| 5 | テストに失敗した変更は、反映されない | テストが失敗するコミットでは、デプロイのジョブが実行されず、動いている版が変わらない |
| 6 | 前の版に戻せる | 戻す手順を実行し、かかった時間を記録している |
| 7 | 片付けが済んでいる | サービス、クラスター、イメージ、GitHub Actions用のロールが残っていない |

```bash
CLUSTER='cloudbook'              # 参考実装の名前。自分で作った場合は、その名前
SERVICE='cloudbook-app'
ROLE='cloudbook-github-deploy'    # GitHub Actions が引き受けるロール

# 1
aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
  --query 'services[].[status,desiredCount,runningCount,deployments[0].rolloutState]' --output table
# 2
TASK_DEF=$(aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
  --query 'services[0].taskDefinition' --output text)
aws ecs describe-task-definition --task-definition "$TASK_DEF" \
  --query 'taskDefinition.containerDefinitions[].image'
# 3
aws iam get-role --role-name "$ROLE" --query 'Role.AssumeRolePolicyDocument.Statement[].Condition'
# 7（片付けの後）
aws ecs list-clusters --query 'clusterArns'
aws ecr describe-repositories --query 'repositories[].repositoryName'
```

提出するもの：1〜3、7の出力、4〜6の記録（GitHub Actionsの実行結果の画面と、かかった時間）。

## わざと壊してみる

:::lab
1. `app/app.py` の `/health` が、`ok` 以外の文字を返すように変えて、PRを作ります。`test` が失敗し、マージできないこと、デプロイのジョブが動かないことを確かめます（無料）

## 本番ではどう変わるか

| 項目 | 学習での構成 | 本番で加わること |
|---|---|---|
| イメージの識別 | コミットIDをタグにし、同じタグの上書きを禁止する | タスク定義では、イメージをダイジェスト（中身から計算した値）で指定する。土台のイメージもダイジェストで固定し、更新は検証してから行う |
| 入れ替えの方法 | 少しずつ入れ替え、起動に失敗し続けたら自動で前の版に戻す（サーキットブレーカー） | 起動はするが、エラーが増えるといった失敗も、アラームで検知して戻す。新旧2つの環境を用意して切り替えるブルー/グリーンや、通信を少しずつ移すリニア、カナリアのデプロイも、ECSの機能として使える（{{ch:sre}}） |
| 本番への反映 | PRとテストを通し、承認後に学習環境へ反映する | 検証環境までは自動、本番の前に承認を挟む、といった段階を設ける |
| イメージの安全性 | 登録のたびに既知の脆弱性を検査し、結果を見る | 重大な脆弱性があれば、反映を止める。登録した後も、定期的に検査し直す |
| ネットワーク | 費用を抑えるため、タスクをパブリックサブネットに置き、ALBからの通信だけを受け付ける | タスクはプライベートサブネットに置き、ECRなどへは、VPCエンドポイントかNATゲートウェイを通す |
| データベースの変更 | 扱わない | テーブルの定義の変更を、アプリの入れ替えと両立させる手順を決める（章末問題） |
| 秘密情報 | なし | Secrets Manager の値を、タスクの起動時にコンテナへ渡す |

:::sum
- コンテナは、アプリと実行環境をひとまとめにし、どこでも同じものを動かせるようにする
- ECSのサービスは、タスクを決まった数だけ動かし続け、新しい版への入れ替えも行う
- CI/CDからAWSへの認証は、アクセスキーを保存せず、OIDCで一時的な認証情報を受け取る
- 自動で届ける仕組みは、自動で止まる仕組み（テスト）と、戻す手順とセットで初めて安全になる
:::

## 章末問題

:::q 説明 | 前の版に戻す
新しい版を本番に出した直後から、エラーが増えました。ECSで動かしている場合、前の版に戻す手順を説明してください。また、戻しただけでは解決しないのは、どのような場合ですか。
:::a
戻す手順：サービスが使うタスク定義を、1つ前の版（リビジョン）に指定し直して、サービスを更新します。ECSが、今のタスクを前の版のタスクに順に入れ替えます。前の版のイメージがECRに残っていること、イメージに版ごとの名前を付けていることが前提です。入れ替えの失敗を検知して自動で戻す設定を有効にしていれば、ヘルスチェックに合格しない版は、自動で前の版に戻ります。

戻しただけでは解決しない場合：

- データベースの定義を変更していた場合：新しい版で列を削除したり、形式を変えたりしていると、前の版のアプリが動かない
- 新しい版が、すでにデータを書き換えていた場合：誤った内容で保存されたデータは、アプリを戻しても元に戻らない
- 外部への通知や連携を行っていた場合：送ってしまったメールや、他システムへの連携は取り消せない

そのため、データベースの変更は「前の版のアプリでも動く形」で先に行い、アプリの入れ替えとは別の段階に分けます。たとえば列の名前を変えるなら、新しい列を追加する、両方に書き込む版を出す、読み取りを切り替える、古い列を消す、と段階を踏みます。
:::

:::q 比較 | OIDCとアクセスキー
GitHub ActionsからAWSを操作するとき、アクセスキーをGitHubの秘密情報として保存する方法と、OIDCでロールを引き受ける方法があります。後者が安全だとされる理由を説明してください。また、OIDCを使う場合に、AWS側の設定で必ず絞り込むべき条件は何ですか。
:::a
安全だとされる理由：

- 長く使える認証情報がどこにも保存されない。アクセスキーは、漏れると無効にするまで使われ続けるが、OIDCで受け取る認証情報は短時間で失効する
- キーの定期的な交換や、退職者が知っているキーの無効化といった管理が要らない
- 誰がその認証情報を受け取れるかを、AWS側の条件で制御できる

絞り込むべき条件：ロールの信頼ポリシーで、引き受けを許可する相手を、特定のリポジトリ（組織名とリポジトリ名）に限定します。本番用のロールは、さらに特定のブランチや環境からの実行に限定します。条件を付けないと、GitHub上のほかのリポジトリからも、そのロールを引き受けられてしまいます。

あわせて、ロールに付ける権限も、デプロイに必要な操作と対象だけに絞ります。認証の方法を安全にしても、権限が管理者権限のままでは、被害の範囲は変わりません。
:::

:::q 指摘 | latest という名前の問題
あるチームは、イメージを常に latest という名前でECRに登録し、タスク定義でも latest を指定しています。この運用の問題点を挙げてください。
:::a
- 今、何が動いているかがわからない：latest という名前は、登録のたびに別の中身を指すようになる。動いているタスクが、どの時点のコードから作られたものかを特定できない
- 前の版に戻せない：前の版も latest という名前だったため、上書きされて指定できない
- タスクによって中身が違うことがある：台数を増やしたときや、タスクが再起動したときに、その時点の latest が取得される。古いタスクと新しいタスクで、別の版が同時に動く
- 意図しないタイミングで新しい版が動き出す：誰かが latest を登録すると、次にタスクが再起動したときに、デプロイの操作をしていないのに新しい版が動く

対策は、コミットのIDなどを使って版ごとに違う名前を付け、同じ名前での上書きを禁止する設定にすることです。タスク定義では、その名前を明示的に指定します。
:::

:::q 整理 | サーバーからコンテナへ、何が変わったか
ステップ3（EC2とAuto Scaling）と比べて、このステップ（ECSのFargate）で管理しなくてよくなったものと、引き続き利用者が管理するものを、それぞれ挙げてください。
:::a
管理しなくてよくなったもの：

- サーバーのOSと、その修正プログラムの適用
- サーバーのイメージ（AMI）の作成と更新
- サーバーへのログイン手段の管理
- サーバーの台数と種類の選定（必要なCPUとメモリをタスクごとに指定するだけになる）

引き続き管理するもの：

- コンテナイメージの中身：土台のイメージや、中に入れたライブラリの更新は利用者の担当。土台のイメージが古いままだと、脆弱性が残る
- アプリそのもの
- タスクの数と、増減の条件
- 権限（タスクロール）、ネットワーク（サブネット、セキュリティグループ）
- 監視とログ

「サーバーの管理がなくなる」ことで、OSの保守からは解放されますが、イメージの保守という形で、同じ種類の責任が残ります。{{ch:model}}の責任共有モデルを、コンテナの場合に当てはめた形です。
:::
